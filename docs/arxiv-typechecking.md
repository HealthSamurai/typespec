# Статическая проверка существующего Clojure: исследования и Typespec

## Короткий вывод

Для поставленной задачи подходит **optional static checking**, а не gradual typing с вставкой casts, wrappers или проверок при исполнении. Основной ориентир — *Practical Optional Types for Clojure*: occurrence typing, неоднородные immutable-мапы и работа с Java проектируются вместе. Для вывода типов полезен двунаправленный checker с ограниченным полиморфизмом; универсальный вывод типов произвольного Clojure, макросов и пользовательских предикатов обещать нельзя.

Рекомендуемый порядок: (1) честные границы проверенного кода и доверия; (2) двунаправленный rank-1 вывод и корректная совместимость функций; (3) факты о путях и ключах мап; (4) проверяемые summaries предикатов; (5) отдельные эксперименты с row variables и более сложным полиморфизмом. SMT, semantic subtyping и зависимые типы — не требования первого выпуска. Отсутствие новых runtime checks означает условность гарантии на непроверенных границах, а не бесплатную soundness смешанной программы.

Попытка извлечь алгоритмические разделы №2 из HTML не дала пригодного текста; её не считаем чтением полного текста.

## Что взять в Typespec

### 1. Отдельно определить гарантию optional checker

**Предложение P1 — F110/F210/F730/F840.** Сформулировать гарантию для поддержанного ядра при истинных внешних контрактах. `unknown` означает отсутствие достаточных сведений; доверенная сигнатура, подавление и проверенное тело — разные источники уверенности. Прохождение статической проверки не гарантирует тип результата произвольного untyped Java/Clojure вызова. Вставки casts и автоматический `s/valid?` не нужны и не предлагаются.

Существующий вызов `(s/valid? ::spec x)` можно использовать как факт о программе: это **уже написанная пользователем** runtime-проверка, а не новая instrumentation checker. Отдельно нужно учитывать, что `:pre` assertions могут быть выключены.

### 2. Двунаправленный вывод, затем полиморфизм

**P2 — F220/F230/F410.** Развести `synthesize(expr)` и `check(expr, expected)`; expected type передавать в `fn`, а ограничения аргументов и результата решать в ограниченном контексте одного вызова. Начать с явно аннотированных rank-1 сигнатур библиотек и проверяемой variance функциональных типов. При нехватке информации просить аннотацию, не подменять успехом/`any`.

F230 уже честно отделяет rank-1 план от специальных правил `map`/`reduce`, а также отмечает отсутствие корректного сравнения `:fn`. Исследования не основание расширить обещание сразу до higher-rank/impredicativity. Нужен дизайн областей видимости type variables, fresh instantiation и поведения при недостатке информации. Отдельные regression cases: callback без аннотации; несовместимый тип второго аргумента; повторное использование polymorphic identity; `comp`/`partial`; функция неправильной арности; transducer/reducing function.

### 3. Сначала точная семантика HMap, затем rows

**P3 — F310/F230.** Различать required, optional, known-absent и неизвестный остаток мапы. Тип значения `nil` не означает отсутствие ключа. Работа №1 особенно полезна, потому что сохраняет Clojure-семантику отсутствующего ключа, а не меняет её на исключение.

Карточка F310 уже отмечает отсутствие общего факта known-absent, отдельную семантику default, проблему optional-overwrite у `merge`. Это не новые обнаружения, а подтверждённые направления. Предложение сверх этого: отдельно оценить, нужна ли **квантифицированная row variable**, сохраняющая неизвестный хвост в результате generic функции, или достаточно HMap/subtyping. Open map сама по себе не даёт такой корреляции входа и выхода. Прежде чем брать №6, определить `assoc`/`dissoc`/`merge`, конфликты полей, порядок overwrite и dynamic keys.

### 4. Summaries предикатов, не произвольные доказательства spec

**P4 — F240/F250/F260/F340.** Summary guard должен описывать отдельно truthy и falsy ветви, происхождение факта и значение/путь, к которому он относится. Одностороннее доказательство не даёт права сузить отрицательную ветвь до дополнения. F250 это уже явно фиксирует; F260 отделяет номинальное свидетельство от структурной аппроксимации.

Практический следующий шаг: проверяемый небольшой язык фактов для built-ins и тел простых guard-функций. Требуется политика потери факта при мутации, повторном deref, изменении spec/Var и неизвестных эффектах. SMT из №5 оставить экспериментом с явным результатом `proved / disproved / unknown`, не запускать произвольные predicates ради «вывода».

### 5. Macros: ограниченные правила и происхождение результата

**P5 — F610/F810/F840.** №7 не снимает проблему типизации уже существующих макросов. В F610 уже различены встроенные правила, непроверенные тела, доверенные контракты и будущий isolated expansion worker. Сохранить этот подход. Для каждого правила нужны scope bindings, evaluation order/multiplicity, ветвления и source mapping; совпадение внешней формы вызова с `let`/`if` недостаточно.

Macro expansion во время анализа — выполнение пользовательского кода на build-time, хотя и не новые runtime checks приложения. Это отдельный риск и граница доверия. Доказать корректность произвольного макроса по его сигнатуре работа №7 не позволяет.

### 6. Удобство и покрытие — часть жизнеспособности

**P6 — F720/F810/F840/F910.** В §5 работы №1 из 1834 `def` в исследованном CircleCI typed-коде проверялись 407 (22%); 78% оставались unchecked. Авторы называют стоимость перепроверки транзитивных зависимостей, нехватку библиотечных аннотаций и неподдержанные идиомы; после двухлетнего эксперимента компания отказалась от проверки. Это историческое наблюдение статьи, не оценка современного Typed Clojure.

Следствие: считать проверенные тела отдельно от числа аннотированных namespace; кэшировать summaries с зависимостями; явно инвалидировать при изменении контрактов, macro rules и provider/spec definitions. Нельзя объявить namespace проверенным только потому, что он прошёл с большим числом skips.

## Пробелы/вопросы для карточек — без их изменения

Это кандидаты для сверки редакторами, **не утверждение, что во всех текущих версиях карточек их нет**:

1. **F220:** явные judgment modes, стратегия expected type и остановки solver; пример, где аннотация нужна принципиально. Карточка пока существенно короче F230.
2. **F230:** спецификация instantiation/quantifier scope и отличие rank-1, higher-rank, impredicative inference; минимальный контракт корректности совместимости `:fn` до сложных HOF.
3. **F310:** решение «HMap + subtyping или дополнительно rows», отдельные tests на сохранение неизвестного хвоста. Known-absent и optional-overwrite уже отмечены карточкой, их не нужно переоткрывать как новые идеи.
4. **F250/F260/F340:** общий протокол переносимости/инвалидации evidence; связь с identity значения, mutable deref и обновлением Var/spec, а не только имя refinement.
5. **F610:** для каждого специального правила тестировать семантическое соответствие расширению и не терять coverage непроверенных аргументов/тел. Это развивает существующий план, не заменяет его Turnstile+.
6. **F720/F810/F840:** единое представление проверенного summary и trusted assumption, зависимости кэша и отдельная метрика skipped bodies. Литература особенно хорошо обосновывает важность этого, но не даёт готового cache protocol для Clojure reload.

## Что не брать

- Transient checks, Deep contracts, proxies и blame как основу: несовместимо с ограничением задачи.
- Заявление «gradual typing без runtime checks и со всеми обычными гарантиями soundness» без точной модели границ.
- Полный higher-rank/System F inference только ради `map`: сначала rank-1 и корректная функциональная совместимость.
- Универсальное превращение `spec`, regex и произвольного predicate в refinement logic.
- Замену существующего Clojure новым макро-DSL ради удобства checker.
- Нулевую overhead из Python-бенчмарка как аргумент, что проверки не вставляются.
- Теорему soundness небольшого calculus как доказательство корректности всей реализации и всех externs.

## Неопределённости и следующий исследовательский шаг

- Для работ №2–9 прочитаны abstracts, не правила и proofs. До реализации нужно читать полные тексты №2/3/4/6 и сравнивать calculus с Clojure arities, subtyping и mutable interop. Здесь нет подтверждения сложности/производительности будущего solver.
- В отбор не включена оригинальная *Local Type Inference* Pierce–Turner: использован прочитанный abstract её развития №3; оригинал в этой сессии не прочитан. Не включена непрочитанная исходная работа по occurrence typing; она не подменяется пересказом по памяти.
- Row polymorphism для extensible records и rows эффектов — разные задачи. Работы про Koka/effect rows не взяты как готовое решение Clojure maps.
- №7 касается построения typed DSL, а не ретрофита произвольных Clojure macros. Для последней задачи остаётся существенный исследовательский пробел.
- Нет проверки текущих GitHub releases/звёзд/активности: этот документ — обзор научных первоисточников, не рейтинг поддерживаемости библиотек. Исторические цифры статьи не описывают текущий Typed Clojure.
- Не запускались benchmark, checker или примеры; никакие предложения здесь не обозначены как реализованные. Следующий практический шаг — небольшой эксперимент на существующем Clojure: rank-1 expected-type propagation + HMap key facts + отчёт assumptions/skips, без instrumentation.
