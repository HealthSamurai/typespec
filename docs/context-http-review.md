# Независимое ревью: выбор перегрузки при неизвестном аргументе (call-fn)

Ревьюер: агент cetg. Объект: изменение `call-fn` в `src/typespec/check.clj` (12 строк), тест `test/typespec/http_replace_regression_test.clj`, харнесс `examples/context-http-check`. База `c7cb557`, проверяемое состояние — коммит `e6ec120` (он уже был сделан к моменту ревью). Исходники я не правил; все прогоны шли на копиях (`git archive`) во временной папке.

**Вывод: исправление делает то, что заявлено, и не прячет конкретные ошибки. Есть одна настоящая проблема (F1): в двух воспроизводимых случаях тип результата недоказанного выбора теперь считается известным и даёт жёсткую ошибку ниже по коду, где раньше был `unknown`.** Для поставляемого контракта `clojure.string/replace` она не проявляется (все перегрузки возвращают `string?`).

## Что подтвердилось

- **Конкретная ошибка рядом с неизвестным аргументом не прячется.** `(s/replace x #"a" 42)`, `(s/replace x "a" \b)`, `(s/replace x \a "b")`, `(s/replace x :k "b")`, `(s/replace x 1 2)`, `(s/replace 42 m "x")`, `(s/replace 42 #"a" r)`, `(s/replace "a" 42 r)` — везде остался `TSP2345`, вывод совпадает с базой построчно.
- **nil.** `(s/replace x nil "b")` и nilable-совпадение при неизвестном первом аргументе — `TSP2345`, как на базе. При известных аргументах `TSP2531` «may be nil» сохранён (3 случая).
- **Callback.** Плохой `(fn [m] 42)` — `TSP2345` и при неизвестном, и при известном входе. Хороший `(fn [m] "z")` — только предупреждение о входе. Callback при строковом совпадении — `TSP2345`.
- **Корректные замены.** Все шесть форм из реального кода дают 0 ошибок и ровно одно `TSP210-01` на неизвестный вход.
- **Доверие не понижено.** Ни один исправленный случай не стал «тихим»: `TSP210-01` остаётся, в `--strict` он ошибка. Trust-счётчики 0/0/0, новых externs/cast/any/ignore нет.
- **Порядок перегрузок.** Кандидат, отвергнутый конкретным аргументом, исключается независимо от позиции; при разных типах результата у оставшихся кандидатов результат `unknown` (покрыто тестом `incomplete-candidates-ignore-order...`, плюс мои E2, E3).
- **Про `int?`.** Нового вывода целых нет: `(s/upper-case (+ w 10))` даёт только предупреждения, результат остаётся `unknown`.

## Замечания

### F1 (средняя важность, регрессия): результат считается доказанным, когда это не так

Старое условие «хоть где-то есть `TSP210-01` и результаты различаются → `unknown`» заменено на «различаются результаты только у incomplete-кандидатов». Из-за этого два случая, воспроизводятся с пользовательскими externs:

**a) Все перегрузки отвергнуты конкретным аргументом, плюс есть неизвестный.**
`v/h ([string? int? :-> string?] [keyword? int? :-> keyword?])`, код `(v/num (v/h x "s"))`.
База: ошибка на `"s"` + результат `unknown`. Сейчас: та же ошибка **и вторая** — `keyword? is not assignable to number?`, хотя `keyword?` просто взят у последней перегрузки.

**b) Кандидат «подходит, если не nil» больше не учитывается.**
`v/f ([int? (s/nilable string?) :-> int?] [any? string? :-> string?])`, код `(s/upper-case (v/f x (v/ns y)))`, `x` неизвестен, `y` nilable.
База: предупреждение + `TSP2531 may be nil`. Сейчас: **`TSP2345 int? is not assignable to CharSequence`**, а `TSP2531` исчез. Если `x` на деле строка, сработает вторая перегрузка и вернётся строка — ошибка ложная. Это тот же класс дефекта, который чинили: жёсткая ошибка из недоказанного выбора.

Набросок правки (проверен на копии: 129/833 проходят, харнесс 0 ошибок / 44 предупреждения, те же 7 ложных срабатываний убраны, оба случая возвращают `unknown`): при пустом `passing` и наличии `TSP210-01` сравнивать результаты у `incomplete` + `nil-only`, а если таких нет — у всех `fits`. Побочный эффект наброска: в случае (b) `TSP2531` не восстанавливается, остаются два предупреждения.

Масштаб: в `core/table` наборов с разным результатом при одной арности 11, все арифметические `int?`/`number?` (`+ - * inc dec abs max min mod quot rem`). На них я форму (a)/(b) не воспроизводил. EDN-декларации из `resources/` кроме `clojure.string/replace` на это не проверял.

### F2 (низкая): текст предупреждения называет самую узкую перегрузку

`(first incomplete)` выбирает первую, т.е. узкую: `(+ w 10)` теперь пишет `t/unknown to int?`, `(s/replace x m r)` — `to java.lang.Character` дважды. Читается как «нужен int / нужен Character», хотя подошёл бы и `number?` / строка. Комментарий в коде двумя строками ниже говорит обратное («with an unknown argument only the general one is safe»), и для `passing` используется `last`. С `(last incomplete)` тесты проходят и прежний текст `number?` возвращается; тогда `expected-current.edn` надо переснять (в нём закреплён `int?`).

### F3 (низкая): пробелы в целевом тесте

- Нет теста на nilable-аргумент вместе с неизвестным и на случай (a) — поэтому F1 не пойман.
- Callback не покрыт совсем (ни плохой, ни хороший) — я проверил руками, поведение верное.
- `invalid-known-pairs-remain-errors` и `unknown-...-never-silently-pass` проверяют только «есть такой код где-то», без позиции и числа диагностик.
- `--strict` не покрыт.
- Приёмка харнесса (`run.sh --accept`) не входит в `clojure -M:test` — это ручной шаг; фраза «автотест» в `docs/context-http-check.md` относится к нему.

### Не регрессии (на базе так же), вне рамок правки

- Сообщения для смешанных пар вводят в заблуждение: `(s/replace x "a" \b)` ругается «"a" is not assignable to Pattern», потому что при отсутствии кандидатов берётся последняя перегрузка.
- `(s/replace "abc" #"a" s/upper-case)` — `TSP2345`: контракт callback требует принимать и вектор групп.
- `clojure.string/replace-first` без контракта: `(s/replace-first x #"a" "")` не даёт ни одной диагностики.
