## Обновление: точность checker

После улучшения loop/recur, use-site Java hints (с сохранением nullability), literal top-level imports и добавления core/abs: полный pg.clj с контрактами даёт **2 ошибки / 11 предупреждений** на Java 27.0.1.1. Обе ошибки сохранены: TSP2322 на 57:15 и TSP2345 на 206:41. Старые результаты ниже и baseline.txt/contracts.txt — исторический снимок до этого изменения, не текущий вывод.

Сам checker убрал четыре предупреждения: два числовых на строке 115, индекс loop на 195 и Java-результат на 244. Source-backed контракт cheshire.core/generate-string убрал предупреждение на 255; на 308 неизвестный receiver TSP7020 стал известным String с предупреждением о рефлексии TSP7023. Не все предупреждения устраняются добавлением типов.

Общий suite: **109 тестов / 686 assertions**, все golden/CLI проходят без изменения эталонов. Пример context-web-pg: 0 errors/0 warnings, unit 3/22 PASS. Runtime HTTP/PG повторно в этом этапе не запускался. Loop использует ограниченное вычисление устойчивых типов; при нестабильности остаётся unknown. Вложенные fn/loop не смешивают recur-цели. Literal import учитывается file-wide; порядок переопределений import не моделируется. Неверная арность recur пока приводит к conservative unknown, а не отдельной syntax-диагностике.

## Исходный прогон одного файла

Исходный прогон охватывал один полный `src/pg.clj` из commit
`aa8ea0eb565e7f70f80f3248e6a83198628e1047`.
[Исходник](https://github.com/context-clj/pg/blob/aa8ea0eb565e7f70f80f3248e6a83198628e1047/src/pg.clj)

451 строка, 54 top-level формы, последняя заканчивается на строке 451. SHA-256: `dca4826d414a66c22dc10ebb2a01e1d8dccaf5cf64cdfe9b8bb952987d023db5`. Стенд проверяет hash перед анализом. Namespace pg не require/исполняется; JDBC-запросы и сервисы не запускаются. Чтение всех форм не означает семантическую поддержку всех макросов.

Из `examples/context-pg-check`:

```sh
clojure -M:check baseline
clojure -M:check contracts
```

Оба запуска ожидаемо завершаются exit 1 из-за диагностик ошибок. Требуются Clojure CLI, JVM и доступные зависимости; classpath строится по закреплённому deps.edn. Сохранённые baseline.txt/contracts.txt получены на Java 25.0.5.1. Независимый родительский повтор на Java 27.0.1.1 дал те же позиции и количества диагностик.

| Без дополнительных контрактов | 1 TSP2345 | 9 TSP210-01, 1 TSP7020 |
| С минимальными контрактами | 1 TSP2322, 1 TSP2345 | 15 TSP210-01, 1 TSP7020 |

Добавлен ровно один extern: `pg/datasource [map? :-> com.zaxxer.hikari.HikariDataSource]`, основанный на get-pool/defstart и нормальном состоянии сервиса. Два явных binding-body контракта описывают system/defstart и defstop. Они не доказывают реализацию макросов. Тип map? для context намеренно грубый, не гарантия структуры state.

Ни одна исходная диагностика не исчезла. Проверка тела datasource сохранена: строка 49 теперь предупреждает, что возвращаемый из динамического состояния тип неизвестен и контракт HikariDataSource не доказан самим телом. Таким образом extern — доверенная граница, а не незаметное стирание реализации.

## Ошибки библиотеки

### 1. DataSource вместо Connection — строка 57

`with-connection` привязывает `(datasource ctx)` к `^Connection`. Фактический объект штатного состояния — HikariDataSource, не java.sql.Connection. С контрактом результата datasource полный файл выдаёт TSP2322.

Runtime-воспроизведение реальных upstream `with-connection` и `array-of`, без БД, ранее подтвердило ClassCastException. Детали и границы: [context-type-bug-hunt.md](context-type-bug-hunt.md). Предполагаемое исправление — получить connection; upstream здесь не менялся.

### 2. BufferedReader вместо InputStream — строка 206

`copy-ndjson-file` строит цепочку `GZIPInputStream → InputStreamReader → BufferedReader`, затем передаёт reader в `copy-ndjson-stream`, где аргумент объявлен `^InputStream`. Уже baseline даёт TSP2345.

Это подтверждённое противоречие исходного кода и JVM-типов, но не отдельное runtime-воспроизведение. Вызов может сначала открыть connection, поэтому запуск ради ClassCastException без контролируемой БД не проводился. Выбор исправления требует решить, должен ли helper принимать Reader или вызывающая функция передавать InputStream; автоматически удалять hint нельзя.

Итого 15 сообщений о неполной проверке и одно о reflective call. Эти предупреждения не являются установленными runtime-дефектами. Для части хватит подтверждённых контрактов аргументов/зависимостей, для других нужен более точный вывод checker. Ошибочного отклонения корректного кода двумя error-диагностиками в данном прогоне не выявлено; это не полный аудит ложных срабатываний.

## Ограничения и следующий шаг

Полный разбор исходников оставляет границы проверки для SQL-схемы, транзакционных свойств, произвольных макросов и реализации extern-контрактов. Счётчики 0 cast/any/ignore не измеряют долю реально доказанного кода.

Полезное продолжение: добавить регрессионный тест Reader/InputStream, затем подтвердить и описать контракты context/JSON, не скрывая неполноту. Исправления upstream и публикация issues/PR требуют отдельного действия; здесь ничего не отправлялось.
