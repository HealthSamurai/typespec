## Находки

### F1. HIGH — `check` исполнял код библиотеки с classpath. Исправлено, перепроверено

Нарушало приёмку п.1 («нет eval/require библиотечного кода»). Код был ещё в `dfc5897`, но стал реально опасен именно с classpath-режимом.

Причина (до): `core_types.clj` — `stdlib-macro?` и `stdlib-tagged?` делали `requiring-resolve`, `stdlib-publics` делал `require`, в том числе для `clojure.core.async` — это сторонняя библиотека, а не часть Clojure.

Repro (`.hyper/tmp/fable-review/trip/`): каталог на classpath с `clojure/core/async.clj`, который при загрузке пишет файл-маркер; проект с `(:require [clojure.core.async :as a])` и `(a/go 1)`; запуск `clojure -M -m typespec.main check`.

- До: маркер `ASYNC_EXECUTED` создан.
- После (текущий `core_types.clj`, `find-ns`/`ns-resolve` без загрузки): маркера нет. В `src/` больше нет `require`/`requiring-resolve`/`eval`/`load-*` в рантайм-путях.

Tripwire в `examples/jar-declarations` этот случай не ловил: он следит только за `vendor-demo.core`.

### F2. MEDIUM — исправление F1 сделало результат зависимым от того, что уже загружено в JVM. Открыто

Теперь метаданные берутся только из уже загруженных пространств имён. В свежем JVM командной строки `clojure.set` и `clojure.test` не загружены, а в тестовом JVM загружены. Одна и та же программа даёт разные диагностики в CLI и в suite — значит suite не описывает поведение, которое увидит пользователь.

Repro (`.hyper/tmp/fable-review/det/src/app/core.clj`, шесть строк с опечатками и `deftest`):

| Строка | `dfc5897` (CLI) | Сейчас (CLI) | Сейчас (тот же JVM, но `clojure.test`/`clojure.set` заранее загружены) |
|---|---|---|---|
| `(set/unionn a b)` | TSP2305 «no var unionn» | **ничего** | TSP2305 |
| `(deftest … (is (= 1 (inc "a"))))` | ничего | TSP2345 | ничего |
| `(clojure.test/are [x] (inc x) "a")` | ничего | TSP210-01 warning | ничего |

Потерянная ошибка на `set/unionn` — прямой ложный пропуск относительно базы. Остальные две строки показывают саму недетерминированность.

Как чинить без возврата F1: пространства из JAR самого Clojure (`clojure.set`, `clojure.walk`, `clojure.edn`, `clojure.pprint`, `clojure.test`, `clojure.string`) безопасно загрузить один раз при старте checker — кто может подменить их на classpath, тот уже подменяет `clojure.core`. Для `clojure.core.async` и `clojure.spec.alpha` загрузки быть не должно: либо статическая таблица имён, либо «неизвестно». И нужен тест, который запускает CLI в отдельном процессе и сверяет диагностики.

### F3. MEDIUM — ресурс из JAR может типизировать что угодно, включая функции самого проекта. Принято как граница доверия

Защита builtin покрывает только `clojure.core/*` и ключи встроенной таблицы. Ресурс может объявить var чужой библиотеки, `clojure.set/*`, `clojure.core.async/*` и неаннотированную функцию проверяемого проекта.

Repro (`trip/proj`): `(defn own [x] (str x)) (defn use-own [] (inc (own 1)))`.

- Без ресурса: `TSP2345 string? is not assignable to number?`, 1 ошибка, exit 1.
- С ресурсом `{app.core/own [t/unknown :-> t/unknown]}`: 0 ошибок, 1 warning, exit 0.

Для файловых `:externs` так было и раньше, но файл свой; JAR — чужой. Родитель решил оставить: ресурс выбирается явно и имеет те же права, что файл; это описано в `docs/type-declarations.md`. Согласен как с известным ограничением, но не как с «безопасно»: в итоговом отчёте это надо называть доверенным вводом, не песочницей. Дешёвое улучшение на потом — запретить ресурсу типизировать var, определённый в проверяемых исходниках.

### F4. LOW — тест валидации имён ничего не различает

`path-and-config-validation` проверяет только «есть диагностика TSP9003». Мутация: `valid-resource?` всегда возвращает true — тест `extern-resources-test` проходит с 0 падений. Все плохие имена всё равно падают позже как «not found» или ClassCast.

Реального обхода нет: с отключённой проверкой `../outside.edn` при существующем файле рядом с classpath-каталогом даёт «not found» (JDK сам не выходит за корень). Но тест не защищает от регрессии валидации. Починка: сверять текст сообщения.

Остальные мутации тесты ловят: снятие проверки дубликатов, чтение через `openStream` для `file:` и для неизвестного протокола, снятие builtin-guard, снятие проверки «ровно одна форма», разрешение тегов, «последний побеждает» при конфликте, дубль записи в JAR. Две выжившие эквивалентны: проверку authority дублирует `io/file` (бросает на URI с authority), подмену разбора пути JAR ловит раньше проверка схемы.

### F5. LOW — глубоко вложенный EDN роняет процесс без диагностики

Ресурс с 20 000 вложенных `[` даёт `StackOverflowError`, который проходит мимо `catch Exception`. Падение громкое, не тихое; задокументировано родителем.

### F6. LOW — невнятное сообщение для multi-release JAR

Если запись есть в `META-INF/versions/9/`, загрузчик отказывает с «JAR resource entry does not match requested name». Отказ правильный (иначе рантайм и checker читали бы разное), сообщение не объясняет причину.

### F7. LOW — результат pg не закреплён автоматической проверкой

`examples/context-pg-check/contracts.txt` и `baseline.txt` устарели (2/16 и 1/10; README это честно говорит). Ни один тест suite не запускает checker на закреплённом `pg.clj`: все pg-тесты синтетические. Число 2/8 и сохранность двух ошибок подтверждаются только ручным запуском `run.sh` под Java 25 с сетью. Стоит хотя бы обновить снимок `contracts.txt`.

## Что проверено и чисто

Загрузчик (`r1.clj`, `r2.clj`):

- Отсутствует ресурс; два JAR; каталог + JAR; родительский + дочерний loader; два одинаковых JAR; дубль записи внутри одного JAR — всегда диагностика, ничего не установлено.

- URL с обработчиком `https:`, `jar:https:`, `file://host/…`, `custom:` — `openConnection` не вызван, диагностика. Тестовый proxy действительно доходит до тела `getResources`, то есть тест не проходит по случайной причине.
- Пути JAR с пробелом, кириллицей, `+`, `%20`, `!`, каталог с `#` — читаются правильно.
- Файл и ресурс с одним ключом и разными типами: ошибка, остаётся первое объявление. Отсутствующий или битый файл рядом с ресурсом: ошибка остаётся, exit ненулевой — тихой подмены нет.
- Имя класса в сигнатуре (`java.lang.Runtime`) загружается через `Class/forName … false`, без инициализации: статический код класса не исполняется.
- Частично битый ресурс: плохая запись не установлена, остальные установлены, ошибка есть.

Контракты pg (сверил с `pg.clj` на пине `aa8ea0eb`, строки 139–146 и 184–196):

- `truncate!`, `safe-execute!`: `(mapv coerce …)`, `coerce` сворачивает в `{}` — «вектор map» верно для нормального возврата. `map?` для ctx — грубое, но верное предусловие (`(:system ctx)`).
- `fetch`: `(name field)`, `.setFetchSize`, счётчик цикла, вызов `on-row` с `(.getString …)` (может быть null) и индексом — сигнатура соответствует.
- Независимый запуск `run.sh contracts` на Java 25.0.2: **2 ошибки / 8 предупреждений**, `:pg-loaded? false`, trust 0/0/0. Обе ошибки на месте: `57:15 TSP2322` и `206:41 TSP2345`.
- Со старым `externs.edn` из `dfc5897` и текущим checker: 2/11. Разница — ровно три предупреждения (140:35, 145:35, 185:19). То есть весь выигрыш 11→8 дают три новых доверенных предусловия, а не улучшение вывода. Внутри `pg.clj` эти три функции никто не вызывает, поэтому обязательство целиком уходит внешним вызывающим. Это честно, если так и написано в отчёте.

Обратный вызов `fetch` (`r2.clj`, `r4.clj`), текущая сигнатура `[(s/nilable string?) int? :-> t/unknown]`:

- Ошибка TSP2345: `nil`, `:kw`, `42`, `"str"`, функция с 1 или 3 параметрами, `count`, `defn` с `:t/sig [string? int? …]` (не принимает nil), `(fn [^Long row i] …)`, не-int fetch-size, nil ctx, nil field.
- Проходит без диагностик и это верно: `println`, `str`, `(fn [row i] nil)`.
- Предупреждение TSP210-01 (не тишина): `inc`, `#(println %1)`, неизвестный параметр `f`, список вместо вектора SQL.

## Известные ограничения (не дефекты ночного диффа)

- **Nullable в лямбде с Java-хинтом.** `(pg/fetch {} [] 10 :id (fn [^String row i] (.length row)))` — 0 диагностик, хотя на NULL-колонке будет NPE. Причина не в контракте: `(defn cb [^String s i] (.length s)) (cb nil 1)` тоже даёт 0 диагностик без всякого pg. Хинт `^String` checker считает допускающим nil и вызов метода на нём не проверяет. Контракт сам по себе звучит правильно; с `:t/sig [string? …]` такой callback отклоняется. Классификация: существующее ограничение checker, не новая несостоятельная сигнатура.
- **Тип параметра не протекает в лямбду.** `(fn [row i] (clojure.string/upper-case row))` даёт warning «unknown to CharSequence», а не ошибку про nil. Существующее ограничение, видимое.
- **Пустой SQL-вектор.** `(pg/fetch {} [] …)` проходит, в рантайме `jdbc/prepare` упадёт. Язык типов не выражает «непустой вектор»; тесты используют `[]` как положительный пример — это пример типа, не рабочего вызова.
- **`user.clj`.** Любой `user.clj` на classpath исполняется при старте JVM до checker (подтверждено маркером `USER_CLJ_EXECUTED`). Это поведение Clojure. Утверждение «код библиотеки не исполняется» верно для checker, не для JVM в целом.
- **Контракты — доверие, не доказательство.** Тела `truncate!`/`safe-execute!`/`fetch` в `pg.clj` проверяются против сигнатуры, но исключения, состояние пула и пустой результат сигнатура не описывает.
