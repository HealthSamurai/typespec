# Sorbet: что перенести в статический Typespec

Дата проверки: **2026-11-17, 20:22 UTC**. Цель — проверять существующий Clojure **без добавления runtime checks**; это исследование Typespec, не интеграция с Aidbox.

## Summary

Главная ценность Sorbet для Typespec — не Ruby-синтаксис типов, а архитектура границ: независимые декларации RBI, разделение разрешения имён и проверки тел, локальный вывод, явные уровни строгости и учёт источников непроверенного кода. Наиболее полезный первый шаг — довести уже существующие F130/F710/F711, а не создавать ещё одну карточку про externs.

Копировать Sorbet целиком нельзя. Его обычный `sig` поддерживается runtime-библиотекой и по умолчанию оборачивает вызовы проверками; RBI, напротив, не исполняются. Shapes имеют документированные ограничения, несовместимые с ролью map в Clojure. Генерация RBI через reflection запускает Ruby-приложение: это не пример безопасного статического анализа макросов.

## Findings

### 1. RBI: интерфейс отдельно от исполнения

**Прочитано:** [RBI Files](https://sorbet.org/docs/rbi). RBI объявляют константы, предков и методы, которые checker не видит: gems, dynamic includes, `const_set`, `define_method`, `method_missing`. Они **не участвуют в runtime-проверке**. Документация разделяет ручные/community annotations, reflection-generated gems, DSL-generated definitions и TODO-заглушки. Сейчас рекомендуются команды Tapioca; hidden-definitions обозначен deprecated.

Это полезное разделение **происхождения**, а не четыре разных системы типов. Отдельно описано vendoring RBI в git: обновление деклараций может добавить ошибки, поэтому оно должно быть явным и воспроизводимым.

**Перенос:** один EDN-формат F130/F711, общая таблица контрактов и отдельные поля происхождения/версии в F710. Алгоритм: найти декларации → проверить схему и ссылки → разрешить конфликты по явной политике → построить таблицу namespace/var/arity → проверять тела и вызовы. Для своего исходника декларация не должна заменять проверку тела; для недоступной библиотеки она остаётся доверенным интерфейсом. Хэш зависимостей и выбранного набора деклараций входит в cache key.

```clojure
;; Исходник не меняется; контракт vendor.lookup/find-name задан снаружи:
;; аргумент string?, результат (s/nilable string?).
(defn greeting [id]
  (if-some [name (vendor.lookup/find-name id)]
    (str "Hello, " name)
    "Not found"))
```

Сам RBI не доказывает истинность декларации. Поэтому автогенератор/LLM может предложить контракт, но не должен автоматически менять его статус на «проверено». Нужно различать declared, inferred candidate и body-checked. Метаданные provenance не являются новым типом.

**Карточки:** F130, F710, F711, F720, F840. **Цена:** средняя; основная работа — конфликты, идентичность var/arity, версии, источники диагностик. Большая библиотека деклараций — постоянные расходы на сопровождение.

### 2. Runtime checks нельзя незаметно включать в заимствованный дизайн

**Прочитано:** [Runtime](https://sorbet.org/docs/runtime), [Static](https://sorbet.org/docs/static). Обычный Ruby `sig` включает runtime-проверку вызова через `sorbet-runtime`. Статический sigil `# typed: ...` этим не управляет: даже `typed: ignore` не выключает runtime-эффект сигнатуры. Доверие Sorbet к аннотациям частично опирается на эти проверки.

**Вывод для Typespec:** брать inert declarations, а не исполняемые wrappers. Нельзя переносить обещание безопасности смешанного typed/untyped кода без runtime-границы. Даже полная статическая проверка выбранного namespace условна относительно внешних деклараций, динамического `resolve`, мутации vars и Java. Это надо показывать в отчёте, а не скрывать словом strict.

Не вызывать `s/instrument`, не регистрировать `s/def` из sidecar, не добавлять `:pre` ради сужения и не менять исходные hints: это меняет поведение или компиляцию. Чтение уже существующих форм — другое действие. **Карточки:** F110/F130/F730/F840. **Цена:** низкая для политики, средняя для контроля границ загрузчика/reader.

### 3. Сначала имена и контракты, затем локальная проверка тел

**Прочитано:** [Why type annotations](https://sorbet.org/docs/why-type-annotations), внутренний pipeline. Sorbet не выводит сигнатуру метода из тела в обычной проверке: изменение inference одного метода не должно влиять на другой; тела можно проверять параллельно. Для локальных переменных документация объясняет однопроходную стратегию и запрет расширения типа внутри цикла без аннотации. Это осознанная цена скорости, не общий алгоритм максимального вывода типов.

**Перенос:** в F220/F720 отделить стабильную таблицу публичных контрактов от локальных результатов. Сначала собрать declarations, затем проверять тела. Предложения сигнатур — отдельный инструмент с review, не неявное изменение интерфейса. Для `loop/recur` проверять каждый recur-аргумент относительно выбранного инварианта loop binding; не объявлять Sorbet-стратегию готовым решением всех Clojure-циклов.

```clojure
(loop [x 0]
  (if (number? x)
    (recur nil)     ; при числовом инварианте — ошибка здесь
    x))
```

Если выбран union `number? | nil`, тело проверяется с этим union с самого начала. Вариант bounded fixed point возможен, но это уже наше решение, не результат данного исследования Sorbet. Не переносить буквально ограничения изменяемых Ruby locals на неизменяемые Clojure `let`.

**Карточки:** F220/F410/F420/F720. **Цена:** средняя/высокая: фазирование, рекурсия, invalidation и проверка инвариантов. Выигрыш производительности пока гипотеза без замера Typespec.

### 4. Локальные условные факты, включая сохранённый boolean

**Прочитано:** [Flow-sensitive typing](https://sorbet.org/docs/flow-sensitive), `infer/environment.h`. `KnowledgeFact` содержит положительные и отрицательные type tests; `TestedKnowledge` хранит факты для truthy/falsy исходов. Есть операции слияния, удаления ссылок на переменную, обратный индекс зависимостей; `KnowledgeFilter` предварительно отбирает факты, которые будут нужны. Это реально существующие структуры кода, не roadmap. Весь алгоритм inference не аудирован.

**Предложение:** расширять F240 через факты, привязанные к идентичности binding, а не тексту имени. На ветке применить совместимые положительные/отрицательные ограничения; на join оставить только гарантированные для всех достижимых путей факты. Для boolean-binding хранить ограниченный набор импликаций.

```clojure
(let [x (fetch-name)
      present (some? x)]
  (if present
    (clojure.string/upper-case x)
    "missing"))
```

Это должно сужать `x`, если fetch-name имеет `nil | string` и модель `some?` известна. Но нельзя переносить факт с `(some? @a)` на второй `@a`: состояние могло измениться. Сначала сохранить snapshot локально. Shadowing также создаёт новую идентичность.

В Ruby и Clojure falsy — `nil` и `false`, но `some?` удаляет только nil. Поэтому нельзя отождествлять `if-some` с `if-let`. Предикаты разрешать по квалифицированному символу и принятой модели core, не по имени `some?`: локально затенённая функция не становится trusted guard.

**Карточки:** F240/F250/F251/F340/F420; нового механизма guards не требуется. **Цена:** высокая для общих импликаций, средняя для ограниченного случая boolean alias. Ограничить размер наборов; потеря точности лучше некорректного доказательства. Оптимизации Sorbet переносить после профилирования.

### 5. Динамические конструкции: описание результата не равно проверке семантики

**Прочитано:** [Unsupported](https://sorbet.org/docs/unsupported), RBI. Sorbet намеренно не поддерживает некоторые формы динамического разрешения констант; `const_get` считается untyped. Причина — разрыв цикла между разрешением имён/иерархии и inference выражений. Reflection/Tapioca может восстановить определения, но для этого запускает код.

**Перенос:** в F610 разделить два продукта DSL-модели: (а) какие vars/арности создаются; (б) как проверять тело, binding и control flow. Декларация созданной функции решает только (а).

```clojure
(defendpoint get-user [id]
  (inc "oops"))
```

Внешнее объявление `get-user : string -> map` не доказывает корректность `(inc "oops")` внутри неизвестного макроса. Нужны trusted macro contract либо поддержанное нормализующее правило; иначе тело помечается unchecked с причиной. Нельзя silently пропускать его и считать покрытым.

`eval`, вычисляемый `resolve`/`intern` нельзя маскировать выдуманными декларациями. Литеральный символ может иметь специальное статическое правило; произвольное выражение — непроверенная граница. Не запускать `require`/`macroexpand` приложения по умолчанию. Reflection-export можно обсуждать отдельно как явную операцию пользователя, но для первого выпуска она не нужна.

**Карточки:** F610/F710/F810/F840. **Цена:** высокая для каждого семейства DSL; низкая для честной диагностики unsupported. Это доведение существующей карточки, не новая универсальная macro engine.

### 6. Строгость — политика диагностики; coverage — не число аннотаций

**Прочитано:** static/gradual/strong и [Untyped blame](https://github.com/sorbet/sorbet/blob/0d4730546f8c4e6c5c5735a146b1b949d8a132ef/docs/untyped-blame.md). Уровни Sorbet разрешают постепенную миграцию; наличие signatures и отсутствие untyped-использований — разные требования. Документ `strong` явно маркирует режим beta. Untyped blame уже реализован, но требует **специальной сборки** из-за существенной дополнительной памяти; это не бесплатная стандартная возможность каждого binary.

**Перенос:** не копировать названия уровней Ruby в F730. Считать отдельно проверенные тела, вызовы через достоверный контракт, доверенные externs, unknown/any-операции, пропущенные макросы, подавленные ошибки. В F810/F840 полезно показывать источник распространения непроверенности:

```clojure
(let [x (legacy/read-value)]
  (consume-a x)
  (consume-b x))
```

Если legacy/read-value не имеет контракта, отчёт должен связывать последствия с этим var, а не предлагать два независимых cast. Начать с ограниченного provenance-id на результате и счётчика уникальных мест; длинные трассы включать по запросу. `unknown` не обязан распространяться как `any`: например, функция с гарантированным строковым результатом может принять неизвестное значение без утраты типа результата. Считать конкретно непроверенные обязательства, а не все последующие выражения.

TODO RBI — важный отрицательный пример: Sorbet прямо предупреждает, что заглушки могут объявить **несуществующую** константу и скрыть настоящий баг. Typespec не должен генерировать declaration для каждого unresolved var и выдавать это за исправление.

**Карточки:** F210/F730/F810/F830/F840/F910. **Цена:** средняя для агрегатов, высокая для полного blame graph. Автоматический запрет роста доверия важнее красивого общего процента.

### 7. Shapes и фильтры: где Sorbet не образец

**Прочитано:** [Shapes](https://sorbet.org/docs/shapes) прямо называет возможность experimental. Приведены ограничения: чтение известного ключа может дать `T.untyped`, отсутствующий ключ не диагностируется, лишние ключи допускаются, изменение значения может не проверяться. Hash literal может деградировать в `Hash[untyped, untyped]`. Обещание “change it one day” — намерение, не реализованное исправление. Вводное описание exact shape нельзя принимать за гарантию вопреки примерам на той же странице.

Для Typespec map — базовый случай, поэтому F310/F311 и literal preservation нельзя отложить, предлагая заменять существующие maps на runtime `T::Struct`-аналоги. Такой совет меняет модель данных, а не только проверку.

Flow-sensitive docs также прямо говорят: произвольный predicate в `filter/select/reject` не выводит более узкий element type. Специальные `compact/grep` и анализ результата `filter_map` помогают, но не являются общим выводом пользовательских guards. В Clojure нужны отдельные проверенные модели `filter`, `remove`, `keep` и F250/F251. **Не копировать Ruby `filter_map` буквально:** он удаляет falsy, тогда как Clojure `keep` удаляет только nil и сохраняет false.

## Предложения и порядок

Новых карточек не требуется. Ниже только уточнения существующих механизмов; их реализация этим отчётом не заявляется.

| Приоритет | Карточки | Конкретное действие и критерий |
|---|---|---|
| P0 | F130/F710/F711 | Инертные versioned declarations; тесты отсутствия исполнения, конфликтов, устаревшей версии, отсутствующей var, несовпадения arity; свои тела продолжают проверяться |
| P0 | F610/F810/F840 | Unknown macro не даёт ложного покрытия; generated var и checked body учитываются отдельно; никаких автоматических TODO-заглушек |
| P0 | F730/F840 | Строгая проверка namespace явно сообщает trusted externs и динамические границы; runtime checks не появляются |
| P1 | F220/F420/F720 | Две фазы: контракты и тела; проверка loop/recur-инварианта; отдельно тест на взаимную рекурсию |
| P1 | F240/F251 | Ограниченные boolean-alias implications; тесты some?/false, shadowing и повторного deref; merge не сохраняет факт с одного пути |
| P1 | F810/F910 | Источник непроверенных обязательств и ранжирование по затронутым местам; агрегаты без полного графа по умолчанию |
| P2 | F710/F610 | Генераторы деклараций для отдельных DSL только после стабильного формата и provenance; не runtime-reflection по умолчанию |

**Что не брать:** runtime wrappers и `T::Struct` как обязательную миграцию; автоматическое доверие generated signatures; TODO declarations для неразрешённых имён; Sorbet shapes как достаточную map-модель; обещание глобальной soundness по уровню strict; дорогой полный blame graph без измерений; жёсткие Ruby-ограничения inference без проверки на идиоматичном Clojure.
