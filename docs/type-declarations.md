# Файлы деклараций типов

## Решение

Используем модель, похожую на `.d.ts` TypeScript, но в обычном EDN. Декларации описывают функции и именованные типы, не содержат реализацию и не исполняются. Один формат предназначен и для встроенных типов, и для пользовательского кода, и для сторонних библиотек.

Берём у TypeScript разделение поставщиков деклараций, но пока не копируем сложный поиск, module resolution, глобальные ambient-декларации или отдельный реестр пакетов.

## Три способа поставки

| Способ | Аналог TypeScript | Typespec |
|---|---|---|
| Встроенные типы | стандартные lib declarations | EDN-ресурсы внутри Typespec |
| Типы вместе с библиотекой | bundled `.d.ts` | EDN-ресурсы в JAR/classpath библиотеки |
| Отдельные типы для чужой библиотеки | `@types/*` | отдельная обычная Clojure dependency с EDN-ресурсами |

Пользовательские локальные декларации дополняют эти способы: можно описать свою функцию или зависимость, не меняя её исходники и не публикуя пакет.

## Что уже работает

Явные файловые декларации задаются относительно корня проверяемого проекта:

```edn
;; typespec.edn
{:paths ["src"]
 :externs ["types/vendor.edn" "types/my-app.edn"]}
```

```edn
;; types/vendor.edn
{vendor.text/upper [string? :-> string?]
 vendor.collections/identity-value (t/all [a] [a :-> a])
 :vendor/name string?}
```

Ключ qualified symbol описывает функцию, qualified keyword — именованный тип. Поддерживаются сигнатуры и конструкции текущего языка типов; EDN не расширяет возможности solver сам по себе. Полные имена не зависят от aliases вызывающего namespace.

Контракты собственных функций также можно вынести в EDN: имеющееся тело продолжает проверяться. Для отсутствующего исходного кода библиотечная декларация остаётся доверенным утверждением, а не доказательством её реализации.

Файлы читаются без require/eval. Ошибки чтения, неподдержанные формы и отсутствующие ссылки диагностируются. Происхождение хранится в `:extern/path`. Конфликт с собственным контрактом не должен молча его заменять; замена встроенных контрактов требует явного `:externs-core :override`.

## Встроенные декларации — реализовано

64 сигнатуры (51 clojure.core и 13 clojure.string) перенесены из `core_types.clj` без изменения смысла в:

```text
resources/typespec/types/clojure/core.edn
resources/typespec/types/clojure/string.edn
```

Загрузка — через classpath, не относительно текущей рабочей папки. `core-types/externs` и `core-types/table` сохраняют API. Специальные правила вывода (`get`, `assoc`, сужение и прочие зависимые от структуры операции) остаются кодом checker, а не вторым набором сигнатур.

Префикс `typespec/types/` изолирует встроенные ресурсы. Загрузчик отказывает при отсутствующем или дублирующемся ресурсе, неверном namespace ключа, плохой сигнатуре или содержимом, не являющемся ровно одной EDN-картой. Частичная загрузка встроенной таблицы недопустима. Для пользовательского файла ограничение «один namespace на файл» не требуется.

Проверено общим запуском: 102 теста / 660 assertions, без ошибок, плюс golden/CLI. Тесты включают загрузку из JAR вне репозитория, пользовательский loader и отказы на повреждённых ресурсах. Ошибка загрузки при старте пока даёт exit 1, как и найденные ошибки типов; различается по сообщению.

## Следующий шаг: декларации из зависимостей — план

Добавить **явное подключение classpath-ресурса** к существующему механизму externs. Автор библиотеки сможет включить декларации в её JAR; сторонний автор — поставить их отдельной dependency. Типы не требуют отдельного сервиса распространения: используется обычный Clojure dependency tooling.

Точный синтаксис config для classpath-источника ещё не принят и не реализован. Нельзя считать пути ресурсов рабочей альтернативой текущим файловым строкам `:externs`.

Требования к следующему шагу:

1. Одинаковые грамматика типов и правила конфликтов для файлов и classpath-ресурсов.
2. Источник декларации доступен в диагностике: файл или ресурс и, где возможно, пакет.
3. Несколько ресурсов с одним выбранным именем — ошибка неоднозначности, не «первый в classpath победил».
4. Никакого автоматического исполнения библиотеки ради чтения её типов.
5. Никакого неявного переопределения core или контрактов проекта.
6. Тест загрузки из JAR в чужой рабочей папке и отрицательные тесты повреждённых/конфликтующих деклараций.
7. Документировать поддержанную версию библиотеки. Совместимость версии нельзя обещать, пока её проверка не реализована.

## Пока не делаем

- Автосканирование всех JAR в поисках произвольных деклараций.
- Собственный аналог npm/@types registry.
- Неявное подключение набора по совпадению namespace.
- Автоматическую проверку диапазонов версий библиотек.
- Полный аналог TypeScript module resolution и declaration merging.
- Исполняемые типовые файлы или загрузку Clojure-кода вместо EDN.

## Проверка качества

Каждый набор должен иметь положительные и отрицательные тесты checker; для библиотечных особенностей — пробы на закреплённой версии настоящей библиотеки. Ноль диагностик не является доказательством реализации внешней библиотеки. Неподдержанное нельзя маскировать общими `any?` или подавлениями.

Первый набор: [аудит clojure.string](clojure-string-audit.md). Реальный потребитель локальных externs: [context-web-pg](../examples/context-web-pg/README.md).
