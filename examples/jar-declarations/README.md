# Декларации типов из JAR

Минимальная сторонняя библиотека `vendor-demo.core` не зависит от Typespec:
`identity-value` возвращает аргумент, `greet` принимает строку по контракту.
Её `library/resources/vendor-demo/types.edn` — обычные данные EDN:

```clojure
{vendor-demo.core/identity-value (t/all [a] [a :-> a])
 vendor-demo.core/greet [string? :-> string?]}
```

Consumer подключает Typespec через `:local/root` в `consumer/deps.edn` и явно
выбирает ресурс в `consumer/typespec.edn`:

```clojure
{:paths ["src"] :extern-resources ["vendor-demo/types.edn"]}
```

## Запуск

Нужны JDK с командой `jar` и Clojure CLI. Из корня репозитория Typespec:

```sh
bash examples/jar-declarations/verify.sh
```

Можно вызвать скрипт по пути из любого каталога. Дополнительные библиотеки для
сборки JAR не нужны; Clojure CLI загрузит обычные зависимости самого Typespec
при первом запуске (для этого может понадобиться сеть).

Скрипт создаёт временный каталог через `mktemp` под `${TMPDIR:-/tmp}` и удаляет
его при завершении. JAR, конфигурация временного consumer и его `.cpcache` не
попадают в репозиторий. Все процессы Clojure запускаются из временного каталога,
а не из корня Typespec. `local/root` вычисляется скриптом; абсолютных путей
конкретного компьютера в примере нет.

## Два способа доставки

1. **Bundled:** `vendor-bundled.jar` содержит `vendor_demo/core.clj` и
   `vendor-demo/types.edn`. Один артефакт с реализацией и декларациями.
2. **Split:** `vendor-code.jar` содержит только реализацию, а
   `vendor-types.jar` — только ресурс деклараций. Оба архива добавляются в
   classpath. Такой архив деклараций можно выпускать отдельно для библиотеки,
   которую нельзя менять; версии деклараций и библиотеки нужно согласовывать.

Скрипт реально собирает и проверяет **оба** варианта командой JDK `jar`.
Это обычные библиотечные JAR с исходниками Clojure, не standalone/uberjar:
их выполняет Clojure CLI с JVM. Для простоты архивы добавляются через `:paths`
в сгенерированном `deps.edn`; в опубликованном проекте это будут зависимости
Maven. Один и тот же ресурс нельзя одновременно добавлять обоими способами.

## Что проверяется

* В отдельной JVM выполняется библиотека: приветствие равно `"Hello, Ada!"`,
  целочисленный результат равен `42`.
* В новой JVM статический checker проверяет `consumer/src`: **0 диагностик**.
  У функций consumer явно указаны возвращаемые `string?` и `int?`.
* `consumer/negative` передаёт `(identity-value 42)` в строковый параметр
  `greet`: проверяется ровно одна ошибка `TSP2345` с сообщением
  `42 is not assignable to string?`. Это также проверяет сохранение типа
  generic-параметра, а не его подмену на `any`.
* На время статической проверки установлено JVM-свойство
  `vendor-demo.check-only=true`. При выполнении namespace библиотеки его
  top-level tripwire выбросит `VENDOR_DEMO_LIBRARY_EXECUTED`. Дополнительно
  проверяется отсутствие namespace через `find-ns` до и после checker.
  Tripwire ничего не записывает во внешние файлы. Runtime-проверка работает
  в другом процессе, где свойство не установлено.

**Граница доверия:** EDN сообщает checker контракт; это не доказательство
соответствия реализации. В частности, `greet` использует `str`, поэтому JVM
сама не отвергнет число. Ошибка отрицательного примера — именно статическое
нарушение заявленного строкового контракта. Typespec не должен выполнять
код библиотеки, чтобы прочитать декларации.
