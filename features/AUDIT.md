# Аудит карточек Typespec

## Что исправлено

Семь первоначальных карточек описывали заимствования Flow, а не весь продукт. Каталог восстановлен по README, docs/reference.md, PLAN.md, существующим тестам и исходникам прототипа. Теперь 26 карточек в пяти группах. Отсутствие карточки не означало отсутствия идеи: большая часть восстановленных тем уже была в reference.

| Группа | Основные темы | Результат аудита |
|---|---|---|
| F1xx | spec/fdef/hints/pre, ключ = тип, sidecars, providers | Основные источники работают частично; sidecars и providers — дизайн |
| F2xx | unknown, inference, generics, narrowing, guards, refinements, операторы, literals | Есть базовый вывод и сужение; общих generics нет; unknown пока небезопасен |
| F3xx | maps, nil, Java, macros, mutation, protocols | Мапы, nil и Java поддержаны частично; макросы — встроенные правила; полной модели mutation/protocols нет |
| F4xx | externs, интерфейсы, strict ns | Есть sig и strict на проект; нет полной системы exports, инкрементального кэша и строгих областей |
| F5xx | coverage, lint, suppressions, trust, agent/editor | Есть диагностики, счётчики, JSON и type-at; нет полноценного покрытия и CI-бюджета |

## Важные расхождения дизайна и реализации

1. **F210 unknown.** reference требует сужения. В `src/typespec/types.clj`, `subtype?` разрешает unknown как источник и цель. Отличать от any — обязательная работа, не новая идея из Flow.
2. **F510 Java.** reference говорит о bytecode, аннотациях nullability и generics. Прототип использует reflection, без инициализации классов; это не весь обещанный механизм.
3. **F610 макросы.** В reference есть lint-as, SCI hooks и worker. Наличие встроенных правил не означает реализацию этих механизмов.
4. **F230 generics.** Специальные правила map/filter/reduce не заменяют параметрическую систему и не гарантируют проверку трансдьюсеров.
5. **F840 доверие.** Счётчики есть, сравнение baseline и запрет ослабления типов в CI — ещё нет.
6. **F720 модули.** Вывод sig не означает наличие стабильных кэшируемых интерфейсов и корректной инвалидации.
7. **F260 refinements.** Opaque/brand не доказывает произвольный предикат. s/conform может преобразовать значение. Аннотация валидатора — не доказательство его тела.

## Правила статусов

`status` — состояние дизайна; `implementation` — состояние реализации. `partial` означает только перечисленные в карточке части. Иллюстрации без fenced-маркеров `example`/`output` не запускаются тестовым раннером. Нельзя объявлять карточку implemented лишь потому, что её Markdown прошёл генерацию индекса.

F280 объединяет ранее задуманный const и новую идею проверки без потери типа (аналог TS satisfies); новая часть имеет decision: proposed. Номера карточек задают будущие семейства диагностик `TSP210-01`, но текущие диагностические коды ещё не изменены.

## Следующий этап: сравнение с TS и Flow

Проверить полноту каталога по официальным документам: generics и variance, tuples/variadic arities, contextual typing, discriminated unions, safe unknown, indexed access, mapped/conditional types, satisfies, const, module interfaces и library declarations. Не переносить механизмы JavaScript буквально. Не считать conditional/mapped/template literal types обязательными для MVP: в исходном дизайне их сознательно нет.

Аудит выполнен по текстам и выборочному чтению реализации; это не доказательство корректности каждой реализованной формы. Для этого нужны исполняемые тесты по карточкам.
