# F110 · Источники типов и их согласование

## Мотивация и границы

В существующем Clojure сведения о типах распределены между spec, hints, предусловиями и телом функции. Полезная проверка должна использовать эти сведения без переписывания проекта на новый язык аннотаций. Но несколько источников не означают несколько независимых истин: hint нужен компилятору, spec описывает контракт, а вывод из тела показывает только то, что смог установить checker.

Эта обзорная карточка задаёт **согласование источников**, а не парсинг всех их конструкций. Цель — не скрывать конфликт выбором удобной декларации, не превращать отсутствие ошибки в доказательство и сохранять происхождение каждого ограничения. Typespec читает текст; он не запускает приложение, spec-предикаты и не добавляет runtime-проверки. Уже написанный `:pre` остаётся частью поведения самой Clojure-функции.

## Что реализовано сейчас (current)

Проверено по `src/typespec/env.clj`, `check.clj`, `types.clj`, а также разделу 2 `docs/reference.md`. Reference описывает и проектируемое поведение; наличие формы в reference не означает готовую реализацию.

1. `env/build` собирает `s/def`, `s/fdef`, `defn` и `:t/sig`. Для var выбирает `t/sig`, иначе `s/fdef`, иначе `hints-sig`. Это **приоритет выбора**, не общий алгоритм объединения ограничений.
2. Если одновременно есть `t/sig` и `s/fdef`, сравнивает внутренние типы через `not=` и сообщает `TSP2790`. Семантическая эквивалентность произвольных типов не проверяется. При конфликте выбранным остаётся `t/sig`.
3. В fallback `hints-sig` распознанный `:pre` для символьного параметра имеет приоритет над hint/типом паттерна; несколько условий на один параметр собираются в map, не пересекаются. При наличии полной декларации этот fallback не используется.
4. `check-defn` связывает параметры с выбранной сигнатурой и проверяет результат тела. Hint на векторе параметров дополнительно сравнивается с объявленным результатом: если ни одно направление `sub?` не проходит, выдаётся `TSP2322`. Это не полноценное согласование всех hints.
5. `var-type` может вывести неизвестный результат fallback-сигнатуры из тела, с кэшем и защитой от рекурсии. Это не поиск общего решения для всех источников.
6. У записей spec/fdef/var есть позиции, а у var — один `:source` (`:sig`, `:fdef`, `:hints`). Полного списка происхождений ограничений нет; `TSP2790` сейчас привязан к имени функции, а не к двум позициям.
7. Проектируемая загрузка `typespec/types.edn` и правила sidecar из reference не реализованы в этом сборщике. Встроенные core-типы не заменяют общий загрузчик externs.

Встроенный контракт `name` принимает строки и реализации `clojure.lang.Named`.
Для известной строки, ключевого слова или символа `name` возвращает
точный строковый тип.
`namespace` принимает `Named` и учитывает возможный `nil` в результате.
Для известного ключевого слова или символа выводится строка пространства
имён либо точный `nil` для неквалифицированного имени.
`qualified-keyword?` и `simple-keyword?` сохраняют этот признак
в Spec-контрактах, ветках условия и после `filter`.
`qualified-symbol?` и `simple-symbol?` дают те же гарантии для символов.

`parse-long` для известной строки выводит точное целое число
или `nil` по правилам JVM, включая переполнение и ведущие пробелы.
Для строки неизвестного значения результат остаётся nullable.
`parse-double` также различает известное число и неудачный разбор.
Строка `"NaN"` даёт ненулевой тип `double?`.
`parse-boolean` различает точные `true`, `false` и `nil`.
`parse-uuid` проверяет известную строку тем же парсером, что Clojure,
и сохраняет ненулевой тип UUID при успехе.

## Примеры

Все фрагменты независимы; где нужен `s`, подразумевается `(:require [clojure.spec.alpha :as s])`. Это обычные примеры исходника, не исполняемые snapshot-тесты карточки. `current` ниже означает вывод из чтения реализации, а не новый запуск тестов.

### 1. Корректно: два одинаковых публичных контракта

```clojure
(s/fdef echo :args (s/cat :x string?) :ret string?)
(defn echo
  {:t/sig '[string? :-> string?]}
  [x]
  x)
```

**Current:** одинаковые разобранные сигнатуры не дают `TSP2790`; тело возвращает входной `string?`. Выбранный `:source` — `:sig`, хотя spec тоже существует.
**Planned:** тот же результат проверки, но объяснение типа содержит обе декларации. Дублирование контракта не делает доказательство сильнее.

### 2. Ошибка: конфликт двух публичных входных контрактов

```clojure
(s/fdef render :args (s/cat :x string?) :ret string?)
(defn render
  {:t/sig '[int? :-> string?]}
  [x]
  (str x))
```

**Current:** `TSP2790` на имени `render`; для дальнейшей проверки используется `t/sig`. Тело, способное вернуть строку, не устраняет конфликт входа. Аналогичный случай уже есть в `test/features/src/f/core.clj` (`f4`) и `test/features/expected.txt`.
**Planned:** показать обе позиции и различающийся параметр. Не выдавать молча пересечение `int?` и `string?` за исправленный публичный контракт.

### 3. Ошибка: результат hint противоречит spec и телу

```clojure
(s/fdef text :args (s/cat :x string?) :ret string?)
(defn text ^long [x]
  x)
```

**Current:** `TSP2322` для несовместимого return hint; тело само по себе согласуется с `:ret string?`. Hint написан на векторе параметров. Форма `(defn ^long text ...)` проверяла бы ещё и другую проблему — неправильное место primitive hint (`TSP7021`), поэтому здесь не используется.
**Planned:** сохранить связь диагностики с hint и `s/fdef`, не подменять spec типом `long`. Особая nil-семантика platform hints относится к F111, а не решается стиранием оболочки platform.

### 4. Погранично: более узкий :pre рядом с широким контрактом

```clojure
(s/fdef keep-value :args (s/cat :x number?) :ret number?)
(defn keep-value [x]
  {:pre [(int? x)]}
  x)
```

**Current:** выбран `s/fdef`; отдельной проверки согласования `number?` и этого `:pre` нет. Нельзя интерпретировать отсутствие такой диагностики как доказательство, что функция принимает любое число: при активных assertions предусловие отвергает нецелое число.
**Planned:** выделить обязательство «публичный вход удовлетворяет предусловию». Для `number?` → `int?` оно не выполняется. Нужно утвердить политику: ошибка нарушенного входного контракта или явно разрешённый частичный контракт с предупреждением. Простое пересечение типов незаметно сузило бы обещание вызывающему коду и потому не годится.

### 5. Погранично: непрозрачный spec не является проверенным результатом

```clojure
(s/def ::short-text
  #(and (string? %) (< (count %) 8)))
(s/fdef identity-text :args (s/cat :x ::short-text) :ret ::short-text)
(defn identity-text [x]
  x)
```

**Current:** этот анонимный предикат не входит в поддерживаемый разбор типов; исходный `s/def` даёт warning `TSP9002` и становится `t/unknown`. Checker не исполняет предикат и не доказывает длину строки. Наличие `s/fdef` не делает непрозрачную ссылку полной гарантией.
**Planned:** сохранить причину неизвестности и зависимость сигнатуры от непрозрачного spec; итог согласования — «недостаточно сведений», а не «контракты доказанно совпадают». Важно: нынешний `parse-type` для `(s/and string? ...)` просто берёт первый тип, игнорируя остальные ограничения. Это другой случай потери точности, а не тот же warning; его развитие обсуждается в F112.

## Алгоритм согласования (planned)

Это проект протокола между сборщиками и checker, **не доказанный sound алгоритм для произвольного Clojure**. Он опирается на ограниченный язык типов и должен уметь вернуть «неизвестно».

1. **Вход.** Прочитанные AST с namespace aliases/imports и координатами; доступные spec и сигнатуры; параметры/арности `defn`; разрешённые внешние декларации; настройки проверки. Не выполнять формы, macroexpansion пользовательского кода или предикаты. Сборщики F111–F115/F130 возвращают ограничения, а не заранее выбранный победивший тип.
2. **Идентификация.** Привести имена к квалифицированному символу var/keyword spec. Разложить сигнатуры по арностям, позициям параметров и результату. Повторные объявления сохранить до анализа: сегодняшнее перезаписывание через `assoc-in` не является политикой разрешения дубликатов. Несовпадение арностей не сводить к конфликту одного результата.
3. **Представление.** Использовать типы текущего `types.clj` (`:fn`, `:arities`, `:params`, `:ret`, refs, platform, unknown), но рядом хранить записи фактов: источник, позиция, объект/слот, роль (`public-contract`, `jvm-hint`, `precondition`, `inferred-body`), тип и причина неполноты. Паттерн деструктуризации — локальное требование, не самостоятельное доказательство типа входа. `any?` отдельно обозначает сознательный отказ от проверки; `unknown` — отсутствие знания.
4. **Публичные декларации.** `t/sig` и `s/fdef` должны совпадать по контракту, как требует reference; совместимость в одном направлении недостаточна. Начать с поддерживаемой нормализации и структурного сравнения. Ссылки раскрывать с защитой от циклов. Семантическое равенство, не доказанное этим ограниченным механизмом, оставить неопределённым, а не объявлять конфликтом только из-за разного написания. Для sidecar var reference требует совпадения с `t/sig`, для sidecar key — подтип относительно spec; это разные отношения, не одна операция merge.
5. **Неравноправные источники.** Hint проверять на совместимость с контрактом с учётом platform/JVM-ограничений, а не повышать до spec-гарантии. Для `:pre` отдельно поставить проверку публичного входа против предусловия. Только после её успешного решения использовать условие как локальный факт. Если публичного контракта нет, распознанный `:pre` может задавать кандидат входа по F114. Нужна отдельная политика для отключённых assertions; runtime-исполнение условия нельзя предполагать безусловно.
6. **Тело.** Согласованные входные факты передать в `bind-pattern` и `infer-body`. Проверить выводимый результат против каждого обязательного публичного результата через существующую проверку возврата, не выводить контракт из того же тела и затем объявлять этим проверенной независимую декларацию. При отсутствии результата в контракте сохранить выведенный тип вместе с отметкой `inferred` и неизвестными зависимостями. Рекурсивное неизвестное значение не считать доказательством.
7. **Результат.** Вернуть выбранную рабочую сигнатуру для продолжения анализа, все происхождения и отдельное состояние обязательств: подтверждено / конфликт / недостаточно сведений. Для продолжения после конфликта допустим детерминированный выбор, но он не устраняет ошибку и не создаёт подтверждённую сигнатуру для отчёта.
8. **Диагностики.** Указывать var, арность, слот, роли источников, оба типа и обе позиции; для неполноты — причину (`opaque spec`, неизвестная ссылка, рекурсия). Сохранять существующие `TSP2790`, `TSP2322`, `TSP9002` в их нынешних областях. Новые категории/коды здесь не утверждаются; политику объединения каскадных ошибок нужно закрепить отдельно.

## Интеграция с текущим checker

Точка сбора — `env/collect-file` и `env/build`: вместо потери конкурирующих деклараций потребуется хранить кандидаты и результат согласования рядом с текущими `:type` и `:source`. Формат `:arities` сохранить для `check-defn`; диагностический слой расширить связанными позициями, не только текстом с двумя типами. `check-defn` остаётся потребителем согласованных входов и проверяет тело; `var-type` возвращает результат вывода, но не перезаписывает историю деклараций. Разбор spec, hints и паттернов остаётся ответственностью соответствующих карточек.

Нельзя просто заменить `not=` двумя вызовами `sub?`: текущий предикат совместимости предназначен для checker и сам по себе не доказывает семантическое равенство, особенно при unknown/platform, рекурсии и неподдержанных конструкциях.

## Матрица проверок

Ниже — конкретные регрессии для будущих тестов, не утверждение, что вся матрица уже покрыта.

| Случай | Current / имеющееся свидетельство | Требуемый результат planned |
|---|---|---|
| Пример 1: одинаковые sig/spec | Структурное равенство в `env/build` | Без конфликта; два происхождения |
| Пример 2: разные типы входа | `f4` + snapshot: `TSP2790` | Тот же конфликт, две позиции, слот параметра |
| Пример 3: spec string / return hint long | Проверка в `check-defn` | `TSP2322`, hint не заменяет spec |
| Пример 4: number / pre int | Нет отдельного согласования | Обязательство входа не подтверждено; утверждённая политика диагностики |
| Пример 5: opaque spec | Ветка opaque в `env/collect-file` | `TSP9002` + неполнота, не доказанное совпадение |
| Spec допускает nil / hint String | Platform-семантика, нет общего объединения | Не терять nil и происхождение; ожидания согласовать с F111 |
| Только pre string и противоречащий hint long на параметре | В fallback pre выигрывает | Явный конфликт ролей, без молчаливого выбора |
| Два pre на одном параметре в обратном порядке | Сейчас map перезаписывает факт | Один и тот же результат согласования независимо от порядка |
| Spec ret string / тело возвращает число | `check-return!` проверяет выбранный результат | `TSP2322`; вывод не исправляет декларацию |
| Несовпадающие арности sig/defn | `check-defn`: `TSP2790` | Ошибка конкретной арности, не ошибка типа результата |
| Одинаковый тип через ref и прямо | Нет общего семантического сравнения | Равенство после поддерживаемого раскрытия либо явно неполнота |
| Две декларации одного var/spec в разных файлах | `assoc-in` оставляет последнюю | Отдельная политика дубликатов; перестановка входных файлов не скрывает конфликт |
| Sidecar var против sig; sidecar key уже spec | В сборщике не поддержано | Для var — совпадение; для key — направленная проверка подтипа |
| Неизвестный результат рекурсивной функции | Кэш в `var-type`, не общий fixed point | Неполнота, без ложного доказательства согласованности |
| `any?` и `unknown` в одинаковом слоте | Разные внутренние типы | Отказ от проверки отличать от неизвестности в отчёте |

## Ограничения и вопросы, требующие исследования

- Семантическое равенство произвольных spec-предикатов в общем случае не решается этим checker. Нужно описать разрешимое подмножество нормализации и критерии результата «неизвестно».
- Более узкий `:pre` не всегда допустимое уточнение публичного входа. Нужны правила для частичных функций и отключённых assertions, прежде чем обещать soundness.
- Не определена полная политика повторных объявлений и конфликтов между несколькими внешними источниками. Зависимость от порядка чтения файлов нельзя принимать за контракт.
- Recursive refs, generics, overloads и platform nullability требуют собственных правил; пересечение всех типов не является универсальным решением.
- Нужны тесты качества объяснений: обе позиции, причина неполноты и отсутствие лавины вторичных ошибок после первичного конфликта.
