# F111 · Type hints как контракты

## Зачем

В Clojure уже есть хинты для компилятора: они помогают выбрать JVM-представление и избежать reflection. Дублировать их отдельной `t/sig` ради простой функции неудобно. Typespec может читать существующие хинты как частичный контракт, проверять вызовы и замечать противоречия между хинтом и известным типом до запуска программы.

Но хинт — не runtime-валидатор: он не проверяет произвольный вход и не доказывает отсутствие `nil`. Особенно важно отличать «тип выведен из значения» от «компилятор поверил аннотации». Эта карточка отвечает за чтение, проверку и происхождение хинтов; выбор Java-overload относится к F520, политика nil — к F320, общее согласование источников — к F110/F115.

## Статус и границы

**Current:** прототип читает символьные хинты параметров, вектора аргументов, имени `defn`, локальных bindings и некоторых выражений. Строит по ним сигнатуру, проверяет часть конфликтов, результаты функции и известные вызовы. Реализованы `TSP2322`, `TSP7021`, `TSP7025` в описанных ниже местах. Это подтверждается кодом и существующими golden-примерами, но не означает поддержку любой формы metadata Clojure.

Символы массивов Clojure 1.12, например `^String/1` и `^int/2`,
разрешаются в JVM-класс массива. Имя компонента можно импортировать
или записать полностью. Сигнатура `(defn labels-count [^String/1 values]
(alength values))` принимает `String[]` при вызове из другого namespace
и выдаёт `TSP2345` на переданном `int[]`.

Для Java-вызова checker учитывает хинт на месте вызова и сохраняет класс
хинта локального binding после сужения. В ветке `(map? value)` значение
с `^Iterable` остаётся мапой для анализа данных, а `(.iterator value)`
использует метод интерфейса
`Iterable`, если его нет в классе уточнённого типа.

**Planned:** полное происхождение фактов, явное различение доказанного уточнения и доверенного утверждения, сообщения о неподдержанном хинте и согласованные правила для всех мест metadata. `implementation: partial` сохранён: исходники подтверждают частичную реализацию, а не только проект.

## Примеры

Обычные `clojure` fences ниже — документация, не исполняемые golden-тесты. Current означает поведение по текущим веткам исходников; где есть существующий golden, он указан отдельно. Сниппеты с `s/nilable` предполагают alias `s` для `clojure.spec.alpha`; форма внутри `:t/sig` читается как данные, а не исполняется.

### 1. Корректная функция и неверный вызов — current

```clojure
(defn upper ^String [^String text]
  (.toUpperCase text))

(upper "clojure")  ; тип результата String, platform; не гарантия non-nil
(upper 42)         ; TSP2345: аргумент не соответствует String
```

Хинты параметра и результата дают полную сигнатуру без `t/sig`. В обычном режиме вызов метода внутри функции разрешён; при `:strict-nil` параметр требует проверки на nil (см. пример 4). Аналогичная проверка вызова hinted-функции `slug` уже есть в `test/examples`: неверные `42` и `"hello"` дают `TSP2345`.

### 2. Ошибочный локальный hint и более точный известный тип — current

```clojure
(defn bad-local []
  (let [^String text (count [1 2])]
    text))                       ; TSP2322 на ^String: int? несовместим со String

(defn keep-known []
  (let [^CharSequence text "abc"]
    text))                       ; конфликт отсутствует; сохраняется более точный тип значения
```

`bind-pattern` не всегда заменяет выведенный тип хинтом: совместимый более точный тип сохраняется. В ошибочном случае checker сообщает конфликт, но затем может использовать хинт для продолжения анализа; последующие выводы не являются доказательством корректности программы. Существующий golden проверяет вариант `^String` над `(first ids)`, где `ids` — коллекция `int?`.

### 3. Результат, явная сигнатура и место primitive-hint — current

```clojure
(defn bad-result ^String []
  42)                            ; TSP2322: тело не соответствует результату String

(defn conflict
  {:t/sig '[string? :-> string?]}
  [^long x]
  "ok")                          ; TSP2322: hint long противоречит string? параметра

(defn wrong-place ^long [^long x] x) ; правильное место return-hint
(defn ^long wrong-name [^long x] x)  ; TSP7021: перенести ^long перед вектором аргументов
```

Первый случай проверяется как обычный возврат по сигнатуре, второй — при связывании параметра. Class-hint на имени, например `defn ^String upper`, прототип также принимает как результат; primitive-hint на имени исключён из синтеза результата и отдельно диагностируется. Для согласованного стиля лучше ставить return-hint перед вектором аргументов. `TSP7021` уже зафиксирован в `test/examples/expected.txt`.

### 4. Nil — граница контракта, а не доказанное значение

```clojure
(defn size ^long [^String text]
  (.length text))
;; current: обычный режим разрешает platform receiver;
;; с :strict-nil ожидается TSP2531 на dereference: text может быть nil.

(defn known-null ^long [^java.util.Map entries]
  (.length ^String (.get entries "missing")))
;; current: даже без :strict-nil TSP2531 для результата Map.get:
;; Java-модель помечает его как возможно null; ^String это не стирает.
```

Второй случай есть в golden `request-id-length`. Хинты выражений, локальных привязок и JVM-ресиверов сохраняют известный `nil`, в том числе из `:ret (s/nilable ...)` в другом namespace. Для Java-метода с nullable-результатом сохраняется также причина из `:null-return`.

### 5. Доверенное утверждение и metadata map

```clojure
(defn assumed [x]
  (let [^String text x]
    (.length text)))
;; current: unknown заменяется на platform String без ошибки о недоказанности.
;; planned: сохранять отметку «доверенный hint», а не считать это доказательством.

(defn map-tag [^{:tag String} x]
  x)
;; Такая запись передаёт тот же контракт String, что и ^String.
```

Первый пример может завершиться ошибкой при реальном неверном входе. Во втором примере checker читает `:tag` из metadata map. При нескольких записях выигрывает внешняя, как у reader Clojure.

## Алгоритм проверки

### Входы и представление фактов

Вход: AST из `parse` с `:meta` и позициями `:pos`, imports файла, объявления `t/sig`/`s/fdef`, таблица переменных и арностей, локальное окружение и опция `:strict-nil`. Исходные формы приложения для этого не исполняются.

Current-представление: `env/tag-node` читает символьный хинт или строковый дескриптор массива, в том числе из `:tag`. `hint-type` разрешает класс через `types/resolve-class` и вызывает `class-type`/`platform`. Ссылочный hint обычно несёт `:platform true` и `:as` для отображения. Primitive сохраняет `:as`. Некоторые JVM-классы нормализуются в примитивные типы checker. `Object` превращается в `any`.

В `env[:vars]` хранится общий `:source` (`:sig`, `:fdef`, `:hints`) и `:tagged?`, у checker — локальные типы, `:hinted` и объяснения `:why`. Этого недостаточно для полного происхождения каждого факта.

### Последовательность в текущем checker

1. **Извлечь hint и разрешить его имя.** Неразрешённое имя даёт отсутствие типа. Сейчас отдельного результата «metadata есть, но не поддержана» нет; это пробел, а не успешная проверка.
2. **Собрать функцию.** `env/hints-sig` обходит арности: фиксированные параметры берутся из распознанных preconditions или `pattern-type`; последний сначала смотрит hint. Результат берётся с вектора параметров, затем с имени, если это не primitive, иначе остаётся unknown. `env/build` предпочитает `t/sig`, затем `s/fdef`, затем синтезированную сигнатуру. Общий протокол согласования всех источников здесь не переопределяется.
3. **Связать параметр или локальное имя.** Для известного ожидаемого/выведенного типа `A` вызвать `check-hint!`. Он учитывает strict-nil через `eff`, убирает nil для сравнения класса и пропускает проверку при `never`, `unknown`, `any`. Для остальных выдаёт `TSP2322`, если не выполняется ни `A <: H`, ни `H <: A`.
4. **Выбрать тип для продолжения.** В `bind-pattern` использовать hint `H`, если `A` — unknown/any либо известная ненулевая часть `A` не является подтипом `H`; иначе оставить `A`. Обновить окружение и `:hinted`. Это включает доверенное сужение широкого типа и восстановление после ошибки, не только доказанные уточнения.
5. **Проверить тело и return-hint.** `check-defn` связывает параметры, проверяет совместимость return-hint на векторе с выбранной сигнатурой, выводит тип последнего выражения и передаёт его в `check-return!`. Primitive на имени даёт `TSP7021`; primitive-параметры при числе фиксированных параметров больше четырёх — `TSP7025`. Проверки других JVM-ограничений нельзя выводить из этих двух веток.
6. **Обработать hint выражения.** После `infer*` функция `infer` проверяет hint для несимвольных узлов. Применяет `H` к ненулевым альтернативам, сохраняя известный `nil` и причину `:null-return`, если она есть. Употребления символов обрабатываются отдельно.
7. **Передать результат потребителям.** Проверки вызовов используют полученную сигнатуру; interop использует тип и отдельный факт доступности хинта компилятору. Ошибки сообщаются с файлом, позицией и текстом: конфликт hint — на tag, неверный возврат — на последнем выражении тела, неверный аргумент — на аргументе. `check` не должен переписывать код или вставлять проверки.

### Что необходимо спроектировать до полной реализации

Текущая двусторонняя проверка подтипов — эвристика совместимости, **не sound-алгоритм пересечения типов**. Несравнимые интерфейсы могут иметь общую реализацию; частично пересекающиеся unions тоже нельзя объявлять несовместимыми лишь по двум отрицательным проверкам `sub?`. Обратно, совместимый широкий тип ещё не доказывает более узкий hint.

Целевое расширение требует отдельных результатов: «доказано», «доказано противоречие», «неизвестно / принято на доверии». Для каждого хинта нужно хранить исходный tag, позицию, место применения, выведенный тип до хинта и основание доверия. Nil-факты хранить отдельно от JVM-класса; hint не должен уничтожать их. Для unknown/any и широкого типа сохранять trust-факт, а не выдавать доказанность. Неподдержанную metadata и неразрешённые классы делать видимыми как непроверенные; точный формат диагностики ещё не принят, новый TSP-код здесь не объявляется.

До замены `check-hint!` необходимо исследовать критерий доказанной непересекаемости для классов, интерфейсов и unions, а также точную семантику metadata Clojure по месту применения. Нельзя просто заменить условие на «пересечь типы»: полноценная операция пересечения и её гарантии пока не описаны этой карточкой.

## Интеграция и ограничения

- Точки интеграции: `env/tag-node`, `hint-type`, `hints-sig`, `build`; `check/check-hint!`, `bind-pattern`, `check-defn`, `infer`, `eff`; примитивы разрешения и подтипов в `types.clj`.
- Полный source-trace и учёт доверия к hints ещё не реализованы. `:hinted` описывает знание компилятора, а не доказательство runtime-типа.
- При явной сигнатуре checker проверяет return-hint вектора аргументов. При его отсутствии проверяется class-hint на имени функции. `TSP2322` указывает на конфликтующий хинт.
- Отдельной инвентаризации требуют Clojure 1.12 `:param-tags`, хинты на `fn`, поля `deftype` и хинты на употреблениях символов. [Выбор перегрузки](F520-java-overloads.md)
- `TSP7026` для бесполезного хинта присутствует в design reference, но эта карточка не объявляет его реализованным. Reflection-fixes и проверка их безопасности — отдельная задача.
- Неясно, должен ли узкий локальный hint над широким типом оставаться неявным доверенным утверждением или требовать явного opt-in. Независимо от решения нельзя выдавать его за runtime-валидацию.

## Конкретная матрица тестов

«Есть golden» ниже означает прочитанный существующий expected, а не запуск тестов в рамках редактирования карточки. Остальные строки — тесты, которые нужно добавить; не обещание уже достигнутого покрытия.

| Случай / вход | Режим | Проверяемый результат | Покрытие / работа |
|---|---|---|---|
| `slug` с hints String/long, неверные аргументы | обычный | `TSP2345` на каждом неверном аргументе | есть golden `test/examples` |
| `upper` и корректный вызов из примера 1 | обычный | нет ошибок, сигнатура из hints; platform-result | добавить точный тест типа |
| `^String` над известным int? | обычный | `TSP2322` на tag, фактический тип в тексте | есть golden `first-len`; добавить literal/count-вариант |
| `^CharSequence` над строковым литералом | обычный | нет конфликта, не теряется более точный тип | добавить тест окружения/type-at |
| Return `42` при `^String` | обычный | `TSP2322` на последнем выражении | добавить изолированный тест |
| `t/sig` string? + параметр `^long` | обычный | `TSP2322`, указаны оба типа | добавить |
| Return-hint на векторе или имени против явной сигнатуры | обычный | `TSP2322` на tag | [Регрессии](../test/typespec/java_overloads_test.clj) |
| Primitive на имени / на векторе | обычный | `TSP7021` только для имени | неверное место есть golden; добавить парный успешный |
| Пять фиксированных параметров, хотя бы один primitive | обычный | `TSP7025`; четыре не дают эту ошибку | есть пример `f6` в `test/features`; добавить граничную пару |
| `^String` receiver | обычный / strict-nil | разрешён / `TSP2531`; guard устраняет nil-риск | добавить обе конфигурации и guard |
| `^long`/`^double` | strict-nil | нет искусственного nil в типе | добавить |
| `^String` над `Map.get` | обычный | `TSP2531` сохраняет причину null-return | есть golden `request-id-length` |
| Hint выражения над другим известным nilable | оба режима | planned: nil-факт не теряется | добавить regression до изменения политики |
| Локальный hint над unknown/any | обычный | current: доверие без ошибки; planned: видимый trust-факт | добавить фиксацию текущего и целевого поведения |
| `^{:tag String}` / неизвестный класс | обычный | planned: распознано либо явно непроверено, не молчаливый успех | добавить |
| Частично пересекающиеся unions / два интерфейса | обычный | не объявлять доказанное противоречие без основания | исследование, затем негативные тесты ложных срабатываний |
| `^String` на употреблении символа и на выражении | обычный | проверить различие текущих путей, затем согласовать политику | добавить |

Готовность: для поддержанных форм есть положительные, отрицательные и пограничные тесты, включая позиции диагностик; для недоказанных утверждений виден источник доверия; для неподдержанных форм видна непроверенность. Ни отсутствие ошибок, ни отсутствие reflection сами по себе не означают sound-проверку хинтов.
