# F112 · Spec: s/def и s/fdef

## Зачем

В Clojure уже бывают описаны формы данных и аргументы функций через `clojure.spec.alpha`. Повторять их в другом языке аннотаций дорого: при изменении API два контракта расходятся. Typespec должен извлекать из исходного spec статически понятную часть и проверять её в местах вызова и в теле функции, не загружая приложение и не исполняя predicates.

Это **не замена runtime spec**: отсутствие ошибок типов не доказывает `s/valid?`, корректность `s/conform` или выполнение отношения `:fn` между аргументами и результатом. Карточка отвечает за извлечение spec-контракта; общая политика нескольких источников относится к F110, явные сигнатуры — к F115, regex-арности — к F410.

## Что реализовано сейчас

`implementation: partial` сохранён. Ниже current означает чтение текущих исходников и имеющихся fixtures, а не обещание всей семантики spec.

- `parse.clj` читает AST с позициями; `env/collect-file` собирает верхнеуровневые `s/def` с keyword-именем и `s/fdef`. Alias в голове декларации разрешается через `env/head`.
- `types/parse-type` понимает примитивы, ссылки на qualified keywords, множества литералов, `s/nilable`, `s/or`, формы мап и коллекций. Множество в позиции предиката Spec принимает элементы с истинным результатом поиска. Для `false` и `nil` подходят `false?`, `nil?` или предикат с `contains?`. `s/tuple` сохраняет типы позиций. [Границы длины](F330-tuples-and-nonempty.md)
- `some?` задаёт контракт на любое значение кроме `nil`, включая `false`. Встроенный контракт `clojure.string/replace` использует его для первого аргумента, который Clojure преобразует через `.toString`.
- `s/fdef` становится сигнатурой при переводимом `:args`. Поддержаны конечные альтернативы и однородный rest в конце, включая минимум один для `s/+`. Неподдержанный regex даёт `TSP9002`. Поддержанные формы приведены в [F412](F412-spec-regex-arities.md). `s/fdef` и `s/fspec` принимают пары ключ/значение и завершающую карту опций. Пропущенный `:ret` даёт `t/unknown`, а ключ без значения получает `TSP9002`. `:fn` не проверяется.
- Тела `defn` и `defmethod` проверяются по аргументам и результату сигнатуры. Вызовы используют тот же контракт. [F440](F440-multimethods.md)
- У `s/fdef` с одним `:ret` результат проверяется для всех реализаций `defn`. Арности и параметры берутся из самого `defn`, в том числе из хинтов. Когда тело отсутствует, обычный вызов получает указанный результат при неизвестной арности.
- Если регулярная форма `:args` остаётся непрозрачной, её `TSP9002` сопровождает проверку распознанного `:ret` в реализации и местах вызова.
- Если `:ret` отсутствует, обычный вызов может получить тип результата из единственного определения `defn` с соответствующей арностью. Для альтернатив Spec одной арности тело анализируется с типами параметров каждой альтернативы. Если фиксированная форма аргументов попадает в вариативную реализацию, известные позиции rest передаются в деструктуризацию. Для вариативной формы Spec учитываются тип и минимальная длина rest, если фиксированная ветка не перехватывает эти вызовы. Этот вывод работает между namespaces.
- Непонятное выражение типа в spec вызывает warning `TSP9002` и даёт `t/unknown`. В явном `:t/sig` аналогичный разбор использует `TSP9001`. Reference описывает общий `TSP9001`, но для spec источники уже отличаются от этого текста.
- `s/keys` и `s/keys*` принимают завершающую карту опций. Списки ключей читаются из последовательностей. Структурные ошибки, например одиночный ключ вместо списка, отсутствующий предикат `s/map-of` или незавершённая пара опций `s/coll-of`, получают локальную диагностику и оставляют остальные файлы доступными для проверки.
- В типах входных значений `s/nonconforming` и `s/with-gen` сохраняют ограничения вложенного Spec. Checker читает форму контракта и не вызывает генератор.
- Предикаты в Spec разрешаются в namespace объявления. Переименование через `:refer-clojure :rename`, alias и явный `:refer` сохраняют тип стандартного предиката. Одноимённый пользовательский Var остаётся непрозрачным.
- `:kind` у `s/coll-of` и `s/every` разрешается по тем же правилам. Непонятный предикат получает `TSP9002`. Пользовательский `:kind` может принимать значения, которые не удовлетворяют `coll?`.
- `s/coll-of` и `s/every` с общим `coll?` принимают мапы и проверяют их элементы как пары ключа и значения. Для известной мапы проверяются типы ключей, значений и границы размера.
- `s/coll-of` и `s/every` с `:kind map?` и двухэлементным `s/tuple` дают тип мапы с типами ключа и значения. Именованный tuple может быть объявлен в другом namespace. `:count` задаёт точный размер мапы.
- `s/map-of` с `:kind vector?`, `set?`, `list?` или `seq?` проверяет коллекцию двухэлементных векторов ключа и значения. Без `:kind` проверяется мапа. Несводимые к этим формам варианты получают `TSP9002`.
- `:kind list?` использует JVM-интерфейс `IPersistentList`. Литеральный список подходит, а `LazySeq` от `map` отклоняется. Общий `ISeq` и список без известного типа элементов дают частичную проверку.
- `char?`, `bytes?` и `class?` задают типы `Character`, `byte[]` и `Class`. В позиции значения импортированный или полностью квалифицированный символ класса удовлетворяет `class?`.
- `seqable?` описывает вход `seq`: `nil`, реализации `Seqable`, `Iterable`, `CharSequence` и `java.util.Map`, а также JVM-массивы. Этот тип работает в именованных Spec и у параметров из `s/fdef`.
- `sequential?` проверяет JVM-маркер `Sequential` в именованных Spec и простых предикатах. Векторы, списки и результаты `map` подходят. Хинт `ISeq` без данных о конкретной реализации даёт `TSP210-01`.
- `counted?` проверяет JVM-маркер `Counted`. Векторы, мапы, множества и списки подходят. `LazySeq` от `map`, Java `ArrayList` и JVM-массивы получают `TSP2345` в контракте `counted?`.
- `associative?` и `indexed?` проверяются по JVM-интерфейсам `Associative` и `Indexed`. Вектор подходит к обоим предикатам, а обычная Clojure-мапа подходит к `associative?`.
- `(partial instance? Class)` и одноаргументная обёртка `instance?` учитывают разрешение предиката и класса. Для `Object` контракт допускает любое значение, кроме `nil`.
- `s/and` сохраняет более узкий из сопоставимых скалярных типов начальных предикатов. `some?` убирает `nil` из известного `s/nilable`, в том числе через именованные Spec. После предикатов, сохраняющих значение, checker также может взять входную форму `s/keys`, `s/tuple`, `s/map-of` или `s/coll-of` с известным видом коллекции, включая ссылку на неё из другого namespace. Дальнейшие условия могут работать уже с изменённым значением. Конфликтующие `s/def` и `s/fdef` из разных файлов вызывают `TSP722-01`. При `s/conform` известного `s/or` выводится отдельный тип результата с тегами. [F261](F261-spec-conform.md)
- Если начальные проверки ключей в `s/and` обёрнуты в `s/nonconforming`, они и следующая проверка ключей получают одну исходную мапу. Checker объединяет требования этих форм, включая именованные Spec из других namespace.
- После сохраняющего значение предиката в `s/and` checker читает входную форму через `s/spec`, `s/nonconforming` и `s/with-gen`. Это сохраняет обязательные поля и их типы из вложенного `s/keys`.
- Последовательные `s/keys` в `s/and` также объединяются, когда очередная форма проверяет неквалифицированные ключи, значения которых предыдущие формы не преобразовывали.
- Для `s/coll-of` и `s/every` с `:distinct true` checker отклоняет доказанные повторы в известных позициях. Проверка произвольных значений остаётся за Spec на JVM.
- `:t/sig` имеет приоритет перед `s/fdef`; структурное неравенство двух представлений даёт `TSP2790`. Это не проверка семантической эквивалентности контрактов.

## Предикаты из `context-clj/http`

`#(contains? #{:get :post :put :delete :patch :head} %)` даёт конечное множество допустимых литералов. `#(or (list? %) (vector? %))` даёт объединение `clojure.lang.IPersistentList` и `vector?`. Типы распространяются через `s/keys` и `s/fdef`, включая вызовы из других namespaces. Для `s/conform` с известным `s/or` эти типы сохраняются в значениях тегированных веток.

Распознавание работает для одноаргументных функций с известными операциями над их параметром. У `or` должен быть понятен каждый предикат. Динамические множества, затенённые функции и произвольные выражения дают `TSP9002`. Сравнение неизвестного значения с контрактом qualified-ключа даёт `TSP210-01`, а известное несовместимое значение даёт `TSP2322`.

На Clojure 1.12.4 тест сверяет статическое решение с `s/valid?` для HTTP-методов, списков, векторов и значений за пределами контракта. Приёмка HTTP дополнительно проверяет вызовы по исходному `::http/endpoint` вместе со всеми восемью файлами библиотеки. [Тесты предикатов](../test/typespec/spec_predicate_test.clj) · [Приёмка HTTP](../examples/context-http-check)

## Примеры

Все блоки иллюстративные, не исполняемые golden-тесты. Каждый самостоятельный пример использует собственный namespace. Ожидания current ниже выведены из кода; новые примеры отдельно не запускались.

### 1. Корректный контракт и вызов — current

```clojure
(ns example.greeting (:require [clojure.spec.alpha :as s]))
(s/def ::name string?)
(s/fdef greet :args (s/cat :name ::name) :ret string?)
(defn greet [name] (str "Hi " name))
(greet "Mira")
```

Ожидание: ссылка `::name` разрешается в string, параметр тела получает этот тип, результат `str` соответствует `:ret`; ошибок этого контракта нет. В runtime ничего не вызывается для извлечения spec. Наличие сигнатуры не запускает `instrument` и не гарантирует проверку вызовов вне анализируемых файлов.

### 2. Ошибка аргумента и ошибка результата — current

```clojure
(ns example.wrong (:require [clojure.spec.alpha :as s]))
(s/fdef label :args (s/cat :n int?) :ret string?)
(defn label [n] n)    ; TSP2322: int не соответствует string
(label "three")      ; TSP2345: string не соответствует int
```

Проверки независимы: ошибка тела не должна скрывать ошибку вызова. На вызове checker использует объявленный результат string, а не заменяет контракт ошибочно выведенным int. Указанные коды уже существуют; точные позиции и текст нового fixture ещё нужно закрепить тестом.

### 3. Граница поддержанных арностей — current

```clojure
(ns example.optional (:require [clojure.spec.alpha :as s]))
(s/fdef add :args (s/cat :a int? :b (s/? int?)) :ret int?)
(defn add
  ([a] (add a 0))
  ([a b] (+ a b)))
(add 1)       ; корректно
(add 1 2)     ; корректно
(add 1 2 3)   ; TSP2554: ожидается 1 или 2 аргумента
```

Это конечные арности `[int -> int]` и `[int int -> int]`, не общий regex-анализ. Аналогичный случай уже есть в `test/features/src/f/core.clj` (`f1`, `f2`) и `expected.txt`. Optional перед обязательным элементом и произвольные вложенные regex-комбинаторы сюда не входят.

### 4. Предикат и refinement: «не найдено ошибок» не значит «spec выполнен»

```clojure
(ns example.refinement (:require [clojure.spec.alpha :as s]))
(s/def ::positive (s/and int? pos?))
(s/fdef keep-positive :args (s/cat :x ::positive) :ret ::positive)
(defn keep-positive [x] x)
(keep-positive -1) ; TSP2345: число не проходит pos?

(s/def ::short-text (fn [x] (and (string? x) (< (count x) 8))))
;; Тип string? сохраняется, а проверка длины получает TSP9002.
```

В одноаргументном предикате `and` позволяет использовать известные
условия на исходный параметр. Непонятные условия получают `TSP9002`.
Для `::positive` проверка знака всё ещё остаётся runtime-условием.

### 5. Повторное определение — current против planned

```clojure
(ns example.redefinition (:require [clojure.spec.alpha :as s]))
(s/def ::item string?)
(s/def ::item int?)
(s/fdef echo :args (s/cat :x ::item) :ret ::item)
(defn echo [x] x)
(echo "book")
```

**Current:** последнее определение побеждает; вызов получает `TSP2345`, отдельного конфликта определений нет. **Planned:** несовместимые определения должны давать диагностику с обеими позициями (`proposed TSP112-02`), а не зависеть от порядка обхода файлов. Даже если runtime допускает переопределение spec, для единого статического снимка нужен явный выбор версии. Правило для одинаковых повторов ещё требует решения; безопасный кандидат — объединять только нормализованно одинаковые декларации с сохранением всех источников.

## Пошаговый алгоритм и интеграция

### Текущий путь данных

1. **Вход:** разобранные файлы с `:ns`, `:aliases`, `:refers`, `:imports`, `:forms` и позициями. `parse/node->data` переводит тело декларации в данные без eval. Декларации, созданные произвольным макросом или скрытые в исполняемом коде, этот сборщик не раскрывает.
2. **Сбор:** `env/collect-file` разрешает голову формы и имя функции. `s/def` записывает `{:type T :file F :pos P}` в `:specs`; ссылки остаются `{:t :ref :name qualified-keyword}`, поэтому определение ссылки может стоять позже. `s/fdef` разбирает `:args` и `:ret`.
3. **Представление:** примитив — `{:t :prim :name ...}`, union — `{:t :union :types [...]}`, map — `{:t :map :req {...} :opt {...}}`. В `s/keys` qualified ключ и ключ `:req-un` могут иметь разные имена, но значение ссылается на один named spec. Разбор `s/or` моделирует допустимые **входные значения**, не tagged-результат conform.
4. **Арности:** `spec-args->arities` строит позиционные ветви из Spec regex. Каждая содержит `:params`, `:rest`, `:ret` и при необходимости `:rest-min`. Метки используются при conformation, а для позиционной проверки вызовов достаточно типов аргументов.
5. **Окружение:** `env/build` объединяет определения с `defn`, диагностирует структурный конфликт `:t/sig`/`s/fdef` (`TSP2790`), ставит `:source :fdef`. Без тела сохраняет контракт как внешнее утверждение. Ссылки раскрываются через `types/members`; отсутствующая или повторно встреченная при раскрытии ссылка становится unknown.
6. **Проверка:** checker выбирает арность вызова, проверяет соответствие каждого аргумента через общие `problems`/`sub?`. `check-defn` сопоставляет параметры с объявленной арностью, связывает локальные имена через `bind-pattern`, выводит тип тела и вызывает `check-return!`. Выход — тип выражения и накопленные диагностики с `:file`, `:pos`, `:code`, `:message`, иногда `:severity`.
7. **Диагностики:** неподходящая арность вызова — `TSP2554`, тип аргумента — `TSP2345` (nil может дать `TSP2531`), результат — `TSP2322`, отсутствующий обязательный ключ — `TSP2741`, несовпадение арности определения с сигнатурой — `TSP2790`. Это общие механизмы checker, не отдельный интерпретатор spec.

### Planned: не терять границу доказанного

1. Валидировать форму и число операндов до `nth`/`hash-map`; неверный или неподдержанный `:args` не должен ни падать, ни молча исчезать. Сохранять AST-путь до проблемного фрагмента.
2. Результат извлечения делать парой **тип + свидетельство полноты**: условно `exact-subset`, `approximate`, `opaque`, с исходной формой, причиной потери и позицией. Это предлагаемая модель, не существующие поля. Статус всего контракта складывать из статусов всех частей; объявленность сигнатуры не равна полноте её проверки.
3. Сохранять все определения одного имени до разрешения конфликтов. Несовместимые повторения блокируют выбор единственного проверенного контракта; порядок файлов не должен решать смысл API. Общий конфликт источников передавать политике F110, а не вводить здесь новый приоритет sidecar/hints.
4. Для поддержанного подмножества строить типы существующими конструкторами. Для `s/and` можно использовать первый компонент только как аппроксимацию входа; хвост хранить как непроверенные условия (`proposed TSP112-01`). Для conformer, `:fn`, сложных regex и неразобранных опций возвращать частичное покрытие, а не «полностью проверено» (`proposed TSP112-03`).
5. Передавать тип в текущие проверки вызовов/тел, а причины неполноты — в диагностики и отчёт покрытия. Нельзя просто считать успешный `sub?` доказательством: сейчас unknown совместим в обе стороны. Для строгого режима нужны согласованные с F210 правила unknown и запрет повышать статус непрозрачного контракта до проверенного.
6. Для сообщения о конфликте показывать обе декларации; для частичного разбора — точный пропущенный фрагмент и действие: упростить spec, оставить runtime-проверку или явно дать отдельную статическую сигнатуру. Новые TSP112-коды здесь только proposed, в реализации их нет.

Это план консервативного извлечения и учёта потерь, **не sound алгоритм проверки всех spec**. Для точных regex нужны модель языка аргументов и проверка его включения; для conformer — отдельные типы входа и выхода; для зависимого `:fn` — логика отношений. Их нельзя получить простым удалением меток и вызовом текущего `sub?`.

## Ограничения и вопросы

- `true?` и `false?` сохраняют допустимое логическое значение, а `some?` исключает `nil`. Для известного числа `pos-int?`, `nat-int?`, `neg-int?`, `pos?`, `neg?` и `zero?` проверяются по правилам Clojure. Для произвольного вычисленного числа вывод остаётся частичным.
- `s/keys` раскрывает группы `and` и `or` в `:req` и `:req-un` в альтернативы обязательных ключей. Если ветвей больше 64, групповые ключи остаются optional. `s/merge` сохраняет более узкие скалярные ограничения на общие поля, когда типы сопоставимы. [Правила для мап](F310-maps-and-destructuring.md)
- Компиляция Spec regex в позиционные арности ограничена. Неоднородные повторения, повторения перед обязательным аргументом и именованные regex пока требуют расширения.
- `:complete?` в `env/build` сейчас истинно при наличии декларации, даже если внутри unknown. Это метка наличия контракта, не сертификат покрытия всех predicates.
- Рекурсивные spec упомянуты в reference, но возврат unknown при цикле не является доказательством корректной рекурсивной проверки. Исследование рекурсивных типов — F295.
- Не определены политика повторного одинакового spec и поведение при динамической регистрации/удалении spec. Анализ одного статического снимка не моделирует историю runtime registry.
- Без тела `s/fdef` — доверенный контракт; проверка клиента не подтверждает реализацию библиотеки. Необходимо различать эти две границы доверия.

## Конкретная матрица тестов

«Есть» означает существующий fixture/ожидание, прочитанные при подготовке карточки; не запуск suite. «Добавить» — предлагаемый регрессионный тест, не уже реализованное поведение.

| Случай | Вход / изменение | Проверяемый результат | Состояние |
|---|---|---|---|
| Простая ссылка | Пример 1; определение `::name` также перенести ниже `fdef` | string у параметра и результата, без ошибок контракта | Добавить отдельный минимальный fixture |
| Ошибки с обеих сторон | Пример 2 | `TSP2322` на теле и `TSP2345` на аргументе, контракт не заменён выводом | Добавить |
| Optional | 1, 2 и 3 аргумента, пример 3 | первые два проходят, третий `TSP2554` | Есть аналог `f1`/`f2` |
| Конфликт источников | `fdef` string, `:t/sig` int для одного параметра | `TSP2790`, текущий приоритет sig | Есть `f4` |
| Missing key / nil | Вернуть map без required; вернуть nil при string-ret | `TSP2741` / `TSP2322` | Есть в `test/features/expected.txt` |
| Непрозрачный predicate | Последняя декларация примера 4 | warning `TSP9002`, unknown; predicate не вызывается | Добавить; проверить счётчик/маркер побочного эффекта отдельно |
| Refinement | `(s/and int? pos?)`, значение `-1` | `TSP2345` на известном отрицательном значении | Есть |
| Rest минимум | `:args (s/cat :xs (s/+ int?))`, ноль аргументов | `TSP2554` при прямом вызове или `apply` | Есть в F412 |
| Конечные альтернативы | `:args (s/alt :n int? :s string?)` | принимаются обе ветви, типы проверяются при вызове | Есть в F412 |
| Неподдержанный args | повторение перед обязательным аргументом | `TSP9002` | Есть в F412 |
| Дубликаты | Пример 5; переставить файлы/декларации | current last-wins; planned конфликт с двумя позициями, независимый от порядка | Добавить |
| Tuple / коллекции | `(s/tuple string? int?)` с перестановкой/лишним элементом; `coll-of` с `:count` | зафиксировать current потери; planned не заявляет полную проверку длины/позиций | Добавить |
| Цикл / missing ref | Необъявленный keyword; `a -> b -> a` | ограниченное завершение раскрытия, current unknown; planned причина неполноты | Добавить |
| Conform / relation | `s/conformer` и `fdef :fn` | не исполнять, не выдавать обычный ret за доказательство отношения | Добавить |
| Повреждённая форма | нечётные opts `fdef`, недостаточно операндов `map-of` | planned диагностировать исходную позицию, не исключение checker | Добавить |
| Alias и граница доверия | `:as sp` вместо `s`, `fdef` без `defn` | контракт найден; тело не обозначено проверенным | Добавить |

Перед переводом карточки в implemented нужны тесты извлечения (`env/build`, `parse-type`, `spec-args->arities`) и интеграционные тесты для оставшихся ограничений.
