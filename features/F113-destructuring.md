# F113 · Деструктуризация

## Зачем и границы

В Clojure параметры функций и `let` часто сразу разбирают входную структуру на локальные имена. Проверка должна переносить известный тип входа в эти имена, но не превращать факт чтения в доказательство наличия поля. Особенно важны различия между отсутствующим ключом, присутствующим `nil` и отсутствующим элементом последовательности: `:or` исправляет только первое.

Эта карточка отвечает за **binding patterns**: извлечение значений, локальные типы, defaults и причины возможного `nil`. Представление мап и операции `assoc`/`get-in` принадлежат [F310](F310-maps-and-destructuring.md), точные позиции и длины коллекций — [F330](F330-tuples-and-nonempty.md). Источники деклараций здесь используются, а не переопределяются.

## Что есть сейчас

`implementation: partial` соответствует исходникам:

- `check/bind-pattern` обслуживает символы, мапы и векторные patterns; используется при проверке параметров и локальных связываний.
- `destructure-map` поддерживает `:keys`, namespaced `:ns/keys`, `:as`, `:or` для ветки `:keys` и явное связывание `{local :key}`, включая вложенный pattern на месте `local`.
- Тип поля берётся из `key-info`: обязательное/необязательное поле, nullable-вход, ссылка на spec ключа. Optional без default получает `T | nil`; optional с default — `T | typeof(default)`, где собственный `nil` внутри `T` остаётся.
- `env/pattern-type` извлекает из `:keys` локальную нижнюю границу с optional-полями, а не доказательство их наличия. Для неизвестного обычного ключа тип остаётся unknown. Для qualified-ключа возможен тип из зарегистрированного spec; неизвестная форма мапы использует permissive/platform-путь, а не полное доказательство безопасности.
- Векторный pattern получает общий `elem-type`, а не тип по индексу. Элемент помечается `:platform true`; `--strict-nil` через `eff` добавляет nil. `s/tuple` уже при разборе типов теряет позиции и превращается в коллекцию с union элементов.
- Для `:keys!` и `:missing` есть отдельные ветки, но `:select`/`:excess`/`:all` и `:strs`/`:syms` дают unknown. Это не полная реализация таблицы reference.

В `deps.edn` закреплён Clojure **1.12.4**. Раздел reference о Clojure 1.13 и дифференциальном генераторе описывает целевой контракт; прочитанный `test/typespec/demo_test.clj` проверяет snapshots и маркеры, а не доказывает соответствие новой версии `destructure`. Нельзя считать новые директивы подтверждёнными runtime-тестами только потому, что checker их распознаёт.

## Примеры

Ниже пять иллюстраций, не исполняемые golden-тесты карточки. `s` — alias `clojure.spec.alpha`; каждый фрагмент с декларациями рассматривается отдельно. «Current» означает вывод из указанных веток исходников и существующих fixtures, а не запуск всех этих фрагментов.

### 1. Корректный default и сохранение исходного значения

```clojure
(s/def :task/title string?)
(defn title
  {:t/sig '[(s/keys :opt [:task/title]) :-> string?]}
  [{:task/keys [title] :or {title "untitled"} :as original}]
  title)

(title {})                       ; runtime: "untitled"
(title {:task/title "Build"})    ; runtime: "Build"
;; Current: title получает string? | тип "untitled", без nil.
;; original сохраняет тип входа; default не добавляет ключ в original.
```

Значение `{:task/title nil}` не удовлетворяет объявленному входному типу; default не делает такой вызов корректным. Это проверка контракта вызова, не запрет Clojure выполнить функцию.

### 2. Ошибка: присутствующий nil не заменяется default

```clojure
(s/def :job/retries (s/nilable int?))
(defn next-try
  {:t/sig '[(s/keys :opt [:job/retries]) :-> int?]}
  [{:job/keys [retries] :or {retries 0}}]
  (inc retries))

;; Вход {} даёт retries = 0.
;; Вход {:job/retries nil} даёт retries = nil; inc небезопасен.
;; Current: TSP2531 на использовании retries, с объяснением,
;; что :or применяется только к отсутствующему ключу.
```

Этот сценарий уже есть в `test/examples/src/ex/more.clj` и его `expected.txt`. Ошибка возникает при требовании non-nil в `inc`, а не от самого допустимого связывания nullable-значения.

### 3. Вложенность: отсутствие родителя переносится вниз

```clojure
(s/def :account/name string?)
(s/def :config/account (s/keys :req [:account/name]))
(defn greeting
  {:t/sig '[(s/keys :opt [:config/account]) :-> string?]}
  [{{:account/keys [name]} :config/account :as config}]
  name)

;; Current: name может быть nil, хотя :account/name обязателен
;; ВНУТРИ присутствующего account. Возврат string? небезопасен.
;; Planned: причина указывает весь путь [:config/account :account/name]
;; и отдельно отмечает отсутствие родителя, не ошибку в типе name.
```

`bind-pattern` уже передаёт строку `why` при рекурсивном связывании. Это ещё не структурированный путь и не гарантия сохранения всех причин при нескольких nullable-уровнях.

### 4. Граница: короткий вектор и остаток

```clojure
(defn second-inc
  {:t/sig '[(s/coll-of int? :kind vector?) :-> int?]}
  [[a b & tail :as original]]
  (inc b))

;; Runtime для [10]: a = 10, b = nil, tail = nil, original = [10].
;; Current: b — platform int; default-режим не доказывает длину.
;; С --strict-nil использование b требует nil-проверки.
;; Planned: b = int? | nil, tail — seq элементов или nil;
;; original сохраняет тип входа даже после &.
```

Есть конкретный пробел: текущая ветка `&` связывает только следующий pattern с `{:t :coll :of el}` и завершает обход. Поэтому следующий `:as original` не обрабатывается; nil-пустой остаток тоже не моделируется точно. Без `&` ветка `:as` сохраняет исходный тип. Отсутствие ошибки в default-режиме нельзя выдавать за доказанную безопасность индексного доступа.

### 5. Граница: явное имя, string keys и defaults

```clojure
(let [{n :count :or {n 7}} {}]
  n)                                  ; runtime: 7

(let [{:strs [label] :or {label "?"}} {"label" nil}]
  label)                              ; runtime: nil

;; Planned: одинаковое правило отсутствия/default для явного имени,
;; :keys, :strs и :syms; присутствующий nil всегда сохраняется.
;; Current: ветка {n :count} не применяет :or;
;; :strs/:syms просто связывают имена с unknown и не типизируют default.
```

Это не два подтверждённых успешных случая checker. Для inferred пустой мапы информация о `:count` попадает в loose/unknown, поэтому нынешний результат нельзя рекламировать как точное выведение `7`.

## Алгоритм проверки и интеграция

Ниже отдельно зафиксированы текущие операции и целевые изменения. Это проект расширения checker, **не доказанный sound алгоритм для всего Clojure**, особенно для union-входов, последовательностей и новых директив.

1. **Вход.** AST pattern с позициями, тип уже вычисленного initializer/параметра, `ctx` с локальным окружением, таблицами specs/aliases и флагами strict. Runtime-значение initializer не вычисляется checker. Общая точка входа — `bind-pattern`; источники типа параметров собирает `env`, проверку тела и локальных выражений ведёт `check`.
2. **Нормализация pattern (planned).** Преобразовать директивы и явные пары в список операций `bind(local, path, default?, pos)` плюс `as` и `rest`. Сохранить namespace ключа отдельно от локального имени: `:task/keys [title]` читает `:task/title`, связывает `title`. Обработать string/symbol keys, вложенность и `:as` после `&` явно, не через общий случай обхода. Проверить допустимость формы для выбранной версии Clojure; не переписывать пользовательский код.
3. **Представление фактов.** Сейчас типы — карты `:t :map` с `:req`/`:opt`, `:coll` с `:of`, union/ref/nil/unknown и platform-флагом. `lookup-key` возвращает `:req/:opt/:unknown/:nil/:missing/:not-map`; `key-info` добавляет `optional?` и диагностики. Для точных defaults нужен дополнительный факт presence: `present/absent/maybe`, отдельно от nullable-типа **присутствующего** значения. Planned: хранить причину как `{path, cause, source-pos}`, не только строку `why`.
4. **Проекция по ветвям (planned).** Для каждой ветви union проверить, допускает ли runtime такую деструктуризацию. Для map-поля получить presence и тип присутствующего значения; nil-родитель даёт отсутствие доступного поля, но не утверждение `field = nil` во всех состояниях. Не объявлять отсутствующим неизвестный ключ открытой мапы. Неподдержанные источники, включая преобразование последовательности пар в map, должны оставаться явно непроверенными до отдельного моделирования. Нынешний `lookup-key` объединяет статусы грубо: `:missing` в одной ветви может завершить lookup диагностикой для всего union.
5. **Применение default.** Для присутствующего поля результат — `Tpresent`; для отсутствующего — `D` при default, иначе nil; для maybe — объединение этих результатов. Присутствующий nil входит в `Tpresent` и не удаляется. Типизировать выражение default и его собственные ошибки независимо от того, попадёт ли его результат в итоговый union: текущий код вызывает `infer` default только при `optional?`, а обязательное поле может скрыть ошибку внутри default. Порядок и область видимости defaults необходимо сверить с раскрытием `clojure.core/destructure` выбранной версии, а не с порядком пар мапы в нашем AST.
6. **Последовательности (planned).** При известных позициях/длине выбрать позиционный тип; за доказанным концом — nil; при неизвестной длине — `T | nil`. Остаток — последовательность соответствующих элементов либо nil, с уточнением непустоты только при доказанном факте. `:as` связывается с исходным входом независимо от элементов. До поддержки F330 нельзя выдавать union всех элементов за точный тип позиции.
7. **Связывание и проверка использования.** Через существующий `bind` записать тип и причину в локальный ctx, через `bind-pattern` рекурсивно разобрать вложенность. `check-hint!` уже проверяет противоречащие hints (`TSP2322`), но hints/platform остаются границей доверия. Отсутствие поля само по себе не ошибка для обычной деструктуризации: ошибкой становится несовместимое использование, возврат или нарушение объявленного контракта.
8. **Результат и диагностики.** Результат — обновлённое локальное окружение и накопленные diagnostics, не изменение типа исходной мапы. Сейчас `report!` сохраняет файл/позицию: `TSP2339` для неизвестного объявленной форме ключа либо чтения не из map, `TSP2304` для соответствующего неизвестного qualified-spec, `TSP2741` для требований `:keys!`, `TSP2531` для небезопасного nil-use. Planned: показывать путь и различать `missing-parent`, `optional-key`, `nullable-value`, `short-sequence`; отдельные новые коды здесь не вводятся.

## Ограничения и исследования

- Не смешивать presence и nilable: сейчас `:nil` возвращает тип nil, который затем объединяется с default, что не является точной моделью отсутствующего поля. Нужны отдельные регрессии на `(let [{:keys [x] :or {x 1}} nil] x)`.
- Прямые пары поддерживают чтение только когда selector — keyword. Произвольные ключи, `:strs`/`:syms`, области видимости и вычисление default требуют расширения; unknown — не свидетельство корректности.
- Правила aliases/qualified-ключей, duplicate bindings и некорректные patterns должны сверяться с Clojure, а не только с parser, читающим исходный текст без компиляции.
- Для Clojure 1.13 сначала закрепить конкретную версию отдельно от текущей 1.12.4, проверить реальные expansion/runtime результаты и только затем обещать semantics `:keys!`, `:req!`, `:select`, `:missing`, `:excess`, `:all`. В частности, распознавание `:keys!` не подтверждает отклонение запрещённого сочетания с `:or`.
- Нужен дифференциальный эксперимент: генерировать небольшие допустимые patterns и значения, выполнять их доверенным тестовым harness в закреплённом Clojure, проверять включение runtime-результатов в предсказанные типы и совпадение ошибок формы. Совпадение конечного набора тестов не является доказательством soundness; модель union/presence и её взаимодействие с narrowing требуют отдельного обоснования.

## Конкретная матрица тестов

Все новые строки — план тестирования, не утверждение о текущем покрытии. Проверять inferred локальные типы, отсутствие лишних diagnostics, код/позицию ошибки и runtime-семантику отдельно; запуск обеих nil-политик обязателен для platform-случаев.

| Случай | Вход/контракт | Ожидание |
|---|---|---|
| `:keys` required | `:req [:task/title]`, string | Локальный string; `:as` равен типу входа |
| `:keys` optional | `:opt [:task/title]`, без default | string или nil; небезопасный non-nil use диагностируется |
| Default | optional string, `{}` / присутствующая строка | Default только для отсутствия; локальный non-nil |
| Nullable default | optional nilable int, `{}` / `{:job/retries nil}` | 0 / nil; `inc` даёт TSP2531; существующий fixture `ex/more` |
| Required default | required int, ошибочное выражение default | Выражение проверяется, хотя его результат не расширяет тип поля; planned |
| Nil-вход | nil, `:or {x 1}` | Runtime 1, не nil; отделить presence от типа nil; planned |
| Явное имя | `{n :count :or {n 7}}` | Та же default-семантика, что у `:keys`; planned |
| Namespace | `:task/keys [title]` и `:keys [task/title]` | Читается один qualified-ключ; локальное имя `title` |
| String/symbol keys | `:strs [x]`, `:syms [x]`, missing/nil/value | Сохранение вида ключа; точные типы/defaults planned |
| Вложенность | optional родитель, required ребёнок | Nil ребёнка объясняется отсутствием родителя; полный путь planned |
| Union мап | ключ есть лишь в части вариантов | Presence по каждой ветви, без ложного доказательства required; planned |
| Неизвестный ключ | опечатка в объявленной форме | TSP2339 и позиция ключа; аналог уже есть в `ex/more` |
| Короткий вектор | `[]`, `[1]`, `[1 2]`, nil | Второй элемент nil/nil/2/nil; точная длина planned |
| Rest и as | `[a & tail :as original]` | Хвост nil/seq и исходный тип original; регрессия выхода после `&` |
| Tuple | `(s/tuple string? int?)` | Разные типы позиций; сейчас теряются, planned совместно с F330 |
| Не-map вход | число для keyword pattern | TSP2339; никаких вымышленных локальных типов |
| Версия/директивы | `:keys!` с `:or`, `:missing`, selector forms | Отдельный version-pinned oracle; не запускать как 1.12 runtime-примеры |

Критерий готовности: каждый поддержанный pattern имеет успешный, ошибочный и граничный тест; unsupported виден как непроверенный; причины nil и позиции стабильны; дифференциальные проверки соответствуют закреплённой версии. До этого статус остаётся `designed`, реализация `partial`.
