# F114 · Предусловия :pre

## Зачем

В Clojure функцию часто начинают с проверки входных значений. Если программист уже написал `{:pre [(string? x)]}`, повторять тот же факт в отдельной аннотации неудобно: два описания могут разойтись. Typespec может извлекать ограниченную часть такого контракта, проверять вызовы и использовать полученный тип в теле без загрузки приложения.

Однако «проверка выполнена перед телом», «автор обещает этот тип» и «все вызывающие обязаны передать этот тип» — разные утверждения. Особенно это важно при отключённых assertions, явной сигнатуре и произвольных условиях. Эта карточка описывает извлечение фактов из `:pre`, а не общий решатель логических формул или полную проверку Clojure spec.

## Текущее состояние — current

По `env.clj` реализована следующая узкая схема:

- `pre-conditions` читает `:pre` только из первой map-формы тела, если после неё есть ещё форма; значение `:pre` должно быть вектором.
- `pre-types` узнаёт одноаргументные вызовы известных предикатов с аргументом-символом. Также узнаёт `clojure.spec.alpha/valid?` с ключом Spec, символом значения и необязательной формой третьим аргументом. Неверная арность диагностируется на вызове предиката.
- Извлечённый факт хранит параметр, тип и исходное условие. Из совместимых ограничений одного параметра используется более узкое вне зависимости от порядка.
- В `and` каждый распознанный операнд даёт отдельный факт. Нераспознанные операнды не отменяют этот факт.
- В `or` типы объединяются, если каждая ветка даёт по одному факту об одном и том же параметре.
- `hints-sig` использует эту map только для простых фиксированных параметров; такой тип имеет приоритет над `pattern-type`/hint. Для rest-параметра и локальных имён из destructuring эта схема тип не переносит.
- `some?` и `nil?` дают противоположные ограничения. `some?` принимает `false` и отклоняет только `nil`.
- `instance?` с разрешимым JVM-классом даёт номинальный тип параметра. Локальное имя класса и примитивная проверка не дают такого факта.
- `env/build` выбирает явный `:t/sig`, затем `s/fdef`, и лишь без них — `hints-sig`. Только в последнем случае выведенные типы ограничивают аргументы вызова.
- При явной сигнатуре `check-defn` проверяет формы `:pre` с исходными типами параметров и перед проверкой остального тела уточняет локальные типы совместимыми фактами. Для `(some? x)` это исключает `nil` из объявленного типа.

Разрешение имени учитывает пользовательские определения и параметры, затеняющие предикат, включая имена из деструктуризации и rest. Несовместимые скалярные ограничения дают `TSP114-01` на условии, которое делает вход недостижимым. Соответствие `integer? → :int` также требует проверки: reference описывает `int?` как long-like, а не все целые числа Clojure. Поэтому `implementation: partial` сохраняется.

## Примеры и ожидаемое поведение

Все блоки ниже — обычные иллюстрации, не исполняемые golden-тесты. **Current** означает вывод из исходников и указанных тестов; **planned** — ещё не реализованное правило. Runtime-проверки Clojure зависят от режима assertions при компиляции; Typespec сам условия не исполняет.

### 1. Корректный вызов и использование типа в теле

```clojure
(defn add-fee [amount fee]
  {:pre [(number? amount) (number? fee)]}
  (+ amount fee))

(add-fee 100 5)
```

**Current:** оба фиксированных параметра получают `number?`, тело проверяется с этими типами; показанный вызов совместим с ними. Вывод числового результата из тела поддержан аналогичным примером в demo-тесте. **Planned:** сохранять происхождение каждого типа — конкретное условие `:pre`, а не только общий источник `:hints`/«from the body».

### 2. Ошибочный аргумент через alias spec

```clojure
(ns example.names
  (:require [clojure.spec.alpha :as s]))

(s/def ::name string?)
(defn echo-name [x]
  {:pre [(s/valid? ::name x)]}
  x)

(echo-name "Ada") ; совместимый аргумент
(echo-name 42)    ; несовместимый аргумент
```

**Current:** для `x` извлекается ссылка на `::name`; последний вызов должен получить обычную диагностику несовместимости аргумента `TSP2345`. Это проверка статического типа, а не запуск `s/valid?`. Поддержка извлечения `s/valid?` уже отражена в demo-тесте сигнатуры; именно этот самостоятельный блок тестом пока не закреплён. **Planned:** диагностика должна вести от аргумента к условию `:pre` и далее к определению spec. Для opaque spec нельзя обещать доказательство соответствия произвольному предикату.

### 3. Пограничный случай: противоречащие условия

```clojure
(defn impossible [x]
  {:pre [(string? x) (number? x)]}
  x)

(impossible 42)
```

Чекер сообщает `TSP114-01` на `(number? x)` и выводит `t/never` для параметра. При включённых assertions ни число, ни строка не проходят оба условия. Для произвольного Spec пересечение может остаться неизвестным.

### 4. Явная сигнатура и более узкое предусловие

```clojure
(defn string-number
  {:t/sig '[number? :-> number?]}
  [x]
  {:pre [(string? x)]}
  x)

(string-number 7)
```

**Current:** публичная сигнатура требует `number?`. Условие `(string? x)` не уточняет этот тип в теле, поскольку совместимость ограничений не доказана. **Planned:** конфликт показывать на условии с отсылкой к сигнатуре.

### 5. Условие вне поддержанного подмножества

```clojure
(defn positive-or-default [x]
  {:pre [(or (nil? x) (and (number? x) (pos? x)))]}
  x)

(positive-or-default nil)
(positive-or-default -1)
```

**Current:** ограничение для вызовов — `(s/nilable number?)`. При включённых assertions вызов с `-1` нарушает `pos?`, который остаётся за пределами вывода типов. **Planned:** явно отмечать непроверенную часть контракта.

## Алгоритм проверки и интеграция — planned

Это план ограниченного анализатора, а не готовый sound алгоритм для любых предусловий.

1. **Вход.** Для каждой arity получить AST `defn`, вектор параметров, начальную map условий, aliases/refers, определения spec, явную сигнатуру, позиции исходного текста и выбранную политику доверия assertions. Не смешивать факты разных arity. Отсутствие map или `:pre` означает отсутствие фактов, а не ошибку.
2. **Разбор и разрешение имён.** Проверить форму вектора и точную арность каждого поддержанного вызова. Привязать символ к конкретному параметру, а голову — к ожидаемому Var. Затенённый параметром или пользовательским определением `string?` не равен `clojure.core/string?`.
3. **Представление фактов.** Вместо map с перезаписью хранить список записей: arity, binding-id, тип (`t/prim` или `t/ref-t`), AST и позиция условия, источник `:pre`, степень проверенности. Отдельно хранить неподдержанные условия с причиной. На первом этапе извлекать только простые фиксированные параметры; destructuring/rest явно помечать как неподдержанные для извлечения.
4. **Ограниченная нормализация.** Снять повторы; если один известный тип — подтип другого, оставить более узкое ограничение, сохранив обе ссылки на источник. Для доказанно несовместимых примитивов отметить противоречие. Если совместимость не доказана, сохранить набор ограничений как нерешённый: не превращать его в `never`, `any?` или последнее условие. Для opaque, рекурсивных spec и произвольных пересечений сначала нужны исследование и тесты соответствия типовой модели реальным множествам значений.
5. **Согласование с сигнатурой.** Разделить `call-contract` и `body-facts`. При явной сигнатуре не подменять её предусловием. В режиме публичного контракта для каждого известного ограничения `P` проверять `DeclaredArg <: P`; доказанное нарушение — конфликт, неизвестный результат — непроверенный контракт. Без сигнатуры можно продолжить существующее извлечение параметров для вызовов, но только для проверенного подмножества и с явно описанной политикой доверия. Режим «только допущение в теле» не должен незаметно усиливать требования к вызывающим.
6. **Проверка тела.** Применять `body-facts` через отдельный этап перед `infer-body`, после связывания параметров в `check-defn`. Не трактовать map `:pre` как обычный литерал вместо семантики предусловий. Проверка well-formedness выражений и факт их истинности — разные операции. При отключённых/неизвестных assertions уточнять тело только в явно принятой статической модели контрактов; иначе одного текста `:pre` недостаточно для runtime-гарантии. Область покрытия этой гарантии (проверенные вызовы, внешние вызывающие, динамические Var) должна быть указана.
7. **Проверка вызова и результат.** Передать выведенный контракт в существующую проверку arity/аргументов (`arg-problems`, `problems` и вызовы `t/sub?` в `check.clj`); сохранить обычные `TSP2345` и структурные диагностики. Результат анализа — типы параметров, отдельные факты тела, список непроверенных условий и диагностик с происхождением. Не выводить runtime-успех из отсутствия ошибки типов.
8. **Диагностики и наблюдаемость.** Для противоречащих скалярных условий используется `TSP114-01`. Другие предложенные коды: **proposed TSP114-02** — конфликт с явной сигнатурой, **proposed TSP114-03** — условие не удалось статически проверить. Указывать позицию условия, параметр, ожидаемый/имеющийся тип и связанный источник. Два предложенных кода ещё не существуют. Предупреждение о неподдержанном условии не должно заменять обычную ошибку неправильной формы или скрывать каскадный источник.

## Ограничения и открытые решения

- Выбрать публичный контракт по умолчанию или opt-in. Прототип уже применяет извлечённые типы к вызовам, но это ещё не окончательное решение дизайна.
- Зафиксировать семантику при выключенных assertions и при вызове из непроверенного Clojure-кода. Проверка типов не делает assertions обязательными и не добавляет runtime-валидацию.
- Не исполнять пользовательские предикаты, макросы и spec. Побочные эффекты, изменяемые значения, зависимость от внешнего состояния и порядок условий не покрываются простым извлечением типа.
- Нужны отдельные решения для `not`, path-фактов (`(:key x)`), destructuring, rest и metadata-формы предусловий. `:post` и `%` не входят в F114.
- Уточнить числовую модель (`int?` против `integer?`), разницу между типовым приближением spec и полным `s/valid?`, а также поведение для отсутствующей/opaque спецификации. Не считать `unknown` успешным доказательством.
- Не объединять ограничения через произвольный intersection без доказанной семантики. Начальный безопасный объём — проверенные простые предикаты, ссылки на поддержанные spec и ограниченные отношения подтипов/несовместимости.

## Конкретная матрица тестов

В [spec-args-test](../test/typespec/spec_args_test.clj) проверяются вызовы из другого namespace, позиции диагностик, локальное уточнение тела и поведение условий на JVM. В таблице зафиксировано оставшееся покрытие.

| Случай | Что зафиксировать сейчас | Критерий целевого поведения |
|---|---|---|
| `number?`, два параметра, корректные числа | Параметры `number?`, числовой результат; аналог есть в demo | Нет ошибок вызова, provenance у обоих параметров |
| Числовой параметр, строковый аргумент | Demo golden содержит `TSP2345` | Ошибка на аргументе + ссылка на `:pre` |
| `s/valid? ::name x`, alias и fully-qualified имя | Извлечение `t/ref-t`; alias покрыт demo | Одинаковая сигнатура, `42` отвергнут для string-spec |
| Каждый предикат из `pre-preds` | Параметризованный тест извлечения всех десяти имён | Подтверждённое соответствие реальным значениям, особенно `integer?` |
| Два одинаковых / совместимых / несовместимых условия | Используется более узкий тип или TSP114-01 | Отдельное представление нерешённых ограничений |
| `:t/sig` или `s/fdef` + конфликтующее `:pre` | Явная сигнатура побеждает, конфликта нет | proposed TSP114-02; публичный тип не переписан |
| `or`, `pos?`, пользовательский предикат | `or` объединяет типы поддержанных альтернатив | Непроверенная часть видна, proposed TSP114-03 |
| Затенённое имя; лишний/отсутствующий аргумент | Проверены обычные параметры, деструктуризация и лишние аргументы | Нет ложного извлечения типа; обычная диагностика формы/arity |
| Две arity; rest; destructuring | Извлечение только простых fixed-параметров каждой arity | Нет утечки фактов между arity и неподтверждённых переносов |
| Нет `:pre`; map — единственная форма; `:pre` не vector | Проверить границы `pre-conditions` | Отсутствие контракта отделено от некорректного синтаксиса |
| Hint + `:pre`; отсутствующий/opaque spec | Проверить приоритет и результат разрешения | Конфликт/неизвестность не скрываются успешной проверкой |
| Assertions включены / отключены при компиляции | Runtime и статический результат проверять раздельно | Документированная политика, никаких обещаний обязательной проверки |

Не запускать эти примеры как обещанный готовый regression-набор: часть строк специально фиксирует дефекты current. Перед `implemented` нужны целевые тесты и устранение этих расхождений.

## Проверенные источники

- [Reference, §2: источники типов](../docs/reference.md): `:pre` — источник типов параметров без сигнатуры; язык типов — данные, не исполняемый код.
- [env.clj](../src/typespec/env.clj): `pre-conditions`, `pre-preds`, `pre-types`, `hints-sig`, `build` — фактическое извлечение и приоритеты.
- [check.clj](../src/typespec/check.clj): `check-defn`, `infer-body`, `problems` — связывание параметров и диагностики.
- [types.clj](../src/typespec/types.clj): представление примитивных типов и приближений Java-интерфейсов.
- [demo-test](../test/typespec/demo_test.clj): assertion сигнатуры, полученной из `:pre` и тела; [demo source](../demo/src/clinic/billing.clj) и [golden](../demo/expected.txt): `s/valid?`, `number?`, ошибка строкового аргумента. Это свидетельства реализации, а не предметная область данной фичи.
