# F115 · Явные сигнатуры t/sig

## Зачем

В Clojure функция может не иметь `s/fdef`, а Java type hints описывают главным образом JVM-представление, не весь контракт. Нужен необязательный способ задать типы параметров и результата рядом с `defn`, в том числе type-only формы, которые нельзя исполнять как spec. Это не замена существующим `s/fdef` и не требование переписать проект.

`{:t/sig '...}` — обычная attr-map функции. Quote сохраняет описание как данные в metadata; Typespec читает исходник, не загружая пользовательский namespace. Наличие аннотации само по себе не доказывает корректность: checker должен проверить и тело, и вызовы.

## Что уже работает, а что запланировано

**Current:** `env/collect-file` находит `:t/sig` в attr-map `defn`/`defn-`, передаёт данные в `types/parse-type`; `env/build` выбирает сигнатуру перед `s/fdef` и hints. Различающиеся внутренние представления `t/sig` и `s/fdef` дают `TSP2790`. `check/check-defn` связывает параметры с объявленными типами и проверяет результат тела. В golden fixture есть корректная сигнатура, конфликт и неизвестный тип.

**Planned:** строгая валидация именно *сигнатуры функции*, обязательности quote, полноты покрытия арностей и более точное объяснение конфликта с двумя позициями. Сейчас парсер принимает общий язык типов, а не отдельную закрытую грамматику значения `:t/sig`. Поэтому отсутствие диагностик для произвольной аннотации нельзя считать подтверждением её поддержки.

Здесь описан путь явной сигнатуры через checker. Подробные правила выбора overload и variadic-арностей принадлежат F410; их полноценный алгоритм эта карточка не обещает.

## Примеры

### 1. Корректная сигнатура и проверяемый вызов — current

```clojure
(ns example)

(defn text-size
  {:t/sig '[string? :-> int?]}
  [text]
  (count text))

(defn- demo []
  (text-size "hello"))
```

Параметр тела имеет тип `string?`, `count` возвращает совместимый с `int?` тип. Сама функция проверяется без ошибки; тип результата вызова — объявленный `int?`. Такой контракт уже проверяется в `test/features/src/f/core.clj` (`f3`); этот конкретный пример не является отдельным golden-тестом.

### 2. Аннотация не скрывает неправильное тело — current

```clojure
(defn wrong-size
  {:t/sig '[string? :-> int?]}
  [text]
  "not a number")
```

Ожидается `TSP2322` на возвращаемой строке: фактический тип не совместим с `int?`. При дальнейшем анализе вызовов checker продолжает использовать объявленный контракт, но ошибка тела остаётся: это восстановление после ошибки, не доказательство корректности функции.

### 3. Конфликт двух источников — current

```clojure
(ns example
  (:require [clojure.spec.alpha :as s]))

(s/fdef render :args (s/cat :value string?) :ret string?)
(defn render
  {:t/sig '[int? :-> string?]}
  [value]
  (str value))
```

Ожидается `TSP2790`: `[int? :-> string?]` против `[string? :-> string?]`. Этот случай соответствует fixture `f4`. Сейчас диагностика указывает на имя `defn`; для дальнейшей проверки выбирается `t/sig`, а не объединение контрактов. Planned: также показывать позицию `s/fdef` и различающийся компонент.

### 4. Опечатка в типе — current с неполным восстановлением

```clojure
(defn size
  {:t/sig '[strng? :-> int?]}
  [text]
  1)
```

Ожидается `TSP9001`, `not a type: strng?`, как в fixture `f5`. Неизвестный компонент восстанавливается как `t/unknown`, не `any?`. Однако наличие объявления уже выставляет `:complete?` в окружении; это технический флаг, а не гарантия, что все компоненты распознаны. Диагностику нельзя игнорировать из-за этого флага.

### 5. Пограничный случай: данные без quote — current/planned

```clojure
(defn identity-text
  {:t/sig [string? :-> string?]}
  [text]
  text)
```

**Current:** статический reader принимает вектор и разбирает его как сигнатуру; отдельной проверки quote нет. При обычной компиляции Clojure элементы attr-map вычисляются: здесь символы предикатов станут значениями функций, а не символами языка типов. Поэтому это не рекомендуемый способ записать контракт, даже если checker не жалуется. **Planned:** требовать quoted data и выдавать понятную диагностику; код для неё пока не закреплён. Исправление — `'[string? :-> string?]`. Нельзя автоматически исполнять аннотацию, чтобы «узнать её тип».

## Алгоритм и интеграция

### Вход и представление

Вход — AST прочитанных файлов с позициями, namespace, aliases/imports, объявлениями spec и функциями. Reader превращает узел аннотации в данные через `parse/node->data`; пользовательский код не выполняется. Тип функции представлен как `{:t :fn :arities [...]}`; каждая арность содержит `:params`, `:ret`, при необходимости `:rest`. Ссылки на specs остаются ссылками во внутреннем языке типов; неизвестный компонент — `t/unknown`. Позиции и происхождение хранятся в окружении отдельно от типов.

### Текущий путь

1. **Собрать объявления.** `env/defn-parts` выделяет имя, attr-map и тела арностей; `collect-file` ищет `:t/sig` именно в attr-map, а не произвольные metadata параметра. Параллельно собираются `s/def` и `s/fdef`.
2. **Разобрать данные.** `types/parse-type` снимает `quote` и для вектора вызывает `parse-sig`. Тот делит вектор по `:->`, разбирает типы аргументов и результата, отклоняет отсутствие результата и лишние элементы после него. Для некорректной формы callback создаёт `TSP9001` на узле аннотации и восстанавливается неизвестным типом. Это не полная валидация грамматики, особенно вокруг `&`.
3. **Согласовать источники.** `env/build` сравнивает разобранные `t/sig` и `s/fdef` через обычное Clojure `not=`. При различии пишет `TSP2790`. Затем выбирает `t/sig`, иначе `s/fdef`, иначе `hints-sig`; сохраняет тип в `:vars` вместе с `:source :sig`, файлом и позицией. Это сравнение структур, не проверка семантической эквивалентности или взаимного подтипирования.
4. **Связать контракт с телом.** `check-defn` ищет арность по числу фиксированных параметров и наличию rest, затем имеет fallback только по числу фиксированных параметров. Если ничего не найдено — `TSP2790` на векторе параметров. Через `bind-pattern` параметры, включая поддержанную деструктуризацию, получают объявленные типы; эти типы становятся локальными фактами для анализа тела.
5. **Проверить тело.** `infer-body` использует обычные правила checker; `check-return!` сопоставляет результат с `:ret`. Для несовместимого результата применяется `TSP2322`, для отсутствующего обязательного ключа возвращаемой map возможен `TSP2741`. Объявленные `any?` и `t/unknown` в результате отключают эту проверку. Отдельно проверяется противоречие return hint на векторе параметров; это не общий механизм согласования всех hints.
6. **Проверить использование.** Вызовы получают тип из того же `:vars` и проходят существующий путь `call-fn`. Новый механизм вывода специально для `t/sig` не нужен. Результат всей проверки — окружение типов и накопленные диагностики; ошибки разбора/конфликта не должны исчезать при успешной проверке остальных выражений.

### Что нужно добавить до полного статуса

Перед шагом 2 нужен валидатор контейнера: quote, допустимая форма сигнатуры, корректный `&`, обязательный функциональный тип. При ошибке нужно явно хранить невалидность объявления, не выдавая её за полноту. Между шагами 3 и 4 нужны сохранённые позиции обоих источников и проверка покрытия реализаций контрактом. Проверка всех арностей, одинаковых по числу аргументов, требует работы F410, а не простой замены `first` на обещание soundness.

Если решим принимать семантически равные, но структурно разные контракты, отдельно понадобятся правила нормализации ссылок, union, рекурсивных specs и их завершения. Пока нельзя называть текущий `not=` sound алгоритмом эквивалентности типов. Изменение политики совпадения источников должно быть самостоятельным решением с тестами, а не побочным эффектом этого улучшения.

## Ограничения и открытые вопросы

- Не вся грамматика reference реализована полностью. Наличие `t/` формы в документации не доказывает её полноценную проверку в теле.
- Отсутствует отдельный запрет не-функционального значения `:t/sig`; нельзя обещать для него точную диагностическую категорию до тестирования и доработки.
- Одинаковая семантика двух контрактов не гарантирует структурного равенства. Нужно определить, что именно значит «должны совпадать» для алиасов и нормализованных типов.
- Текущий подбор арности не доказывает покрытие всех объявленных overload и может использовать fallback с несовпадающим rest. Детали — F410.
- Hints не являются равноправным третьим контрактом: общий алгоритм их согласования пока отсутствует; сейчас есть отдельная проверка return hint.
- Диагностика разбора привязана к узлу всей аннотации; конфликт — к имени функции. Нужно решить, как хранить span каждого компонента и related location для `s/fdef`.
- Quote не делает аннотацию runtime-проверкой. При вызове обычного Clojure кода Typespec не добавляет guard, spec instrumentation или автоматическое приведение типов.

## Матрица тестов

Примеры выше — спецификация ожидаемого поведения, не новые исполняемые fixtures. Существующее покрытие и необходимые проверки разделены явно; golden-файлы нельзя обновлять вместо проверки причин изменений.

| Случай | Ожидаемая проверка | Покрытие / работа |
|---|---|---|
| `[string? :-> int?]`, тело `(count s)` | Нет ошибки в объявлении, `:source :sig` | Есть fixture `f3`; отдельно проверить поля окружения |
| Возврат строки при `:ret int?` | `TSP2322` на результате тела | Добавить точечный тест именно для `t/sig` |
| Неверный тип аргумента вызова аннотированной функции | Ошибка существующего пути `call-fn`, не молчаливое принятие | Добавить позитивный/негативный вызов одной функции |
| Конфликт `string?` / `int?` с `s/fdef` | `TSP2790`; дальнейший выбранный источник `:sig` | Есть fixture `f4`; добавить проверку выбранного типа |
| Совпадающие `t/sig` и `s/fdef` | Нет конфликта | Добавить парный тест к `f4` |
| `strng?` в сигнатуре | `TSP9001`; компонент `t/unknown`, не `any?` | Есть fixture `f5`; добавить проверку восстановления |
| Нет `:->`, нет результата, лишний результат | `TSP9001`, без падения checker | Добавить таблицу отрицательных форм |
| Вектор без quote | Сейчас принимается; целевое поведение — отказ с причиной | Зафиксировать current отдельно от planned |
| Quoted scalar вместо функции; некорректный `&` | Planned: ранний отказ, не «полная сигнатура» | Добавить после определения строгой грамматики |
| Тело имеет другую арность | `TSP2790` на параметрах | Добавить фиксированную арность; overload/rest — F410 |
| `defn-` с `t/sig` | Те же проверки тела, что у `defn` | Добавить тест приватной функции |
| Аннотация содержит неизвестную вызываемую форму | Не исполнять её; `TSP9001` | Добавить безопасный тест парсинга без загрузки namespace |
| Конфликт с двумя исходными позициями | Planned: primary у `defn`, related у `s/fdef` | Добавить после расширения диагностики |
