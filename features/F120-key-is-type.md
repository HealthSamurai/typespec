# F120 · Ключ задаёт тип значения

## Мотивация и граница обещания

В Clojure одно поле встречается в разных открытых мапах: запись пользователя, событие, аргументы команды, результат запроса. Объявление `:account/id` позволяет переиспользовать тип значения, не переписывая его в каждом `s/keys`. Форма мапы отдельно определяет, обязательно ли поле. Тип поля не делает мапу номинальной сущностью и не превращает `:account/id` и `:order/id` с одинаковым `string?` в разные brands.

**Current:** прототип собирает `s/def` из текста, связывает квалифицированные ключи с типами, проверяет некоторые места записи и использует объявление при чтении. Это не runtime-валидация. Само наличие `s/def` не доказывает корректность произвольной входной мапы. Нынешнее доверительное чтение из неизвестного значения — ограничение, а не доказательство безопасности.

**Planned:** согласование с `types.edn`, явная политика повторных объявлений и границ доверия. Подробные правила sidecar принадлежат F130, операции над мапами — F310; здесь фиксируется только общий контракт «ключ → тип значения».

## Примеры и ожидаемое поведение

Ниже обычные иллюстрации, не исполняемые golden-тесты. Каждый блок независим; `s` — alias `clojure.spec.alpha`. Current означает поведение, прочитанное в исходниках, а не новый выполненный тест.

### 1. Корректно: один тип поля, две формы мапы — current

```clojure
(ns demo.reuse (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)
(s/def :event/kind #{:opened :closed})
(s/def ::account (s/keys :req [:account/id]))
(s/def ::event (s/keys :req [:account/id :event/kind]))

(s/fdef account-id :args (s/cat :a ::account) :ret string?)
(defn account-id [a] (:account/id a))

(s/fdef opened :args (s/cat :id :account/id) :ret ::event)
(defn opened [id] {:account/id id :event/kind :opened})
;; Оба тела соответствуют контрактам.
;; :req доказывает присутствие; string? сам по себе его не доказывает.
```

Ключи в `#:account{:id ...}`, `#::alias{:id ...}` и `#::{:id ...}` получают
namespace мапы, включая ключи из выбранной ветки reader conditional.
Префикс `_` оставляет ключ неквалифицированным. Значения сохраняют свои имена.

### 2. Ошибка записи без ожидаемого типа целой мапы — current

```clojure
(ns demo.write (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)

(defn- wrong [] {:account/id 42})
;; TSP2322 на 42: значение не соответствует :account/id (string?).

(defn- replace-id [] (assoc {:account/id "a"} :account/id 42))
;; TSP2322 на аргументе 42 в assoc с литеральным ключом.
;; Проверка привязана к ключу, а не только к s/fdef принимающей функции.
```

### 3. Пограничный случай: :id не имеет глобального типа — current

```clojure
(ns demo.unqualified (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)
(s/def :job/id int?)
(s/def ::account (s/keys :req-un [:account/id]))
(s/def ::job (s/keys :req-un [:job/id]))

(s/fdef text-id :args (s/cat :a ::account) :ret string?)
(defn text-id [a] (:id a))
(s/fdef numeric-id :args (s/cat :j ::job) :ret int?)
(defn numeric-id [j] (:id j))

(defn- free-id [] {:id false})
;; Корректно: здесь нет контекста ::account или ::job.
;; Передача {:id false} в text-id должна дать ошибку значения :id
;; (для свежей мапы используется TSP2322), а не глобальный запрет :id.
```

`parse-keys` поддерживает также `:opt-un`: связь локальна форме мапы, но значение при чтении может отсутствовать. Это шире краткой формулировки reference о `:req-un`.

### 4. Объявление не заменяет проверку входа — current и planned

```clojure
(ns demo.boundary (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)
(s/def ::account (s/keys :req [:account/id]))

(defn- unchecked [x] (:account/id x))
;; Current: при неизвестном x checker берёт ссылку :account/id,
;; помечает её :platform, не доказывая ни наличие ключа, ни string?.
;; Runtime: (unchecked {:account/id 42}) возвращает 42.

(s/fdef maybe-id
  :args (s/cat :a (s/keys :opt [:account/id]))
  :ret (s/nilable string?))
(defn maybe-id [a] (:account/id a))
;; Current: известная optional-форма даёт string? | nil.
;; Planned: отдельно учитывать доверие к x; нельзя повысить unknown
;; до доказанного string? лишь потому, что ключ зарегистрирован.
```

### 5. Повторное объявление — текущая потеря информации

```clojure
(ns demo.duplicate (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)
(s/def :account/id int?)

(defn- row [] {:account/id "a"})
;; Current: последнее собранное объявление заменяет предыдущее;
;; row проверяется против int? и получает TSP2322.
;; Planned: конфликт должен быть виден до проверки тел, с обеими
;; позициями объявления; предлагаемый код — proposed TSP120-01.
```

Порядок обхода файлов checker не следует путать с порядком загрузки программы. Даже если последний `s/def` в одном файле совпадает с runtime-поведением, это не общая политика для нескольких модулей.

## Алгоритм проверки и интеграция

### Реализованный путь

1. **Вход:** разобранные файлы с формами, aliases, imports и позициями; опции `strict`; локальные типы выражений. `env/collect-file` распознаёт верхнеуровневый `clojure.spec.alpha/def`, не выполняя исходный код. `types/parse-type` переводит тело spec в поддержанное представление. Непрозрачный предикат даёт `TSP9002` и `unknown`, а не доказанную проверку произвольного условия.
2. **Реестр:** `env/build` создаёт `:specs {keyword {:type T :file ... :pos ...}}` и `:key-nss`. Запись пока выполняется через `assoc-in`, то есть предыдущая декларация теряется. Ссылка на поле — `{:t :ref :name k}`; разрешение ссылок использует окружение.
3. **Форма:** `types/parse-keys` строит `{:t :map :req {...} :opt {...}}`. Для квалифицированных ключей сохраняет имя, для `:req-un`/`:opt-un` отображает короткий ключ на ссылку к полному имени. Обязательность и тип значения — разные факты.
4. **Запись:** `check/infer` для мапы, где все ключи литеральные keywords, вычисляет тип каждого значения. `check-key-value!` для зарегистрированного qualified keyword сравнивает эффективный тип значения с `ref(k)` через `types/sub?`. Несовместимость даёт `TSP2322` на значении. Этот helper также вызывается в поддержанных ветках `assoc` и `update` с литеральным ключом. Успешная проверка не означает, что все возможные способы создания мап покрыты.
5. **Восстановление после ошибки:** неверному значению литерала присваивается тип spec, чтобы не размножать диагностики. Это recovery, а не доказательство корректности программы. Для корректного литерала сохраняется выведенный тип значения; не надо утверждать, что все значения немедленно заменяются ссылкой на spec. Ветка `assoc` использует `key-type`, который выбирает ссылку для объявленного ключа.
6. **Чтение:** `lookup-key` сначала ищет ключ в `:req`/`:opt` конкретной формы. Если его там нет, зарегистрированный qualified key может дать optional-ссылку. `key-info`/`read-key` добавляют `nil` при отсутствии или nilable-получателе. Для unknown/any и некоторых менее точных типов используется доверительный fallback с `:platform`; он не является фактом runtime-валидации.
7. **Диагностики и результат:** возвращается тип выражения плюс накопленные сообщения с позицией. `TSP2339` покрывает отсутствующий ключ известной формы/неподходящий получатель. `TSP2304` сейчас ограничен namespace, уже входящим в `:key-nss`, и условием strict либо похожего имени; это не универсальная ошибка для любого необъявленного qualified keyword. Контекстная проверка свежих мап отдельно даёт `TSP2741` для отсутствующего обязательного поля и `TSP2322` для неверного значения.

### Что нужно спроектировать, а не считать готовым

1. Сохранять все декларации ключа с происхождением, прежде чем выбирать эффективный тип. Для повторных `s/def` определить политику: совпадающие типы можно объединять только после согласования семантики равенства; конфликтующие не должны молча зависеть от обхода файлов.
2. Подключить результат согласования источников из F130. Reference требует `EDN <: spec` и называет `TSP2791`, но текущий `env/build` сам этого не реализует. Здесь не вводится второй независимый алгоритм sidecar.
3. Отделить тип ожидаемого значения от доказанного типа содержимого мапы: факт наличия, факт проверки значения и происхождение доверия должны быть различимы. Нужны исследования совместимости с `unknown`, platform, runtime guards и операциями над открытыми мапами; механическая замена fallback на spec не sound.
4. При конфликте выдавать proposed `TSP120-01` с обеими позициями и исключать молчаливое принятие одной декларации. Конкретный recovery-тип ещё требуется согласовать; гарантировать soundness этого эскиза нельзя.

## Ограничения и открытые вопросы

- Мапа с вычисляемым или строковым ключом попадает в менее точную ветку; такой путь нельзя объявлять полностью проверенным контрактом ключей.
- Код за пределами анализируемых файлов, макросы, runtime `s/def` и внешние данные могут нарушить глобальное соглашение. Checker не устанавливает instrumentation и не вставляет `s/valid?`.
- Два `:req-un` имени с одним коротким ключом сейчас схлопываются при построении map. Нужна явная политика коллизий и диагностика; без неё нельзя утверждать однозначность связи.
- Логические группы внутри `s/keys :req` прототип ослабляет до optional-полей. Это не полная семантика `or`/`and` требований spec.
- Пользовательские предикаты, рекурсивные ссылки и циклы требуют правил F112/F295, а не обещания проверить любой spec здесь.
- Открытый вопрос: допустимо ли доверительное чтение из unknown в обычном режиме, и как отдельно показывать его в отчёте доверия? До решения отсутствие ошибок не равно доказанной типобезопасности.

## Конкретная матрица тестов

Это план точечных проверок, не утверждение о существовании всех тестов.

| Случай | Ожидаемая проверка | Состояние |
|---|---|---|
| Один `:account/id` в двух `s/keys` | Оба чтения имеют string?, нет ошибок | Current, добавить отдельную фикстуру F120 |
| Литерал `{:account/id 42}` при string? | Один TSP2322 на значении, без каскада после recovery | Current, проверить число/позицию |
| `assoc` литерального ключа: string / int | Успех / TSP2322 | Current, нужны парные проверки |
| `update` обязательного string-поля функцией, возвращающей int | TSP2322 на функции обновления | Current, нужна отдельная фикстура |
| `:req-un` string и int в разных формах | Разные локальные типы :id; вне форм нет глобального ограничения | Current, нужна пара успех/ошибка |
| `:opt-un` и отсутствующий ключ | Тип значения объединён с nil | Current, нужна проверка типа |
| Неизвестный получатель с зарегистрированным ключом | Зафиксировать platform fallback, не помечать как валидированный | Current regression; planned пересмотр доверия |
| Необъявленный ключ: известный/чужой namespace, strict on/off | Проверить точные условия TSP2304 и подсказки опечатки | Current regression |
| Два несовместимых s/def, перестановка файлов | Сейчас последнее побеждает; затем proposed TSP120-01 независимо от порядка | Planned политика конфликтов |
| Коллизия :req-un из двух namespace | Сейчас перезапись; затем явное разрешение или отказ | Planned |
| Вычисляемый ключ и непрозрачный spec | Не считать полностью проверенными; для opaque spec TSP9002 | Current ограничение |
| EDN уже/шире s/def | Принять / TSP2791 согласно reference | Planned, интеграционный тест F130 |

Уже имеющееся свидетельство: `test/features/src/f/core.clj`, функция `m4`, проверяет неверное значение в литерале внутри `merge`; `test/features/expected.txt` содержит соответствующий `TSP2322` для `:u/age`. `m2` проверяет потерю обязательного поля. Это полезные регрессии, но не полное покрытие F120. Запуск общего suite и обновление snapshots для изменения документа не требуются.
