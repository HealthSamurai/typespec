# F130 · Файлы типов рядом с исходником

## Зачем это нужно Clojure

Приложение должно получать проверяемые типы без переписывания всех `defn`, регистрации дополнительных runtime-spec или форка зависимости. **Отдельные файлы аннотаций для своего кода, существующих библиотек и `clojure.core` — обязательная возможность Typespec**, а не необязательное удобство. Типы в таком файле — данные: они не вызывают функции, не меняют metadata var и не исполняют `s/def`.

F130 отвечает за type-only EDN, связь декларации с namespace/var и согласование с `s/def`, `s/fdef`, `t/sig`, hints. [F710](F710-externs-and-exports.md) отвечает за поиск наборов аннотаций, версии библиотек и Clojure, упаковку, распространение, exports, приоритеты и явные overrides. Локальный файл рядом с исходником и аннотации чужого namespace используют одну семантику записей; для чужой библиотеки не требуется файл внутри её исходного jar.

## Что есть сейчас

- `docs/reference.md`, §2.2 описывает общий `typespec/types.edn`: keyword объявляет тип данных, symbol — сигнатуру var. Это дизайн, не работающий загрузчик.
- `main/source-files` собирает только `.clj`/`.cljc`; `main/run-check` не читает sidecars. `env/build` собирает декларации из исходников. Он сравнивает `t/sig` и `s/fdef` через равенство разобранных типов и выдаёт существующий `TSP2790`; аналогичного согласования с EDN пока нет.
- `core-types/externs` уже содержит встроенную таблицу сигнатур `clojure.core` и `clojure.string`; `core-types/table` разбирает её через `types/parse-sig`. Это частичное основание формата, **не внешняя загрузка аннотаций**.
- `check/resolve-var` обращается к окружению и встроенному каталогу; `check-defn` проверяет доступные тела. Есть отдельные специальные правила вывода для core-вызовов, поэтому заменить каталог недостаточно для всей интеграции.
- В `test/typespec/demo_test.clj` есть golden-проверки исходников и карточек; F130 не является исполняемой карточкой. Ниже только обычные `clojure` fences, без заявления о пройденных тестах sidecar.

`implementation: not-implemented` сохранён: самого механизма файлов аннотаций нет.

## Контракт формата — planned

Минимальный payload — одна EDN-map: fully qualified symbol → сигнатура функции, qualified keyword → тип данных. Значения используют type language из reference; они **не quoted**, поскольку файл уже является данными. `s/` и `t/` — фиксированные префиксы грамматики, не runtime aliases. Пользовательские имена должны быть полными; `::id`, `::alias/id`, локальные aliases и неуточнённые var-ключи в первой версии запрещены. Java-классы пишутся полными именами, без зависимости от `:import` соседнего исходника.

Предлагаемое локальное расположение: `src/app/text.clj` → `src/app/text.types.edn`, владелец `app.text`. Для внешнего набора F710 передаёт в F130 payload и manifest с целевым ns, происхождением и режимом доверия. Это логическая граница, не существующий API/синтаксис manifest. Общий `typespec/types.edn` из reference содержит несколько ns; его записи группируются по полным именам и проходят тот же алгоритм. Окончательный перечень путей фиксирует F710; cwd не участвует в разрешении имён.

В namespace-файле var-ключ обязан принадлежать целевому ns. Namespace keyword — идентификатор типа, а не доказательство существования одноимённого Clojure ns; он может отличаться от владельца файла. Дубликаты и неизвестные формы должны обнаруживаться до преобразования в обычную map, иначе можно незаметно потерять декларацию.

## Примеры и ожидаемое поведение

### 1. Корректный свой код: декларация не заменяет тело

```clojure
;; PLANNED: src/app/text.types.edn, без quote
{:app.text/label string?
 app.text/decorate [:app.text/label :-> string?]}

;; src/app/text.clj — менять исходник ради аннотации не требуется
(ns app.text)
(defn decorate [label] (str "[" label "]"))
(decorate "draft")
```

Planned: `label` получает тип по ссылке `:app.text/label`, тело возвращает строку, вызов принят. Current: файл EDN игнорируется; никакой результат текущего запуска не подтверждает использование этой аннотации.

### 2. Ошибочный вызов и ошибочное тело — две разные проверки

```clojure
;; PLANNED: src/app/text.types.edn
{app.text/decorate [string? :-> string?]}

;; src/app/text.clj
(ns app.text)
(defn decorate [label] 42) ; ошибка результата тела
(decorate 42)             ; ошибка аргумента вызова
```

Planned: две диагностики с разными позициями в `.clj`, обе с указанием источника контракта в EDN. Нельзя принять тело как extern только из-за наличия sidecar. Для обычных проверок используются существующие категории `TSP2322` (результат) и `TSP2345` (аргумент); точный вывод sidecar пока не реализован. Current: эта EDN-сигнатура не участвует в проверке, поэтому обещать такие ошибки нельзя.

### 3. Пограничный случай: одинаковый контракт допустим, конфликт не скрывается

```clojure
;; src/app/labels.clj
(ns app.labels (:require [clojure.spec.alpha :as s]))
(s/def :app.labels/name string?)
(s/fdef render :args (s/cat :x string?) :ret string?)
(defn render ^String [^String x] x)

;; PLANNED: src/app/labels.types.edn
{:app.labels/name #{"draft" "ready"} ; допустимое уточнение string?
 app.labels/render [string? :-> string?]} ; совпадает с fdef

;; Альтернативная, ОШИБОЧНАЯ запись вместо сигнатуры выше:
;; app.labels/render [int? :-> string?]
```

Planned: литеральное множество для ключа допустимо, поскольку оно подтип исходного spec; сигнатура var должна совпадать с `s/fdef`/`t/sig`. Альтернативная запись конфликтует с `s/fdef` и входным `^String`; приоритет файла не должен скрыть конфликт. Hint — platform-ограничение Java, а не независимое доказательство non-nil. Отношение совместимости hints нужно применять к платформенному представлению, не сравнивать сырые формы `String` и `string?`. Current: тип ключа берётся из `s/def`, сигнатура из `s/fdef`, EDN-уточнение и его конфликт не проверяются.

### 4. Существующая внешняя библиотека без изменения её исходников

```clojure
;; PLANNED: payload набора аннотаций F710, target ns = clojure.data.json
;; Узкий контракт только одноаргументного использования; это не полное API.
{clojure.data.json/read-str [string? :-> any?]}
;; Здесь один аргумент: входная JSON-строка, без keyword options.

;; Пользовательский код
(ns app.decode (:require [clojure.data.json :as json]))
(json/read-str "{\"ok\":true}") ; принять, результат any? — явная потеря точности
(json/read-str 10)                ; ошибка аргумента по внешнему контракту
```

Planned: проверить вызовы по доверенной декларации, не загружая библиотеку ради выполнения её функций. Этот пример покрывает только одноаргументный вызов; options/другие арности не описаны, и отсутствие их в аннотации нельзя выдавать за полноту реального API. Наличие символа в доверенном наборе не доказывает корректность реализации библиотеки. Current: внешняя EDN-таблица не читается. Проверка существования var и выбранной версии зависимости — отдельный вход из F710, а не вывод из успешного разбора типа.

### 5. `clojure.core`: перенос существующего формата и будущие generics

```clojure
;; PLANNED: отдельный EDN payload для clojure.core
{clojure.core/inc ([int? :-> int?] [number? :-> number?])}

(inc 1)       ; принять
(inc "one")   ; ошибка аргумента

;; PROPOSED, отдельная будущая декларация, НЕ поддерживается parse-type:
{clojure.core/identity (t/all [a] [a :-> a])}
(identity "one") ; желаемый результат string?, а не any?
```

Current: контракт `inc` уже существует во встроенном `core-types/externs`; это не демонстрация чтения EDN. `t/all` есть в языке дизайна, но ветки разбора/универсальной инстанциации в текущем `parse-type` нет. Planned: обеспечить внешний формат также для core; поддержка generic `identity` требует отдельного механизма generics, не одного загрузчика. Макросы и специальные правила core нельзя описать произвольной сигнатурой и объявить проверенными.

## Алгоритм согласования источников — planned

Это алгоритм сборки контрактов, а не новая система вывода типов или доказательство soundness.

1. **Вход.** Разобранные исходники с ns/aliases/позициями; список выбранных F710 payload с целевыми ns, origin, режимом `local`/`extern` и результатом проверки доступности библиотеки; встроенный core-каталог. F710 уже разрешил конфликты наборов/версий и явные overrides. Наличие собственного проверяемого исходника нельзя скрыть режимом extern.
2. **Безопасное чтение.** Читать EDN как данные с позициями каждого ключа и значения; отвергать reader-eval, tagged readers, несколько корневых форм, дубликаты ключей, недопустимый тип ключа и неявные aliases. Не использовать `load-file`/`eval`/`require` для чтения аннотации. Сначала проверять структуру записи, затем type language; неизвестная форма — ошибка декларации, не успешная замена на `any?`.
3. **Имена и факты.** Получить канонический fully qualified var symbol или keyword. Проверить соответствие var целевому ns. Хранить список кандидатов `{type, origin, file, range, role}` для каждого имени, не сразу `assoc` последнего. Отдельные факты: существует ли определение, есть ли тело в проверяемом наборе, полный ли список var данного ns, доверенный ли внешний контракт. Отсутствие тела и доказанное отсутствие var — разные факты.
4. **Типы.** В два прохода зарегистрировать имена типов, затем разобрать значения в существующее представление `{:t :fn :arities [...]}`, `{:t :ref ...}`, map/union/class и др. Var-значения — через `parse-sig` для поддержанной грамматики, keyword-значения — через `parse-type`. Проверить ссылки после регистрации всего набора. Циклы, generics и другие ещё неподдержанные конструкции нельзя молча принять как `unknown`: для первого этапа явно отклонять неподдержанную декларацию; полноценные рекурсивные типы требуют отдельного исследования.
5. **Согласование.** Для var сравнить EDN с `t/sig`/`s/fdef` после разбора и нормализации; первый этап может консервативно требовать равенства представлений, как нынешний `env/build`, но не обещать семантическую эквивалентность всех типов. Для keyword проверить `EDN <: spec`, как требует reference §2.2. Это правило отличается от равенства сигнатур! Неподдержанный spec или `unknown` не является доказательством уточнения. Hints проверить как платформенные ограничения параметров/результата в пределах поддержанного отношения совместимости; его точное правило для nil, Java-классов и перегрузок ещё должно быть специфицировано и протестировано. Не выдавать простой эскиз с `sub?` за доказательство общей совместимости.
6. **Связь с реализацией.** Для локального полного ns неизвестный var — устаревшая/ошибочная запись. Для намеренного extern без доступного тела — доверенный контракт, а не ошибка только из-за отсутствия исходника. При неполном индексе или неизвестной версии сообщить, что существование var не подтверждено; не превращать удалённый свой var в extern автоматически. Сопоставить арности декларации и реализации, затем передать контракт в проверку тела; сам факт совпадения арностей не доказывает тип тела.
7. **Интеграция.** Между сборкой деклараций и выводом тел в `check/check-files` сформировать объединённые `:specs`/`:vars` с provenance. Нынешний `env/build` потребуется разделить на сборку и согласование либо расширить явным входом аннотаций. Не удалять `:parts`/`:pfile` собственного определения. `check-defn` должен продолжить проверять тело и возвращаемый тип, `call-fn` — вызовы. Изменить обе ветки `resolve-var`: сейчас неуточнённый core-symbol обращается прямо к `core/table`. Отдельно согласовать special rules с выбранными core-контрактами; не обещать, что произвольный override автоматически меняет такие правила.
8. **Результат.** Окружение согласованных контрактов, диагностики и сведения о доверии для extern. При конфликте нет «успешного победителя»: пометить запись конфликтной; при продолжении анализа не использовать её как доказанный тип. Для `sig` потребуется отображение источника sidecar; сейчас `main/sig-lines` знает только `t/sig`, `s/fdef` и hints. CLI/JSON должны ссылаться на одно событие и диапазоны EDN и исходника; текущий JSON не имеет related locations, их добавление — отдельная работа.

### Диагностики

Новые обозначения ниже — только **proposed**, не уже доступные коды:

- **proposed TSP130-01** — неверная структура EDN/ключ, duplicate, неподдержанная форма типа; диапазон проблемной записи.
- **proposed TSP130-02** — var не принадлежит target ns либо отсутствует в подтверждённо полном локальном ns; показать ожидаемое имя/владельца.
- **proposed TSP130-03** — конфликт источников сигнатуры, недопустимое уточнение ключа или несовместимый hint; показать обе формы и оба места. Reference называет `TSP2790`/`TSP2791`, но sidecar-веток для них сейчас нет; окончательное переиспользование кодов нужно согласовать.
- **proposed TSP130-04** — не удалось подтвердить ссылку/совместимость/существование внешнего var; не маскировать неопределённость сообщением «контракт проверен».

Ошибка вызова или результата тела после успешного согласования остаётся обычной диагностикой checker, не ошибкой чтения EDN.

## Ограничения и открытые вопросы

- Без доказательства полноты ns нельзя одновременно гарантировать обнаружение устаревших записей и разрешать все extern. Нужен явный режим и достоверный inventory, а не эвристика «тела нет — значит extern».
- Общая семантическая эквивалентность сигнатур, рекурсивные типы, variance/generics, полное взаимодействие Java hints и nil не решаются загрузкой файлов. Консервативное отклонение допустимого контракта предпочтительнее ложного доказательства; границы поддержки должны быть видны.
- Текущий parser некоторых сложных форм теряет точность (например, `s/tuple` превращает элементы в union). Нельзя принимать результат такого разбора за точное доказательство эквивалентности исходных форм. Нужен поддерживаемый поднабор/метка точности декларации.
- Файл аннотаций обычных функций не описывает macro expansion, `defmulti`/`defmethod`, динамический `intern` или произвольную смену root var. Первая версия должна объявить их неподдержанными там, где нельзя проверить соответствие.
- Поведение `.cljc`/reader conditionals, правила безопасных уточнений встроенных special rules и формат связанных позиций пока не зафиксированы. Поставка jar, версии и override-политика остаются в F710, не дублируются здесь.
- Внешний контракт — доверенная предпосылка. Проверка вызовов по нему не доказывает ни соответствие библиотеки контракту, ни общую soundness текущего прототипа.
