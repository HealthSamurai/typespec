# F150 · Генераторы типов из схем

## Зачем

Clojure-программа часто работает с данными, контракт которых уже описан вне кода: OpenAPI, JSON Schema, каталог таблиц БД. Ручное повторение полей и обязательности в `s/def` расходится с оригиналом. Провайдер должен переводить **закреплённый снимок** такого контракта в декларации Typespec и сохранять происхождение каждого поля.

Это опциональный источник типов, не новый валидатор и не доказательство состояния внешнего сервиса. Генерация не подтверждает, что HTTP-ответ соответствует схеме или что миграция БД применена. Карточка задаёт общий протокол согласования источников; правила проверки maps, функций и границ доверия остаются в checker.

## Current: что действительно есть

- `main/source-files` и `main/run-check` читают `.clj`/`.cljc` из выбранных путей. Команды провайдера, импорта OpenAPI, introspection БД и проверки manifest отсутствуют.
- `env/collect-file` собирает `s/def`, `s/fdef` и `:t/sig` из текста, не загружая namespace. `env/build` строит окружение `:specs`/`:vars`; несовпадение `:t/sig` и `s/fdef` даёт `TSP2790`.
- `types/parse-type` представляет ссылки как `{:t :ref :name k}`, maps как `{:t :map :req … :opt …}`, допускает объединения и nilable. Эти структуры можно переиспользовать, но они не несут доказательства корректности преобразования внешней схемы.
- Повторный `s/def` сейчас записывается через `assoc-in`: более поздняя декларация заменяет предыдущую. Это **не** алгоритм согласования провайдеров.
- Sidecar `typespec/types.edn`, externs и правило `TSP2791` описаны в reference как дизайн. В текущем пути `main/run-check` нет загрузчика этих файлов. Нельзя считать их готовым backend генерации.

Таким образом, `implementation: not-implemented` сохранён. Вручную подготовленный `.clj` с обычными spec-декларациями checker уже может прочитать; автоматическое получение, контроль версии и слияние источников ещё planned.

## Примеры

Все блоки иллюстративные, не golden-тесты. Обозначения manifest и источников ниже — предлагаемые данные, не существующий API. Каждый пример независим.

### 1. Корректный локальный результат генерации

Предположим, схема объекта требует integer `id` и разрешает необязательный string `name`. Профиль преобразования явно выбирает **keywordized map с ключами без namespace**, а диапазон integer ограничен представлением, совместимым с `int?`.

```clojure
(ns generated.account
  (:require [clojure.spec.alpha :as s]))

;; PLANNED: провайдер выдаёт эти декларации из локальной схемы.
;; CURRENT: checker умеет читать такие декларации из .clj.
(s/def :account/id int?)
(s/def :account/name string?)
(s/def :account/record
  (s/keys :req-un [:account/id] :opt-un [:account/name]))

(defn account-id
  {:t/sig '[:account/record :-> int?]}
  [account]
  (:id account))

(defn correct-calls []
  (account-id {:id 42 :name "Ada"}) ; совместимый аргумент
  (account-id {:id 42}))            ; name может отсутствовать
```

Здесь `:account/id` — имя декларации, а `:id` — ключ значения. Сырая JSON-map с ключом `"id"` не получает этот тип автоматически. Генератор не должен незаметно смешивать wire-представление и результат декодирования.

### 2. Ошибка в потребителе сгенерированного контракта

```clojure
(ns generated.bad-account
  (:require [clojure.spec.alpha :as s]))
(s/def :account/id int?)
(s/def :account/record (s/keys :req-un [:account/id]))
(defn account-id
  {:t/sig '[:account/record :-> int?]}
  [account]
  (:id account))

(defn wrong-calls []
  (account-id {:id "42"}) ; CURRENT: несовместимый тип значения id
  (account-id {}))        ; CURRENT: отсутствует обязательный id
```

Ожидаются обычные диагностики checker на аргументах, а не новый код ошибки провайдера. Точные тексты/количество сообщений здесь не закреплены golden-тестом. PLANNED: диагностика дополнительно связывает ожидаемый тип с файлом схемы и путём свойства, но не заменяет позицию ошибочного Clojure-выражения.

### 3. Пограничный случай: отсутствие поля не равно null

```clojure
(ns generated.optional
  (:require [clojure.spec.alpha :as s]))
(s/def :account/name (s/nilable string?))
(s/def :account/record (s/keys :opt-un [:account/name]))
(defn echo
  {:t/sig '[:account/record :-> :account/record]}
  [account]
  account)

(defn boundary-calls []
  (echo {})              ; допустимо: поле отсутствует
  (echo {:name nil})     ; допустимо: поле присутствует и nullable
  (echo {:name "Ada"})   ; допустимо
  (echo {:name 17}))     ; ошибка: ни string, ни nil
```

CURRENT: формы типов поддержаны. PLANNED: провайдер обязан независимо вычислять обязательность поля и допустимость nil. Если сделать поле обязательным, `{}` станет ошибкой, хотя `{:name nil}` останется допустимым. `default` во внешней схеме сам по себе не означает, что декодер вставляет значение, и не превращает optional в required.

### 4. Конфликт источников: не «последний победил»

```clojure
;; PLANNED: записи входа согласователя, не конфигурация текущего CLI.
[{:source :generated :key :account/id :type 'int?
  :origin {:file "schemas/accounts.json" :pointer "/properties/id"}}
 {:source :manual :key :account/id :type 'string?
  :origin {:file "src/account/specs.clj" :line 8}}]

;; Ожидается: конфликт, публикация нового артефакта запрещена.
;; proposed TSP150-03: несовместимые декларации :account/id;
;; показать оба типа и обе позиции, не выбирать источник по порядку файлов.
```

CURRENT: такой согласователь отсутствует; две формы `s/def` не дают обещанного обнаружения конфликта. Для начальной версии proposed правило консервативно: совпадающие нормализованные типы объединяют provenance, любые различающиеся типы требуют явного разрешения. Автоматическое пересечение или выбор «более узкого» типа не обещаются.

### 5. Неподдержанная точность и воспроизводимость

```clojure
;; PLANNED: фрагмент manifest, имена полей предварительные.
{:source {:file "schemas/accounts.json" :dialect "json-schema-2020-12"
          :sha256 "<digest исходных байтов>"}
 :provider {:id :json-schema :version "<закреплённая версия>"}
 :representation :keywordized
 :unsupported :error
 :dependencies []}

;; Схема string + pattern не сводится без потери смысла к string?.
;; В строгом режиме: proposed TSP150-02, генерация не публикуется.
;; При отдельно разрешённом ослаблении: string? + запись loss(pattern),
;; но не заявление, что checker доказал соответствие pattern.
;; Изменились байты схемы без обновления manifest:
;; proposed TSP150-01, обычная проверка не скачивает свежую схему.
```

Проверка базового типа может сохраниться при разрешённом ослаблении, но проверка regex/диапазона остаётся непроведённой. Это не повод заменять всё на `any?` и выдавать полностью проверенный контракт.

## Planned: алгоритм генерации и согласования

Это проект интерфейса и консервативный порядок проверок, **не готовый sound перевод произвольных схем**. Каждый адаптер должен отдельно обосновать семантику поддержанного подмножества.

1. **Вход.** Получить локальный снимок схемы, все зависимости, dialect/version, версии провайдера и целевого формата, настройки представления данных, политику потерь и manifest. HTTP/БД доступны только отдельной явной операции обновления снимка, не обычному `check`.
2. **Целостность.** Проверить digest каждого файла, наличие ссылочных зависимостей, допустимость dialect и версии. Неразрешённая внешняя ссылка не запускает сетевой запрос. Несовпадение или отсутствие входа завершает генерацию с proposed `TSP150-01`; старый артефакт не выдается за свежий.
3. **Нормализация схемы.** Адаптер строит граф сущностей со стабильными идентификаторами и origin: файл плюс JSON pointer либо имя таблицы/колонки. Факты обязательности, nullability, ограничений значений, открытости объекта и преобразований декодера хранятся раздельно. Detect cycles до разворачивания; рекурсивные компоненты в начальной версии отклонять явно, а не обрывать ссылку на произвольной глубине.
4. **Перевод подмножества.** Для каждого узла выбрать поддержанный тип и зарегистрировать ограничения, не выразимые в Typespec. Например, optional становится `:opt`, null входит в union отдельно. Не считать JSON integer автоматически `int?`, SQL timestamp автоматически `inst?`, а строковый `format` — Java-классом: нужны ограничения диапазона и договор с декодером/драйвером. Неизвестная конструкция: proposed `TSP150-02`, либо явная запись потери при разрешённом ослаблении.
5. **Промежуточные декларации.** Выдать записи `symbol/keyword → type + origin + losses + artifact identity`. Целевые type-формы разбирать тем же `types/parse-type`; проверять все ссылки, уникальность имён и полноту зависимостей. Коллизия имён между схемами не исправляется молчаливым переименованием. Provenance хранить рядом с типом, не менять ради него смысл `:t`.
6. **Согласование.** До построения обычного окружения собрать все определения одного имени: generated, ручные spec и, когда появится загрузчик, sidecar. Начальное правило — одинаковые нормализованные типы допустимы, различающиеся блокируют публикацию с proposed `TSP150-03`. Сравнение порядка обязательных ключей не должно давать ложный конфликт. Для spec/sidecar reference задаёт отдельное правило подтипизации; его будущая реализация не должна незаметно ослабить правило generated/manual. Совместимость функций и `s/fdef` остаётся ответственностью общего согласователя источников.
7. **Выход.** Стабильно отсортированные декларации, manifest и таблица происхождения/потерь. Одинаковые байты входов и настройки должны давать одинаковые байты результата, без timestamp и зависимости от порядка обхода файлов. Публиковать набор атомарно только после успешной проверки; при ошибке не оставлять частично обновлённые файлы. Перед использованием сверять digest артефакта с manifest.
8. **Проверка кода.** Подать согласованные декларации в окружение, затем использовать существующие операции checker для выражений, вызовов и присваиваний. Сообщения генерации показывают origin схемы; сообщения использования показывают Clojure-позицию плюс связанный origin. Отдельный отчёт перечисляет потери и непроверенные свойства: отсутствие ошибок не означает доказанную runtime-валидацию.

Для свойства «принимаемое схемой значение не отвергается типом» нужно доказать включение множества значений схемы в целевой тип с учётом декодера. Обратное включение нужно, если типом хотят заменить валидатор. Ослабление `pattern` до `string?` в лучшем случае помогает первому, но не второму. Ни один общий результат soundness здесь не заявляется.

## Интеграция с текущим checker

Временный путь эксперимента — явно включить сгенерированный `.clj` в проверяемые paths: `main/run-check → parse/parse-file → check/check-files → env/build`. Не нужно `require` или выполнение генератора при анализе. Но это ещё не интеграция F150: отсутствуют provenance, manifest и предварительное разрешение дубликатов.

Полноценный путь потребует отдельного загрузчика/нормализатора деклараций перед `env/build`, согласования до `assoc-in` и передачи origins в диагностики. Парсер типов и правила `types/sub?` можно переиспользовать для поддержанного нерекурсивного подмножества. Нельзя обходить checker прямым доверием к выводу провайдера или считать его текущий permissive `unknown` доказательством совместимости. Генерация настоящих runtime `s/def` также меняет реестр spec, поэтому предпочтение type-only артефакту требует отдельного решения и загрузчика, а не просто нового расширения файла.

## Ограничения и открытые вопросы

- Поддержанные версии OpenAPI/JSON Schema и профили SQL-драйверов ещё не выбраны. Различия request/response (`readOnly`, `writeOnly`) требуют разных контрактов, не одного общего типа.
- `$ref` с циклами, `oneOf` с исключающей семантикой, `allOf`, условные схемы, `additionalProperties`, зависимости полей и неограниченные числа требуют исследований. Простая union не выражает эксклюзивность `oneOf`; произвольное слияние maps не является корректной реализацией `allOf`.
- Тип строки таблицы не равен типу результата запроса: outer join добавляет null, алиасы меняют ключи, выражения меняют значения. Провайдер каталога не доказывает тип любого SQL-запроса.
- Нет автоматического доказательства соответствия реального payload снимку; отдельно нужны runtime validation либо явно доверенная граница.
- Хранить результат в Git или в версионированном кэше — открытый вопрос. В обоих случаях необходимы offline-воспроизводимость, контроль устаревания и аудит изменений.
- Правила override/уточнения, нормализация эквивалентных форм и доверие к стороннему генератору пока не решены. Начальный запрет спорных конфликтов намеренно строже возможного будущего дизайна.

## Конкретная матрица тестов

Все provider-тесты ниже **planned**, не описание существующего покрытия. Обычные примеры текущих типов нужно проверять отдельно от генератора.

| Случай | Вход / изменение | Проверяемый результат |
|---|---|---|
| Базовый объект | required integer id, optional string name | Стабильные декларации; корректные вызовы примера 1 проходят |
| Неверный consumer | строка вместо id; отсутствие id | Диагностика checker на каждом неверном аргументе |
| Optional × nullable | четыре комбинации признаков, `{}`, nil, string | Независимые решения для наличия и значения |
| Представление ключей | string-key payload против keywordized profile | Нет неявного признания одной map другой |
| Повторяемость | два запуска, перестановка входных файлов | Побайтово равные output/manifest |
| Offline | запрещённая сеть, все snapshots локальны | Успех без запросов; внешняя отсутствующая ссылка — proposed TSP150-01 |
| Устаревание | изменён digest входа или артефакта | proposed TSP150-01; нет молчаливой регенерации |
| Дубликат | одинаковое имя и одинаковый нормализованный тип | Один тип, сохранены оба origins |
| Конфликт | одинаковое имя, int? против string? | proposed TSP150-03; нет зависимости от порядка файлов |
| Неизвестная конструкция | pattern/условие вне поддержанного подмножества | Строгий отказ proposed TSP150-02; при opt-in ослаблении — loss в отчёте |
| Рекурсия | self-reference и цикл из двух сущностей | Начальная версия даёт явный отказ, не зависает |
| Диапазон/декодер | integer вне int?, timestamp без профиля драйвера | Нет необоснованного int?/inst?; отказ или явная потеря |
| Частичный сбой | второй вход повреждён после успешного первого | Старый набор не перезаписан наполовину; запуск неуспешен |
| Происхождение | неверное использование поля из схемы | Clojure-позиция плюс origin ожидаемого типа |
| Runtime-граница | внешний ответ нарушает snapshot | Не обещать статическое обнаружение без валидатора |

Критерий готовности: адаптер с документированным подмножеством, тесты каждого правила и диагностик, воспроизводимый offline artifact, явный учёт потерь и отсутствие молчаливого разрешения конфликтов. До этого статус реализации не меняется.
