# F210 · Unknown, any и never

## Обновление реализации — топ-10

sub? больше не считает unknown подтипом конкретного типа. sub-result возвращает proved/mismatch/inconclusive и reasons. На основных границах вызова/возврата неполная проверка даёт TSP210-01 warning, в strict — error; JSON сохраняет reasons. Это не полный аудит всех путей checker.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Зачем это нужно в Clojure

На границах программы — чтение EDN, сторонняя библиотека, неподдержанная макроформа — checker часто не знает тип значения. Это не означает, что значение подходит для любой операции. Без различения «ещё не знаем», «сознательно не проверяем» и «значение не возвращается» ошибки проходят через обычные сигнатуры, а отсутствие диагностик ошибочно воспринимается как доказательство безопасности.

Целевые роли:

- **`t/unknown`** — безопасный верхний тип: можно сохранить, передать потребителю произвольных значений, проверить предикатом; нельзя без доказательства использовать как `string?`, число, функцию или карту.
- **`any?`** — явное отключение проверки совместимости. Это доверие программисту, не гарантия успешного выполнения и не обычный математический подтип всех типов.
- **`t/never`** — нижний тип: выражение не возвращает нормального значения или путь доказан невозможным. Это не `nil`, не ошибка checker и не неизвестный результат.
- **Неподдержанная проверка** — отдельный статус анализа с причиной. Нельзя превращать его в доказанный успех или в `never`; полезный консервативный тип результата — `unknown`, но причина должна сохраняться отдельно.

## Что действительно реализовано

В `types.clj` существуют `{:t :unknown}`, `{:t :any}`, `{:t :never}`, чтение и печать соответствующих форм. `union` удаляет `never`, возвращает `never` для пустого объединения, поглощает остальные члены сначала через `any`, затем через `unknown`.

**Главный разрыв с дизайном:** `sub1?` разрешает `unknown` с обеих сторон, а `sub?` использует это правило для совместимости. Поэтому `unknown` сейчас проходит как строка и даже как `never`; `any` тоже проходит как `never`. Это не реализация обещания «narrow first» из reference. Имя функции — `sub?`, не `subtype?`.

В `check.clj` уже есть:

- положительное уточнение локальной переменной через `string?`, `number?` и несколько других предикатов; отрицательная ветка таких проверок остаётся без уточнения;
- результат `never` для `throw` и `recur`, объединение результатов веток `if`;
- `t/unknown` как результат ряда неподдержанных/неизвестных операций;
- директива `#_(t/any)` с увеличением счётчика `:trust :any`;
- отдельные обходы проверок для `unknown`/`any` в Java-вызовах, hints и выборе сигнатур. Исправить только `sub1?` недостаточно.

Чтение ключа из `unknown` сейчас не гарантирует ошибку «сначала уточни»: `key-info`/`read-key` допускают loose lookup; для qualified-key может отдельно возникнуть `TSP2304` в strict-режиме. Java-вызов на неизвестном receiver может давать warning `TSP7020`, а не запрет операции. `sub?` при глубине больше 12 возвращает `true`: это ещё один источник недоказанного успеха, независимый от верхнего типа.

`implementation: partial` сохранён: представление типов, часть нормализации и отдельные правила существуют, но безопасная семантика ещё не реализована полностью.

## Примеры и ожидаемое поведение

Это обычные примеры для спецификации, **не исполняемые golden-блоки**. Current ниже установлен чтением исходников, не запуском этих примеров. Каждый блок можно рассматривать отдельно; `t/` в quoted metadata — язык данных Typespec, не вызов runtime-функции.

### 1. Корректно: доказать строку до операции

```clojure
(ns sample.safe
  (:require [clojure.string :as str]))

(defn label
  {:t/sig '[t/unknown :-> string?]}
  [value]
  (if (string? value)
    (str/upper-case value)
    "<not a string>"))
```

**Current:** положительная ветка получает `string?`; `upper-case` имеет строковую сигнатуру, обе ветки возвращают строку. **Planned:** тот же результат, без escape hatch. Отрицательная ветка не обязана получать точный тип «всё, кроме строк», пока такой тип не представлен; достаточно оставить `unknown`. На `nil`, числе или карте выполнение возвращает запасную строку.

### 2. Ошибка: неизвестное значение передано строковой функции

```clojure
(ns sample.unsafe
  (:require [clojure.string :as str]))

(defn label
  {:t/sig '[t/unknown :-> string?]}
  [value]
  (str/upper-case value))
```

**Current:** проверка совместимости допускает `unknown` как `string?`; отсутствие ошибки здесь не доказывает безопасность. **Planned:** ошибка на аргументе `value`: фактический тип `t/unknown`, ожидается `string?`, нужно уточнение или явное принятие риска. Для несовместимого аргумента уже существует `TSP2345`; отдельный новый код не требуется. `label` с числом может упасть при выполнении — checker не должен скрывать это неопределённостью типа.

### 3. Явный `any`: разрешение с риском, а не доказательство

```clojure
(ns sample.escape
  (:require [clojure.string :as str]))

(defn unchecked-label
  {:t/sig '[t/unknown :-> string?]}
  [value]
  (str/upper-case #_(t/any) value))
```

**Current:** reader сохраняет директиву, `infer` заменяет тип выражения на `any` и увеличивает `:trust :any`. Проверка аргумента пропускается; заявленный результат `upper-case` остаётся строковым. **Planned:** сохранить явное разрешение и след происхождения доверия. Вызов всё ещё может упасть. Само присутствие `any?` в сигнатуре сейчас не означает, что этот же счётчик учитывает каждое такое место: полный trust budget — отдельная задача, а не выполненное обещание F210.

### 4. `never` полезен при объединении веток

```clojure
(ns sample.bottom)

(defn require-text
  {:t/sig '[t/unknown :-> string?]}
  [value]
  (if (string? value)
    value
    (throw (ex-info "Expected text" {}))))
```

**Current:** первая ветка уточняется до строки, `throw` получает `never`, `union(string?, never)` даёт строку. **Planned:** такое же нормальное возвращаемое значение. Это не утверждение, что функция всегда завершается успешно: исключение остаётся возможным. `never` описывает отсутствие нормального возврата, не отсутствие эффектов.

### 5. Пограничный случай: неизвестность не доказывает невозможность

```clojure
(ns sample.false-bottom)

(defn pretend-impossible
  {:t/sig '[t/unknown :-> t/never]}
  [value]
  value)

(defn nil-is-not-bottom
  {:t/sig '[:-> t/never]}
  []
  nil)
```

**Current:** первый возврат проходит через правило `unknown <: everything`; второй несовместим с `never` и попадает в проверку возврата (`TSP2322`). **Planned:** оба возврата ошибочны. Проверенный normal-return `never` допустим лишь при доказанном отсутствии нормального значения. Если в этом месте используется `any`, совместимость по доверию не должна становиться доказательством недостижимости последующих веток.

## Уточнение дизайна: семантика отдельно от причины неизвестности

`unknown` остаётся безопасным top, **не Pyright Unknown** (у Pyright это разновидность Any). К сведениям шага 2 ниже добавить причину и путь неизвестного листа: `missing-extern`, `unsupported-macro`, `unresolved-java`, `inference-limit`, `explicit-any`, `inherited-any`. Например, неизвестный элемент вектора не делает неизвестным сам факт «это vector»; после объединения веток и кеширования причина должна оставаться доступной. Отсутствующий контракт core или библиотеки — `missing-extern`, не разрешение операции: внешние декларации обязательны для проверяемой границы (F711).

Не заменять строгую совместимость правилом Elixir dynamic «достаточно непустого пересечения»: `(inc (if flag 1 "bad"))` должен быть отвергнут, хотя числовая ветка допустима. Для конечных unions можно отдельно проверять пустоту пересечения/вычитать доказанно покрытые варианты; неизвестный результат этой операции не равен `never`. Бюджет и `inconclusive(reason)` согласовать с [F295](F295-recursive-types.md); незавершённость нельзя кешировать как proved (F720).

**Дополнительные planned-тесты:** перенос `missing-extern` через `let`, union и элемент коллекции; различение явного и унаследованного any; числовая/строковая ветки выше; лимит пересечения не делает ветку недостижимой. Тесты здесь не запускались.

**Основание:** [отчёт Python, §2](../docs/research-python.md) и [отчёт Elixir, §2.2/2.4](../docs/research-elixir.md). Первоисточники: [Pyright: inference/Unknown](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md), [Elixir 1.20.5: gradual types](https://hexdocs.pm/elixir/1.20.5/gradual-set-theoretic-types.html), [Descr](https://github.com/elixir-lang/elixir/blob/v1.20.5/lib/elixir/lib/module/types/descr.ex). При переносе прочитаны отчёты; документация и выборочные участки Descr изучены авторами отчётов, не повторно здесь. Это не аудит solver и не перенос BDD.

## Алгоритм проверки: целевой контракт и места интеграции

Это план изменения checker, **не доказанный sound алгоритм для всего Clojure**. Ниже определён ограниченный порядок действий для верхнего/нижнего типов; точные пересечения, рекурсия, effects и исчерпывающий flow-анализ требуют отдельной работы.

1. **Вход.** Получить AST с позициями и директивами из `parse.clj`, окружение деклараций из `env.clj`, типы locals и ожидаемый тип выражения/параметра/возврата. Различать явную аннотацию `unknown` и неизвестность из отсутствующего контракта или неподдержанной формы.
2. **Представление.** Сохранить имеющиеся теги типов. В результате анализа дополнительно хранить происхождение, статус проверки (`checked`, `trusted`, `unsupported` — предлагаемые состояния, ещё не API) и факт нормальной достижимости. `any` помечать как доверенный; внутренний recovery-результат ошибки не смешивать с пользовательским `unknown`. Эти сведения не должны пропадать при `union` и сохранении локальной переменной.
3. **Нормализация.** Для обычных типов использовать `T | never = T`, пустой union = `never`, `T | unknown = unknown`. `any` может поглощать тип объединения как сейчас, но не должен поглощать информацию о доверии/непроверенных ветках. Отдельно хранить, был ли `never` доказан, а не получен из принятой на доверие сигнатуры.
4. **Разделить отношения.** Семантическое включение типов и разрешение присваивания с `any` — не одно отношение. В проверенном фрагменте: `never <: T`; `T <: unknown`; `unknown` не подтип конкретного `T`; `unknown <: unknown`. Для `any` возвращать «разрешено по доверию», а не математическое доказательство. В частности, разрешённое через `any` присваивание в `never` не должно делать путь недостижимым. Политику полного запрета такого присваивания ещё следует выбрать.
5. **Уточнение.** Для поддержанного тотального предиката, например `string?` над локальным `unknown`, в истинной ветке записать строковый тип. В ложной оставить `unknown`, если отрицательные типы не поддержаны. Для уже конкретного типа требуется корректное пересечение, а не безусловная подмена его строкой. Не выводить невозможность по провалу эвристического `sub?`. Операции чтения ключей, вызова и Java receiver проверять после уточнения, а не автоматически разрешать для top.
6. **Проверка использования.** В аргументах (`call-fn`/проверка assignability), возвратах (`check-return!`), полях карт и Java-операциях применять единый результат совместимости. `unknown` в конкретной позиции — ошибка с actual/expected и источником неизвестности; `any` — принятие риска; неподдержанный анализ — непроверенный результат с причиной, не зелёная проверка. Пересмотреть особые ветки `vague?`, hints и loose lookup, иначе они обойдут новый контракт.
7. **Поток управления.** `throw` не имеет нормального результата; `recur` не возвращает в текущую точку, но требует отдельной проверки целевого loop/арности. При объединении `if` исключать только доказанно не возвращающие ветки. `infer-body` должен учитывать достижимость последовательности, а не просто тип последнего выражения. Нельзя объявить полноценную поддержку bottom на основании одного обработчика `throw`.
8. **Результат и диагностики.** Вернуть тип плюс статус/основания и diagnostics с позициями. Существующие `TSP2345` (аргумент) и `TSP2322` (возврат) подходят для ошибок совместимости; текст должен объяснять необходимость уточнения. Сохранять исходные сообщения о неподдержанной форме и не плодить каскад одинаковых ошибок на её recovery-значении. Способ группировки причин ещё нужно определить. Никаких новых зарегистрированных TSP-кодов карточка не объявляет.

## Ограничения и открытые решения

- Встроенные сигнатуры используют `any?` и для действительно тотальных функций (`str`, предикаты), и как грубый контракт (`count`). Для безопасного top нужна ревизия контрактов: не запрещать полезные проверки, но и не выдавать слишком широкий extern за доказанную безопасность. Не все `any?` следует механически заменить на `unknown`.
- Полное доказательство bottom требует контроля normal flow и контрактов вызываемых функций. Аннотированная `[:-> t/never]` из extern — доверие, не доказательство поведения библиотеки.
- Пересечения и отрицательные факты, исчерпываемость `case`, хвостовые переходы, `try/finally`, рекурсивные типы и инвариантные контейнеры нельзя решить одним условием в `sub1?`. Глубинный cutoff `true` нужно заменить результатом «не доказано», отдельно исследовав завершение и совместимость с текущими ссылочными типами.
- Сигнатура результата как единственный carrier информации теряет происхождение `any` и unsupported. Нужны решение о переносе фактов через API checker и тесты на отсутствие их потери.
- Это изменение совместимости: прежние чистые отчёты могут получить новые ошибки. Режим миграции и политика strict/non-strict пока не определены; нельзя сохранять старое поведение под названием «безопасный unknown».
- Эта карточка определяет роли трёх типов и точки их применения. Полные алгоритмы narrowing, trust budget и coverage принадлежат соответствующим фичам; здесь они не объявляются реализованными.

## Конкретная матрица тестов

Матрица — требования к будущим unit/integration-тестам, не утверждение о нынешнем покрытии. Проверять не только diagnostics, но и выведенный тип, статус доверия и факт достижимости.

| Слой / вход | Current по коду | Требуемый результат |
|---|---|---|
| Чтение/печать `t/unknown`, `any?`, `t/never` | Теги и печать есть | Round-trip каждого тега |
| `string? <: unknown` | Разрешено | Разрешено, checked |
| `unknown <: string?`, `unknown <: never` | Разрешено | Отказ, без доказательства bottom |
| `never <: string?`, `never <: nil?` | Разрешено | Разрешено; `nil? <: never` — отказ |
| `union(never, string?)`, пустой union | Строка / never | Те же типы |
| `union(unknown, string?)`, `union(any, unknown)` | unknown / any | Те же типы плюс сохранённое происхождение |
| Пример 1: guard и fallback | Положительное уточнение есть | Нет ошибок; результат string, checked |
| Пример 2: прямой вызов | unknown пропускается | `TSP2345` на аргументе, actual/expected |
| Пример 3: `#_(t/any)` | trust counter +1 | Разрешение trusted; не стирать причину |
| Пример 4: строка или throw | union исключает never | string на нормальном выходе |
| Пример 5: unknown/nil → never | Первый принят, второй отвергнут | Оба `TSP2322`; не помечать функцию доказанно не возвращающей |
| Чтение `(:k x)` при `x : unknown` | Loose lookup | Требовать уточнение; отдельная проверка strict qualified-key |
| Вызов локального `x : unknown` как функции | Возврат unknown | Ошибка использования неизвестного callee |
| Java-вызов на unknown receiver | Возможен `TSP7020` warning | Не считать типобезопасным; сохранить reflection-диагностику |
| Неподдержанная форма внутри аргумента | Обычно unknown | Причина unsupported + отсутствие ложного успеха; без каскада |
| Противоречивый предикат над конкретным типом | Возможна подмена типом предиката | Пересечение либо консервативный факт, не выдуманный тип |
| Сложный тип глубже cutoff | `sub?` возвращает true | Не доказано, а не checked |
| `any` используется как never | Совместимость разрешена | Не использовать для exhaustiveness/reachability |

В `test/typespec/demo_test.clj` есть общие snapshot/marker-проверки и проверка trust counters. В `test/features/src/f/core.clj` встречается `any?` в `s/fdef`, но это не заменяет отдельную матрицу для безопасного unknown. Обычные fences этой карточки не подхватываются golden-runner, который ищет только `clojure example` + `text output`.
