# F220 · Локальный и контекстный вывод типов

## Зачем это нужно в Clojure

Обычный код Clojure соединяет `let`, деструктуризацию и функции над коллекциями. Требовать отдельную сигнатуру для каждого промежуточного значения и каждого `fn` неудобно: тип элемента уже известен из коллекции, а тип результата часто виден из тела. Локальный вывод должен сохранять эту информацию и находить ошибку там, где она возникла, а не требовать аннотаций на каждом шаге.

Граница обещания: сигнатуры на границах программы остаются источником требований; локальный вывод не заменяет их глобальным Hindley–Milner-выводом. Вывод снизу вверх и передача типа параметра внутрь callback — разные операции. Полноценная проверка произвольного `fn` против ожидаемой сигнатуры пока не реализована.

## Что есть сейчас

**Current:** `infer`/`infer-body` выводят типы выражений; `bind-pairs` последовательно типизирует `let`; `bind-pattern` обрабатывает параметры и деструктуризацию. Специальные правила `map`, `mapv`, `filter`, `keep`, `reduce` передают типы элементов в `apply-fn-node`. Для непосредственно записанного `(fn ...)` эта функция вызывает `infer-fn` с известными типами аргументов; для `#(...)` связывает `%`, `%1`, `%2`, `%3`. Это набор специализированных правил, не общий решатель ограничений.

`var-type` выводит неизвестный результат функции с `:source :hints` из её тела, используя уже известные типы параметров, и кеширует результат в `*rets*`. Перед обходом тела в кеш кладётся исходная сигнатура: рекурсивный вызов видит её, а не результат поиска неподвижной точки. Типы параметров частной функции не восстанавливаются автоматически из всех мест вызова.

**Planned:** общий контекстный режим для функциональных аргументов, явное объяснение происхождения вывода и видимый статус неполной проверки. Сейчас `call-fn` сначала самостоятельно вызывает `infer` для каждого аргумента, а затем проверяет совместимость. Ожидаемая сигнатура параметра не передаётся внутрь произвольного callback.

## Примеры и ожидаемое поведение

Ниже обычные примеры спецификации, не исполняемые golden-тесты. Current-ожидания выведены из исходников; отдельный запуск этих фрагментов здесь не заявляется. Имена типов в комментариях описывают внутренний результат, а не точный текст CLI.

### 1. Последовательный `let` и тип callback — current, корректно

```clojure
(let [xs [1 2 3]
      ys (mapv (fn [x] (inc x)) xs)
      zs (mapv (fn [y] (+ y 10)) ys)]
  zs)
;; xs: vector<int>; x получает int из xs.
;; ys и zs: vector<int> по текущим int-перегрузкам арифметики.
;; Отдельные аннотации let и параметров fn не нужны.
```

Инициализатор каждого следующего binding проверяется уже в расширенном окружении. В этом случае выбираются int-перегрузки `inc` и `+`; в общем случае точность результата ограничена библиотечной сигнатурой.

### 2. Ошибка внутри callback — current

```clojure
(mapv (fn [x] (inc x)) ["one" "two"])
;; x: string. inc ожидает number.
;; Ожидается TSP2345 у аргумента x; аннотация callback не нужна.
```

Ошибка обнаруживается по пути «коллекция → элемент → параметр → вызов `inc`». Сам тип результата `mapv` не должен восприниматься как доказательство отсутствия ошибок: checker продолжает вывод после диагностики.

### 3. `filter` не доказывает сужение элемента — current, граница

```clojure
(let [xs [1 nil]]
  (mapv (fn [x] (inc x)) (filter some? xs)))
;; Current: filter сохраняет исходный тип элемента int | nil.
;; В inc ожидается TSP2531: возможен nil.
;; Это консервативное ограничение: во время исполнения nil уже отфильтрован.
```

Проверка тела предиката и перенос его логического результата в тип выходной коллекции — разные возможности. В этой карточке не обещается произвольный вывод предикатных фильтров. Специальное правило `keep` удаляет nil из типа результата callback, но это не общее доказательство свойств `filter`.

### 4. `reduce`: нельзя принять возвращаемый тип за инвариант — current/planned

```clojure
(reduce (fn [acc x] "changed") 0 [1 2])
;; Current: acc получает int, тело проверяется, но результат тела
;; не сверяется с acc; для inline fn и явного init возвращается int.
;; Реальный результат этого выражения — строка.
;; Planned: фиксированный тип аккумулятора требует проверки string <: int
;; и ошибки; это требование пока НЕ обеспечено реализацией.
```

Это не успешный пример sound-вывода: текущая ветка для локального/inline callback игнорирует его возвращаемый тип при выборе результата `reduce`. Ветка для символа нелокальной функции устроена иначе — возвращает результат `apply-type`. Обе ветки нужно согласовать, включая пустую коллекцию и вызов reducer без аргументов в варианте без init.

### 5. Пользовательская функция высшего порядка — planned

```clojure
(defn transform
  {:t/sig '[[string? :-> number?] :-> number?]}
  [f]
  (f "abc"))

(transform (fn [s] (inc s)))
;; Planned: ожидаемая сигнатура f передаёт string в параметр s;
;; inc должен сообщить TSP2345.
;; Current: call-fn не передаёт этот контекст; s остаётся unknown.
;; Отсутствие такой ошибки сейчас не означает, что callback проверен.
```

Перенос callback в `let`, перегрузки и rest-параметры требуют собственных правил: нельзя считать, что поддержка inline `fn` в `map` уже решает эти случаи.

## Алгоритм и точки интеграции

### Текущий проход: описательный алгоритм, не доказательство soundness

1. **Вход:** узел AST с позицией и директивами, `ctx` с `:env`, `:file`, `:locals`, настройками и вспомогательными фактами. Окружение содержит спецификации, сигнатуры vars и типы core-функций. Грамматика источников описана в `docs/reference.md`; её приоритеты здесь заново не определяются.
2. **Представление:** тип — Clojure map с тегом `:t`. Используются литералы, примитивы, `:union`, `:coll` с `:kind`/`:of`, map с `:req`/`:opt`, ссылки на specs, `:fn` с `:arities`, `:params`, `:rest`, `:ret`, а также `unknown`, `any`, `never`. Это не свободные переменные унификации. `:fresh` отличает свежий map-литерал; `:why`, `:hinted`, `:missing-of` — вспомогательные сведения окружения, не полный граф доказательств.
3. **Синтез выражения:** `infer*` выбирает правило по AST. Коллекция объединяет типы элементов; `widen` расширяет литералы до примитивов там, где правило это предусматривает. `infer-body` посещает все формы и возвращает тип последней (для пустого тела — nil).
4. **Локальные binding:** `bind-pairs` выводит инициализатор в текущем окружении, снимает `:fresh`, вызывает `bind-pattern`, записывает тип и только затем переходит к следующей паре. Деструктуризация извлекает поля/элементы; hint проверяется отдельно и может повлиять на тип binding. Область видимости определяется контекстом рекурсивного обхода, а не глобальной таблицей локальных имён.
5. **Контекст коллекции:** специальное правило получает `elem-type` каждой входной коллекции и вызывает `apply-fn-node`. Inline `fn` связывает параметры с этими типами и выводит тело. Для `map` результат тела становится типом элемента выхода; `mapv` меняет kind на vector; `keep` удаляет nil; `filter` оставляет исходный тип элемента. `reduce` имеет отдельные неполные ветки, описанные выше.
6. **Обычный вызов:** `call-fn` синтезирует аргументы, выбирает подходящие арности и использует проверки совместимости. `apply-type` выполняет похожую работу для вызова уже имеющегося функционального типа. Это проверка подтипов, не решение универсальных полиморфных ограничений.
7. **Результат и диагностики:** `infer` применяет hints/директивы и вызывает `record!`; ошибки добавляются отдельно через `report!`. Используются существующие `TSP2345` (несовместимый аргумент), `TSP2531` (возможен nil), `TSP2554` (арность), а ошибки возвращаемого значения обрабатывает `check-return!`. Наличие возвращённого типа не отменяет ошибок или пробелов проверки.

### Планируемый контекстный режим: обязательства перед реализацией

1. Разделить операции «синтезировать тип» и «проверить против ожидаемого типа». Для функционального аргумента передавать ожидаемые параметры в тело, затем проверять синтезированный результат против ожидаемого результата.
2. Для единственной фиксированной сигнатуры проверить число параметров, связать их через существующий `bind-pattern`, проверить все формы тела и совместимость результата. Не позволять contextual binding молча отменять несовместимую явную аннотацию.
3. Для перегрузок не выбирать контекст случайно: нужны изолированные попытки с отдельными диагностическими буферами и определённое правило неоднозначности. Для rest/kwargs, рекурсии и переноса `fn` в `let` нужны отдельные решения и тесты. До этого поддерживаемый фрагмент следует ограничить одной фиксированной арностью.
4. Для `reduce` с явным init исследовать вариант фиксированного инварианта A: init имеет тип A, reducer проверяется как `[A E -> A]`, результат учитывает пустую коллекцию. Расширение A по телу требует монотонности, ограниченного widening и критерия остановки; простое повторение текущего прохода sound-алгоритмом не является. Для варианта без init отдельно учитываются пустая/одноэлементная коллекции и нулевая арность reducer.
5. Возвращать вместе с типом происхождение и полноту проверки. Предлагаемые причины: неизвестный параметр, неподдержанный контекст, рекурсивный цикл, исчерпание бюджета. Новый код, если нужен: **proposed TSP220-01** — локальный вывод неполон; пока его нет в checker.
6. Нельзя строить гарантию на текущем булевом `sub?`: в `types.clj` глубина более 12 возвращает `true`, а `unknown` совместим в обе стороны. Требуется различать «совместимо», «несовместимо», «не доказано» и протащить последнее через callers. Это изменение контракта проверки с отдельным исследованием завершимости, не косметическая диагностика F220.

### Следующий этап: отложенный контекст, а не ранний unknown

После фиксированной арности из шагов 1–2 рассмотреть worklist ограничений с результатами `resolved | blocked(dependency-ids) | error`. Например, в `(map-like (fn [x] (inc x)) strings)` ожидаемый тип `x` может стать известен только после аргумента `strings`, стоящего правее callback. Сначала собрать доступные ограничения обычных аргументов; отложенный callback возобновлять при уточнении его зависимостей. Generalization допустима лишь после решения относящихся к ней ограничений. Остановку прогресса/лимит сообщать как неполную проверку, не подставлять any. Это развитие F230/F231, не новый глобальный HM-solver.

Контракт собственного `map-like` и внешние декларации core/библиотек (F711) должны питать один механизм. **Planned-тесты:** одинаковая ошибка `inc` для строк у core `map` и собственного HOF; контекст из аргумента справа; цепочка заблокированных callbacks возобновляется после уточнения; цикл завершает анализ с причиной неполноты. Кеш не должен закреплять ранний unknown после появления контекста.

Основание: [Luau, §4.2/4.4](../docs/research-luau.md), [Python, §4](../docs/research-python.md); первоисточники — [ConstraintGenerator](https://github.com/luau-lang/luau/blob/c87565b8b0db5d5d5bfd2b8b00ad6573e5d06d9f/Analysis/src/ConstraintGenerator.cpp), [ConstraintSolver](https://github.com/luau-lang/luau/blob/c87565b8b0db5d5d5bfd2b8b00ad6573e5d06d9f/Analysis/src/ConstraintSolver.cpp), [Pyright inference](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md). Здесь прочитаны отчёты; в них — выборочные участки generator и основной цикл solver, не весь Luau. Luau-файлы отчёт читал с master без побайтовой сверки с указанным SHA. Примеры не запускались, forced pass Luau не переносится.

## Ограничения и открытые вопросы

- Нет общего полиморфного вывода и восстановления параметров из всех вызовов. `unknown` не следует показывать как доказанную безопасность или подменять пользовательским `any`.
- Кеш результатов `var-type` предотвращает повторный вход, но не вычисляет рекурсивные типы до неподвижной точки.
- `apply-fn-node` для inline `fn` объединяет результаты арностей; это не полноценный выбор перегрузки по числу переданных элементов. Нужны негативные тесты неправильной арности callback.
- Вызов `map` без коллекции возвращает unknown после обхода callback: типизация трансдьюсера не следует из типизации двухаргументного `map`.
- Нужно определить, где хранить цепочку происхождения и как показывать её без повторных каскадных ошибок. Текущие `why-of`/`record!` дают основу, но не полный пользовательский trace.
- Сужение фактов внутри веток уже отдельно обрабатывает `narrow`; вывод произвольных логических свойств предикатов не входит в эту карточку.

## Конкретная матрица тестов

Это план проверок; наличие строки не означает, что тест уже добавлен. Проверять нужно и тип узла, и диагностики, а после введения полноты — её статус.

| Сценарий | Current / ожидаемая проверка | Целевой критерий |
|---|---|---|
| Последовательный `let`, пример 1 | Типы промежуточных vector, отсутствие ошибок | Следующий binding видит предыдущий; shadowing не меняет внешний scope |
| Строковый элемент в `inc`, пример 2 | `TSP2345` у аргумента | Ошибка с источником типа параметра |
| `filter some?`, пример 3 | `TSP2531`; nil не удаляется | Ограничение явно документировано, не случайный false negative |
| `map` двух коллекций и `#(+ %1 %2)` | Тип каждого параметра из своей коллекции | Поменять вторую коллекцию на строки: ошибка второго аргумента |
| Callback с неверной арностью | Регрессия для обхода арности inline `fn` | `TSP2554`, а не union результатов всех арностей |
| `keep (fn [x] x)` над int/nil | Выход без nil по специальному правилу | Не переносить это правило автоматически на `filter` |
| `reduce` с меняющимся acc, пример 4 | Зафиксировать текущий неверный int как известный пробел, не норму | Проверка инварианта либо явно неполный результат |
| `reduce` без init: пусто / один элемент / несколько | Отдельные варианты и 0-/2-арный reducer | Корректный учёт арностей и возможных результатов |
| Пользовательский HOF, пример 5 | Контекст пока не доходит до `s` | В контекстном режиме `TSP2345` внутри callback |
| Callback через `let`, overloaded и rest | Отдельно от inline fixed-arity | Поддержанный вывод либо видимая неполнота |
| Возврат private defn, прямой/взаимный рекурсивный вызов | Проверить кеш и сохранение unknown | Завершение без ложного обещания полного вывода |
| Вложенные типы, пересекающие предел `sub?` | Сейчас после глубины 12 возвращается true | Исчерпание бюджета не превращается в успех |
| `(map inc)` без коллекции | unknown | Не заявлять проверенную сигнатуру transducer |

Существующие примеры `c1`–`c4` в `test/features/src/f/core.clj` покрывают коллекционные цепочки, nullable результат, `keep` и `reduce +` поверх inline `map`. Они не доказывают общий контекстный вывод или корректность аккумулятора. `test/typespec/demo_test.clj` содержит harness проверок; эта карточка не добавляет исполняемых golden-блоков.
