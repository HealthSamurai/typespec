# F230 · Generics и функции высшего порядка

`comp` и `partial` реализованы для известных позиционных сигнатур.
Проверка стыков, остаточные арности и исполняемый пример описаны в
[F233](F233-function-composition.md). Прямые `map` и `filter`
в трёхаргументном `into` описаны в [F234](F234-transducers-into.md),
их композиция — в [F235](F235-transducer-composition.md).

Когда функция высшего порядка может вызвать колбэк, заведомо
невызываемое значение, например строка, целое число или `nil`, даёт
`TSP2345` на месте передачи колбэка. Тип значения может следовать
из Spec-контракта другого namespace. Карты, ключевые слова и множества
сохраняют семантику вызываемых значений Clojure.

Контекст первого вызова уточняет параметры локального `fn` и `letfn`.
Рекурсивный вызов с другими типами аргументов проверяется по арности и
подсказкам реализации. Это позволяет, например, передать хвост
последовательности и наполненный аккумулятор после входа с вектором и `[]`.

## Свертка по ключам и значениям

`reduce-kv` передает редьюсеру типы аккумулятора, ключа и значения. Для
`s/map-of` ключ и значение берутся из Spec, для карты с полным набором
известных ключей — из ее записей, для типизированного вектора ключ — `int?`,
а значение — тип элемента. Inline-функция получает эти типы для проверки тела
и деструктуризации. Для именованной функции используется ее существующая
сигнатура, включая `s/fdef` из другого namespace.

Тип результата учитывает переходы аккумулятора между вызовами. Пустая
коллекция или `nil` возвращает начальный аккумулятор. Если вход может
оказаться пустым, его тип входит в результат вместе с типом возврата
редьюсера. Для открытых карт с произвольными дополнительными ключами типы
ключа и значения остаются неопределенными.

## Индексированное преобразование

Двухаргументный `map-indexed` проверяет колбэк с индексом типа `int?` и
типом элемента входной коллекции. Для `s/coll-of` тип элемента берётся из
Spec, включая вложенный `s/tuple` для деструктуризации. Именованный
колбэк проверяется по его сигнатуре, включая `s/fdef` из другого namespace.
Тип результата колбэка становится типом элемента ленивой последовательности
и доступен следующим шагам `->>`. В трёхаргументном `into` те же типы
доступны для прямого `(map-indexed f)`. Отдельное значение трансдьюсера
имеет тип `t/unknown`. [F234](F234-transducers-into.md)

## Обновление: rank-1 solver

Реализован первый ограниченный срез: явный `t/all`, свежая инстанциация на вызов, проверка generic-тела с rigid-параметрами, простые primitive bounds, generic extern и контекст параметров inline `fn`. Сигнатуры сравниваются с учётом переименования binders. Нерешённые ограничения дают TSP210-01, а не доказательство. Одна фиксированная арность; без higher-rank, row inference, автоматического let-generalization и общего вывода из ожидаемого результата. Подробности и исполняемые тесты: [solver-usage](../docs/solver-usage.md). Общий запуск: 60 тестов / 309 assertions плюс golden/CLI. Прежние утверждения ниже об отсутствии solver описывают историческое состояние.


## Обновление реализации — топ-10

Добавлена совместимость функциональных типов: контравариантность параметров и ковариантность результата, фиксированные и ограниченные homogeneous-rest арности. Это НЕ generic solver; t/all и общий HOF inference остаются планом.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Зачем это Clojure

Clojure-код передаёт функции как значения: преобразует коллекции, строит обработчики через `comp` и `partial`, собирает трансдьюсеры. Одного знания «это функция» недостаточно: надо связать тип элемента коллекции с параметром callback, а результат callback — с результатом всей операции. Без этого ошибка внутри композиции либо пропускается, либо требует повторять одну и ту же аннотацию для каждого конкретного типа.

Параметрическая сигнатура выражает такую связь один раз: identity сохраняет тип аргумента, map меняет тип элемента, partial сохраняет незаполненные параметры. Она не равна `any?`: последнее отключает проверку связи, а переменная типа должна означать один согласованный тип в пределах одной инстанциации.

## Примеры и ожидаемое поведение

Это обычные иллюстрации Clojure, не исполняемые golden-тесты карточки. `t/`-формы в metadata — данные для checker, а не вызовы библиотечного кода. Current ниже означает поведение, следующее из реализации; новые примеры отдельно не запускались.

### 1. Current: локальное правило map проверяет callback

```clojure
(ns sample.map)

(mapv inc [1 2 3])       ; корректно: вектор int?
(mapv inc ["1" "2"])   ; ошибка: inc получает string?, а не number?
(mapv (fn [x] (str x)) [1 2]) ; вектор string?
```

`special mapv` получает типы элементов и вызывает `apply-fn-node`. Для `inc` проверяются его перегрузки; несовместимый вход диагностируется `TSP2345`. Для непосредственного `fn` параметры заполняются типами элементов. Это контекстный вывод в специальном правиле, не доказательство поддержки произвольной HOF.

### 2. Planned: одна декларация, независимые инстанциации

```clojure
(ns sample.generic)

(defn same
  {:t/sig '(t/all [a] [a :-> a])}
  [x] x)

(same 42)       ; planned: int?
(same "hello") ; planned: string?, без связи с предыдущим вызовом

(defn broken-same
  {:t/sig '(t/all [a] [a :-> a])}
  [x] "always") ; planned: отвергнуть тело для произвольного a
```

Current: `t/all` не распознаётся; ожидается `TSP9001`, а не корректная проверка generics. Planned: тело `same` проверяется с жёсткой переменной `a`, вызовы — со свежими решаемыми переменными. Нельзя «доказать» `broken-same`, выбрав `a = string?`: декларация обязана работать для всех допустимых `a`. В минимальном варианте числовые/строковые литералы здесь расширяются до базовых типов.

### 3. Planned: callback нельзя заменить просто на fn?

```clojure
(ns sample.hof)

(defn transform
  {:t/sig '(t/all [a b]
             [(s/coll-of a) (t/fn [a :-> b]) :-> (s/coll-of b)])}
  [xs f] (map f xs))

(transform [1 2] (fn [x] (str x))) ; planned: коллекция string?
(transform ["a"] inc)             ; planned: несовместимый вход callback

(defn needs-text
  {:t/sig '[(t/fn [int? :-> string?]) :-> string?]}
  [f] (f 1))
(needs-text inc) ; planned: ошибка результата callback (int? вместо string?)
```

Current: generic-декларация `transform` неподдержана. Мономорфный `needs-text` разбирается, но текущий `sub1?` сравнивает лишь теги `:fn` и не отвергает передачу `inc` по несовместимому результату. Это конкретный пробел проверки функций как значений: специальная проверка непосредственного `(map inc xs)` его не исправляет.

### 4. Направление композиции и остаточная арность

```clojure
(ns sample.compose)

(defn render-number {:t/sig '[int? :-> string?]} [x] (str x))
(defn text-size {:t/sig '[string? :-> int?]} [s] (count s))
(defn add-int {:t/sig '[int? int? :-> int?]} [x y] (+ x y))

((comp text-size render-number) 10) ; int?
((comp inc text-size) "abc")       ; int?
((comp inc render-number) 10)      ; ошибка стыка string? -> number?
((partial add-int 10) 2)           ; int?, остаточная арность 1
((partial add-int 10) 2 3)         ; неверная остаточная арность
```

Для двух функций `comp f g` сначала выполняется `g`. Её выход обязан
подходить единственному аргументу `f`. Формы и границы реализации
описаны в [F233](F233-function-composition.md).

### 5. Граница: трансдьюсер и пустая коллекция

```clojure
(ns sample.transducer)

(defn number-labels
  {:t/sig '[(s/coll-of int?) :-> (s/coll-of string? :kind vector?)]}
  [xs]
  (into [] (map str) xs)) ; вектор string?, точный пустой источник сохраняет тип назначения

(defn wrong-labels
  {:t/sig '[(s/coll-of int?) :-> (s/coll-of string? :kind vector?)]}
  [xs]
  (into [] (comp (map inc) (filter odd?)) xs))
; Ошибка возвращаемого типа: объявлен вектор строк, выведен вектор целых.

(mapv (fn [x] x) []) ; planned: нельзя придумывать int? или string? без контекста
```

F234 выводит тип элементов для прямых `map` и `filter`. F235
передаёт тип между шагами `comp` и выдаёт `TSP210-01` для
неподдержанного шага.
Вектор с исходным `t/never` для элементов остаётся пустым, если
прямой трансдьюсер получает заведомо пустой источник.

## Алгоритм проверки: минимальное ядро и исследовательские части

Ниже — проект алгоритма, **не готовый sound solver**. Реализация должна начать с явно ограниченного фрагмента: rank-1, фиксированные арности, явные generic-декларации, неизменяемые коллекции и мономорфные callbacks. Overloads, unions и рекурсивные ограничения требуют отдельных правил и доказательства корректности; их нельзя закрыть простым объединением всех найденных типов.

### Вход и представление

Вход: AST с позициями из `parse.clj`, окружение деклараций из `env.clj`, локальные типы и факты сужения, ожидаемый тип (если есть), сигнатура вызываемого значения. Выход: тип выражения, диагностики с позициями и статус полноты проверки; неразрешённое не помечается как проверенное.

Текущий функциональный тип — `{:t :fn :arities [{:params [...] :rest ... :ret ...}]}`. Предлагаемые дополнительные узлы: схема `forall` с binders и bounds, жёсткая переменная для тела, свежая решаемая переменная для вызова. Это внутреннее представление, не существующий API. У каждой переменной уникальный ID; у ограничения `L <: U` — происхождение (аргумент, callback, результат, граница композиции). Подстановка должна обходить вложенные функции и коллекции, не захватывая чужие binders.

### Последовательность

1. **Прочитать декларацию.** Расширить `types/parse-sig`/`parse-type`: область видимости `t/all`, уникальность binders, неизвестные переменные, корректность bounds. Не интерпретировать свободное `a` как `unknown`. Неподдержанная форма остаётся ошибкой декларации, а не успешным fallback.
2. **Проверить тело полиморфной функции.** Заменить binders жёсткими переменными; доступны только их объявленные верхние границы. Проверить параметры и результат тела против этой схемы. Не решать жёсткую переменную по телу; возврат константы вместо произвольного `a` отвергнуть. При выходе переменные не должны утекать в окружение.
3. **Подготовить вызов.** Получить сигнатуру, отобрать подходящие арности; для каждого кандидата отдельно создать свежие переменные и локальный набор ограничений. Несовпадение числа аргументов — существующий `TSP2554`. Решения разных вызовов/кандидатов не смешивать.
4. **Собрать ограничения.** Для обычного аргумента `actual <: formal`; результат вызова ограничить ожидаемым типом. Для неизменяемой коллекции спуститься к элементу ковариантно. Для функции `S <: T` с одной фиксированной арностью требовать `T.param[i] <: S.param[i]` и `S.ret <: T.ret`. Это замена нынешней проверки только тегов, а не дополнение к ней. Из bounds добавить `a <: bound` с корректной подстановкой.
5. **Проверить callback с контекстом.** Из уже известных входов коллекций получить ожидаемые параметры непосредственного `fn`, проверить его тело, добавить ограничение результата. Для именованной функции сравнить сигнатуру, а не только вызвать её на удобном наборе входов. Если контекста недостаточно, запросить аннотацию/вернуть неполную проверку; нельзя угадывать тип по первому использованию. Циклические зависимости между выводом callback и решением ограничений — отдельная исследовательская задача.
6. **Решить поддержанный фрагмент.** Накопить нижние/верхние границы, выполнить проверку вхождения переменной в собственное решение, проверить удовлетворимость всех границ. В простом ковариантном случае допустимо рассмотреть объединение нижних границ, но только после проверки всех верхних; это не общее правило для функций и перегрузок. Недоопределённые, рекурсивные и неоднозначные случаи явно отклонять из минимального фрагмента, не заменять на `any?`. Лимит вычислений означает «не проверено», не `true`.
7. **Проверить решение повторно.** Подставить найденные типы во все исходные ограничения и bounds; проверить отсутствие нерешённых переменных в результате. При нескольких подходящих перегрузках применять отдельно утверждённую политику неоднозначности; не брать первый удобный вариант. Вернуть инстанцированный выход, сохранив цепочку происхождения ошибки.
8. **Построить HOF-контракты поверх ядра.** Для фиксированного `comp` проверять стыки справа налево, сохранить входы крайней правой функции и выход крайней левой. Для `partial` проверить захваченный префикс аргументов и построить остаточные арности. Для неизвестной длины аргументов и variadic-перегрузок нужны отдельные правила — вычитание одного числа недостаточно.

### Интеграция с текущим checker

- `env.clj` по-прежнему собирает сигнатуры из текста; конфликт источников декларации не решается новым solver. Эта карточка описывает проверку полиморфной схемы, а не переопределяет приоритеты источников.
- `call-fn` сейчас сначала выводит все аргументы без ожидаемых типов. Для generic/HOF-вызовов нужен двунаправленный путь проверки; `infer-fn` уже умеет принимать контекстные `arg-types`, но это только заготовка.
- `apply-type`, `apply-fn-node` и обычный `call-fn` должны использовать единый механизм инстанциации и проверки арностей. Иначе именованный callback, непосредственный `fn` и callback через `let` будут проверяться по-разному. Нынешний путь непосредственного `fn` в `apply-fn-node` объединяет выходы арностей, а не реализует полноценное покрытие арностей.
- `types/sub1?` требует структурного сравнения функций; текущие послабления для `unknown` и возврат `true` при глубине `sub? > 12` нельзя использовать как доказательство удовлетворимости generic-ограничений. Для solver нужны раздельные исходы «да / нет / неизвестно» и явная граница доверия `any?`.
- Методы `special` для map/update и прочих коллекционных операций можно сохранить, но передавать проверку callback в общее ядро. Наличие этих методов само по себе не позволяет обобщать пользовательские функции.

### Диагностики

Существующие `TSP9001` (неподдержанная форма типа), `TSP2554` (арность), `TSP2345` (несовместимый аргумент) и `TSP2531` (возможный nil при вызове) не переименовываются. Для будущих случаев предлагаются, но **не существуют сейчас**:

- **proposed TSP230-01** — несовместимые ограничения/bound; показать переменную, нижнюю и верхнюю границу и оба места их происхождения.
- **proposed TSP230-02** — требуется аннотация или случай вне поддержанного фрагмента; назвать причину (неоднозначность, цикл, лимит), не писать «тип корректен».
- **proposed TSP230-03** — тело не удовлетворяет универсальной декларации; показать жёсткую переменную и выражение результата.

Для несовместимого callback сообщение должно различать вход, выход и арность. Для `comp` — показывать соседние функции и тип на стыке, а не только ошибку последнего вызова.

## Ограничения и вопросы до обещания полноты

1. **Rank-1 не higher-rank.** Передача самой полиморфной функции как полиморфного аргумента, автоматическая let-generalization и полиморфная рекурсия не входят в первый этап. Правила инстанциации перегруженных core-функций тоже надо определить отдельно.
2. **Bounds, unions и overloads.** Нужны формальная модель разрешимого фрагмента, политика выбора решения и независимые отрицательные тесты. Из reference следует намерение поддержать bounds, но там нет готового solver или доказательства soundness.
3. **Трансдьюсер не просто `A -> B`.** Он преобразует reducing function, сохраняет тип аккумулятора, поддерживает init/completion/step и раннее завершение через `reduced`. Нужно исследовать, достаточно ли отдельного типового конструктора или требуется higher-rank представление. До этого шага обобщённое правило `comp` не означает поддержку трансдьюсерной композиции.
4. **Изменяемые значения.** Инвариантность atom/volatile/array/channel заявлена в reference, но здесь не реализована. `swap!` должен сохранять тип состояния, `fnil` учитывать замену nil, `update-in` — наличие промежуточных ключей и путь. Общий solver не заменяет эти контракты; пример с их цепочкой пока не критерий первого этапа.
5. **Пустота и сужение.** Уточнить тип пустой коллекции, расширение литералов, перенос nil и поведение фильтров. `filter` с truthy-предикатом не обязан возвращать boolean и не должен автоматически сужать элемент без доказанного guard-контракта.
6. **Граница доверия.** Декларации externs и `any?` остаются доверенными допущениями. Даже корректный алгоритм для ограниченного фрагмента не делает весь текущий checker sound.

## Критерий готовности и основания

Первый этап готов, когда parser, проверка универсального тела, инстанциация, структурные функции и diagnostics работают согласованно в обозначенном rank-1 фрагменте; все положительные случаи имеют намеренную ошибку-пару. Неподдержанные случаи видны как непроверенные. Поддержку `comp`/`partial` и тем более трансдьюсеров следует объявлять отдельными этапами, а не включать по наличию `t/all` в parser.
