# F231 · Ограничения generics и проверка обязательств

## Мотивация

Проверять generic-функцию один раз по объявленным ограничениям, а не считать её корректной по одному успешному вызову. От Rust берём модель обязательств; не переносим ownership, monomorphization или закрытость реализаций.

## Пример целевого поведения

```clojure
;; Иллюстрация требования, синтаксис generic bounds ещё не утверждён.
(defprotocol Named (label [x]))
(defn labels [xs]
  (map label xs))
;; Для элемента T требуется контракт Named с известным типом label.
;; Один удачный вызов с конкретным record не доказывает тело для всех T.
```

Иллюстрация, не исполняемый тест и не утверждение о текущем checker.

## Алгоритм — проект ограниченного подмножества

1. При входе в generic-тело вводить жёсткие параметры типов и окружение объявленных bounds. Не подставлять конкретный тип из первого вызова.
2. Каждая операция порождает обязательство: совместимость аргумента, поддержка протокола, равенство/ограничение параметра. Сохранять позицию и цепочку причин.
3. Доказывать обязательства из bounds, проверенных деклараций и поддержанных правил типов. Не использовать permissive unknown как доказательство.
4. В месте вызова инстанцировать параметры свежими переменными, собрать ограничения из аргументов и ожидаемого результата, затем проверить bounds.
5. Различать proved, contradicted и unresolved. При unresolved не объявлять ни заведомую ошибку runtime, ни успешную полную проверку.
6. Для рекурсивных обязательств использовать ограниченный рабочий список и memoization; исчерпание бюджета не означает true.
7. Объяснять путь: вызов → generic-параметр → необходимый контракт → отсутствующее доказательство.

## Границы и открытые вопросы

Открытые extend-* и :extend-via-metadata не позволяют скопировать Rust trait selection буквально. Требуется фиксировать наблюдаемую границу анализа; внешние promises доверенные. Generic protocol constraint — предлагаемый контракт, не уже существующий Clojure-синтаксис. Необходимые предпосылки: безопасный subtype из F210, параметры типов F230 и модель протоколов F430.

Это проект исследования, не доказательство soundness и не готовый перенос rustc.

## Матрица тестов

Корректный bound; операция без bound внутри тела; несовместимый аргумент; unknown-аргумент; неоднозначное доказательство; рекурсивная цепочка; extension за пределами проекта. Проверять не только итог, но и причину/позицию диагностики.
