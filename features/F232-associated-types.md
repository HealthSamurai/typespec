# F232 · Связанные типы контрактов

## Мотивация

Связывать интерфейс с типом результата операции: например, источник данных имеет тип элемента. Из Rust берём идею associated types; в Clojure это возможное type-only расширение контрактов, не изменение defprotocol.

## Пример целевого поведения

```clojure
(defprotocol Source (read-items [source]))
(defn first-item [source]
  (first (read-items source)))
;; Цель: контракт Source для S задаёт Item(S).
;; read-items: S -> Coll<Item(S)>
;; first-item: S -> Item(S) | nil
;; Это эскиз контракта, а не поддержанный синтаксис аннотации.
```

Иллюстрация, не исполняемый тест и не утверждение о текущем checker.

## Алгоритм — проект ограниченного подмножества

1. Сначала проверить, нельзя ли выразить сценарий обычным параметром типа; не вводить associated type ради сокращения записи.
2. Представлять проекцию как отдельный узел Projection(contract, receiver-type, name) с происхождением.
3. Хранить равенства проекций в выбранном контракте реализации. Допускать только непротиворечивые объявления в ограниченном первом подмножестве.
4. Нормализовать проекцию при однозначном доказанном контракте. Для generic-получателя сохранять символическую проекцию и использовать bounds.
5. Unknown, неоднозначная реализация и неподдержанная динамика не превращаются в произвольный Item.
6. Передавать проекцию через обычные функции/контейнеры без потери связи. Рекурсивную нормализацию ограничивать и явно отмечать неуспех.

## Границы и открытые вопросы

В Rust тип связывается с trait implementation; открытые протоколы Clojure и metadata dispatch могут зависеть не только от класса. В MVP рассматривать только явно описанные статически различимые получатели. Не обещать автоматический Item для любого seq или Java-объекта. Вопрос: даёт ли механизм преимущество перед Source<T> в type-only модели? Нужны реальные сценарии до принятия в реализацию.

Это проект исследования, не доказательство soundness и не готовый перенос rustc.

## Матрица тестов

Источник int и источник string; перенос проекции через helper; неверный результат read-items; конфликт Item для одного receiver; generic receiver; динамическая metadata-реализация; цикл проекций. Проверить, что first по-прежнему допускает nil независимо от Item.
