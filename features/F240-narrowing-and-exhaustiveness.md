# F240 · Сужение, tagged unions и полнота веток

## Обновление реализации — топ-10

Исправлена базовая Clojure truthiness: false/nil ложны, some? исключает только nil; есть регрессионные тесты сужения. Tagged-map correlation и общие logical summaries остаются planned.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Зачем это нужно в Clojure

В Clojure проверки `nil?`, `string?` и `case` часто уже описывают допустимые значения. Checker должен использовать эти проверки, чтобы не требовать повторных аннотаций внутри веток. Для событий, команд и состояний, представленных maps с тегом, проверка тега должна давать доступ к полям соответствующего варианта. Добавление нового варианта должно обнаруживать забытые обработчики — но только если множество вариантов действительно закрыто.

Сужение — факт о значении в конкретной ветке, а не изменение объявления типа и не runtime-проверка входных данных. Полнота `case` — отсутствие пропущенных вариантов в доказанном домене; это не обещание, что ветки завершаются без исключений.

## Что уже работает, а что запланировано

`implementation: partial` сохранён. Основание — `narrow` и обработчики `special` в [check.clj](../src/typespec/check.clj), а не весь список пожеланий в reference.

| Возможность | Current | Planned / граница |
|---|---|---|
| Локальная переменная в условии | Удаление `nil` в истинной ветке | Точное разделение truthy/falsy, включая `false` |
| `some?`, `nil?`, `not` | Удаление `nil` в соответствующей ветке; `not` меняет контексты местами | Точная положительная ветка `nil?` и отрицательная `some?` |
| `string?`, `int?`, `number?`, `keyword?`, `map?`, `vector?`, `boolean?` | Положительное сужение; отрицательная ветка остаётся прежней | Проверенное пересечение/вычитание типов |
| `instance?`, `s/valid?`, равенство литералу | Положительная замена типа локального символа | Не считать замену общим алгоритмом пересечения |
| `and`, `or`, `cond` | Последовательная передача части фактов между проверками | Полная модель короткого замыкания и объединения путей |
| `case` по конечному union литералов | `TSP8001` при пропуске без default; `TSP2678` для невозможных строковых, keyword и числовых меток | Дополнительные домены и точный остаток в default |
| `case` по локальному символу | В ветке символ получает тип метки или группы меток | Пересечение с исходным типом, обработка недостижимых веток |
| Тег поля map | Тип чтения поля может быть union литералов, поэтому полнота самого `case` возможна | Обратное сужение всей map и корреляция полей отсутствуют |
| `contains?`, `condp`, полнота `cond` по равенствам | В `narrow`/описанных обработчиках такого общего механизма нет | Обещания reference, не текущая гарантия |

Пользовательские guards — [F250](F250-checked-guards.md), контракты управления потоком — [F420](F420-control-flow.md), закрытые multimethods — [F440](F440-multimethods.md). Здесь не дублируются их алгоритмы.

## Примеры и ожидаемое поведение

Это обычные примеры дизайна, не golden-тесты. Current ниже сверено с исходниками; эти фрагменты отдельно не запускались. `s` означает `clojure.spec.alpha`, `str` — `clojure.string`. Сигнатуры — статические данные для checker, без запуска instrumentation.

### 1. Корректно: защитная проверка nullable-строки (current)

```clojure
(ns example.narrow
  (:require [clojure.spec.alpha :as s]
            [clojure.string :as str]))

(defn display-name
  {:t/sig '[(s/nilable string?) :-> string?]}
  [x]
  (if (some? x)
    (str/upper-case x) ; x: string?, nil удалён
    "anonymous"))
```

Ожидание: вызов `upper-case` допустим, результат соответствует `string?`. Ложная ветка сейчас не получает точный тип `nil`; для этого примера точность не нужна. Аналогичные уже существующие сценарии: `n1`, `n2`, `n3` в `test/features/src/f/core.clj`.

### 2. Ошибка: пропущенный вариант и невозможная метка (current)

```clojure
(defn action-label
  {:t/sig '[#{:create :delete} :-> string?]}
  [action]
  (case action
    :create "Create"
    :remove "Remove"))
;; TSP2678: :remove не входит в домен.
;; TSP8001: :delete не обработан, default отсутствует.
;; Исправление: заменить :remove на :delete.
```

Ожидание: две независимые диагностики. Невозможная метка не покрывает пропущенную. Добавление default убирает ошибку полноты, но не делает `:remove` допустимой меткой закрытого домена. `case` без совпадения в Clojure бросает исключение: checker не добавляет к результату такого `case` неявный `nil`.

### 3. Погранично: `cond` без `:else` и открытый `case` (current)

```clojure
(defn maybe-label
  {:t/sig '[keyword? :-> (s/nilable string?)]}
  [action]
  (cond (= action :create) "Create"))
;; Законный nil при несовпадении; не TSP8001.
;; Если потребовать :-> string?, ожидается ошибка возврата TSP2322.

(defn open-label
  {:t/sig '[keyword? :-> string?]}
  [action]
  (case action :create "Create"))
;; Current: нет TSP8001, keyword? не является закрытым union литералов.
;; Runtime: другое значение приводит к исключению. Отсутствие ошибки
;; checker здесь НЕ доказывает полноту. Default сделает поведение явным.
```

Даже если последовательность равенств в `cond` выглядит полной для конечного типа, текущий обработчик без завершающей безусловной ветки добавляет `nil`. Любой keyword-тест и литерал `true` обработчик считает безусловной веткой, не только `:else`.

### 4. Tagged union: связь тега и payload (planned)

```clojure
;; Обе карты имеют обязательный :kind. t/keys здесь — язык типов,
;; не предложение вызывать такую функцию в runtime-коде.
;; Синтаксис t/keys также planned: текущий parser его не поддерживает.
(defn render-event
  {:t/sig '[(s/or :text (t/keys :req {:kind #{:text}
                                    :payload string?})
                 :count (t/keys :req {:kind #{:count}
                                     :payload int?}))
            :-> string?]}
  [event]
  (case (:kind event)
    :text  (str/upper-case (:payload event))
    :count (str (inc (:payload event)))))
;; Planned: event сужается до целой карты своего варианта;
;; оба использования payload допустимы.
;; Current: этот фрагмент целиком ещё не поддержан (включая t/keys).
;; Даже для эквивалентного внутреннего union карт checker не сужает event:
;; payload остаётся string? | int?, что мешает вызовам этих функций.
```

В ошибочной planned-версии `inc` в ветке `:text` должен дать `TSP2345`, а не быть принят за счёт объединения типов соседних веток. При добавлении варианта `:reset` без новой ветки ожидается существующий `TSP8001`. Разные метки `:text` и `:count` у `s/or` сами по себе не являются тегами значений: доказательство строится по полю `:kind`.

### 5. Граница устойчивости факта: снимок и повторное чтение (planned)

```clojure
(defn snapshot-name [state]
  (let [x @state]
    (if (string? x)
      (str/upper-case x)          ; локальное значение x устойчиво
      "unknown")))

(defn reread-name [state]
  (if (string? @state)
    (str/upper-case @state)       ; другой поток мог изменить state
    "unknown"))
;; Planned: факт первого deref нельзя переносить на второй deref.
;; Current: narrow распознаёт аргумент-локальный символ, но не @state;
;; отсутствие такого переноса есть, полноценной модели эффектов нет.
```

Здесь не обещается конкретный текущий вывод о неаннотированном `state` или полная типизация atom. Проверяется принцип: факт принадлежит значению, а не тексту выражения. Типизация изменяемых контейнеров — отдельная задача F340.

## Алгоритм текущего прототипа

1. **Вход.** `infer` получает AST с позициями и `ctx`: `:env` с объявлениями, `:locals` с типами локальных символов, вспомогательные `:why` и `:missing-of`. Отдельного хранилища логических формул нет. Типы — maps из [types.clj](../src/typespec/types.clj): `:lit/:val`, `:union/:types`, `:nil`, `:never`, `:unknown`, `:any`, `:map/:req/:opt`, `:ref/:name`.
2. **Разбор условия.** `narrow` возвращает `[true-ctx false-ctx]`. Для символа/`some?` удаляет `nil` в true-ctx; для `nil?` — в false-ctx. У символа в false-ctx может сработать специальная связь `:missing-of` от destructuring. `not` переставляет контексты. `and` последовательно уточняет истинный путь, `or` — ложный; противоположный путь остаётся исходным.
3. **Другие проверки.** Для двухаргументного `=` локального символа со строкой, keyword или числом положительный тип заменяется литералом. Для встроенного предиката сохраняются члены исходного union, которые `t/sub?` считает подтипами целевого типа; если подходящих членов нет или они слишком неопределённы, берётся тип самого предиката. `instance?` и `s/valid?` также заменяют положительный тип. Это описание кода, не доказательство soundness: произвольное пересечение/вычитание здесь не реализовано.
4. **Ветки.** `if`/`if-not` проверяют тела в полученных контекстах, затем объединяют результаты через `t/union`. Отсутствующий else даёт `nil`. `when`/`when-not` добавляют `nil`; `cond` передаёт false-ctx следующей паре и добавляет `nil` при исчерпании пар без безусловной ветки. `if-let` и `if-some` сейчас пользуются одним helper, удаляющим только `nil`; это не точная модель различия `false` и `nil`.
5. **Домен `case`.** Вывести тип discriminant; раскрыть ссылки и unions через `t/members`. Домен закрыт только если список членов непуст и каждый член имеет `:t :lit`. `keyword?`, `unknown`, `any`, неразрешённая/циклическая ссылка не удовлетворяют этому условию. Наличие `:nil` также не проходит текущий критерий закрытости.
6. **Покрытие.** Собрать значения меток, раскрывая list-группы `(:a :b)`. Default определяется нечётным количеством элементов clauses. В закрытом домене проверить допустимость строковых, keyword и числовых меток (`TSP2678`); если нет default, вычислить разность домена и обработанных значений (`TSP8001`, перечисление пропущенных). Это конечная операция над множествами, без solver.
7. **Результат `case`.** Если discriminant — локальный символ, присвоить ему union литералов метки данной ветки. Если это `(:kind event)`, контекст `event` не меняется. Default проверяется в исходном контексте, не в остаточном домене. Объединить типы результатов; `never` устраняется функцией `union`. Диагностики тел идут обычным путём checker (`TSP2345` для аргумента, `TSP2322` для несовместимого возврата); позиции берутся из исходного AST.

## План расширения: ограниченный алгоритм для tagged unions

Это проект следующего шага, **не готовый sound алгоритм для всего Clojure**. Первая проверяемая область: конечный union структурных неизменяемых maps, обязательный ключ-тег с конечным набором литералов, чтение поля непосредственно из устойчивого локального binding. Не начинать с произвольных предикатов и путей через mutable-объекты.

1. Ввести идентификатор binding, а не только имя символа, и представление пути `[binding-id key]`. Связать прочитанный тег с исходным значением. При shadowing создаётся новый идентификатор. Повторные вызовы/deref не получают ту же идентичность автоматически.
2. Раскрыть варианты исходного union, сохраняя **целые карты**, а не отдельно union тегов и union payload. Для каждого варианта вычислить конечный домен обязательного тега. Если встречаются неизвестный вариант, необязательный тег, нерешённая рекурсия или неустойчивый путь, прекратить доказательство в этом режиме; не выдавать вывод о полной проверке корреляции.
3. Для метки `case` выбрать варианты, домен тега которых пересекается с меткой/группой. В выбранных вариантах ограничить тип тега пересечением, остальные поля оставить связанными со своим вариантом. Один тег может соответствовать нескольким картам: тогда тело получает их union, а не произвольно одну карту. Пустой набор — недостижимая ветка, политика проверки её тела ещё требует решения.
4. Для default вычислить остаток по всем меткам; для отсутствующего default проверить пустоту остатка. На этой ограниченной области использовать существующие `TSP8001`/`TSP2678`. Для неизвестного домена не подменять «не удалось доказать» выводом «всё покрыто». Минимальный контрпример сначала — отсутствующая метка, не выдуманная полностью валидная map.
5. Проверить каждое тело с уточнённым типом исходного binding; объединить результаты, не утекать branch-фактами наружу. При последующем `assoc`/`dissoc` нужен новый результат с заново вычисленной связью, а не наследование фактов об исходной map.
6. Для `if (= (:kind event) :text)` и последовательного `cond` расширять тот же механизм только после реализации отрицательного остатка. Общие `and`/`or` требуют объединения альтернативных путей; простого накопления всех фактов недостаточно. `cond` без else сохраняет законный путь с `nil`, если отсутствие этого пути не доказано.
7. Перед распространением на aliases, destructuring, nested paths и произвольные guards проверить модель идентичности значений, пересечения/разности типов и эффекты. Нужны отдельные исследования и контрпримеры soundness: сейчас `t/sub?` — не solver логических утверждений. Бюджет раскрытия и отказ от доказательства при его превышении должны быть явными.

### Planned: результат выражения несёт условные факты

Не расширять список имён внутри `if`: производитель факта возвращает внутренний `Result = {type, truthy-prop, falsy-prop, object}`, а ветвление потребляет его. `object` — стабильный BindingId с разрешённым immutable-путём либо `none`; атомы формул — `Is(object,T)` / `Not(object,T)`, композиция — ограниченные `And` / `Or`. При `none` нет адресата сужения. Неподдержанная формула или исчерпанный бюджет дают отсутствие дополнительного факта, **не** доказательство недостижимости. Противоречие допустимо выводить лишь поддержанными правилами. `unknown` здесь безопасный top, не разрешение произвольных операций и не Pyright Unknown.

Факты можно сохранить вместе с boolean-binding, не только применить сразу:

```clojure
;; Внешняя декларация fetch-name: [] -> string? | nil.
(let [x (fetch-name), present (some? x)]
  (if present (clojure.string/upper-case x) "missing"))
```

Целевые тесты: пример принимается; shadowing `x` не наследует импликацию; `(some? false)` истинно, тогда как `(if false ...)` идёт в falsy-ветку; неизвестный predicate не исключает варианты. Для core (`some?`, строковые функции) и библиотек обязательны внешние декларации F711, включая основание доверия summary; совпадения имени недостаточно.

Основание: [Typed Racket: occurrence typing](https://docs.racket-lang.org/ts-guide/occurrence-typing.html), [Sorbet: flow-sensitive typing](https://sorbet.org/docs/flow-sensitive). Перенос по [отчёту Typed Racket](../docs/research-typed-racket.md) (Guide, выборочные §2–3 статьи и структуры propositions, `tc-if` целиком) и [отчёту Sorbet](../docs/research-sorbet.md) (документация и `infer/environment.h`, не весь inference). Здесь прочитаны отчёты, первоисточники повторно не аудированы; формат Result — проект Typespec, не готовый перенос solver.

## Ограничения и открытые решения

- Открытая структурная map и закрытый **набор вариантов** — разные свойства: дополнительные ключи не мешают доказательству по обязательному конечному тегу. Но неизвестный вариант в union мешает.
- `false` — falsy в Clojure. Текущее удаление только `nil` не даёт точных truthy/falsy-типов; отдельные ошибки вывода `and`/`or` нельзя исправить одной таблицей предикатов.
- Отрицательное сужение по большинству предикатов и `=` отсутствует. Поэтому сейчас «в предыдущей ветке был `string?`» не означает «ниже точно не string».
- `contains?` означает наличие ключа, а не non-nil значение. Будущее правило должно различать missing, present-nil и present-value; оно не получается заменой на `some?`.
- Необходимо уточнить семантику сравнения литералов, boolean/nil-меток, групп `case`, дубликатов и недостижимых тел. Текущая проверка невозможных меток ограничена AST-категориями, указанными выше.
- Общие custom guards, mutable paths, макросы и внешние данные не входят в доказанный минимум. Наличие аннотации не валидирует фактические данные в runtime.
- Новых диагностических кодов карточка не вводит. Политику сообщения «доказательство недоступно» ещё предстоит согласовать с покрытием, чтобы отсутствие `TSP8001` не считалось сертификатом полноты.

| Полный `case` + группа `(:create :delete)` | Нет ошибки полноты, локальный тип ветки — union меток | Добавить, current |
| Неполный `case` + default | Нет `TSP8001`; невозможная метка всё ещё `TSP2678` | Добавить, current |
| Пример 3: `cond` без else | Nilable-возврат принят; non-nil-возврат — `TSP2322` | Добавить, current |
| Открытый `keyword?`, `unknown`, union с nil | Не объявлять доказанную полноту; текущий gate не выдаёт `TSP8001` | Добавить, current limitation |
| Внутренний union карт из примера 4 без сужения map | Зафиксировать union payload и ошибки его использования; t/keys отдельно пока не поддержан | Добавить, current baseline |
| Пример 4 после реализации; `inc` в `:text` | Корректные ветки приняты / ошибка `TSP2345` | Добавить, planned |
| Две карты с одним тегом и разными payload | Сохраняется union payload, нельзя выбрать один вариант | Добавить, planned |
| Новый вариант `:reset` | Без ветки — `TSP8001`; с веткой — чисто | Добавить, planned |
| Optional-тег, неизвестный вариант, рекурсивная ссылка | Явный отказ от доказательства корреляции, не ложная полнота | Добавить, planned |
| `false` в `if-let` и `if-some` | Разные достижимые пути; регрессия точной falsy-модели | Добавить, planned |
| Пример 5: snapshot против повторного deref | Факт остаётся у snapshot, не переносится на второй deref | Добавить, planned |
| Shadowing имени и изменение тега через `assoc` | Старый факт не применяется к новому binding/значению | Добавить, planned |

Критерий готовности расширения: положительные и отрицательные проверки этой матрицы, тесты типов веток (не только наличия диагностик), независимые контрпримеры для мутации/aliasing, документированная граница отказа от доказательства. До этого `partial` не повышать.
