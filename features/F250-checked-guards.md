# F250 · Проверяемые guard-функции

## Что и зачем

В Clojure проверку формы данных часто выносят в именованный предикат. Хотим,
чтобы после `(if (record-like? x) ...)` checker знал о `x` то же, что после
проверок внутри предиката. Это позволяет переиспользовать проверки на границах
программы, не дублируя `s/valid?` и не расставляя доверенные cast.

Главное различие: «если предикат вернул truthy, значение имеет тип T» не означает
«если предикат вернул false или nil, значение не имеет тип T». Дополнительное
условие, например непустая строка, обычно делает guard односторонним.

## Текущее состояние и границы обещания

**Current:** `check.clj/narrow` возвращает два контекста для truthy/falsy ветвей.
Он распознаёт локальные символы, `some?`, `nil?`, `not`, ограниченные `and`/`or`,
`=`, `instance?`, `s/valid?` с литеральным keyword и ряд встроенных предикатов.
Для `s/valid?` положительная ветвь получает `t/ref-t`, отрицательная не меняется.
У `string?` и других `pred-narrow` отрицательная ветвь также не меняется.
Произвольный вызов пользовательской функции возвращает исходные контексты.

**Planned:** вывод и проверка постусловий пользовательских функций, хранение
проверенного summary и применение его в месте вызова. Это не реализовано.
`docs/reference.md`, §3 описывает также доверенный `{:t/guard '::record}`,
но в текущем checker нет обработки такой аннотации. Это проектный интерфейс,
а не работающая возможность. Он не должен автоматически означать «проверено».
Синтаксис явного запроса *проверяемого* guard пока не выбран.

## Примеры

Все блоки — обычный Clojure; комментарии с expected описывают контракт карточки,
а не записанный вывод запуска. `t/unknown` встречается только в quoted `:t/sig`.

### 1. Прямая проверка — current, корректный код

```clojure
(ns guards.demo
  (:require [clojure.spec.alpha :as s]
            [clojure.string :as str]))

(s/def ::label string?)
(s/def ::entry (s/keys :req-un [::label]))

(defn label-or-default
  {:t/sig '[t/unknown :-> string?]}
  [x]
  (if (s/valid? ::entry x)
    (str/trim (:label x))
    "unknown"))
;; Current: then получает ::entry, else сохраняет исходный тип x.
;; Аналогичная ветка s/valid? есть в существующем fixture n7.
```

### 2. Пользовательский guard — planned, корректный односторонний вывод

```clojure
(defn nonblank-string? [x]
  (and (string? x) (not (str/blank? x))))

(defn normalize-label
  {:t/sig '[t/unknown :-> string?]}
  [x]
  (if (nonblank-string? x)
    (str/trim x)
    "unknown"))
;; Planned: truthy => x : string?, falsy => без нового факта.
;; Current: вызов nonblank-string? не сужает x для str/trim.
;; Неизвестный для анализа результата blank? не мешает сохранить
;; string?-факт на любом truthy-пути через and.
```

### 3. Ошибочная заявка на guard и цена доверия — planned

```clojure
(defn looks-like-entry?
  {:t/guard '::entry}
  [x]
  (map? x))

(looks-like-entry? {}) ; true, хотя обязательного :label нет
;; Это НЕ доказательство truthy => ::entry.
;; :t/guard в reference означает доверенную заявку, а не проверенную.
;; Planned checked-режим должен отказать в сертификате для такого тела:
;; map? не доказывает обязательные ключи и тип значения :label.
;; Если явно разрешён trusted-режим, это доверенное допущение и расход
;; trust budget, а не успешная проверка тела. Current: guard не применяется.
```

### 4. Пограничный случай: false не исключает тип — planned

```clojure
(defn empty-on-failure
  {:t/sig '[string? :-> string?]}
  [x]
  (if (nonblank-string? x)
    x
    (str/trim x)))

(nonblank-string? "") ; false, но "" всё ещё string?
(empty-on-failure "") ; ""
;; Planned: else достижим, x остаётся string?; нельзя выводить never.
;; Current: исходный string? сохраняется, но summary guard отсутствует.
;; Даже s/valid? для (s/and string? дополнительный-предикат)
;; не даёт отрицания string?: typespec сохраняет только первый тип.
```

### 5. Пограничный случай: snapshot и повторный deref — planned

```clojure
(defn unstable-read [a]
  (if (nonblank-string? @a)
    (str/trim @a) ; guard проверил другое чтение, доказательства здесь нет
    "unknown"))

(defn stable-read [a]
  (let [x @a]
    (if (nonblank-string? x)
      (str/trim x) ; planned: доказательство относится к сохранённому x
      "unknown")))
;; Между двумя deref другой поток может заменить строку в atom на nil.
;; Это требование к будущим фактам, не утверждение о сегодняшней
;; полноте типизации atom/deref. Current не применяет оба custom guard.
```

## Алгоритм проверки (проект, не доказательство soundness)

Минимальная первая версия: одна арность, один обычный позиционный параметр,
факты о самом параметре, без обобщений, рекурсии и переносимых фактов о полях.
Не требуется запускать код проекта или реально вызывать `s/valid?`.

1. **Вход.** AST функции с позициями, разрешённые имена и aliases, окружение
   spec/signature, тип параметра, при наличии — заявка на целевой тип и режим
   checked/trusted. Сначала проверить тело обычным checker. Ошибка тела не
   превращается в успешный сертификат; `any?`, cast и trusted-источники нельзя
   считать независимым доказательством.
2. **Представление.** Использовать типы `types.clj` (`:prim`, `:ref`, `:union`,
   `:map`, `:unknown` и др.). Отдельный proposed summary содержит identity
   параметра, исходную область входов D, положительный факт T, необязательный
   отрицательный факт, происхождение/позиции и уровень доверия. Для локальных
   значений нужны identity binding, а не только имя символа: shadowing не
   должен переносить факт. Факт относится к snapshot, не к выражению deref.
3. **Разбор путей.** Вычислять гарантии отдельно для нормального truthy и
   falsy возврата (`false` и `nil` — falsy; остальные значения truthy).
   Начать с известных атомарных проверок и `not`, `and`, `or`, `if`.
   В `and` truthy требует truthy каждого операнда; в `or` достаточно одного.
   Учесть short-circuit и все пути возврата, а не искать `string?` текстом.
   Неизвестный вызов даёт обе возможности результата и не добавляет фактов.
   Исключение не является falsy-возвратом. Неподдержанное тело означает
   «не удалось доказать», а не «guard ложен».
4. **Объединение.** На последовательном пути накапливать совместимые гарантии;
   на альтернативных путях сохранять только общее гарантированное свойство.
   Например, для `(or (string? x) (keyword? x))` положительный тип — union,
   не string. Нельзя просто переиспользовать текущее присваивание типа в
   `narrow`: полноценное пересечение, противоречивость и недостижимость путей
   требуют отдельного обоснования. Первая версия должна отказываться от вывода
   там, где представление не позволяет безопасно совместить факты.
5. **Положительная проверка.** Для каждого возможного truthy-выхода проверить,
   что доказанные факты в области D влекут заявленный T. Для вывода без заявки
   экспортировать только общее доказанное свойство. `t/sub?` можно использовать
   для обычной совместимости, но его permissive-правила для unknown/any не
   являются логическим доказательством. Нужен отдельный ограниченный proof gate.
6. **Отрицательная проверка.** По умолчанию её нет. Для двустороннего guard
   отдельно доказать, что каждый falsy-выход исключает T внутри D. Для
   `s/valid?` этого обычно нельзя заключить: runtime-spec сильнее его статической
   аппроксимации, особенно при `s/and`. Не вычислять произвольное дополнение
   структурного типа. Первый выпуск может вообще не экспортировать отрицание;
   последующий — только доказанно исключать целые варианты закрытого union.
7. **Результат и применение.** Хранить checked/trusted/unproven раздельно.
   При вызове проверить арность и обычную допустимость аргумента, сопоставить
   параметр стабильному local binding и применять summary только в нужной
   ветви. Неподдержанный аргумент/вызов сохраняет исходный контекст. Повторное
   чтение atom или Java-поля не наследует факт о предыдущем чтении.
8. **Диагностики.** При явном checked-запросе непроверяемый контракт должен
   объяснять, какая импликация не доказана, с позицией заявки и проблемного
   возврата. Для добровольного inference отсутствие summary само по себе не
   ошибка. Возможные новые коды: **proposed TSP250-01** — положительное
   постусловие не доказано; **proposed TSP250-02** — отрицательное не доказано;
   **proposed TSP250-03** — неподдержанное тело/источник доказательства. Этих
   кодов сейчас нет. Ошибки использования значения остаются обычными
   диагностическими сообщениями checker, а не ошибками guard-заявки.

## Интеграция с текущим checker

- `env.clj` уже собирает `s/fdef`, `:t/sig`, hints и ограничения из `:pre`.
  Потребуется отдельное поле summary; наличие `:pre` или `:ret boolean?`
  само по себе не доказывает постусловие относительно аргумента.
- `check.clj/narrow` — точка применения summary. Её вызывают ветвления и
  short-circuit формы; результат по-прежнему пара контекстов. Не заменять
  ею анализ всех возвращающих путей функции.
- `types.clj` даёт refs, unions, members и subtype-проверку, но не готовый
  решатель импликаций. В частности, разбор `s/and` сохраняет первый компонент.
- Сначала собирать обычные declarations, затем анализировать независимые
  guard-тела, затем проверять использования. Циклы зависимостей в первой
  версии не сертифицировать. Для меж-ns интерфейса нужны сохранение summary
  и инвалидирование при изменении тела, spec или зависимого summary.

## Ограничения и нерешённые вопросы

Это эскиз ограниченного анализа, **не доказанный sound алгоритм для Clojure**.
Нужны формальные правила для truthiness, пересечений, join и недостижимости;
отдельно — проверка атомарных правил и доказательная subtype-проверка без
opt-out. Текущий `narrow` нельзя считать такой формальной базой без аудита.

Нужно выбрать checked-аннотацию, не изменяя молча смысл доверенного `:t/guard`.
Также решить: разрешать ли не-boolean результаты (например `and` с последней
строкой); как показывать неполный inference; как учитывать trust budget
транзитивно; как различать Var и локально затенённый предикат. `with-redefs`,
динамическая смена Var/spec и неизвестные макросы требуют явной границы модели.
Полиморфизм, несколько параметров/арностей, рекурсивные guards, пути ключей,
мутабельные объекты и эффектные predicates остаются за пределами первой версии.

## Конкретная матрица тестов

Все строки planned, кроме явно отмеченных существующих регрессий. Каждый
новый тест должен проверять тип обеих ветвей и отсутствие лишних диагностик,
а не только успешный exit code.

| Сценарий | Проверка |
|---|---|
| Прямой `s/valid?`, встроенный `string?` | Сохранить current: положительный тип, неизменённый else; базовый fixture `n7` |
| `some?` для локального optional-значения | Сохранить current-регрессию `n9` |
| Обёртка над `string?` | Checked summary даёт string только на подтверждённой ветви |
| `nonblank-string?`, значения `"a"`, `""`, nil | Положительный факт; false для `""` не исключает string |
| `(or (string? x) (keyword? x))` | Union в then, нельзя безопасно передать всё значение в `str/trim` |
| `map?` вместо проверки `::entry`, значение `{}` | Checked-заявка отклонена; trusted отдельно помечен |
| `(s/and string? дополнительный-предикат)` | Нельзя экспортировать отрицание string при провале spec |
| `not` и вложенный `if` с разными возвратами | Факты отражают все пути; односторонность сохраняется при инверсии |
| `and` возвращает строку / nil / false | Truthiness не подменяется проверкой равенства true |
| Cast, any, неподдержанный macro, рекурсивный guard | Нет ложного checked-сертификата; явная заявка получает объяснение |
| Snapshot `let` против двух deref | Факт применим к local; повторное чтение его не наследует |
| Shadowing параметра и затенённый `string?` | Никакого переноса по совпадению имён |
| Изменение тела/spec в другом ns | Старый summary инвалидируется |
| Ошибка checked-заявки через CLI и JSON | Совпадают код, файл, позиции заявки и причины отказа |
