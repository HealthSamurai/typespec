# F260 · Уточнения spec как номинальные свидетельства

## Что и зачем

В Clojure одна и та же строка может быть необработанным вводом, проверенным именем ветки Git или ключом конфигурации. Структурный тип `string?` этого не различает. Нужна возможность передать значение в функцию, требующую **факт успешной проверки определённого spec**, не доказывая статически регулярное выражение или пользовательский предикат.

Различаем структурную аппроксимацию spec и номинальное свидетельство. Совпадение структур двух spec не делает их свидетельства взаимозаменяемыми. Успешная проверка даёт факт о конкретном значении, а не разрешение считать все строки проверенными. Это не механизм автоматического выполнения spec при каждом вызове и не доказательство чистоты произвольного Clojure-кода.

## Current: что действительно есть

- `types.clj/parse-type` обрабатывает `s/and` **только по первому компоненту**; последующие ограничения не проверяются. `:ref` хранит имя spec, но `members` раскрывает ссылку через `env[:specs]`, и проверка совместимости структурная.
- `check.clj/narrow` уже распознаёт `(s/valid? ::spec local)` и в успешной ветке заменяет тип локальной переменной на `ref-t`; ложная ветка сохраняет контекст. Это структурное сужение, не номинальное свидетельство.
- `env.clj/pre-types` извлекает структурный тип из `:pre [(s/valid? ::spec x)]`. Это не отдельное доказательство исполнения проверки; assertions могут быть отключены.
- В прототипе нет правил номинальных свидетельств и отдельной модели результата `s/conform`. В `docs/reference.md` есть проектные `t/brand` и `t/opaque`, но в `parse-type` нет их реализации. `t/opaque` для непроницаемого Java-значения не следует смешивать с проверенным spec.
- Имеющийся тест `test/features/src/f/core.clj`, функция `n7`, проверяет структурное сужение через `s/valid?`. Номинальность он не тестирует.

Поэтому `implementation: not-implemented` остаётся верным для **этой** возможности. `status: designed` означает принятую область работы, а не завершённое доказательство корректности алгоритма.

## Примеры и ожидаемое поведение

Все блоки иллюстративные, не исполняемые snapshot-тесты. Для planned-примеров ниже предполагается будущий **явно включённый режим validated-spec**, где `::slug` в контракте требует свидетельство полного spec. Синтаксис включения ещё не выбран; обычный `s/fdef` сегодня такого обещания Typespec не даёт. Определения первого блока используются в следующих.

### 1. Корректно: проверка непосредственно перед использованием

```clojure
(ns example
  (:require [clojure.spec.alpha :as s]))

(s/def ::slug (s/and string? #(boolean (re-matches #"[a-z][a-z0-9-]*" %))))
(s/fdef publish :args (s/cat :slug ::slug) :ret string?)
(defn publish [slug] (str "/posts/" slug))

(s/fdef checked-publish :args (s/cat :raw string?) :ret string?)
(defn checked-publish [raw]
  (if (s/valid? ::slug raw)
    (publish raw)
    "invalid slug"))
```

**Current:** успешная ветка получает структурную ссылку на `::slug`, раскрывающуюся в `string?`. **Planned:** в ней появляется свидетельство именно для `raw`; вызов разрешён. В отрицательной ветке свидетельства нет. Checker не вычисляет регулярное выражение, а доверяет семантике разрешённой операции `s/valid?` при оговорённых ниже условиях.

### 2. Ошибка: структурный тип и обещание в сигнатуре недостаточны

```clojure
(s/fdef unchecked-publish :args (s/cat :raw string?) :ret string?)
(defn unchecked-publish [raw]
  (publish raw))

(s/fdef fake-validator :args (s/cat :raw string?) :ret ::slug)
(defn fake-validator [raw]
  raw)
```

**Current:** по структурным правилам `string?` совместим с аппроксимацией `::slug`; эти формы не проверяют формат. **Planned:** ошибка у аргумента `publish` и у возвращаемого `raw`: нет свидетельства. Даже литерал `"good-slug"` не получает его только по содержимому. Контракт `fake-validator` — проверяемое обязательство тела, не источник доказательства. Для внешней функции без проверяемого тела такой контракт допустим лишь как отмеченное доверенное допущение.

### 3. Граница: объединение веток, изменение значения и разные spec

```clojure
(s/def ::other-slug
  (s/and string? #(boolean (re-matches #"[a-z][a-z0-9-]*" %))))

(defn branch-and-copy [raw]
  (let [candidate (if (s/valid? ::slug raw) raw "fallback")]
    (publish candidate))) ; planned: fallback не проверен

(defn transformed [raw]
  (if (s/valid? ::slug raw)
    (publish (str raw "!")) ; planned: новое значение, старый факт неприменим
    "invalid"))

(defn other-proof [raw]
  (if (s/valid? ::other-slug raw)
    (publish raw) ; planned: проверен другой spec
    "invalid"))
```

**Planned:** все три вызова отклоняются. На слиянии веток остаются только гарантии каждого возможного результата. Текстуально одинаковые предикаты не дают равенства номинальных идентификаторов. Чистый алиас `(let [copy raw] ...)` может сохранить факт при сохранении идентичности значения; `str`, `assoc` и произвольный вызов — не алиас. **Current:** эти различия не представлены; отсутствие ошибки не означает проверенности.

### 4. `conform`: результат проверки может быть другим значением

```clojure
(s/def ::choice (s/or :text string? :count int?))

(let [input "hello"
      result (s/conform ::choice input)]
  (if (= ::s/invalid result)
    :invalid
    [input result]))
;; На runtime: ["hello" [:text "hello"]], а не ["hello" "hello"].
```

**Planned:** поддержанная модель `conform` разделяет входной тип, успешный выход и `::s/invalid`. Для этого конкретного `s/or` выход — тегированное значение, а не строка со свидетельством. Его нельзя автоматически передавать в контракт для входного `::choice` или `::slug`. Для произвольного `s/conformer` нужна отдельная модель преобразования либо честный `unknown`; полного универсального правила здесь нет. **Current:** отдельного анализа `conform` нет; показан результат Clojure, не проверенный вывод checker.

### 5. Изменяемый источник: проверен снимок, не следующий deref

```clojure
(def current-slug (atom "first"))
(let [snapshot @current-slug]
  (when (s/valid? ::slug snapshot)
    (reset! current-slug "NOT VALID")
    (publish snapshot)       ; planned: допустимо для неизменяемой строки
    (publish @current-slug))) ; planned: отклонить, это другое чтение
```

Факт относится к неизменяемому `snapshot`. Нельзя закрепить его за выражением `@current-slug` на будущее. **Current:** номинальная проверка этих двух вызовов отсутствует; пример не обещает, что остальные части модели atom уже реализованы. Для изменяемого Java-объекта даже сохранение ссылки не гарантирует сохранения свойства объекта.

## Planned: алгоритм и граница его применимости

Это план ограниченного анализа, **не sound-алгоритм для любых spec**. Первый этап должен принимать только стабильные spec над неизменяемыми значениями с явно доверенной чистотой предикатов. Без анализа эффектов это допущение, а не автоматически установленное свойство.

1. **Вход.** Разрешённый AST из `parse`, окружение `env` со spec и контрактами, структурные типы, локальные привязки и позиции исходника; отдельно — политика включения validated-spec и доверенных границ. Не выполнять проектный код при анализе.
2. **Разделить представления.** Сохранять структурный `base(S)` отдельно от требования `Validated(S-id, base)`. `S-id` должен включать идентичность декларации в стабильном снимке проекта, а не только keyword. Для локальных значений хранить `value-id → {S-id}` и происхождение факта (позиция проверки/контракт/доверенная граница). Это проектное IR, не новый уже поддержанный синтаксис типов.
3. **Проверка контракта.** При входе в функцию validated-параметр даёт предположение о параметре; каждый проверяемый вызывающий код обязан его обеспечить. Возвращаемый validated-тип создаёт обязательство для каждого нормального выхода тела. Взаимные объявления функций не превращают произвольную строку в свидетельство: необходима проверка тел, а непроверенные externs остаются границей доверия.
4. **Распознать проверку.** В `narrow` разрешать только настоящий `clojure.spec.alpha/valid?`, известный зарегистрированный spec и локальное значение допустимой стабильности. В true-контекст добавить свидетельство и совместимое структурное сужение, в false-контекст — не добавлять его. Исключение из предиката не является успешным выходом. Отрицательный результат не даёт общего типа «все значения вне этого spec». Затенённая функция с именем `valid?` свидетельств не создаёт.
5. **Перенос фактов.** `let`-алиас сохраняет `value-id`; shadowing создаёт новую привязку. Результат преобразования получает новый id без факта, пока отдельное правило сохранения свойства не доказано. При join учитывать все достижимые пути: для phi-результата сохранить только общий набор свидетельств всех входов. При циклах нужен монотонный конечный анализ до неподвижной точки; нельзя добавлять свидетельство только по одной итерации. На первом этапе неподдержанные loop/recur и эффекты должны терять факт, а не угадывать его.
6. **Совместимость.** `Validated(S, B)` можно забыть до `B`. Обратный переход запрещён без факта для того же значения и того же `S-id`; одинаковый `base` не позволяет перейти к `Validated(R, B)`. Структурную часть продолжает проверять `types/sub?`, но раскрытие `:ref` не должно стирать номинальное требование. `any`/cast/доверенный extern не считать доказательством: разрешённый escape hatch обязан сохранять отметку доверия.
7. **Conform — отдельная операция.** Для известного преобразования хранить `input/output/invalid`; только после исключения invalid раскрывать успешный output. Не выдавать выходу свидетельство входного spec. Свидетельство для исходного input разрешать лишь при отдельно обоснованной модели, не выводить его из любого непрозрачного вызова `conform`. Пользовательские conformers и композиции с эффектами остаются за границей первого этапа.
8. **Выход.** Типы выражений, факты веток и диагностики с позицией использования, ожидаемым spec, имеющимися фактами и местом их потери. В `assignable!`/`problems` проверять свидетельство до структурного успеха; переиспользовать существующий путь CLI/JSON. Не смешивать отсутствие свидетельства с несоответствием базового типа.

### Диагностики (только proposed)

- **proposed TSP260-01:** требуется свидетельство `::slug`, имеется только `string?`; предложение проверить конкретное значение через `s/valid?`.
- **proposed TSP260-02:** проверка другого spec либо потеря факта при преобразовании/join; показать origin и место потери, если они известны.
- **proposed TSP260-03:** невозможно гарантировать стабильность spec/значения или модель conform; указать неподдержанный случай и необходимость явной границы доверия.

Это будущие коды, не текущий вывод CLI. При совпадении причин нужна одна основная диагностика и пояснение, а не три ошибки на один аргумент.

## Интеграция и нерешённые вопросы

- `env.clj` должен хранить исходную декларацию, структурный тип и номинальную идентичность раздельно. Нельзя просто заменить все нынешние ссылки на spec номинальными: это сломает существующие структурные контракты. Выбор opt-in и взаимодействие с `types.edn` пока открыты.
- `check.clj/bind`, `narrow`, join выражений и проверка вызовов/возвратов должны переносить **факты о значениях**, а не метки имён переменных. Текущий `assoc-in [:locals ...] (ref-t ...)` для этого недостаточен.
- `types.clj` нуждается в представлении validated-требования и правилах union/subtyping/печати, которые не теряют его при раскрытии `:ref`. Отношение к `t/brand` ещё не решено: бренд может означать доверенное конструирование, а validated-spec — событие проверки; автоматически приравнивать их нельзя.
- `s/def` меняет глобальный реестр. Повторная регистрация, динамическая загрузка, `with-redefs` и зависимые spec делают одного keyword недостаточным. Нужны политика замороженного реестра и инвалидирование зависимых свидетельств; хеш одной декларации не решает зависимости от внешних Var и состояния.
- Предикат может читать часы/atom/файл или менять объект; утверждение «прошёл раньше» не равно «пройдёт сейчас». Нужны исследования эффектов и стабильности, либо ограниченная документированная доверенная область. Персистентная коллекция с mutable элементами не автоматически безопасна.
- `:pre` может быть отключён при компиляции; обычный `s/fdef` сам по себе не проверяет каждый runtime-вызов. Нельзя основывать безопасность внешнего ввода на включённой instrumentation или assertions без явной политики.
- Не решены обобщённые свидетельства для вложенных путей, higher-order валидаторы, межмодульная сериализация фактов и сохранение свойства при произвольных преобразованиях. В первой версии их лучше отвергать/забывать, чем заявлять доказанность.

## Конкретная матрица тестов

Все новые строки ниже — план, не утверждение о существующих тестах. Успех/ошибка относятся к opted-in validated-режиму; отдельно нужны регрессии прежнего структурного режима.

| Сценарий | Ожидаемый результат |
|---|---|
| `n7` из текущего feature fixture | Сохранить существующее структурное сужение без новых ошибок |
| Пример 1, проверка `raw` | Успех в true-ветке; нет факта в false-ветке |
| Вызов в false-ветке, без проверки и после join с непроверенным fallback | proposed TSP260-01 либо TSP260-02 у аргумента |
| `fake-validator` возвращает сырой параметр | Ошибка у return; один контракт не оправдывает тело |
| Оба плеча `if` возвращают значения с одним свидетельством | Успех для результата join |
| `let [copy raw]` после проверки; затем shadowing `raw` | Алиас разрешён; новая непроверенная привязка отклонена |
| `str`/`assoc` после проверки | Факт не переносится без отдельного правила |
| Два spec с одинаковой структурой и предикатом | Их свидетельства несовместимы |
| `not (s/valid? ...)` | Свидетельство только в соответствующей противоположной ветке |
| Затенённый `valid?`, динамический spec keyword | Нет автоматического свидетельства |
| `s/or` conform из примера 4 | Успех даёт тегированный output; invalid остаётся отдельной альтернативой |
| Непрозрачный `s/conformer` | Нет выдуманного output/свидетельства; явное ограничение |
| Пример 5: snapshot и повторный deref | Snapshot разрешён, новое чтение отклонено |
| Изменяемый объект, stateful-предикат, повторный `s/def` | Отказ в гарантии/явная граница доверия, не молчаливое сохранение факта |
| Проверка только внутри одной итерации цикла | Факт не появляется на входе/выходе без достаточного анализа |
| Отключённые assertions и непроверенный extern | Не считать runtime-доказательством; видна граница доверия |
| CLI и JSON для одной ошибки | Одинаковые код, severity, файл и позиция; объяснение origin |

Критерий готовности: unit-тесты представления и переноса фактов, интеграционные fixtures вызовов/возвратов/ветвлений, явная проверка всех доверенных допущений и работающий небольшой snapshot-пример. Нынешний `test/typespec/demo_test.clj` исполняет только блоки `clojure example` с `text output`; обычные блоки этой карточки намеренно в этот механизм не включены.

## Проверенные источники

- [Reference](../docs/reference.md): язык типов, type-only формы, сигнатуры, `:pre` и проектное правило повторного deref. Документ описывает дизайн, не весь текущий прототип.
- [types.clj](../src/typespec/types.clj): `ref-t`, `members`, `sub?`, `parse-type`.
- [env.clj](../src/typespec/env.clj): `pre-types` и сбор spec; [check.clj](../src/typespec/check.clj): `bind`, `narrow`, `problems`, `assignable!`.
- [Feature fixture](../test/features/src/f/core.clj): `n7`; [test runner](../test/typespec/demo_test.clj): маркеры и формат исполняемых карточек.
- [Flow: Opaque Types](https://flow.org/en/docs/types/opaque-types/) — прочитана документация: внутри определяющего файла underlying type прозрачен, снаружи действует непрозрачность; supertype constraint разрешает забыть номинальность, но не изготовить её из базового типа. Это источник идеи доверенной границы, **не доказательство корректности конструктора** и не готовая семантика для Clojure spec.
