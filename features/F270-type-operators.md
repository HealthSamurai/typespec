# F270 · Операторы над типами мап

## Зачем это нужно в Clojure

У одной формы данных часто несколько контрактов: полная запись, набор изменяемых полей, краткое представление для списка, значение одного поля. Ручное повторение `s/keys` расходится с оригиналом при переименовании ключей и изменении обязательности. Операторы должны строить эти контракты из одного типа, сохраняя различие между отсутствующим ключом и присутствующим `nil`.

Это операции **над типами**, не над значениями: `t/pick` не вызывает `select-keys`, а `t/omit` не удаляет данные и не обеспечивает сокрытия секретов. Тип результата описывает гарантии, но сам ничего не преобразует.

## Что есть сейчас, что предлагается

**Current:** в `types.clj/parse-type` нет ветвей для `t/pick`, `t/omit`, `t/partial`, `t/keys-of`, `t/get`. В `:t/sig` такая форма попадает в `fail`, возвращает `unknown` и через `env.clj/collect-file` получает существующую диагностику `TSP9001 not a type`. Это не поддержка оператора с неточным результатом. В `s/def` неизвестная форма обрабатывается иначе — как непрозрачный spec с `TSP9002`; type-only формы туда помещать не следует.

Есть необходимые кирпичики: `{:t :map :req {...} :opt {...}}`, ссылки `{:t :ref :name ...}`, литеральные типы и объединения. `map-sub?` различает обязательные и необязательные поля, `check.clj/read-key` добавляет `nil` при чтении необязательного поля. Поддержка обычного `(partial instance? C)` в парсере не связана с `t/partial`.

**Planned:** reference перечисляет пять форм, но не задаёт все их законы. Ниже — предлагаемый минимальный контракт для конечной явно объявленной формы `s/keys`, без union-входов, typed tail, exactness и вычисляемых ключей. Это уточнение проекта, не описание реализованного поведения.

| Форма | Предлагаемый результат |
|---|---|
| `(t/pick T k...)` | Только выбранные объявления полей, с прежними типами и обязательностью |
| `(t/omit T k...)` | Все объявления кроме выбранных; отсутствие удалённых ключей в значении не гарантируется |
| `(t/partial T)` | Все верхнеуровневые поля необязательны; их типы не меняются |
| `(t/keys-of T)` | Объединение литеральных **объявленных** ключей, включая необязательные |
| `(t/get T k)` | Тип чтения: тип обязательного поля; тип необязательного поля объединяется с `nil` |

Последние две строки требуют явного закрепления в reference: `keys-of` открытой мапы не означает множество всех ключей любого её runtime-значения; `get` здесь выбран как тип безопасного чтения, а не тип значения при доказанном наличии. Несуществующий ключ — ошибка объявления, не `nil`. Для `pick`/`omit` также предлагается отклонять незнакомые ключи, чтобы ловить опечатки.

## Примеры

Все блоки — обычный Clojure с type-only данными в цитированной `:t/sig`. Они не являются исполняемыми golden-тестами. Первое объявление задаёт общую среду для следующих блоков; `t` не нужно загружать как runtime-библиотеку. Для каждого блока с оператором **current** — `TSP9001` на неподдержанную форму, а не обещанные ниже проверки.

### 1. Корректная проекция, требуемые и необязательные поля

```clojure
(ns example.operators
  (:require [clojure.spec.alpha :as s]))
(s/def :item/id int?)
(s/def :item/title string?)
(s/def :item/note (s/nilable string?))
(s/def ::item (s/keys :req [:item/id :item/title]
                      :opt [:item/note]))

(defn brief
  {:t/sig '[::item :-> (t/pick ::item :item/id :item/note)]}
  [item]
  (select-keys item [:item/id :item/note]))
;; Planned: :item/id обязателен, :item/note необязателен и nilable.
;; Для проверки всего тела также нужна достаточная точность select-keys;
;; одной реализации нормализатора типов недостаточно.
```

### 2. Partial: пропуск допустим, nil не появляется автоматически

```clojure
(defn accept-patch
  {:t/sig '[(t/partial ::item) :-> boolean?]}
  [patch] true)
(accept-patch {})                         ; planned: OK
(accept-patch {:item/title "New title"})   ; planned: OK
(accept-patch {:item/note nil})            ; planned: OK, nil был в исходном spec
(accept-patch {:item/title nil})           ; planned: ошибка типа поля
(accept-patch {:item/id "42"})             ; planned: ошибка типа поля
;; Существующий код для несовместимого значения поля: TSP2322.
;; Partial не делает вложенные обязательные поля необязательными.
```

### 3. Omit не означает запрет ключа

```clojure
(defn accept-title
  {:t/sig '[(t/omit ::item :item/id) :-> boolean?]}
  [item] true)
(accept-title {:item/title "Hello"})       ; planned: OK
(accept-title {})                         ; planned: TSP2741, нет :item/title

(defn pass-through
  {:t/sig '[::item :-> (t/omit ::item :item/id)]}
  [item] item)
;; Planned: структурно допустимо; :item/id физически остаётся в item.
;; Нельзя использовать такой контракт как доказательство удаления поля.
```

### 4. Keys-of и indexed access: ошибка имени и nil при чтении

```clojure
(defn accept-key
  {:t/sig '[(t/keys-of ::item) :-> boolean?]}
  [k] true)
(accept-key :item/title)                   ; planned: OK
(accept-key :item/note)                    ; planned: OK, optional тоже входит
(accept-key :item/typo)                    ; planned: ошибка аргумента

(defn title-of
  {:t/sig '[::item :-> (t/get ::item :item/title)]}
  [item] (:item/title item))               ; planned: string?
(defn maybe-title
  {:t/sig '[(t/partial ::item)
            :-> (t/get (t/partial ::item) :item/title)]}
  [item] (:item/title item))               ; planned: string? | nil
(defn bad-type
  {:t/sig '[(t/get ::item :item/typo) :-> boolean?]}
  [x] true)                               ; planned: ошибка объявления типа
;; Наличие отдельного s/def :item/typo не должно легализовать последний t/get.
```

### 5. Пограничные случаи и ограничение области

```clojure
(defn empty-projection
  {:t/sig '[::item :-> (t/pick ::item)]}
  [item] {})
;; Planned: мапа без объявленных полей, не exact-empty-map и не nil.

(defn impossible-key
  {:t/sig '[(t/keys-of (t/pick ::item)) :-> boolean?]}
  [k] true)
;; Planned: параметр t/never; ни один конкретный ключ ему не подходит.

(defn unsupported-source
  {:t/sig '[(t/partial (s/nilable ::item)) :-> boolean?]}
  [x] true)
;; Planned MVP: явная ошибка неподдержанного входа, не снятие nil молча.
;; Аналогично исключены (t/keys-of (s/map-of keyword? string?))
;; и (t/get ::item k), где k — переменная, а не литеральный ключ.
```

## Пошаговый алгоритм проверки (planned MVP)

Это алгоритм конечных преобразований объявленной формы, а не доказательство soundness всего checker. Он намеренно не использует произвольные вычисления Clojure и не обещает решение для recursive/union/generic типов.

1. **Вход и разбор.** Получить форму типа, позицию объявления, aliases/imports и собранную таблицу specs. Распознать оператор в `parse-type`; проверить арность (`partial`/`keys-of`: один тип, `get`: тип и один ключ, `pick`/`omit`: тип и ноль или больше ключей). Ключи — литеральные keywords. Дубликаты `pick`/`omit` можно убрать без изменения смысла. Создать отложенный узел оператора с исходной формой/позицией: разрешать ссылки во время разбора одного файла слишком рано.
2. **Разрешение и проверка области.** После построения environment нормализовать операторы изнутри наружу. По ссылкам раскрывать только путь до внешней формы мапы. Отслеживать стек разрешаемых ссылок/операторов и лимит работы; цикл на пути к форме — диагностируемый неподдержанный случай. Ссылки в значениях полей не раскрывать рекурсивно: для shallow partial это не нужно. Неизвестная ссылка, `unknown`/`any`, union, nullable-вход, `map-of`, примитив, exact/merge/intersection или недоступная форма не превращаются в пустую мапу.
3. **Представление фактов.** После разрешения получить `M = (R, O)`, где `R` и `O` — непересекающиеся таблицы ключ → тип, `K = dom(R) ∪ dom(O)`. Если объявление одного ключа противоречиво, отклонить его, а не выбирать случайную обязательность. Это факты объявления, не факты runtime-присутствия. Сохранить происхождение поля для сообщений; глобальный spec ключа не добавляет его в `K`.
4. **Проверки ключей.** У каждого ключа `pick`, `omit`, `get` проверить принадлежность `K`. Для `:req-un`/`:opt-un` использовать реальный ключ мапы (`:id`), а тип брать из сохранённой ссылки (`:item/id`). На ошибке перечислить допустимые ключи и показать позицию исходного оператора.
5. **Вычисление.** Для множества выбранных ключей `S`: `pick` ограничивает обе таблицы на `S`; `omit` удаляет `S` из обеих; `partial` возвращает `R' = {}`, `O' = R ∪ O`. `keys-of` возвращает `union(lit(k) for k in K)`; для пустого `K` — `never`. `get` возвращает `R[k]` либо `union(O[k], nil)`. Значения полей и их ссылки сохраняются, вложенные мапы не переписываются. Порядок печати должен быть стабильным.
6. **Выход и интеграция.** Передать нормальную форму `:map`, `:union`, `:lit` или `:never` существующей проверке аргументов/возвратов. Исходное выражение оставить для объяснения типа. `types.clj/show` сейчас печатает мапы через списки имён ключей: для типов с преобразованными вложенными значениями этого недостаточно; MVP должен проверить round-trip печати и не терять семантику. Ошибка нормализации должна оставлять диагностику и recovery-тип, но не считаться успешно доказанным контрактом.
7. **Диагностики.** Сейчас неподдержанная форма в сигнатуре — `TSP9001`; после реализации несовместимые значения используют существующие `TSP2322`, недостающие поля — `TSP2741`. Для новых проверок предлагаются только **proposed TSP270-01** (арность/нелитеральный ключ), **proposed TSP270-02** (ключ не объявлен), **proposed TSP270-03** (неподдержанная форма входа, неразрешимая ссылка или цикл с уточнением причины). Эти коды ещё не существуют; источник ошибки должен отличаться от последующих каскадных ошибок использования.

### Точки подключения к прототипу

- `env.clj/build` собирает specs и сигнатуры; нормализатору нужен полный environment, включая forward references. Нельзя ограничиться новой веткой `parse-type`, которая попытается разрешить всё немедленно.
- `types.clj/members` и `resolve-t` уже раскрывают ссылки, но recovery через `unknown` не годится как успешное доказательство применимости оператора. Нужен отдельный результат нормализации с причиной отказа и защитой от циклов.
- `check.clj/lookup-key` допускает fallback к глобальному spec квалифицированного ключа, даже когда его нет в форме. Для type-level `get` это правило намеренно не используется: иначе ошибка имени зависит от посторонних specs.
- `read-key`, `map-sub?`, `fresh-problems` полезны для проверки нормализованного результата, но проверки свежих литералов уже имеют свои правила лишних ключей. Операторы не должны незаметно изменять их или объявлять любую мапу закрытой.

## Ограничения и открытые вопросы

- **Открытые мапы.** `keys-of` даёт только объявленные ключи. Без отдельного доказательства закрытости нельзя утверждать, что результат runtime `(keys x)` всегда имеет этот тип. `omit` убирает гарантию/ограничение поля, но не устанавливает факт его отсутствия.
- **Optional против nil.** Для `get` выбрана семантика чтения; если понадобится тип присутствующего значения, нужен отдельный явно названный режим/оператор. Сам `partial` не добавляет nil.
- **Union, intersections и merge.** Распределение операторов, пересечение или объединение множеств ключей и конфликты типов требуют отдельных правил и проверки soundness. Текущий `members` сливает `:merge` таблицами, а `parse-type` у `t/and` и `t/exact` берёт второй элемент; нельзя на этой основе обещать корректную поддержку этих случаев. Требуется сохранять такие конструкции до проверки области MVP, иначе неподдержанный вход будет скрыт.
- **Рекурсия.** Ссылка на рекурсивный тип внутри значения поля может остаться ссылкой. Цикл разрешения самой формы, вложенные операторы с рекурсией, гарантии завершения и устойчивое кеширование требуют исследования; до него — явный отказ с причиной, не бесконечное раскрытие.
- **Не входят в MVP:** deep partial, row polymorphism, generics, строковые/вычисляемые ключи, typed tails, records с сохранением номинальной идентичности, перенос операторов в runtime spec и автоматическая генерация валидаторов.
- **Пределы существующего checker.** `sub1?` разрешает `unknown` с обеих сторон; отсутствие второй ошибки после `TSP9001` не означает успех. Для доказательства корректности преобразований нужны законы подтипизации, отдельная политика recovery и тесты всего пути, а не только снимки печати.

## Конкретная матрица тестов

Все planned-строки — задания на будущие тесты, не заявление о наличии покрытия. Каждый тест должен проверять и тип, и диагностики; current-регрессия не должна молча поменяться на успех без новых проверок.

| Слой | Случай | Ожидаемый результат |
|---|---|---|
| Current parser/env | Каждая из пяти форм внутри `:t/sig` | `TSP9001`, recovery `unknown` |
| Planned parser | `partial` без аргумента/с двумя; `get` без ключа; ключ-символ | proposed TSP270-01, без исключения JVM |
| Planned normalization | `pick` обязательного и optional поля | Сохранены соответствующие `R`/`O` и типы |
| Planned normalization | `pick T`, `omit T` без ключей | Пустые таблицы / исходные таблицы соответственно |
| Planned normalization | Повтор ключа в `pick`/`omit` | Тот же результат, что при одном ключе |
| Planned normalization | `partial` дважды; поле с вложенной мапой | Идемпотентность; вложенная обязательность не меняется |
| Planned checker | `{}`, корректный patch, nil в non-nilable поле | Успех, успех, `TSP2322` |
| Planned checker | После `omit` отсутствует оставшееся обязательное поле | `TSP2741` |
| Planned checker | Полная запись передана как `omit` через переменную | Допустима; нет обещания удаления ключа |
| Planned normalization | `keys-of` с optional; пустой результат `pick` | Литералы всех объявленных ключей; `never` |
| Planned checker | Несуществующий литерал передан в `keys-of` | Ошибка аргумента, не принятие любого keyword |
| Planned normalization | `get` required/optional/nilable-required | `V` / `V | nil` / исходный nilable-тип |
| Planned normalization | `get`/`pick`/`omit` с незнакомым ключом; для него есть глобальный spec | proposed TSP270-02 в обоих вариантах |
| Planned normalization | `s/keys :req-un [:item/id]`: запрос `:id` и `:item/id` | Успех со ссылкой на тип `:item/id`; ошибка имени |
| Planned resolution | Forward reference, рекурсивное значение поля | Разрешение после сборки env; shallow результат без обхода значения |
| Planned resolution | Цикл внешней формы, отсутствующий ref, превышение лимита | Диагностика причины; завершение без stack overflow |
| Planned scope | Union, nilable, map-of, exact, and, merge | proposed TSP270-03, без молчаливого стирания оболочки |
| Planned integration | Сигнатура `brief` и реальный `select-keys` | Проверить отдельно вывод выражения и совместимость с нормализованным типом |
| Planned printing | Печать → повторный разбор, стабильный порядок, исходная позиция ошибки | Эквивалентный тип и воспроизводимая диагностика |

Готовность: реализованы нормализация и её ограничения, тесты матрицы, согласованные правила `keys-of`/`get` в reference, затем отдельный исполняемый пример карточки. Текущие тесты `test/features/src/f/core.clj` и `test/examples/src/ex/more.clj` показывают базовые `s/keys` и optional-поля, но не реализацию этих операторов. `demo_test.clj` запускает карточки только с особыми fences `clojure example`/`text output`; здесь они намеренно не используются.
