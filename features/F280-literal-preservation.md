# F280 · Литералы и проверка без потери типа

## Зачем это нужно в Clojure

Таблицы маршрутов, описания команд и настройки сборки часто задаются обычными неизменяемыми maps. Автору нужны две разные гарантии: данные соответствуют общему контракту, а дальнейший вывод помнит конкретные ключи и значения. Если проверка превращает `:get` в `keyword?`, теряется возможность передать его функции, принимающей только `#{:get}`, или различать варианты по тегу. Если вместо проверки использовать cast, ошибка в данных останется незамеченной.

Предложение разделяет **сохранение точности** (`t/const`) и **проверку совместимости без замены выведенного типа** (аналог `satisfies`). Ни одна операция не должна выполнять runtime-валидацию, вычислять пользовательский код или делать изменяемый объект неизменяемым.

## Что уже есть, а что только предлагается

По текущим `parse.clj`, `check.clj` и `types.clj`:

- Числа, строки и keywords выводятся как `{:t :lit :val v}`; `nil` имеет отдельный тип. Boolean-выражение выводится как `boolean?`, не singleton.
- Map с keyword-ключами получает `:req`, `:opt {}`, `:fresh true`, `:inferred true`; значения в ней обычно сохраняют литеральные типы. Это не обещание точного набора runtime-ключей: inferred map остаётся открытой.
- `bind-pairs` снимает `:fresh`, но не расширяет литерал. Поэтому `(let [n 1] n)` сейчас сохраняет `1`. Это расходится с проектным правилом «в let расширять до int?» в §3 reference.
- Элементы vector/set расширяются через `widen`; скалярный литеральный результат функции без объявленного return тоже расширяется. `widen` обрабатывает литералы и union, но не рекурсивно все поля map.
- Парсер узнаёт `#_(t/const)` и прикрепляет директиву к следующему AST-узлу. В `infer` нет ветки, реализующей её семантику: само распознавание не означает поддержку.
- Проверки совместимости существуют (`problems`, `assignable!`, `t/sub?`), но отдельной операции «проверить и вернуть исходный тип» нет. `t/cast` заменяет тип и увеличивает trust-счётчик.

`implementation: not-implemented` относится именно к новым операциям, а не к отсутствию литеральных типов вообще. Ниже `t/satisfies` — **предлагаемое имя**, ещё не часть API. Сейчас такой reader-discard не распознаётся как директива и не проверяет контракт.

## Примеры и ожидаемое поведение

Это обычные иллюстрации, не golden-тесты. Каждый пример независим; `t/*` внутри `#_` не требует runtime namespace.

### 1. Current: сохранение литерала в локальной map

```clojure
(ns literal.current)

(defn only-get {:t/sig '[#{:get} :-> string?]} [method]
  "read")

(let [route {:method :get :path "/items"}]
  (only-get (:method route)))
;; CURRENT: :method выводится как литерал :get, вызов совместим.
;; Это ещё не проверка всей map по контракту маршрута.
```

### 2. Planned: проверить форму, не расширяя значение

```clojure
(ns literal.valid (:require [clojure.spec.alpha :as s]))
(s/def ::method #{:get :post})
(s/def ::path string?)
(s/def ::route (s/keys :req-un [::method ::path]))

(defn only-get {:t/sig '[#{:get} :-> string?]} [method] "read")

(let [route #_(t/satisfies ::route)
            {:method :get :path "/items"}]
  (only-get (:method route)))
;; PLANNED: проверить ::route; результат всё ещё содержит :method = :get.
;; Нельзя подменить результат типом ::route: тот допускает также :post.
;; CURRENT: t/satisfies игнорируется; успешный вызов не доказывает контракт.
```

Для keyword-map отдельный `t/const` здесь не нужен: точность уже выводится. Проверка совместимости не обязана сама запрещать widening во всех конструкциях.

### 3. Planned: намеренные ошибки в контракте

```clojure
(ns literal.invalid (:require [clojure.spec.alpha :as s]))
(s/def ::method #{:get :post})
(s/def ::path string?)
(s/def ::route (s/keys :req-un [::method ::path]))

#_(t/satisfies ::route) {:method :delete :path "/items"}
;; PLANNED: TSP2322 для :method, actual :delete, expected #{:get :post}.
#_(t/satisfies ::route) {:method :get}
;; PLANNED: TSP2741, отсутствует обязательный :path.
;; CURRENT: именно этот контракт не проверяется — директива отброшена.
;; Здесь ключи unqualified: их значения не проверяются автоматически
;; как значения одноимённых qualified spec-ключей.
```

Названные коды уже существуют в `fresh-problems`; их применение новой директивой пока только планируется. Ошибка не должна превращаться в успешный cast к `::route`.

### 4. Пограничный случай: литералы в vector

```clojure
(ns literal.collection)
(defn only-get {:t/sig '[#{:get} :-> string?]} [method] "read")

(let [methods #_(t/const) [:get :post]]
  (only-get (first methods)))
;; CURRENT: t/const не действует; элементы расширены до keyword?.
;; Вызов несовместим с #{:get} (TSP2345).
;; PLANNED, минимальная модель: элементы #{:get :post}, без обещания
;; позиции/длины; first может дать nil. Вызов всё равно отклоняется.
;; Точный вывод :get для first требует отдельной поддержки tuple/non-empty,
;; а не только сохранения литералов.
```

### 5. Пограничный случай: точность не равна закрытости map

```clojure
(ns literal.open (:require [clojure.spec.alpha :as s]))
(s/def ::method #{:get :post})
(s/def ::path string?)
(s/def ::route (s/keys :req-un [::method ::path]))

(let [route {:method :get :path "/items" :cache true}]
  #_(t/satisfies ::route) route)
;; PLANNED: открытый структурный контракт допускает :cache;
;; результат сохраняет поле :cache с boolean?, не singleton true в MVP.
;; CURRENT: проверки директивой нет; локальная map уже не :fresh.
;; Для запрета любых лишних полей нужен отдельный exact-контракт.
```

## Предлагаемый алгоритм MVP

Это проект ограниченного механизма, не доказанный sound алгоритм для всего Clojure. MVP сохраняет поддержанные скалярные литералы внутри immutable map/vector/set; не обещает positional types, исполнение предикатов или восстановление утраченных значений.

1. **Вход.** AST выражения с координатами и reader-discard директивами, окружение spec/vars/locals, параметры checker. Добавить согласованное имя `t/satisfies` в `parse/directive-heads`. Проверить арность: у `t/const` нет аргументов, у `t/satisfies` один тип. Неизвестный/неподдержанный тип нельзя молча считать проверенным `unknown`; отказ в проверке с отдельной proposed `TSP280-01` («контракт не поддержан»).
2. **Разобрать контракт.** Использовать существующий путь `parse-directive-type` и разрешение spec-ссылок, сохраняя исходное имя контракта для сообщения. Ограничить MVP уже поддержанными проверяемыми типами. Требуется отличать ошибку разрешения от намеренно написанного `t/unknown`.
3. **Вывести исходный тип A один раз.** Обычный `t/satisfies` не передаёт ожидаемый тип внутрь выражения: иначе ожидаемый union может изменить вывод. `t/const` включает локальный режим сохранения литералов при обходе синтаксических immutable коллекций; в этом режиме не вызывать `widen` для их элементов. Не протаскивать режим в тела вызываемых функций. У символа брать известный тип, не угадывать значение по имени.
4. **Представление.** Переиспользовать `:lit`, `:union`, `:map` с `:req/:opt`, `:coll` с `:kind/:of`, `:nil`. Хранить происхождение `:fresh` отдельно по смыслу от точности: const не делает bound map свежим литералом. Для vector/set MVP сохраняет union типов элементов, а не всю коллекцию как singleton. Boolean остаётся `boolean?` до отдельного решения.
5. **Проверить A против E.** Использовать `problems`/`assignable!` и `t/sub?`, учитывая strict-nil. Для fresh map действуют существующие проверки обязательных полей, значений и эвристика лишних ключей. Для связанной map — обычная структурная совместимость. Не вводить скрытую exact-семантику. Обязательный дополнительный gate: `any`/неизвестные части и доверенные cast не должны выдаваться за независимо доказанное соответствие; точную политику отказа/coverage нужно согласовать до реализации.
6. **Результат.** При успехе вернуть A, не E и не искусственное пересечение A с E. Не повышать trust-счётчики. После ошибки оставить A для продолжения анализа и отметить неуспех проверки; не выдавать значение за E. При обычном связывании сохранить существующее снятие `:fresh`. Не менять глобальное правило widening в рамках этой карточки без согласования с reference.
7. **Диагностики.** Привязать ошибки к выражению, по возможности к проблемному значению поля; выводить путь поля, actual и expected. Переиспользовать существующие `TSP2322`, `TSP2741`, `TSP2353`, fallback `TSP2345` и nil-диагностики. Для некорректной формы директивы зарезервировать только proposed `TSP280-02`. Не подавлять независимые ошибки тела и не дублировать уже выданную ошибку qualified spec-ключа.
8. **Зафиксировать тип.** Вызвать существующий `record!` с сохранённым A. Проверять не только отсутствие диагностики, но и тип в `:types`: без этого реализация, ошибочно возвращающая E, тоже пройдёт позитивный тест.

## Интеграция и ограничения

Основные точки изменения при реализации: `parse/directive-heads`, обработка директив в `check/infer`, места widening в `infer*`, существующие `parse-directive-type`, `problems` и `record!`. Модель литералов и базовая совместимость уже находятся в `types/lit`, `types/lit-prim`, `types/sub?`. Эта карточка не меняет их сейчас.

До реализации нужно решить:

- **Порядок директив и hints.** Сейчас hint может заменить выведенный тип до cast/any. MVP следует отвергать конфликтующие const/satisfies/cast/any на одном узле (proposed `TSP280-02`), пока не определено, какой тип проверяется. Нельзя обещать сохранение до-hint типа без изменения этого пути.
- **Вложенные ошибки.** Inference уже восстанавливается после неверного значения qualified ключа, подменяя его spec-типом. Новый механизм не должен объявлять такой результат безошибочно проверенным. Нужна связь с уже выданными diagnostics, а не лишь финальный `sub?`.
- **Unknown и доверие.** Общая assignability не равна доказательству runtime-соответствия; проверить её shortcuts и вложенные any/platform-типы. Не обещать soundness на основе одного вызова `sub?`.
- **Границы const.** Он не сужает результат произвольного вызова с `keyword?` до конкретного keyword, не замораживает atom/Java object, не восстанавливает потерянные литералы у связанного значения. Maps со строковыми/вычисляемыми ключами сейчас не получают ту же структуру, что keyword-maps; их расширение — отдельная работа.
- **Стоимость.** Большие литеральные unions требуют лимита/нормализации. При лимите нельзя незаметно расширить тип и одновременно заявить полное сохранение; политика диагностики пока открыта.
- **Дизайн против кода.** Widening в let и boolean-singletons нужно согласовать отдельно. Не копировать правила TypeScript целиком: readonly-модификатор не имеет того же смысла для persistent collections Clojure.

## Конкретная матрица тестов

| Случай | Ожидание current | Приёмка planned |
|---|---|---|
| `let` с `1`, `"x"`, `:get` | singleton сохраняется | regression, решение widening явно зафиксировано |
| Пример 1, чтение map-поля | вызов совместим | тот же тип и отсутствие ошибок |
| Пример 2 | директива не проверяет контракт | контракт проверен; поле остаётся `:get`, trust не растёт |
| Пример 3, неверное значение | нет проверки discard-контракта | `TSP2322`, actual/expected и позиция |
| Пример 3, пропущен ключ | нет проверки discard-контракта | `TSP2741` с именем `:path` |
| Пример 4 | `keyword?`, ошибка вызова | union литералов; вызов по-прежнему ошибочен |
| Пример 5 | открытая inferred map | дополнительный ключ и его тип сохранены |
| Fresh map с опечаткой `:methdo` | проверить существующую эвристику отдельно | `TSP2353` и подсказка, без закрытия всех maps |
| Вложенные keyword-maps и vector/set | widening коллекций | рекурсивное сохранение, без tuple-обещаний |
| Boolean и nil внутри const | `boolean?` и nil-тип | те же типы в MVP, без ложного singleton |
| Const над символом широкого типа | широкое значение | не восстанавливать литерал |
| Неразрешённый контракт / неверная арность | discard не гарантирует ошибку | proposed `TSP280-01` / `TSP280-02` |
| Qualified ключ с неверным значением | уже есть диагностика inference | не объявлять успех, не дублировать ошибку |
| Any/unknown/cast в поддереве | существующие trust/compatibility правила | явный отказ от обещания доказанного соответствия |
| Повторный запуск с тем же AST | детерминированный результат | одинаковые типы/диагностики, без двойного inference |

Критерий готовности: отдельные проверки типов результата, диагностик и trust; негативные тесты обязаны отличать реально действующую директиву от молча отброшенного reader-discard. Текущий `test/typespec/demo_test.clj` проверяет golden-карточки только с fence `clojure example`; обычные fences этой карточки не считаются исполненными тестами. В существующем `test/features/src/f/core.clj` есть пример cast, но это не покрытие const/satisfies.
