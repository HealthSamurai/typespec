# F290 · Доменные brands

## Зачем

В Clojure идентификатор пользователя, заказа и имя файла часто представлены одной строкой. Проверка `string?` не замечает перестановку аргументов. Brand добавляет статическую идентичность поверх представления: значение остаётся строкой, но checker различает его назначение. Это полезно для API, ключей кеша, денежных величин и единиц измерения без обязательных wrapper-records.

Brand не доказывает существование объекта, формат строки, права доступа или успешную проверку spec. Это не runtime-tag и не секрет: маркировка стирается, обычные операции Clojure её не видят. Свидетельства валидации относятся к F260, а не к этой карточке.

## Current: что действительно есть

В `types.clj/parse-type` нет ветви `:t/brand`; нет и соответствующего представления или печати в `show`. Неизвестная форма вызывает `:fail` и превращается в `t/unknown`. В `env.clj/collect-file` для `:t/sig` это **TSP9001**, для непрозрачного тела `s/def`/`s/fdef` — предупреждение **TSP9002**. Это не проверка несовместимости brands.

`check.clj/infer` уже понимает reader-discard директиву `#_(t/cast T)`, считает её границей доверия и заменяет тип выражения. Но brand в целевом типе пока не разбирается. `main.clj/run-check` загружает конфигурацию и исходники, а `env.clj/build` собирает spec/signatures; загрузка `typespec/types.edn` и включение brands флагом здесь не реализованы. Флаг `:brands` и sidecar-файл в reference — дизайн, не действующий интерфейс.

Особенно важно: `types.clj/sub1?` сейчас разрешает исходный `unknown` как любой тип. Поэтому отсутствие последующей ошибки после нераспознанного brand не означает доказанную совместимость.

## Примеры: целевой контракт, не golden-тесты

Во всех примерах `t/brand` — **данные языка типов**, а не исполняемая функция. Формы в `:t/sig` цитируются; директива `#_` не выполняется Clojure. Далее planned означает предлагаемое поведение после реализации. Эти блоки намеренно не помечены `example/output`.

### 1. Корректная передача и забывание маркировки

```clojure
(ns example.brands)

(defn user-id->text
  {:t/sig '[(t/brand string? :user/id) :-> string?]}
  [id]
  (let [saved id] saved))

(defn forward-user-id
  {:t/sig '[(t/brand string? :user/id)
            :-> (t/brand string? :user/id)]}
  [id]
  (let [saved id] saved))
```

**Planned:** оба тела проходят. Локальный binding сохраняет brand; branded string можно передать потребителю обычной строки. Обратное направление не разрешается. **Current:** формы brand в сигнатурах дают TSP9001, проверенной brand-гарантии нет.

### 2. Ошибка: одинаковое представление не делает brands совместимыми

```clojure
(defn load-user
  {:t/sig '[(t/brand string? :user/id) :-> string?]}
  [id] id)

(defn wrong-owner
  {:t/sig '[(t/brand string? :order/id) :-> string?]}
  [order-id]
  (load-user order-id))

(defn plain-string-is-not-id
  {:t/sig '[string? :-> string?]}
  [text]
  (load-user text))
```

**Planned:** ошибка у `order-id` в первом вызове и у `text` во втором. Сообщение показывает actual/expected, оба brand-id или отсутствие brand и место объявления параметра. Можно использовать существующий TSP2345 с более точной причиной; это предложение, не существующая brand-диагностика. **Current:** TSP9001 на brand-формах; требовать двух ошибок несовместимости от прототипа нельзя.

### 3. Явное создание — граница доверия, а не валидация

```clojure
(defn assume-user-id
  {:t/sig '[string? :-> (t/brand string? :user/id)]}
  [text]
  #_(t/cast (t/brand string? :user/id)) text)

;; На runtime получится ровно "", без проверки формата и существования:
(assume-user-id "")
```

**Planned:** разрешённый явный unsafe cast, отражённый в счётчике доверия. Функция — конструктор по соглашению; checker не выводит её корректность из названия или объявления результата. Без cast возврат обычной строки должен быть ошибкой. Runtime-валидацию при необходимости пишет автор, но она сама по себе не создаёт brand. **Current:** директива cast есть, целевой brand не поддержан. Политика допустимых brand-конструкторов ещё требует решения.

### 4. Пограничный случай: nil и преобразование строки

```clojure
(defn maybe-id->text
  {:t/sig '[(s/nilable (t/brand string? :user/id)) :-> string?]}
  [id]
  (if (some? id) id "missing"))

(defn rewrite-id
  {:t/sig '[(t/brand string? :user/id)
            :-> (t/brand string? :user/id)]}
  [id]
  (str id "-copy"))
```

Здесь `s` — обычный alias `clojure.spec.alpha` в namespace. **Planned:** первый пример проходит: удаление nil сохраняет brand оставшейся ветви. Второй отклоняется: `str` создаёт обычную строку, а не новый подтверждённый идентификатор. Даже `(string? id)` не позволяет восстановить потерянный brand. **Current:** brand-формы не разбираются; имеющиеся правила nil/narrowing не дают поддержки brands автоматически.

### 5. Единицы: разные brands, но не готовая размерностная алгебра

```clojure
(defn seconds->text
  {:t/sig '[(t/brand double? :unit/seconds) :-> string?]}
  [seconds] (str seconds))

(defn wrong-unit
  {:t/sig '[(t/brand double? :unit/metres) :-> string?]}
  [metres]
  (seconds->text metres))

(defn add-seconds
  {:t/sig '[(t/brand double? :unit/seconds)
            (t/brand double? :unit/seconds)
            :-> (t/brand double? :unit/seconds)]}
  [a b]
  (+ a b))
```

**Planned минимальный вариант:** `wrong-unit` отклоняется. `add-seconds` тоже не доказан: стандартный числовой результат `+` не получает brand автоматически. Для сложения, умножения и конверсий нужны отдельные контракты и проверенные правила; строка «units are a special case» в reference не является их алгоритмом. **Current:** brand-формы дают ошибки разбора типов.

## План проверки и интеграции

Ниже — проект минимального механизма для неизменяемых скалярных значений, **не доказательство soundness для всего Clojure**. Сначала нужно закрыть пути, где `unknown`, hints, Java или внешние контракты незаметно превращаются в доверенный тип.

1. **Вход.** AST с позициями, явные `:t/sig`/контракты, таблица именованных типов и настройка расширения. В первой реализации можно ограничиться inline-сигнатурами; sidecar не обязателен и не должен молча считаться загруженным. При выключенном расширении сообщать о неподдержанной форме, а не снимать оболочку до базового типа.
2. **Разбор.** Добавить в `parse-type` форму строго из трёх элементов `(t/brand Base :qualified/id)`. Проверить base и квалифицированный keyword. Предлагаемое IR: `{:t :brand :base Base :id :user/id}`; это новый вариант, не текущий формат. На первом этапе запретить вложенные brands и mutable/container bases до определения их семантики. Некорректный тип помечать непроверенным, не допускать его как доказательство.
3. **Идентичность и факты.** Для минимальной модели identity — точный qualified keyword, не имя переменной и не путь поля. Ссылки `:t :ref` разрешать через существующее окружение, сохраняя оболочку. Хранить тип binding и provenance явного cast; не добавлять факта `validated-spec`. Предлагается отклонять повторное объявление одного id с несовместимым base. Публичный keyword допускает создание того же brand в другом namespace: это не закрытый opaque token.
4. **Совместимость.** Для `B(S,k) -> B(T,k)` проверить `S <: T`; при разных id отказать. Для `B(S,k) -> T`, где ожидаемый тип не brand, забыть оболочку и проверить `S <: T`. Для обычного `S -> B(T,k)` отказать независимо от сходства значений. `never` допустим как недостижимый поток. `unknown` требует уточнения, `any` и cast — только явно учитываемый отказ от гарантии. Эти правила должны быть встроены в `sub1?`/`sub?` с учётом порядка ветвей, а не добавлены после нынешнего безусловного принятия unknown.
5. **Union и потоки.** Сохранить оболочку при `let`, аргументах, возврате и выборе ненулевой ветви. Проверять все исходные альтернативы union против допустимых целевых; разные brands не склеивать по base. В `union`, `members`, `resolve-t`, `remove-nil`, `narrow` проверить, что brand не исчезает. Предикат базового типа не создаёт brand; если сужение внутри brand не поддержано, оставить исходный безопасный тип или явно сообщить ограничение, не придумывать новое свидетельство.
6. **Операции.** Вызовы идут через `call-fn`, `arg-problems` и `assignable!`; проверки возврата должны применять то же отношение. Обычная функция с результатом `string?` возвращает строку без brand. Сохранение brand через generic identity или контейнер возможно только при корректном полиморфном контракте, не через эвристику имени функции. Создание brand разрешается лишь на явно выбранной границе доверия; тело функции с branded результатом проверяется, а не считается конструктором автоматически.
7. **Результат и диагностика.** `show`, `sig` и `type-at` печатают `(t/brand Base :id)`, а не только base. Ошибка передачи показывает позицию аргумента, actual/expected и причину («другой brand» либо «brand отсутствует»). TSP2345 уже есть для общей несовместимости; новые специфические проверки могли бы использовать **proposed TSP290-01** (некорректное объявление/конфликт base) и **proposed TSP290-02** (неподдержанная форма brand или выключенное расширение). Непроверенные участки и trust-casts видны отдельно от успешных проверок.

## Ограничения и решения до реализации

- Не выбран синтаксис регистрации доверенных конструкторов. Минимальный путь — существующая явная cast-директива, но её произвольная сила остаётся пользовательским допущением.
- Brand должен переживать лишь операции, сохраняющие доказанный контракт. Нужен аудит widening, объединения ветвей, destructuring, hints, межфайловых сигнатур и Java interop; простого нового case в parser недостаточно.
- JSON/EDN-сериализация не сохраняет статическое свидетельство. Повторное чтение требует нового контракта на границе. Имя ключа `:user/id` само по себе не маркирует произвольную строку.
- Модель с keyword-id открытая, а не generative/opaque: одинаковый keyword в двух библиотеках обозначает тот же brand. Конфликты версий и bases требуют проектной политики. Вложенные brands, пересечения и branded mutable values пока вне минимального алгоритма.
- Units требуют отдельного исследования правил числовых операций, widening и размерностей. Здесь обещается только различение номинальных меток, не вывод единиц и не контроль масштаба.
- `any`, casts и непроверенные внешние объявления ограничивают гарантию. До исправления поведения unknown и исследования взаимодействия с narrowing нельзя объявлять описанный механизм sound.

## Конкретная матрица тестов

Все строки с brand — **планируемые тесты**, если явно не написано current. Будущий набор должен проверять и диагностики, и результирующие типы, а не только отсутствие ошибок.

| Слой / вход | Ожидаемый результат |
|---|---|
| Current: brand в `:t/sig` | TSP9001; тип не считается проверенным brand |
| Current: brand в `s/def` | TSP9002; fallback unknown, не доказательство |
| Parser: корректный base + qualified id | IR brand, round-trip через `show` без потери id |
| Parser: отсутствующий id, лишний аргумент, unqualified id | Отказ с позицией формы |
| Config: расширение выключено | Явная неподдержка, без тихого превращения в base |
| `B(string,user) -> B(string,user)` | Успех, включая let и возврат |
| `B(string,order) -> B(string,user)` | Ошибка на аргументе, оба id в сообщении |
| `string?` или литерал `"u1" -> B(string,user)` | Ошибка: нет brand |
| `B(string,user) -> string?` | Успех; обратное преобразование не выводится |
| Один id и несовместимые bases | Ошибка объявления, не случайная совместимость |
| `nil | B(string,user)` после `some?` | В then только B, в else nil; brand не стирается |
| `B(user) | B(order) -> B(user)` | Отказ; ветвь order не потеряна при union |
| `(string? x)` для обычной строки/unknown | Не создаёт user-id |
| Явный cast / конструктор без cast | Первый учитывается как trust; второй отклоняется |
| `(str branded "suffix")` | Обычная строка; branded возврат отклоняется |
| Metres в seconds; `+` над seconds | Несовместимость; без отдельного правила результат + не branded |
| any / unknown / never в branded позиции | Явный opt-out / отказ без уточнения / успех для недостижимого потока |
| EDN round-trip, hints, внешний вызов | Не создают brand без явно учтённой доверенной границы |
| Вложенные brands, mutable base | Явное ограничение минимальной реализации |

В текущем `test/typespec/demo_test.clj` карточки исполняются только при специальных fences `clojure example` и `text output`; здесь их нет. В `test/features/src/f/core.clj` проверяется обычный cast в `string?`, не branded cast. После реализации нужны отдельные unit-тесты parser/subtyping и интеграционные проверки позиций, trust и `sig/type-at`; затем можно сделать примеры исполняемыми. Полный suite и `--update` для этой правки не нужны.
