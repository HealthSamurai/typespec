# F310 · Мапы, пути и деструктуризация

## Обновление реализации — топ-10

`get` с default сохраняет присутствующий `nil`. `merge` обязательного поля слева и опционального справа сохраняет обязательность и объединяет типы значений. Вложенные `get-in`, `assoc-in` и `update-in` описаны отдельно в [F312](F312-literal-map-paths.md).

Смешанные пути вроде `[:headers "content-type"]` работают в `assoc-in` и `update-in`. `select-keys` сохраняет типы и обязательность выбранных полей, когда список keyword и строковых ключей известен из кода или из `s/tuple`. Если список допускает несколько вариантов, результат объединяет соответствующие формы. Обычный `check` использует полученную форму при вызове функции с `s/fdef`, в том числе из другого namespace. [Регрессии мап](../test/typespec/maps_regression_test.clj) · [PG-приёмка](../examples/context-pg-check/probe/select_columns.clj)

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Мотивация и границы

В Clojure мапы — обычный способ передавать настройки, события и результаты вычислений. После `assoc`, `dissoc` или деструктуризации важно знать не только тип значения, но и гарантировано ли наличие ключа. Отсутствующий ключ и присутствующий `nil` ведут себя по-разному при `:or` и `get` с default. Проверка должна сохранять это различие, а не маскировать ошибки удобным, но неверным non-nil типом.

Эта карточка задаёт передачу формы мапы между выражениями, чтение путей и связь с локальными bindings. Источники сигнатур и синтаксис параметров подробнее описаны в [F113](F113-destructuring.md), политика nil — в [F320](F320-nil-and-platform.md), records — в [F350](F350-records.md). Здесь не обещается полная поддержка всех их механизмов.

## Что уже реализовано (current)

`implementation: partial` соответствует исходникам, но не всем обещаниям reference:

- `types.clj`: структурный тип `{:t :map :req {k T} :opt {k T}}`, ссылки на spec, unions, `:map-of`; map-subtyping допускает дополнительные ключи. `t/exact` сейчас разбирается как внутренний тип без проверки закрытости.
- `check.clj`: `lookup-key` / `key-info` / `read-key` различают обязательный, опциональный, неизвестный ключ, nil и не-мапу. Чтение необъявленного ключа из объявленной формы может дать `TSP2339`, хотя сама мапа открыта. Глобальный spec qualified-ключа позволяет прочитать его как optional. У inferred-мапы неизвестный ключ не считается доказанно отсутствующим.
- `assoc` и `update` с keyword делают ключ обязательным. `dissoc` с keyword удаляет его из обеих таблиц. Эти операции проходят по объединению известных форм мап. Для вычисляемого ключа точная форма ослабляется.
- `update` проверяет callback и записывает тип результата в форму. `merge` объединяет таблицы и учитывает правые optional-поля.
- После `update` с литеральным keyword в `s/map-of` изменённый ключ становится обязательным и получает тип результата callback. `assoc` делает то же для литерального ключа или конечного набора ключей, заданного его Spec. Остальные значения сохраняют общий `s/map-of` контракт.
- `dissoc` сохраняет отсутствие удалённого литерального ключа в `s/map-of`. Для конечного набора ключей результат учитывает каждый возможный выбор.
- `merge` с одним `s/map-of` сохраняет исходную форму. Если справа идут мапы с точно известными обязательными полями, их значения перекрывают одноимённые ключи, а тип остальных значений берётся из исходного `s/map-of`.
- `conj` на мапе сохраняет форму после добавления двухэлементного вектора с известным ключом или закрытой мапы. `nil` оставляет форму исходной, а вектор неправильной длины получает диагностику.
- `select-keys` сохраняет обязательность для известного списка keyword и строковых ключей. `get-in` учитывает default на каждом шаге пути. `assoc-in` и `update-in` восстанавливают форму вдоль пути из keyword и строк.
- `keys` и `vals` берут типы элементов из `s/map-of` и мап с известным набором ключей. Пустой вход даёт `nil`. Проверка `get-ig` отклоняет числовой контракт после извлечения и сортировки строковых ключей версий.
- `get` выводит тип значения из `s/map-of` при вычисляемом ключе. Отсутствующий ключ даёт `nil` или default, а присутствующий `nil` сохраняется. `get-ig` проверяет этот вывод при чтении пакета по ключу версии, полученному из сортировки.
- `get` с известным строковым ключом использует обязательность и тип поля структурной мапы. Проверка `get-ig` закрепляет это на чтении `"resourceType"` из карты полей JSON.
- `assoc` с литеральным строковым ключом обновляет тип поля и делает его обязательным. `dissoc` отмечает поле отсутствующим. Чекер переносит известные правки через вызов функции. Проверка `get-ig` использует удаление `"text"` и запись `"_filename"`.
- Деструктуризация поддерживает `:keys`, namespaced `:keys`, `:as`, keyword lookup с вложенным pattern и часть `:keys!` / `:missing`. `:select`, `:excess`, `:all`, `:strs` / `:syms` дают unknown, а не обещанные reference точные типы.

## Примеры

Обычные иллюстрации, не golden-тесты. Примеры 2–3 продолжают объявления примера 1. `current` означает поведение, выведенное из исходников; новые примеры в этом изменении не запускались.

### 1. Корректно: обязательность сохраняется при преобразовании

```clojure
(ns map-demo (:require [clojure.spec.alpha :as s]))
(s/def :account/id string?)
(s/def :account/title string?)
(s/def ::account (s/keys :req [:account/id] :opt [:account/title]))

(defn normalize
  {:t/sig '[::account :-> ::account]}
  [{:account/keys [id] :as account}]
  (-> account
      (assoc :account/title (str "Account " id))
      (dissoc :account/title)))
;; current: id обязателен; :as сохраняет исходный тип.
;; assoc делает title обязательным, dissoc убирает его;
;; обязательный id остаётся, результат совместим с ::account.
```

Обычный `:keys` сам по себе не требует ключ: здесь обязательность пришла из сигнатуры, а не из pattern.

### 2. Ошибка: удалён обязательный ключ

```clojure
(defn without-id
  {:t/sig '[::account :-> ::account]}
  [account]
  (dissoc account :account/id))
;; current: TSP2741 при проверке результата — отсутствует required :account/id.
;; Это ошибка контракта функции, не ошибка выполнения dissoc.
```

### 3. Граница: default не заменяет явный nil

```clojure
(s/def :account/retries (s/nilable int?))
(s/def ::job (s/keys :opt [:account/retries]))

(defn next-attempt
  {:t/sig '[::job :-> int?]}
  [{:account/keys [retries] :or {retries 0}}]
  (inc retries))
;; current: TSP2531 — retries может быть nil даже с :or.
;; В Clojure {} выбирает 0, {:account/retries nil} сохраняет nil.

(defn attempts
  {:t/sig '[::job :-> int?]}
  [job]
  (get job :account/retries 0))
;; current: get удаляет nil и может ошибочно принять этот контракт.
;; planned: результат int? | nil; контракт должен быть отклонён.
```

### 4. Пограничный merge: правый optional может перезаписать значение

```clojure
(s/def :left/value int?)
(s/def :right/value string?)
(s/def ::left (s/keys :req-un [:left/value]))
(s/def ::right (s/keys :opt-un [:right/value]))

(defn combine
  {:t/sig '[::left ::right :-> any?]}
  [left right]
  (merge left right))
;; (combine {:value 1} {})               => {:value 1}
;; (combine {:value 1} {:value "new"})   => {:value "new"}
;; current: таблицы merge сохраняют required :value с левым int?.
;; planned: :value обязателен, тип int? | string?, не только int?.
```

Пример специально использует разные `:req-un` / `:opt-un` источники: конфликт нельзя скрыть глобальным контрактом одного qualified-ключа.

### 5. Путь и default: поведение языка шире текущей передачи типов

```clojure
(s/def :cfg/port int?)
(s/def :cfg/server (s/keys :opt [:cfg/port]))
(s/def ::config (s/keys :opt [:cfg/server]))

(defn port
  {:t/sig '[::config :-> int?]}
  [config]
  (get-in config [:cfg/server :cfg/port] 8080))
;; Clojure: {} и {:cfg/server {}} дают 8080.
;; Тип результата совместим с int? и включает 8080 при отсутствии поля.
;; Для nilable конечного port результат обязан сохранить явный nil.
```

## Алгоритм текущего checker

1. **Вход.** AST из `parse.clj`, окружение specs/signatures из `env.clj`, локальные типы и позиции. `pattern-type` извлекает нижнюю границу из верхнеуровневого `:keys` / `:keys!`: обычные keys становятся optional, bang — required, кроме случая `:missing`. Это не рекурсивный решатель требований.
2. **Представление.** `:req` / `:opt` хранят типы присутствующих значений. Optional описывает возможное отсутствие ключа. `:fresh` включает проверки свежего литерала. Для литеральных мап и записей с сохранённым списком ключей checker знает, какие ключи отсутствуют.
3. **Чтение.** `lookup-key` раскрывает members типа, рассматривает nil отдельно, ищет ключ в `:req`, `:opt`, затем в specs. `key-info` добавляет политику неизвестных ключей и диагностики, `read-key` добавляет nil для optional-чтения или nilable-контейнера. `:map-of` даёт optional value; проверка типа ключа этим lookup не реализована.
4. **Преобразование.** `special`-обработчики вызывают `infer` для аргументов и преобразуют таблицы описанными выше правилами. `assoc` проверяет глобальный spec через `check-key-value!`, затем сохраняет тип через `key-type`. Это не произвольное изменение объявленного qualified-контракта.
5. **Bindings.** `destructure-map` читает ключ через `key-info`; optional без default получает `T | nil`, с default — `T | typeof(default)`, причём nil внутри T остаётся. `:as` связывается с полным исходным типом. Вложенный keyword-pattern рекурсивно вызывает `bind-pattern`. Полная корректность defaults на всех ветках из этого не следует: например, явный `{x :k :or {x d}}` не проходит ту же ветку defaults, что `:keys`.
6. **Результат.** `infer` возвращает тип выражения; при вызове/возврате `problems` сопоставляет его контракту. `fresh-problems` отдельно проверяет ключи литерала; при связывании `let` свежесть снимается. Диагностики включают позицию и сообщение, а для bindings — объяснение источника nil.

Существующие коды: `TSP2339` — неизвестное поле/чтение из не-мапы; `TSP2304` — отсутствие spec qualified-ключа в соответствующих условиях; `TSP2741` — недостающий required-ключ; `TSP2322` — несовместимый тип; `TSP2353` — подозрительный лишний ключ свежего литерала; `TSP2531` — использование возможно nil значения. Здесь не вводятся новые коды.

## Планируемый алгоритм передачи формы

Ниже проект ограниченного ядра для persistent map и literal-ключей, **не доказанный sound алгоритм** для всех операций Clojure.

1. Нормализовать форму в required/optional/known-absent плюс политику неизвестных дополнительных ключей. Отдельно хранить nil в типе присутствующего значения. Для union проверять каждую ветвь; определить ограничение роста числа ветвей и безопасное widening.
2. Lookup возвращает пару «возможное отсутствие / тип присутствующего значения», не готовый `T | nil`. Обычное чтение преобразует отсутствие в nil; `get` с default заменяет только отсутствие. Деструктуризация с `:or` использует ту же операцию. Это исправляет пример 3 без удаления значимого nil.
3. Для `assoc` literal-ключа проверить value-контракт и сделать ключ required с новым типом; для `dissoc` — удалить значение и записать отсутствие. Для динамического ключа нельзя сохранять прежнюю точную форму: он может совпасть с любым известным ключом. Нужна отдельная консервативная политика ослабления и проверки spec.
4. Для `update` получить тип чтения с nil при отсутствии, проверить callback и аргументы, проверить его результат, затем записать результат как required. Ошибку callback нельзя лечить молчаливым удалением nil. Нужны правила для nil-контейнера и unknown-callback до расширения обещаний.
5. Для `merge A B` правый required перекрывает левый тип. Правый optional объединяет свой тип с возможным левым значением; обязательность остаётся, если левый ключ был required. Если оба optional, результат optional. Отсутствие справа сохраняет левое значение. **Открытый неизвестный остаток B тоже может перезаписать ключи A**: без модели остатка эти правила сами по себе недостаточны.
6. `select-keys` проецирует форму без превращения optional в required. `get-in` переносит отсутствие отдельно от nil по каждому шагу: default применяется при провале пути, но не к существующему nil в конце. Для числовых индексов требуются факты о длине/границах, а не только тип элемента.
7. `assoc-in` / `update-in` требуют рекурсивного восстановления родительских форм и проверки каждого промежуточного контейнера. Сначала ограничить ключи и допустимые контейнеры; отдельно исследовать создание промежуточных мап из nil, векторы, exceptions и пустой путь. Простая замена листа не является готовым алгоритмом.
8. Подключить transfer-функции в существующие `special`, общий lookup — в `read-key` и `destructure-map`, проверку результата — в `problems`. Не менять смысл `:inferred` ради имитации exact. Новую модель закрытости нужно согласовать с `types/map-sub?` и парсером `t/exact`.

## Ограничения и открытые вопросы

- Reference формулирует целевую точность map operations и `t/exact`, а код реализует лишь часть. Отсутствие ошибки на динамическом ключе, unknown или неточной ветке не доказывает безопасность.
- Удалённый ключ в текущем типе может снова читаться по глобальному spec как optional; known-absent нельзя выразить одной очисткой таблиц.
- Необходимо исследовать совместимость открытых форм с глобальными spec-ключами, правила widening, nil-контейнеры, unions, динамические ключи/пути, числовую индексацию и records. Алгоритм должен учитывать все возможные перезаписи, а не только явно перечисленные поля.
- Clojure 1.13 directives нельзя объявлять проверенными по одному reference: нужны pinned версия и дифференциальный тест реального `destructure`. Найденные тесты не подтверждают заявленный там генератор случайных форм. `:select` / `:excess` / `:all` остаются unknown.
- `s/merge` сохраняет обязательность ключа из любой входной мапы и объединяет альтернативы из групп `s/keys`. Раскрытие ограничено 64 формами. Для общего поля с сопоставимыми скалярными типами выбирается более узкий тип. Доказанное отсутствие общего значения даёт `t/never` у поля. Необязательное поле с таким типом можно опустить.
- Для конечных скалярных объединений checker пересекает до 256 пар вариантов. Например, у двух nullable-типов может остаться только общий `nil`.

## Конкретная матрица тестов и готовность

| Сценарий | Что проверять | Состояние |
|---|---|---|
| `assoc` optional keyword + корректное значение | Ключ required, соседний required сохранён | Основа есть в `m1`; нужен assert типа |
| `dissoc` required / optional | Required нарушает возврат (`TSP2741`), optional допустим | `m2` / `m1` существуют |
| `update` optional через `inc` | Nil передаётся callback, `TSP2531` | `m1` существует |
| `update` с безопасным callback и новым типом unqualified-поля | Новая required-форма результата, не старая | Добавить регрессию |
| `select-keys` required + optional / опечатка | Обязательность сохраняется / `TSP2339` | `m3` покрывает опечатку; типовой assert добавить |
| `merge` с неправильным spec-value | Ошибка типа поля | `m4` существует |
| `merge` левый required + правый optional | Пример 4: required union; ветки present/absent | Добавить регрессию; сейчас дефект |
| `get` optional non-nil + default | Non-nil результат | `m5` существует |
| `get` optional nilable + default | Отдельно `{}`, explicit nil, число; nil не теряется | Пример 3; добавить регрессию |
| `get-in` default | Отсутствие первого/последнего шага, explicit nil в конце | Покрыто в F312 |
| `:keys`, `:as`, вложенный pattern | Локальные типы и сохранение исходного аргумента | Добавить изолированные asserts |
| `:or` при nullable spec / явное `{x :k}` | Nil сохраняется; обе формы дают одинаковую семантику | `ex.more` покрывает nullable `:keys`; вторую форму добавить |
| Динамический ключ в assoc/dissoc | Не сохранять необоснованные required-факты | Добавить отрицательный тест точности |
| Open/exact и fresh/non-fresh | Open принимает добавочные поля; exact отвергает их в обоих случаях | Выведенная открытая форма из деструктуризации принимает дополнительные ключи литерала. Для объявленных форм действует проверка подозрительных ключей. Exact planned |
| `assoc-in` / `update-in`, nil и скаляр на пути | Корректный результат либо ошибка записи по ключу | Покрыто в F312 |
| 1.13 directives | Сравнить предсказанный тип с выполнением формы на pinned runtime | Planned, требуется исследование |

Критерий готовности: позитивный, негативный и пограничный тест каждого обещанного transfer; asserts типов, а не только отсутствие diagnostics; устранение ложного non-nil у `get` и потери правой ветви `merge`. В этой правке изменяется только описание, тесты и checker не меняются.
