# F330 · Tuples, длина и непустые коллекции

[F331](F331-fixed-vector-positions.md) реализует точную длину и типы
позиций вектора. Описание ниже фиксирует исходное состояние и план
общих фактов о длине последовательностей.

## Зачем

В Clojure вектор часто обозначает не однородную коллекцию, а запись по позициям: координаты, пару `[ключ значение]`, строку результата запроса. `(s/tuple keyword? string?)` должен отличаться от вектора произвольной длины с элементами `keyword? | string?`: перестановка позиций и потерянный элемент — ошибки контракта.

Другая задача — отличить отсутствие элемента от допустимого `nil` внутри коллекции. Проверка `(seq xs)` доказывает существование первого элемента полученной последовательности, но не его non-nil тип. Это позволяет проверять обычный Clojure-код с `first`, `nth`, `rest`, `next` и последовательной деструктуризацией, не требуя заменять его специальными конструкциями.

## Что уже работает, а что только запланировано

**До F331:**

- `types.clj/parse-type` распознаёт `s/tuple`, но переводит его в `{:t :coll :kind :vector :of <union элементов>}`. Позиции и длина теряются. `s/coll-of` хранит вид и тип элемента; ограничения количества не сохраняются.
- В `check.clj/infer` литерал вектора тоже становится коллекцией с объединённым, расширенным типом элементов. `types.clj/sub1?` для коллекций сравнивает вид и `:of`, не длину.
- `elem-type`, `indexed` и `bind-pattern` дают последовательной деструктуризации общий тип элемента. Обычно доступ помечается `:platform`; строгая nil-проверка учитывает возможный nil. Доказательства наличия конкретной позиции нет.
- Обработчик `nth` выводит общий тип элемента, не проверяет границы и не включает тип аргумента по умолчанию. `seq` и `next` возвращают nilable-коллекцию, `rest` — коллекцию; длина не отслеживается.
- `narrow` и обработчики `when-let`/`if-let` не создают фактов длины. Снять nil с результата `seq` ещё не значит научить текущий `first` доказанной непустоте.

**Planned:** отдельное представление tuple, точный доступ по позиции, интервалы длины и факты непустоты. `implementation: partial` сохраняется: синтаксис и общие операции есть, но основные гарантии этой карточки ещё не реализованы. Отсутствие ошибки сегодня не подтверждает соблюдение tuple-контракта.

## Примеры и ожидаемое поведение

Это иллюстрации, не исполняемые golden-тесты. Каждый блок самостоятельный. Метаданные `t/sig` — существующий способ объявить тип без исполнения типовых форм.

### 1. Корректная пара с разными типами позиций

```clojure
(ns tuple-label (:require [clojure.spec.alpha :as s]))
(s/def ::entry (s/tuple keyword? string?))
(defn label
  {:t/sig '[::entry :-> string?]}
  [[kind text]]
  (str (name kind) ": " text))
(label [:info "ready"])
```

**Planned:** `kind : keyword?`, `text : string?`; обе позиции существуют, обращение к `name` безопасно без nil-проверки. **Current:** для обеих переменных получается объединение типов элементов, с platform-поведением доступа. Точная проверка позиции не работает; вызов `name` не получает доказательства `keyword?` именно из позиции 0 (его сигнатура допускает также строки).

### 2. Ошибки длины и перестановка элементов

```clojure
(ns tuple-errors (:require [clojure.spec.alpha :as s]))
(defn consume
  {:t/sig '[(s/tuple keyword? string?) :-> nil?]}
  [entry]
  nil)
(consume [:info "ready"])           ; planned: OK
(consume ["ready" :info])           ; planned: неверные позиции 0 и 1
(consume [:info])                   ; planned: отсутствует позиция 1
(consume [:info "ready" "extra"])   ; planned: длина 3 вместо 2
```

**Current:** эти аргументы совместимы с потерявшим длину и позиции `vector<keyword? | string?>`; указанные ошибки не выявляются сравнением коллекций. **Planned:** ошибка контракта на аргументе с ожидаемой/фактической длиной либо индексом, ожидаемым и фактическим типом. Лишние элементы в tuple запрещены, даже если код функции их не читает.

### 3. Непустота не исключает nil в элементе

```clojure
(ns nonempty (:require [clojure.spec.alpha :as s]
                       [clojure.string :as str]))
(defn shout
  {:t/sig '[(s/coll-of (s/nilable string?)) :-> (s/nilable string?)]}
  [values]
  (when-let [xs (seq values)]
    (str/upper-case (first xs))))
(shout [nil])                       ; runtime: обращение к nil, не безопасно

(defn safe-shout
  {:t/sig '[(s/coll-of (s/nilable string?)) :-> (s/nilable string?)]}
  [values]
  (when-let [xs (seq values)]
    (when-let [x (first xs)]
      (str/upper-case x))))
```

**Planned:** первая функция получает nil-диагностику; вторая проходит. Для `(s/coll-of string?)` вместо nilable элемента первая функция должна проходить: в ветке есть элемент и он строка. **Current:** факта непустоты нет; поведение доступа зависит от platform/strict-nil, поэтому случай без nil в типе элемента не доказан. Эти три варианта нужно проверять отдельно, а не считать `seq` фильтром nil-элементов.

### 4. Индекс за границей, default и мягкая деструктуризация

```clojure
(let [v [:ok "ready"]
      [tag text missing & tail :as whole] v]
  [(nth v 1)            ; planned: string?, "ready"
   (nth v 2 :absent)    ; planned: литерал :absent
   missing              ; planned: nil, не ошибка привязки
   tail                 ; runtime: nil при исчерпанном остатке
   whole])              ; planned: исходный tuple
(nth [:ok "ready"] 2)   ; runtime: исключение; planned: ошибка границ
```

**Current:** `nth` в том числе с default выводит общий тип элемента; тип `:absent` не учитывается. Деструктуризация не знает, что третьего элемента нет. **Planned:** `nth` без default и мягкая деструктуризация имеют разные правила. Отсутствующая привязка допустима сама по себе, ошибка возникает при её использовании как non-nil значения. Исчерпанный `& tail` нельзя типизировать как гарантированно non-nil последовательность.

### 5. Непустой вход не делает остаток непустым

```clojure
(when-let [xs (seq [42])]
  [(first xs)           ; 42: guaranteed-present
   (first (rest xs))    ; nil: rest может быть пустым
   (next xs)])          ; nil: второго элемента нет
(when-let [ys (next [42 43])]
  (inc (first ys)))     ; planned: OK, первый элемент ys — int?
```

**Planned:** `rest` сохраняет возможность пустоты, `next` — nil либо непустой остаток. **Current:** различие nilable/non-nil контейнера частично есть, но граница длины не переносится; `first` использует общий `indexed`, а не доказательство наличия элемента.

## Алгоритм проверки: ограниченное целевое ядро

Ниже проект правил для неизменяемых последовательных значений, а не утверждение о soundness всего checker. Нынешние permissive-правила `unknown`, platform и fallback типов не становятся строгими от добавления длины.

1. **Вход.** AST выражения с координатами, типы аргументов и локальных переменных, объявления `s/tuple`/`s/coll-of`, окружение фактов и режим nil-проверки. Не выполнять пользовательские предикаты, не вычислять `count` реальной коллекции при анализе.
2. **Представление.** Предлагается внутренний узел `{:t :tuple :items [T0 ... Tn]}` для вектора точной длины и отдельный интервал длины `[min,max]`, где `max` может быть бесконечным. Для последовательных представлений хранить известный префикс, общий тип остальных элементов и различать nil/пустую/nonempty последовательность. Это внутренний проект, не новая публичная форма `t/nonempty` в reference. Tuple автоматически имеет длину `[n,n]`; обычный `coll-of` — `[0,∞]`.
3. **Создание и совместимость.** Литерал вектора сохраняет позиции; tuple-объявление сохраняет каждый тип. Tuple совместим с другим tuple только при равной длине и попозиционном `sub?`. Tuple можно забыть до `coll-of T`, если все элементы совместимы с `T` и подходит вид. Из одного лишь `coll-of T` нельзя получить tuple: даже точная длина сама по себе не доказывает разные типы позиций. `any`/`unknown` не служат доказательствами длины; непроверенный переход должен быть видим отдельно от доказанного.
4. **Доступ.** Для известного неотрицательного целого индекса и tuple вернуть тип позиции. Для `nth` без default вне границ выдать ошибку возможного/неизбежного исключения, а не выдумывать nil-результат. Для `nth` с default вернуть тип позиции, тип default либо их объединение — в зависимости от доказанного диапазона. Динамический индекс без диапазона не считать безопасным; проверить хотя бы тип индекса, сохранить общий тип возможных элементов и явную неопределённость границ. Отрицательные индексы и нецелые числовые аргументы требуют отдельного согласования с Clojure `nth`, не переносить механически правила векторного вызова.
5. **Мягкий доступ и привязки.** `first` получает тип позиции 0/элемента; добавляет nil только при возможности отсутствия, но никогда не удаляет nil из самого типа элемента. Пустая последовательность даёт именно `nil?`, не `never`. Для последовательной деструктуризации повторить мягкий доступ для каждой позиции; `:as` сохраняет исходный тип. `&` получает оставшийся префикс и интервал длины, с nil при исчерпании согласно семантике destructuring. Отдельно реализовать `rest` (пустая последовательность вместо nil) и `next` (nil либо непустой остаток).
6. **Условия и факты.** `seq` возвращает nil либо последовательность с `min >= 1`; на пустом известном входе — nil. В истинной ветке `when-let`/`if-let` факт относится к привязанному результату `seq`, не к произвольному повторному выражению. Для `rest`/`next` уменьшить известные границы на один с нижним пределом 0; для истинного результата `next` снова установить минимум 1. Связи с исходным локальным значением переносить только при доказанной стабильности. Два чтения `@state` — разные значения.
7. **Слияние веток.** Сохранять union tuple-альтернатив, когда это нужно для связи длины с позицией. При вынужденном расширении интервала брать минимум нижних и максимум верхних границ; факты, верные лишь в одной ветке, терять. Нельзя усреднять длины или делать min=1 после ветки с пустым значением. Предел числа альтернатив и widening для рекурсии требуют отдельного исследования.
8. **Результат и диагностики.** Возвращать тип, факты, происхождение доказательства и список диагностик с координатами. Несовместимые типы и nil могут использовать существующие `TSP2345`/`TSP2531`. Для точной длины предлагается **proposed TSP330-01**, для границ — **proposed TSP330-02**: операция, индекс, известный диапазон длины, ожидаемое/фактическое значение. Эти коды ещё не существуют. Недостаток информации нельзя сообщать как доказанный выход за границы; он должен оставаться отдельным непроверенным случаем.

## Интеграция с текущим checker

- `types.clj`: `parse-type`, `sub1?`, `show` и операции union должны понимать tuple без немедленного превращения в `:coll`. Печатать его существующим `(s/tuple ...)`, а не новым недокументированным синтаксисом.
- `check.clj`: изменить вывод вектора в `infer`, извлечение `elem-type`, последовательный `bind-pattern`, обработчики `first`/`nth`/`seq`/`rest`/`next`. Нельзя просто убрать `:platform` у любого `first`: сначала нужно доказательство наличия.
- `narrow`, контекст локальных привязок и слияние веток должны переносить факты, не только non-nil тип. `if-let` и `when-let` должны потреблять факт результата вычисления, а не повторно анализировать его как новое значение.
- `core_types.clj` сейчас даёт `count` тип `int?`. Уточнение через `(pos? (count xs))`/`(< i (count xs))` — отдельное расширение, требующее связей между выражениями и диапазонами; оно не появляется автоматически от tuple-поддержки.
- F113 отвечает за общую деструктуризацию, F240 — за ветвления, F320 — за nil/platform, F410 — за arity и `apply`. Здесь определяются только длина и позиции; раскрытие tuple в аргументы `apply` передаёт эти данные F410, не дублирует его алгоритм.

## Ограничения и вопросы для исследования

- Первое ядро ограничить persistent-векторами и устойчивыми последовательностями. Lazy seq, потенциально бесконечные источники, Java Iterable/Iterator, mutable collections и ошибки реализации `seq` требуют явной модели эффектов. Не материализовать их ради доказательства длины.
- Карта и множество не получают tuple-позиции только потому, что у них есть `seq`. Для map-entry нужен самостоятельный проверенный контракт преобразования.
- Не переносить непустоту через `filter`, `keep`, `take-while`; `map` может сохранять длину только при подходящих контрактах источника и операции. Общая таблица переносов пока не определена.
- `first`, `peek`, `rand-nth`, `ffirst` сейчас объединены одним обработчиком, но имеют разную семантику. Для точных правил их надо разделить; вложенный доступ `ffirst` не равен одному извлечению элемента.
- Нужен ли экспортируемый nonempty-тип или достаточно локального факта? Пока предлагается локальный факт; публичный синтаксис и round-trip печати интервалов не утверждены.
- При использовании диапазонов индекса нужны отдельные правила отрицательных значений, JVM-приведения чисел, overflow и границ `count`. Описанное ядро не решает эту задачу и не объявляет анализ произвольной арифметики sound.

## Конкретная матрица тестов

Все строки ниже — требуемые тесты, не отчёт об уже пройденных. Проверять вывод типа, координаты/причину диагностики и оба режима nil там, где это отмечено.

| Случай | Ожидаемая проверка |
|---|---|
| Parse `(s/tuple keyword? string?)`, печать и повторный parse | Две позиции в том же порядке; round-trip без потери длины |
| Пример 1 | Разные типы привязок, вызов проходит в обычном и strict-nil режиме |
| Пример 2: правильный / переставленный tuple | Первый проходит; второй сообщает индексы и несовместимые типы |
| Пример 2: длина 1 / 3 вместо 2 | proposed TSP330-01 на аргументе с обеими длинами |
| Tuple → однородный `coll-of`; обратное направление | Первое при совместимости элементов разрешено; обратное без доказательств не считается проверенным |
| `[]`, `(first [])`, `(seq [])` | Длина 0; оба результата доступа/seq — nil, не never |
| Пример 3: элемент `string?`, элемент nilable, вложенный `when-let` | Проход / nil-ошибка / проход; проверить оба nil-режима и политику совместимости |
| Пример 4: `nth` внутри / вне / с default | Точный тип позиции / proposed TSP330-02 / тип default |
| `nth` с динамическим int-индексом / индексом-строкой | Непроверенные границы отдельно от неверного типа индекса |
| `[a b c & xs :as all]` на tuple длины 2 | `c=nil`, остаток nil, `all` сохраняет tuple; сама привязка допустима |
| Пример 5: `rest` и `next` длины 1 и 2 | Правильное различие пустого результата и nil; непустота только в доказанной ветке |
| Слияние `[1]` и `[]` через `if` | После слияния нет гарантии наличия первого элемента |
| `(seq @a)` и повторное `@a` | Факт не переносится на повторное чтение |
| `filter` над непустым входом | Результат может быть пустым |
| Tuple как аргумент/результат объявленной функции | Сохранение длины через границу сигнатуры; ошибка неверного возврата |

Критерий готовности: эти случаи становятся отдельными тестами с проверкой типов и диагностик, неподдержанные случаи видны как непроверенные, а новые правила не ломают существующее поведение nil/platform. В текущих fixtures есть проверки доступа к элементам и strict-nil, но поиск `tuple`/`nonempty` не обнаруживает специализированного покрытия F330. Полный suite и обновление golden-файлов для этой правки документации не запускались.
