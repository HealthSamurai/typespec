# F340 · Изменяемые значения и variance

## Мотивация и границы

В Clojure неизменяемое значение и ссылка на меняющееся значение — разные вещи. Локальное имя снимка atom продолжает обозначать тот же снимок после `reset!`, но следующий `deref` может вернуть другое значение. Проверка типов должна разрешать безопасное сужение снимка и не переносить его на содержимое ссылки. Это нужно для кешей, счётчиков, состояния приложений и очередей.

Вторая задача — не дать записать неверное значение через псевдоним ссылки. Если `int?` является подтипом `number?`, то коллекцию целых можно читать как коллекцию чисел. Но atom целых нельзя передавать как atom произвольных чисел: получатель сможет записать дробное число. Для полного интерфейса чтения и записи параметр типа **инвариантен**, то есть расширять его в одну сторону нельзя.

Минимальный этап реализации: `t/atom`, `atom`, `deref`, `reset!`, `swap!`, локальные снимки и проверка инвариантности. Volatile, массивы и каналы сохраняются в общей цели дизайна, но требуют отдельных правил; наличие правила atom не означает их поддержку. Здесь нет обещания доказать отсутствие гонок, взаимоблокировок или корректность побочных эффектов.

## Реализовано для atom

`(t/atom T)` хранит тип содержимого `T`. Прямое создание ссылки
берёт этот тип из ожидаемого `s/fdef` или `t/sig`, а без контракта
выводит его из инициализатора. Из литерала карты выводится `map?`;
точные поля и однородные карты можно описать через `s/keys` и `s/map-of`.
Обычные `def` и `defonce` с одним инициализатором `atom` сохраняют тип
ссылки при использовании из другого namespace.

`deref` и `@` возвращают тип содержимого. `reset!`, `reset-vals!` и
`compare-and-set!` проверяют записываемое значение. `swap!` и
`swap-vals!` проверяют параметры и результат колбэка. Формы `*-vals!`
сохраняют типы в двухэлементном векторе `[old new]`. Для
`compare-and-set!` результат имеет тип `boolean?`, старое значение
служит для сравнения по идентичности. Вызов
`(swap! state assoc k v)` переиспользует вывод результата `assoc`.
Совместимость ссылок проверяется по совпадению нормализованных типов
содержимого. Локальная переменная со снимком сужается независимо от
последующих чтений.

В полном `context-clj/http` кеш `uui.heroicons/cache` выводится как
`(t/atom map?)`. Оригинальный `swap!` с `assoc` проходит. Замена
колбэка на `(fn [_] 42)` даёт `TSP2345` на месте.
[Проверка кеша](../examples/context-http-check/probe/atom-cache.clj)
проверяет также `reset-vals!`, `swap-vals!` и `compare-and-set!`
на ссылке из другого namespace.

## Запись в ссылочные JVM-массивы

`aset` проверяет индексы и значение по компоненту массива. Локальная
подсказка `^objects` сохраняет более точный тип инициализатора. Например,
`(let [^objects values (into-array String ["param"])] (aset values 0 42))`
даёт `TSP2345` на `42`. Запись строки или `nil` в `String[]` и числа
в массив, созданный `object-array`, допустима. Результат вызова получает
тип записываемого значения.

Если известна только подсказка `^objects`, фактический компонент может
быть уже `Object`. Для записи ненулевого значения в такой массив чекер
выдаёт `TSP210-01`, когда совместимость с фактическим компонентом
не установлена. То же правило действует для других ссылочных массивов,
допускающих более узкий класс компонента.

## Запись через `aset-*` в примитивные JVM-массивы

Специализированные `aset-boolean`, `aset-byte`, `aset-char`, `aset-short`,
`aset-int`, `aset-long`, `aset-float` и `aset-double` проверяют тип
компонента, индексы и преобразование записываемого значения. JVM допускает
расширение примитива при записи. Например, `aset-int` принимает `long[]`
и выдаёт `TSP2345` на `short[]`. Чекер также отмечает литералы вне
диапазона преобразования, например `128` для `aset-byte`. Результат
вызова имеет тип исходного значения до преобразования. Так, запись
`nil` через `aset-boolean` хранит `false` и возвращает `nil`.

Обычный `aset` с тремя аргументами использует перегрузки `RT.aset`.
Литерал `42` имеет тип JVM `long` и не подходит для `byte[]` даже
через `^bytes`. Явное `(byte 42)` подходит. Результат вызова имеет тип
компонента, так как перегрузка может преобразовать значение при записи.
В форме с несколькими индексами последний шаг использует `Array.set`.
Там допустимо стандартное расширение JVM после распаковки, а результат
сохраняет исходный тип значения. Чекер выдаёт `TSP210-01`, когда
доступный тип не определяет JVM-представление значения или выбор
перегрузки, а также при возможном переполнении `int` в checked math.

## Копирование массива через `aclone`

`aclone` возвращает поверхностную копию с тем же JVM-классом.
Если `^objects` скрывает точно известный `String[]`, копия сохраняет
компонент `String`, и запись числа через `aset` даёт `TSP2345`.
Для вложенных массивов копируется внешний массив, строки остаются общими.
Выбор примитивной перегрузки учитывает тип, который видит компилятор Clojure.

## Преобразование массива через `amap`

`amap` возвращает копию массива с тем же JVM-классом. В теле
доступны индекс типа JVM `long` и имя копии. Чекер проверяет результат
тела по правилам `aset`. Запись числа в `String[]` и запись индекса
в `byte[]` дают `TSP2345` на выражении тела. Явное преобразование
`(byte i)` подходит для `byte[]`.

## Примеры

Блоки ниже иллюстрируют использование типов. Тесты atom находятся в
[atom_test.clj](../test/typespec/atom_test.clj). Пример канала описывает
следующий этап.

### 1. Корректный снимок: сужение переживает запись в atom

```clojure
(defn display-old
  {:t/sig '[(t/atom (t/or string? int?)) :-> string?]}
  [state]
  (let [snapshot @state]
    (if (string? snapshot)
      (do (reset! state 42)
          (clojure.string/upper-case snapshot))
      "not text")))
;; snapshot в then имеет string?.
;; reset! допустим: 42 входит в string? | int?.
```

Снимок здесь — строка или число, а не глубокая копия. Если снимком окажется mutable объект, свойства его внутреннего состояния не становятся стабильными.

### 2. Ошибка: проверка предыдущего чтения не защищает следующее

```clojure
(defn display-current
  {:t/sig '[(t/atom (t/or string? int?)) :-> string?]}
  [state]
  (if (string? @state)
    (do (reset! state 42)
        (clojure.string/upper-case @state))
    "not text"))
;; Ошибка у аргумента upper-case: string? | int?, ожидается string?.
;; Даже без reset! результат тот же: другой поток мог изменить atom.
;; Исправление: связать результат одного deref через let, как в примере 1.
```

### 3. Ошибка через псевдоним: почему atom не ковариантен

```clojure
(defn write-fraction
  {:t/sig '[(t/atom number?) :-> number?]}
  [state]
  (reset! state 1.5))

(defn keep-integers
  {:t/sig '[(t/atom int?) :-> number?]}
  [ints]
  (write-fraction ints))
;; write-fraction корректен, вызов в keep-integers запрещён.
;; Atom<int> не является Atom<number>, хотя int <: number.
;; Обратная передача Atom<number> в Atom<int> также запрещена.
;; Для immutable (s/coll-of int?) -> (s/coll-of number?) это ограничение не нужно.
```

### 4. Пограничный swap!: обновление обязано принимать весь T

```clojure
(defn bump
  {:t/sig '[(t/atom int?) :-> int?]}
  [counter]
  (swap! counter (fn [n] (inc n))))
;; Параметр n контекстно получает int?.

(defn corrupt
  {:t/sig '[(t/atom int?) :-> string?]}
  [counter]
  (swap! counter (fn [_] "oops")))
;; Ошибка результата callback: string? нельзя записать в Atom<int>.

(defn bump-mixed
  {:t/sig '[(t/atom (t/or string? int?)) :-> (t/or string? int?)]}
  [state]
  (swap! state (fn [n] (inc n))))
;; Ошибка аргумента inc: n может быть строкой.
;; Нельзя проверять callback лишь по текущему наблюдённому значению atom.
```

Функция `swap!` может вызываться повторно при конфликте обновления. Проверка `[T ... :-> T]` обеспечивает совместимость типов, но сама по себе не доказывает отсутствие побочных эффектов callback.

### 5. Граница канала: закрытие добавляет nil к чтению

```clojure
;; Предполагается (:require [clojure.core.async :as a]).
(defn receive-text
  {:t/sig '[(t/chan string?) :-> (s/nilable string?)]}
  [ch]
  (a/<!! ch))

(defn receive-uppercase
  {:t/sig '[(t/chan string?) :-> string?]}
  [ch]
  (let [value (a/<!! ch)]
    (if (some? value)
      (clojure.string/upper-case value)
      "closed")))
;; Planned extension: принимаются; чтение имеет string? | nil.
;; upper-case без some? должен дать ошибку возможного nil.
;; nil не становится допустимым значением для записи в канал.
;; Current: нет типизированной модели канала и этих операций.
```

Reference прямо задаёт это правило для `<!`; перенос на блокирующий `<!!` здесь — отдельное планируемое расширение, не уже реализованная сигнатура. Проверка допустимости `<!` внутри `go` относится также к обработке макросов.

## Обобщение ячейки и граница стабильных путей

Дополнение к инвариантности: переменные типа, достижимые из созданной mutable-ячейки, не обобщать независимо при каждом использовании `let`. Пока нет отдельного доказательства безопасности, одна ячейка и все её aliases имеют один согласованный параметр, даже если внутри хранится полиморфная функция.

```clojure
(let [cell (atom (fn [x] x))
      alias cell]
  (reset! alias (fn [n] (inc n)))
  (@cell "text")) ; нельзя принять через новую независимую инстанциацию cell

(defn leaks []
  (let [a (atom 0)]
    (fn [] (swap! a inc)))) ; локальный atom утекает через closure
```

Скрывать локальный state-effect можно было бы лишь после проверки отсутствия утечки через результат, closure, callback, другие объекты и внешние вызовы. На первом этапе **не скрывать**: даже неутекающий atom не устраняет эффекты обхода входного lazy seq, validator/watch или Java-вызова. Для операций нужны внешние декларации core и библиотек; неизвестный получатель ссылки не подтверждает отсутствие утечки.

Для фактов ввести whitelist стабильных объектов `BindingId + immutable-selector-path`; путь прекращается перед `deref`, Java field/array или иным mutable referent. Пустой object не порождает факт о повторном вычислении. Это позволяет сохранять факт о строковом snapshot после неизвестного вызова, не требуя сначала полного effect analysis F450. Value-level `unknown` — безопасный top, а не обход проверки записи или инвариантности.

Planned-тесты сверх обычной записи: polymorphic cell с alias из примера не принимается через freshening; closure сохраняет state-effect; путь по persistent map сохраняет факт после вызова, путь через atom/Java field — нет; чистота обхода lazy-источника не выводится из локальности atom.

Основание: [Koka, Finding 5](../docs/research-koka.md) и [Typed Racket, Findings 3–4](../docs/research-typed-racket.md). Здесь прочитаны отчёты, первоисточники повторно не аудированы. В них выборочно прочитаны §2.5–2.6 [Koka 2014](https://arxiv.org/pdf/1406.2061), §2–3 [Logical Types for Untyped Languages](https://www2.ccs.neu.edu/racket/pubs/icfp10-thf.pdf), определения objects/propositions и [Guide, caveat о set!](https://docs.racket-lang.org/ts-guide/occurrence-typing.html). Heap-polymorphism Koka и запрет `set!` Racket не являются готовым escape-анализом Clojure; доказательства целиком не проверены.


## Предлагаемый алгоритм минимального этапа

Это консервативный проект для ограниченного набора atom-операций, **не готовый sound алгоритм для всего Clojure**. Перед реализацией требуется определить строгую совместимость параметров и границы доверия к внешним писателям.

1. **Вход.** AST с позициями, окружение деклараций и локальных связываний, ожидаемый тип выражения. Распознавать операции по разрешённому Var, а не только по имени: пользовательская функция `reset!` не получает core-правила. Учесть фактическое представление reader-формы `@x` в `parse.clj`; проверить эквивалентность с `(deref x)` тестом.
2. **Типы.** Добавить отдельный узел, например `{:t :cell :kind :atom :of T}`. Тип `T` — допустимое содержимое на всём протяжении использования ссылки, не только сейчас. Не смешивать его с номинальным Java-классом `Atom`. Обобщение `:kind` на volatile и другие носители допускается только после определения их операций.
3. **Создание.** Для `(atom init)` в контексте `Atom<T>` проверить `init <: T`. Без контекста вывести стабильный расширенный тип инициализатора, а не singleton текущего значения. Не расширять тип существующей ссылки при последующей записи. Политику для `(atom nil)`, пустых коллекций и объединений согласовать с выводом типов: в первом этапе требовать явный ожидаемый тип, если вывод слишком узок.
4. **Передача ссылки.** Требовать одинаковый kind и доказанную эквивалентность параметров после разрешения ссылок на типы. Для ограниченного первого этапа допустимо принимать только нормализованно одинаковые типы; сложные недоказанные равенства отклонять как неподдержанные. Не использовать permissive `sub?` как доказательство инвариантности. `unknown`, `any`, cast и непрозрачные типы должны обозначать непроверенную границу, а не давать статус «доказано». Правила рекурсивных типов требуют отдельного исследования.
5. **Чтение и факты.** `deref` известного `Atom<T>` возвращает `T`; каждое чтение независимо. Факты ветки привязать к идентичности локального связывания снимка, не к тексту выражения `@state` и не к имени atom. Сужение `snapshot` не меняет `:of T`. Повторное чтение через alias также возвращает полный `T`. При затенении имени старые факты не переносятся на новое связывание.
6. **Запись.** Для `reset!` проверить тип нового значения против `T`; для минимального этапа возвращать консервативно `T`. Запись через alias проверяется тем же правилом. Факты о неизменяемом снимке сохраняются; никаких фактов о текущем содержимом ссылки накапливать не нужно. Не выводить после записи «в atom теперь точно int»: конкурентная запись возможна немедленно.
7. **Обновление.** Для `(swap! cell f args...)` дать callback ожидаемые параметры `[T A1 ... An]`, где `Ai` — типы дополнительных аргументов. Проверить арность, возможность принять **каждый** вариант `T`, затем результат `<: T`. Inline `fn` анализировать контекстно; именованную функцию проверять по всем применимым контрактам, не по одному удачному варианту. Неизвестный callback не считать проверенным. Результат всего `swap!` консервативно `T`.
8. **Выход.** Вернуть тип выражения, факты стабильных локальных значений и диагностики с позициями. У несовместимой ссылки показать оба параметра и причину запрета расширения; у записи — ожидаемое содержимое и фактический тип; у callback — неверный вход или результат. У повторного чтения советовать `let`-снимок, но не предлагать молча менять семантику программы.

Планируемые специализированные диагностики: **proposed TSP340-01** — несовместимые параметры mutable-ссылки; **proposed TSP340-02** — запись/результат callback не входит в T; **proposed TSP340-03** — mutable-контракт не удалось проверить. Это не существующие CLI-коды. Ошибки аргумента и возможного nil можно отдавать обычной проверке совместимости (`TSP2345`, `TSP2531` сейчас), не вводя отдельный код для каждого deref.

## Интеграция с checker

- `types.clj`: чтение/печать нового типа, нормализация, строгая проверка инвариантного параметра; сохранить существующую ковариантность immutable `:coll`.
- `env.clj`: принять новый тип в существующих декларациях, не создавать параллельный источник аннотаций.
- `check.clj`: специализированные правила по разрешённому имени операции, ожидаемый тип при создании atom, переиспользование `bind-pairs`/`narrow` для снимков. `infer-fn` уже принимает контекстные типы аргументов; `apply-type` и текущая совместимость `:fn` недостаточны для общего доказательства контракта callback.
- `core_types.clj`: согласовать сигнатуры с правилами checker. Одна негeneric сигнатура вида `[any? :-> any?]` не заменяет зависимость чтения и записи от T.
- Каналы требуют интеграции с макросами и библиотечными контрактами; массивы — с Java interop. Не подключать их автоматически к правилу atom.

## Ограничения и открытые вопросы

- Soundness возможна лишь при контроле всех записей либо явно обозначенных доверенных границах. Внешний Java-код, непроверенные namespace, `any` и cast могут нарушить инвариант содержимого.
- Снимок стабилен как значение, но не как глубокий граф mutable объектов. Нужна классификация фактов, которые допустимо сохранять для вложенных объектов; полный heap/effect-анализ здесь не предложен.
- Validators, watches, `ref`/STM и agent остаются отдельными задачами.
- Volatile также инвариантен по чтению/записи, но не получает гарантий атомарности atom. Для JVM-массивов чекер распознаёт алиасы `^bytes`, `^objects` и строковые дескрипторы `^"[[I"`. Конструкторы массивов и `into-array` с явным классом выводят класс результата. `alength` возвращает известную длину или `int?`. `aget` выводит тип компонента на каждой размерности. Ссылочный элемент допускает `nil`. `aget`, `aset` и `aset-*` проверяют известные границы индексов. Анализ перегрузок `aset` ограничен доступными JVM-типами.
- У каналов остаются transducer-каналы с различными входным и выходным типами, `alts!`, закрытие, исключения и read-only/write-only интерфейсы. Последние потенциально допускают другую variance, но `t/chan T` в этом дизайне — полный инвариантный интерфейс.
- Нужны исследование строгого subtyping функций (контравариантные входы, ковариантный результат), политика `unknown` и завершение сравнения рекурсивных типов. До этого общий контракт высшего порядка нельзя объявлять sound.

## Конкретная матрица тестов

Матрица включает регрессии atom и план расширения на другие изменяемые типы.

| Сценарий | Ожидаемая проверка |
|---|---|
| `parse/show` для `Atom<int>` и `Chan<string>` | Round-trip сохраняет kind и параметр; неверная арность формы типа отклоняется |
| `Atom<int>` → `Atom<int>` | Принимается; alias сохраняет тот же контракт |
| `Atom<int>` → `Atom<number>` и обратно | Оба направления отклоняются; диагностика на аргументе |
| `Coll<int>` → `Coll<number>` | Принимается; регрессия существующей ковариантности |
| `Atom<unknown>`, `Atom<any>`, непрозрачный/рекурсивный T | Нет ложного доказательства эквивалентности; проверяется выбранная политика непроверенной границы |
| `atom` с ожидаемым T и неверным init | Ошибка инициализатора; не молчаливое расширение T |
| `(atom nil)` без ожидаемого union | Не выводит произвольный будущий T; тест фиксирует выбранную политику вывода |
| Пример 1; затенение имени snapshot | Сужение старого снимка сохраняется после reset; не переносится на новое связывание |
| Пример 2 с записью, без записи, с alias | Повторное чтение всегда полного T; все небезопасные вызовы отвергаются |
| `@state` и `(deref state)` | Одинаковый тип; неподдержанный deref другого класса не получает правило atom |
| `reset!` правильного/неправильного значения через alias | Успех / ошибка записи; тип ссылки неизменен |
| Три функции из примера 4 | Успех / ошибка результата / ошибка входа callback |
| `swap!` с extra args, неверной арностью, именованным callback | Проверяются все аргументы и результат; перегрузка не выбирается только по удачному члену union |
| Пользовательская функция с именем `swap!` | Обычный пользовательский контракт, не специальное core-правило |
| `aset` через `^objects` с известным `String[]` | Строка и `nil` допустимы, число отклоняется на месте записи |
| `aset` числа в `(object-array 1)` и в аргумент, известный только по `^objects` | Успех для конструктора, `TSP210-01` для аргумента |
| `aset-int` в `long[]` и `short[]`, `aset-byte` со значением `128` | Расширение допустимо, несовместимый компонент и недопустимый литерал отклоняются |
| `aset` в `byte[]` с `42` и `(byte 42)` | Литерал отклоняется, явное преобразование допустимо |
| Многоиндексный `aset` с `42` в элемент `long[][]` и `int[][]` | Допустим для `long[][]`, отклонён для `int[][]` |
| `aclone` массива `String[]` через `^objects` | Копия сохраняет класс, `aset` числа отклоняется |
| `amap` с телом `i` и `(byte i)` на `byte[]` | Индекс `long` отклоняется на теле, явное преобразование допустимо |
| Чтение канала до/после close; some? и отсутствие проверки | Всегда объединение T с nil; narrowing снимка разрешает использование T, без проверки ошибка |
| Запись nil в канал; mutable массив/volatile без поддержки | Не принимаются за реализованную безопасную операцию |

В строке про канал `T | nil` означает объединение типов. Существующие [test/features/src/f/core.clj](../test/features/src/f/core.clj) проверяют narrowing и коллекции, но не F340. [demo_test.clj](../test/typespec/demo_test.clj) запускает golden-примеры карточек только с метками `clojure example`/`text output`; обычные блоки этой карточки не дают автоматического покрытия.

## Критерий готовности и источники

Минимальный этап готов, когда положительные и отрицательные atom-тесты выше реально проверяют типы и позиции ошибок, unknown не маскирует отсутствие контракта, а ограничения внешних записей явно видны. Каналы/volatile/массивы отмечаются отдельно; до их покрытия нельзя заявлять выполнение всей карточки.
