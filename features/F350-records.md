# F350 · Records и номинальные классы

## Зачем

В Clojure record совмещает два свойства: это значение именованного JVM-класса и ассоциативная структура с полями. Структурно одинаковые `User` и `Team` не взаимозаменяемы там, где нужен конкретный класс. При этом обычные операции с данными не должны без причины терять информацию о классе. Особенно важно заметить обратный переход: удаление объявленного поля превращает record в обычную map, а последующий `assoc` класс не восстанавливает.

## Реализовано

Обычный `check` индексирует фабрики верхнеуровневых `defrecord` по исходникам. `->R` принимает по аргументу на каждое поле, `map->R` принимает один аргумент. Вызовы через alias, `:refer` и `apply` с известной длиной хвоста используют те же сигнатуры. Неверная арность даёт `TSP2554`. Явный `s/fdef` или декларация EDN с арностью фабрики задаёт типы аргументов и результата. Несовместимая арность декларации даёт `TSP2790`.

Те же правила действуют для `potemkin/defrecord+` и `potemkin.types/defrecord+`.

Если `s/fdef` задаёт только `:ret`, он описывает результат фабрики. Число аргументов берётся из `defrecord` у `->R` и равно одному у `map->R`.

Без явного контракта результата `->R` сохраняет обязательные поля и
типы переданных аргументов. Для полей `^long` и `^double` учитывается JVM-тип
сохранённого значения. В неуточнённой сигнатуре позиционной фабрики
эти поля принимают числовые аргументы. `map->R` сохраняет известные поля входной мапы
и её дополнительные ключи. При отсутствии объявленного поля
запись хранит `nil`, если это поле допускает `nil`. Явный контракт
результата сохраняет приоритет.
Для вектора или последовательности пар `map->R` проверяет записи
по правилам `into {}`, включая длину пары и последнее значение
при повторении ключа.
Для примитивных полей `map->R` требует сохранённые значения класса
`Long` или `Double` соответственно. Отсутствие поля и `nil`
дают ошибку. Проверка учитывает эти требования при явном контракте
результата.
Номинальная идентичность результата и тела методов остаются в плане F350.

## Примеры и ожидаемое поведение

Ниже пять самостоятельных сценариев. **Runtime** означает семантику Clojure. **Planned** обозначает будущую проверку. Неверная арность из второго сценария уже проверяется.

### 1. Корректно: фабрика и дополнительные ключи

```clojure
(defrecord User [id])
(let [u (->User 1)
      named (assoc u :name "Alex")]
  [(instance? User named) (:id named) (:name named)])
;; Runtime: [true 1 "Alex"]
```

Planned: `->User` требует ровно один аргумент; результат несёт идентичность `User`, обязательное поле `:id` со значением целочисленного типа. После `assoc` появляется обязательный дополнительный ключ `:name` строкового типа. Из самого имени поля `id` тип `int?` не следует: это факт конкретного значения, а не контракт всех `User`.

### 2. Ошибка: неверная арность конструктора

```clojure
(defrecord User [id])
(->User 1 "Alex")
;; Runtime: фабрика не поддерживает два аргумента.
```

Обычный `check` выдаёт `TSP2554` на вызове, где передано два аргумента при ожидаемом одном. Все аргументы анализируются. Дополнительные ключи можно добавить через `assoc` или map-фабрику.

### 3. Ошибка: структурная map вместо номинального значения

```clojure
(ns records.nominal)
(defrecord User [id])
(defrecord Team [id])
(defn take-user {:t/sig '[records.nominal.User :-> any?]} [u] u)
(take-user (->User 1))  ; planned: OK
(take-user {:id 1})    ; planned: ошибка, это не User
(take-user (->Team 1)) ; planned: ошибка, это Team
```

Метаданные `:t/sig` — существующий формат; разрешение объявленного в исходнике, но ещё не загруженного класса здесь **planned**. Clojure не исполняет эту сигнатуру как проверку: без checker все три вызова просто возвращают аргумент. Одинаковые поля не дают права построить номинальное доказательство. В обратную сторону record может удовлетворять структурному контракту по своим известным полям — при соблюдении требований к открытому хвосту.

### 4. Погранично: удаление поля необратимо теряет класс

```clojure
(defrecord User [id])
(let [u (assoc (->User 1) :name "Alex")
      a (dissoc u :name)
      b (dissoc u :id)
      c (assoc b :id 2)]
  [(instance? User a) (instance? User b) (instance? User c)
   (:name b)])
;; Runtime: [true false false "Alex"]
```

Planned: `a` остаётся `User`; `b` — структурная map с `:name`, без `:id`; `c` — map с двумя ключами, но не `User`. Удаление отсутствующего дополнительного ключа тоже сохраняет record. Для ключа, неизвестного статически, нельзя без доказательства оставить только record-ветку.

### 5. Погранично: отсутствующее поле в map-фабрике

```clojure
(defrecord User [id])
(let [u (map->User {:name "Alex"})]
  [(instance? User u) (contains? u :id) (:id u) (:name u)])
;; Ожидаемая семантика Clojure: [true true nil "Alex"]
```

Planned: отсутствие `:id` во входной map не означает отсутствие поля в результате. Для обычного поля без primitive hint оно заполняется `nil`, а дополнительные ключи сохраняются. Если в будущем у поля задан non-nil контракт, ошибка должна говорить о подставляемом `nil`, а не утверждать, что Clojure вообще запрещает такой конструктор. Синтаксис и источник такого контракта ещё не выбраны. Primitive-поля требуют отдельной проверки поведения JVM-конструкторов; этот пример на них не распространяется.

## Planned: алгоритм проверки

Это проект ограниченного механизма для обычных immutable JVM-records, а не доказанный sound алгоритм для всего `defrecord`, interop и произвольных макросов.

1. **Вход.** AST с позициями, namespace/import/alias-окружение, объявления `defrecord`, сигнатуры и типы аргументов. До анализа тел собрать таблицу record-деклараций: полное имя класса, символы фабрик `->R`/`map->R`, упорядоченный список полей, keyword каждого поля, hints и позиции. Не исполнять проектный код и не требовать загрузки сгенерированного класса. Повторные определения и конфликты имён не разрешать молча.
2. **Представление.** Добавить внутренний вариант типа record (название и формат пока проектные): nominal-id, карта обязательных объявленных полей, карты обязательных/возможных дополнительных ключей и описание открытого хвоста. Отдельно хранить доказанные ограничения хвоста и факты отсутствия ключей. Не смешивать тип конкретного экземпляра, например `:id = int?`, с глобальным контрактом поля. У record все объявленные поля присутствуют, даже если их значение `nil`.
3. **Конструкторы.** Для `->R` проверить арность по порядку полей, вывести тип каждого аргумента и сопоставить с явным контрактом поля, если он существует. Для `map->R` проверить, что вход — поддержанный ассоциативный источник; извлечь объявленные ключи, для отсутствующих подставить `nil`, для optional объединить значение с `nil`. Остальные ключи перенести в дополнительные. При неизвестном входе не выдумывать точные поля: результат может иметь известный nominal-id, но значения остаются непроверенными. Потенциальное исключение конструктора — отдельный вопрос, не доказательство успешного результата.
4. **Чтение и совместимость.** Keyword lookup/get/destructuring используют проекцию record в поля. Объявленное поле не получает `nil` только из-за возможности отсутствия: оно всегда есть; `nil` может уже входить в его тип. Для nominal-цели требовать совпадение класса либо доказанное отношение JVM-классов/интерфейсов. Для структурной цели проверять проекцию полей и хвост. Map не становится record через структурное сравнение. Открытый неизвестный хвост не доказывает exact-map контракт.
5. **Изменение.** `assoc` с literal-ключом сохраняет nominal-id, заменяет факт о значении поля либо добавляет обязательный extra-key; при наличии контракта проверяет новое значение. `dissoc` extra-key сохраняет nominal-id и удаляет ключ; `dissoc` объявленного поля создаёт обычную map с оставшимися полями/extra-keys/хвостом. Несколько ключей обрабатывать последовательно: после потери класса следующие операции уже структурные. `update` нельзя просто возвращать исходным типом: результат функции меняет факт о поле и проверяется как запись.
6. **Неизвестные ключи и объединения.** Для конечного множества возможных ключей разнести проверку по вариантам и объединить результаты; для union входов аналогично. Для произвольного ключа учитывать обе возможности `dissoc`: record сохраняется или превращается в map с возможным отсутствием объявленных полей. Без реализованного представления этих альтернатив вернуть консервативный непроверенный результат, а не точный record. Правила неизвестного `assoc` должны также ослаблять типы всех полей, которые он мог заменить; это требует отдельного проектирования хвостов и корреляций.
7. **Результат и диагностика.** Вернуть тип/факты результата, признак непроверенной части и диагностики с позицией операции, ожидаемым/фактическим типом, nominal-id и причиной потери класса. Предлагаемые категории: `proposed TSP350-01` — арность фабрики, `proposed TSP350-02` — nominal mismatch, `proposed TSP350-03` — нарушение контракта поля, `proposed TSP350-04` — неподдержанная record-операция. Это не существующие коды; сначала проверить возможность использования общей диагностики арности/типов.

## Интеграция с checker

- `env.clj`: сбор record-объявлений и фабрик рядом с обычными vars; поддержка ссылок между исходными namespace без `Class/forName`.
- `types.clj`: новый внутренний вариант, его печать и сравнение; structural projection не должна стирать nominal-id исходного значения. Текущая терпимость `sub?` к `unknown` не должна считаться доказательством контракта.
- `check.clj`: отдельный обработчик `defrecord` вместо заглушки; разрешение фабрик в обычной проверке вызовов; ветки для record в чтении ключей, `assoc`, `dissoc`, `update`. Обычные map-правила оставить самостоятельными. `instance?` может уточнять класс, но не доказывает типы значений полей, которые не закреплены глобальным контрактом.
- `java.clj`: согласовать исходные классы с reflection/interop. Загруженный JVM-класс без описания полей даёт номинальность, но не точную структуру. Прямые `R.`/`new`, методы протоколов и field access нельзя молча считать покрытыми правилами двух фабрик.

## Ограничения и нерешённые вопросы

- Reference задаёт nominal class + fields + open extra keys, но не задаёт язык контрактов record-полей. Нельзя автоматически приписывать `id` тип зарегистрированного `:some.ns/id` или выводить глобальный тип по одному вызову конструктора.
- Открытый хвост должен учитывать не только keyword-ключи; record допускает дополнительные ассоциативные ключи. Нужны тесты перекрытия хвоста с полями и фактов отсутствия после `dissoc`.
- Нужны исследования primitive hints, прямых JVM-конструкторов, сериализации и внешних экземпляров: nominal-id сам по себе не гарантирует исследованный набор типов значений полей.
- `merge`, `conj`, `empty`, `select-keys`, Java field access, тела протокольных методов и пользовательские макросы требуют самостоятельных transfer rules. Простое использование нынешнего `merge`, создающего структурную map, не реализует record-семантику. До появления правил отмечать такие пути непроверенными.
- Уточнение через `record?` доказывает только принадлежность к records вообще, не конкретный класс. ClojureScript, `deftype`, generic records и полный JVM interop вне первой версии F350.
- Soundness требует согласования с открытыми maps, narrowing, неизвестными значениями и импортированными классами; перечисленные шаги — спецификация первого этапа, не доказательство корректности всей системы.

## Конкретная матрица тестов

Арность фабрик уже проверяется. Остальные свойства результатов в таблице запланированы. Runtime-проверки сравнивают семантику на зафиксированной версии Clojure.

| Случай | Ожидаемый результат |
|---|---|
| `->R` с 0/1/2 аргументами при одном поле | Ошибка / record / ошибка; точная арность и позиция |
| `->R` с разными типами значений, без контракта | Оба допустимы, факты экземпляров различаются |
| Пример 3: R / map / другой record | Только R удовлетворяет nominal-цели |
| Record передан в structural-map контракт | Поля проверяются, nominal-id у исходного значения не теряется |
| `assoc` declared-key / extra-key | Класс сохраняется; факт значения заменяется / появляется |
| `dissoc` extra-key / absent-key / declared-key | Record / record / map |
| Удалить поле, затем вернуть его `assoc` | Всё ещё map |
| `map->R`: поле required / optional / absent | T / T union nil / nil; поле результата присутствует |
| `map->R` с дополнительными ключами | Ключи сохраняются, не становятся объявленными |
| `dissoc` с union ключей и произвольным ключом | Union record/map либо явно непроверенный результат |
| Неизвестный ключ `assoc`, `update` меняет тип поля | Нет сохранения устаревшего факта о поле |
| Non-nil контракт и пропущенное поле | Ошибка подставляемого nil после выбора языка контрактов |
| Два namespace с одинаковым коротким именем R | Разные nominal-id; aliases разрешаются корректно |
| Загруженный класс без схемы; неизвестный macro-конструктор | Нет выдуманных фактов о полях; видна непроверенность |
| Обычные map-тесты m1/m2 | Существующее поведение не меняется |

Готовность: реализованы поддержанные ветви, отрицательные случаи дают устойчивые диагностики, unsupported-пути явно видны; примеры превращены в исполняемые тесты. Одного успешного `instance?` недостаточно для смены implementation.
