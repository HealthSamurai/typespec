# F410 · Арности, перегрузки и apply

[F411](F411-apply-fixed-tail.md) реализует `apply` с известной
формой хвоста. Замечания ниже о пропуске `apply` описывают
исходное состояние до F411. Для однородного хвоста чекер
проверяет, покрывают ли сигнатуры все достижимые арности.

[F412](F412-spec-regex-arities.md) добавляет нижнюю границу `s/+`
и конечные `s/alt` из `s/fdef` и `s/fspec`.

Рекурсивный вызов именованного `fn` проверяется по арностям самого
`fn`. Контекст колбэка даёт типы для вызовов с подходящей арностью.
`(fn step [x & [option]] ...)` может вызвать себя с дополнительным
аргументом, даже если `map` передаёт только `x`. Ошибка арности
остаётся видна в прямом вызове и через `apply` с известным хвостом.
Когда тело вызывает другую арность того же `fn`, типы аргументов
передаются в выбранное по правилам Clojure тело. Это также работает
через `apply` с известным хвостом и в коллекционных правилах. При
возврате к уже анализируемой арности используется доступный контракт.

Если все перегрузки отвергают вызов, диагностика берётся из перегрузки
с наименьшим числом несовместимых аргументов. При равенстве предпочтение
получают перегрузки, у которых совпадают более ранние аргументы.

Прямой вызов известной мапы, вектора, множества или символьного ключа
проверяется по тем же правилам доступа, что и `apply` с известным хвостом.
Вывод работает для локальных значений и доступных типов Var из другого namespace.
Мапа и вектор в роли callback проверяются по тому же контракту доступа.
`map`, `mapv` и `pmap` сохраняют результат каждой из известных позиций
при таком lookup, если их не больше 64.
Вызов через `apply` использует `:ret` из `s/fdef`, когда входная арность не объявлена.
Это работает и с известными позициями хвоста, и с последовательностью неизвестной длины.

## Обновление реализации — топ-10

Функциональная совместимость теперь проверяет арности/параметры/результат. Неподдержанные mixed fixed+rest source contracts и kwargs между различными контрактами дают inconclusive. При неоднозначных непроверенных перегрузках результат консервативно unknown. apply не реализован.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Зачем

В Clojure одна функция часто имеет короткую форму вызова, форму с дополнительными параметрами и variadic-ветвь. Ошибка в количестве аргументов иначе обнаруживается только при выполнении. `apply` переносит эту проблему на данные: нужно проверить не один аргумент-коллекцию, а список аргументов, который из неё получится. Эти проверки нужны и без generics.

Следует различать **ветви реализации по числу аргументов** и **типовые перегрузки** одной ветви. JVM/Clojure не выбирает тело `defn` по типу аргумента. Поэтому порядок типовых перегрузок сам по себе не доказывает, какой результат вернёт тело.

## Что есть сейчас

Проверено по исходникам, не по полноте обещаний reference:

- `types/parse-sig` читает `[A B :-> R]`, `[A & E :-> R]` и список таких векторов. Внутренний тип — `{:t :fn :arities [{:params [A B] :rest E-or-nil :ret R}]}`. `:rest` означает тип **каждого дополнительного аргумента**, а не всей коллекции.
- `env/defn-parts` и `split-params` извлекают ветви реализации. `check/arity-fits?` допускает ровно `k` аргументов для фиксированной ветви и `n >= k` при `:rest`/`:kwargs`. `arg-problems` проверяет фиксированные и дополнительные аргументы.
- `call-fn` выдаёт `TSP2554` при неподходящем количестве; при несовместимости типов используются обычные диагностики, в том числе `TSP2345` и `TSP2531`.
- Сейчас при нескольких подходящих типовых перегрузках выбирается первая; для верхнеуровневого `unknown`/`any` — последняя подходящая, а при разных возвращаемых типах результат становится `unknown`. Есть эвристика снятия `nil` для выбора диагностики. Это **не** общий алгоритм разрешения неоднозначности.
- `check-defn` выбирает одну декларацию для тела по числу параметров и признаку rest, затем имеет fallback только по числу. Rest-параметр с известным `E` получает `nil | seq<E>`. Все типовые перегрузки одного тела независимо не проверяются; лишние декларации не гарантированно отсекаются.
- Для `clojure.core/apply` нет ни специального правила, ни записи в `core-types/externs`. Его аргументы обходятся обычным inference, но целевой вызов не проверяется, результат — `unknown`. Внутренние `apply-type`/`apply-fn-node` обслуживают HOF, а не реализуют семантику `clojure.core/apply`.
- Литерал вектора сейчас становится однородной коллекцией с объединением типов элементов: длина и позиционные типы теряются. Tuple-разворачивание для `apply` — planned.

Таким образом, `implementation: partial` сохранён: обычные арности и rest работают частично, `apply` и надёжное согласование перегрузок ещё не готовы.

## Примеры

Обычные fences ниже — спецификация поведения, не исполняемые golden-тесты. Current означает вывод из текущих путей checker; отдельный прогон этих примеров здесь не заявляется. Planned не следует считать уже поддержанной гарантией.

### 1. Корректные фиксированные ветви — current

```clojure
(defn label
  {:t/sig '([string? :-> string?]
            [string? string? :-> string?])}
  ([x] x)
  ([prefix x] (str prefix x)))

(label "item")       ; current: string, допустима ветвь с одним аргументом
(label "#" "item")   ; current: string, допустима ветвь с двумя
(label)              ; current: TSP2554, ожидается 1 или 2, получено 0
```

### 2. Тип rest и его нижняя граница — current

```clojure
(defn total
  {:t/sig '[int? & int? :-> int?]}
  [x & xs]
  (reduce + x xs))

(total 1)            ; current: допустимо, дополнительных аргументов нет
(total 1 2 3)        ; current: int
(total)              ; current: TSP2554, минимум один аргумент
(total 1 "2")        ; current: TSP2345 на "2", rest ожидает int
```

Пустой rest в теле не равен обязательной непустой последовательности. Тип `E` в сигнатуре ограничивает элементы при их наличии.

### 3. `apply` с известными аргументами — planned

```clojure
(defn pair-text
  {:t/sig '[string? int? :-> string?]}
  [s n] (str s n))

(apply pair-text ["n=" 2])       ; planned: string, эквивалент двух аргументов
(apply pair-text "n=" [2])       ; planned: string, явный префикс + хвост
(apply pair-text ["n="])         ; planned: TSP2554, передан только один
(apply pair-text ["n=" "two"])   ; planned: TSP2345 на втором элементе
```

Current для этих `apply`: `unknown`, без проверки арности/типов целевой функции. Нельзя объявлять отсутствие ошибок успехом. Planned должен учитывать также пустой хвост: `(apply pair-text "n=" 2 nil)` эквивалентен `(pair-text "n=" 2)`.

### 4. Неизвестная длина — planned, не точная арность

```clojure
(defn add-two {:t/sig '[int? int? :-> int?]} [a b] (+ a b))
(defn add-many {:t/sig '[int? & int? :-> int?]} [a & xs]
  (reduce + a xs))

(defn fixed-from-data
  {:t/sig '[(s/coll-of int? :kind vector?) :-> any?]}
  [xs]
  (apply add-two xs))        ; planned: непроверено, длина xs не доказана

(defn variadic-from-data
  {:t/sig '[(s/coll-of int? :kind vector?) :-> any?]}
  [xs]
  (apply add-many 0 xs))     ; planned: int; префикс покрывает минимум,
                            ; каждый дополнительный элемент подходит
```

Current оба вызова `apply` дают `unknown`. Тип однородной коллекции не доказывает длину 2. Второй случай допускает любой конечный хвост, включая пустой; завершаемость ленивых последовательностей здесь не доказывается.

### 5. Перекрывающиеся типовые перегрузки — граница гарантии

```clojure
(defn classify
  {:t/sig '([int? :-> int?]
            [number? :-> string?])}
  [x] x)

(classify 1)       ; current: выбирается первая подходящая, результат int
(classify 1.5)     ; current: заявленный string из второй перегрузки
```

Current тело проверяется по первой подходящей декларации с одним параметром, поэтому вторая декларация не получает полноценной проверки. Реальное тело возвращает `1.5`, а не строку. Planned: отклонить такую декларацию по результатам проверки тела для каждого контракта; `int` также входит в `number`, и обещания результатов на пересечении должны быть согласованы. Это не две ветви runtime-dispatch. Простая перестановка списка сигнатур не должна менять доказанность программы.

## Пошаговый алгоритм проверки

Ниже — целевой консервативный план. Точный вызов и ограниченный случай однородного хвоста реализуемы отдельно; общий случай пересечений перегрузок ещё требует исследования. Это не заявление о soundness текущего checker.

1. **Вход.** AST вызова, разрешённый символ вызываемой функции, тип функции, окружение spec/алиасов, позиции аргументов и факты о коллекциях. Для `apply` распознавать именно `clojure.core/apply`, а не затенённое локальное имя. Сначала проверить наличие функции и последнего аргумента-хвоста; их отсутствие не смешивать с арностью целевой функции.
2. **Нормализация контрактов.** Сохранить существующие `:params`, `:rest`, `:ret`, позиции и источник деклараций. Сопоставить их с фактическими fixed/variadic-ветвями. Отдельно проверить отсутствующие и лишние декларации, несовпадение fixed/rest. Для каждой декларации проверить соответствующее тело под её входными типами, а не выбрать одну по порядку. Согласование источников (`t/sig`, `s/fdef`, sidecar) остаётся задачей соответствующих карточек; здесь нужны уже согласованные контракты.
3. **Форма списка аргументов.** Обычный вызов даёт точный вектор типов и узлов. Для `apply` предлагается внутренний факт `prefix + tail`: prefix — позиционные типы с origin, tail — точный tuple либо однородный элементный тип с нижней/верхней границей длины. Эти поля ещё не реализованы. `nil`/пустой хвост дают длину 0. Не исполнять коллекцию при анализе. Векторный AST можно развернуть локально, но перенос знания через переменные требует инфраструктуры F330, а не повторного чтения литерала по имени.
4. **Арность и runtime-ветвь.** Для точного списка вычислить `n`: фиксированная ветвь требует `n=k`, rest — `n>=k`. Учитывать реальную диспетчеризацию Clojure: фиксированная ветвь при совпадении числа аргументов имеет приоритет над variadic fallback. Для интервала длин проверить покрытие **всех** возможных длин, а не наличие хотя бы одного кандидата. Если все длины запрещены — ошибка; если часть возможна, но доказательства нет — непроверено. Минимально реализуемый безопасный случай: префикс уже покрывает обязательные параметры единственной variadic-ветви, и ни одна фиксированная ветвь не перехватывает возможную длину.
5. **Типы аргументов.** Сопоставить каждый позиционный тип с параметром через существующие `problems`/`sub?`. Остальные элементы проверить против rest. Для однородного хвоста проверить его элементный тип против всех позиций, которые он может занять, и rest; не считать неизвестный элемент подходящим без основания. `any` сохраняет явно небезопасный характер, а не превращает результат в доказанный. `:kwargs` не приравнивать к произвольному rest: ему нужны правила пар ключ/значение.
6. **Перегрузки.** Если остаётся один доказанный контракт — использовать его результат. Не выбирать произвольную декларацию при нескольких кандидатах. Пока не доказаны совместимость контрактов и проверка тела для каждого из них, вернуть непроверенный результат. После такого доказательства возможен консервативный union результатов достижимых случаев; это менее точно, но не должно зависеть от порядка деклараций. Объединение результатов само по себе не исправляет непроверенное тело. Разбиение union аргументов с корреляциями, проверка пересечений доменов и специфичность контрактов — отдельная исследовательская работа.
7. **Результат и диагностика.** Возвращать тип вместе с состоянием «проверено / ошибка / непроверено» и причиной. Ошибка количества — существующий `TSP2554`; ошибка элемента — существующий `TSP2345` (или более точная существующая диагностика). В `apply` указать позицию элемента и путь через хвост; для неизвестной длины — позицию хвоста. Для ещё не поддержанных случаев предлагаются **proposed TSP410-01** (не доказана форма/длина хвоста) и **proposed TSP410-02** (не разрешены перекрывающиеся контракты). Это не зарегистрированные коды прототипа.

## Интеграция и ограничения

- Вынести общую проверку уже выведенных типов аргументов из `call-fn` и `apply-type`, сохранив позиции, nil-диагностики и одинаковую политику перегрузок. Сейчас эти два пути расходятся, например по возвращаемому типу при ошибке арности.
- Добавить специальное правило `apply` в `check/special`, использующее тот же механизм, а не фиктивную сигнатуру «функция + коллекция → any». Не выводить аргументы повторно с дублированием диагностик.
- Укрепить `check-defn`: fallback только по числу параметров не доказывает совместимость fixed/rest; проверка одного контракта не подтверждает все перегрузки.
- `types/cat-items` сейчас переводит и `s/*`, и `s/+` в одинаковый rest. Поэтому минимальная длина для `s/+` теряется. Нужны отдельный факт нижней границы и отрицательный тест; не считать поддержку `s/fdef` полной.
- Не расширять эту карточку до всей грамматики regex-spec: вложенные `s/alt`, зависимости аргументов, ограничения cardinality и коррелированные union требуют отдельного дизайна. Аналогично callable maps/keywords/sets, JVM `IFn`, примитивные ограничения и Java-overloads не покрываются одним `{:t :fn}` алгоритмом.
- `nil` как пустой хвост нужно отличать от неподдержанного/non-seqable значения. Политику строк, массивов, map/set-хвостов и ленивых/бесконечных последовательностей следует описать и проверить отдельно; нельзя без доказательства назначать им tuple-порядок.
- F330 отвечает за tuple/длину, F230 — за generics/HOF. Здесь описано использование этих фактов, а не повторение их вывода.

## Конкретная матрица тестов

| Сценарий | Вход/вариации | Проверяемый результат | Состояние |
|---|---|---|---|
| Фиксированные арности | `label`: 0, 1, 2, 3 аргумента | успех только 1/2; `TSP2554` для 0/3 | механизм current; existing fixture покрывает вызов 3 вместо 1/2 |
| Несовместимый аргумент | `label 1` | `TSP2345`, позиция `1` | current, добавить отдельную регрессию |
| Rest | `total`: 0, 1, 3 аргумента, строка в хвосте | минимум 1; все rest проверены; позиция строки | current, нужны выделенные тесты |
| Тело rest | пустой/непустой rest | локальный тип допускает nil; элементы имеют E | current, нужен тест выведенного типа |
| Fixed + variadic | точная fixed-арность и соседние числа | runtime-приоритет fixed, не порядок контрактов | planned |
| Контракт ↔ тело | лишняя арность; отсутствующая; fixed/rest с одинаковым k | несовпадения отклонены, все контракты проверены | частично current, усиление planned |
| Перекрытие | `classify`; обратный порядок деклараций | тело не подтверждает все контракты; порядок не скрывает ошибку | planned |
| Неизвестные типы | unknown/any и несколько разных `:ret` | не выбирать узкий результат без доказательства | current частичная эвристика, planned единая политика |
| Точный apply | tuple целиком; явный prefix + tuple | тот же тип/ошибки, что у прямого вызова | planned |
| Пустой apply-хвост | `[]`, `nil`, prefix с ними | 0 дополнительных аргументов; проверена целевая арность | planned |
| Однородный хвост | vector<int> неизвестной длины к fixed/variadic | fixed непроверен; покрытый prefix + rest<int> допустим | planned |
| Границы длины | интервал полностью допустим / частично / полностью запрещён | проверено / непроверено / ошибка | planned |
| Не seqable / неизвестный хвост | число / unknown | ошибка доказанно неподходящего хвоста / непроверено | planned, уточнить набор seqable |
| `s/+` против `s/*` | ноль и один повторяемый аргумент | ноль запрещён только для `+` | known gap текущей нормализации |
| Разрешение имени | core apply / локальная функция с именем apply | специальное правило только для core | planned |
| Диагностики | ошибка в tuple-элементе; неизвестная длина | origin элемента/хвоста, причина, без дублей | planned |

Критерий готовности: добавить эти регрессии без изменения ожидаемых результатов ради сокрытия ошибок; проверить не только текст диагностик, но выведенный тип и состояние непроверенности. Перед `implemented` нужны доказанные ограничения алгоритма перегрузок и golden-тесты `apply`.
