# F420 · Throw, assert и try

## Зачем

В Clojure проверка входных данных часто заканчивается `throw`, чтение внешних данных — `try/catch`, а освобождение ресурсов — `finally`. Проверяющий должен отличать возвращаемое значение от отсутствия нормального продолжения: ветка с исключением не добавляет `nil` к результату. И наоборот, `catch`, возвращающий `nil`, действительно делает результат nullable. Нельзя считать `assert` безусловной проверкой: assertions могут быть отключены при компиляции формы.

Это карточка о **типах нормальных результатов и достижимости**, а не о checked exceptions. Reference §4.3 прямо исключает отслеживание checked exceptions; сигнатуры функций не получают список `throws`.

## Current: что есть в исходниках

- `check.clj`, `special 'throw`: обходит аргументы через `infer` и возвращает `t/never`. Не проверяет число аргументов и принадлежность значения `Throwable`.
- `types.clj`, `union`: удаляет `:never`; объединение только из `never` даёт `never`. `special 'if` объединяет результаты двух ветвей и использует `narrow` для локальных контекстов.
- `special 'try`: объединяет тип тела и **всех** `catch`. Локальный символ исключения получает разрешённый Java-класс, а если разрешить класс не удалось — `unknown`. Порядок перехватов и возможность исключения из тела не анализируются.
- `finally` обходится для диагностики, но его результирующий тип отбрасывается, даже если это `never`.
- `infer-body` — `reduce`, возвращающий тип последней формы. После `throw` он продолжает обход и теряет отсутствие нормального продолжения. Факты от предыдущей формы в следующий контекст не передаются.
- Для `assert` нет специального правила. `infer-list` возвращает `unknown` для стандартного макроса без правила, не проверяя его содержимое; это не реализация assertion narrowing и не гарантия диагностики пропущенной проверки.

Следовательно, `implementation: partial` сохранён. Наличие `never` само по себе не означает реализованный анализ потока.

## Примеры и ожидаемое поведение

Обычные fences ниже — спецификация и разбор исходников, **не исполняемые golden-тесты**. Current означает вывод из текущих правил, а не результат нового запуска. Каждый фрагмент независим; `t/sig` читается как данные типов.

### 1. Корректная ветка с исключением

```clojure
(defn require-name
  {:t/sig '[(s/nilable string?) :-> string?]}
  [x]
  (if (string? x)
    x
    (throw (Exception. "name is required"))))
```

Current: положительная ветка сужает `x` до строки, отрицательная даёт `never`; объединение даёт строку. Planned сохраняет это поведение. Это не доказательство правильности конструктора исключения: проверка `throw` пока не проверяет тип операнда.

### 2. Ошибочный операнд throw

```clojure
(defn broken []
  (throw "not an exception"))
```

Current: возвращает `never`, но нарушение контракта `Throwable` не диагностирует. Planned: ошибка на строковом операнде — `proposed TSP420-01`, «throw ожидает Throwable, получен string?». Отсутствие нормального результата и корректность операнда — независимые свойства. Для `unknown` нельзя выдавать подтверждение совместимости: требуется результат «не проверено», а не ложная точность.

### 3. Catch меняет тип результата

```clojure
(defn parse-number
  {:t/sig '[string? :-> (s/nilable int?)]}
  [s]
  (try
    (Long/parseLong s)
    (catch NumberFormatException e
      nil)))
```

Current: объединение результата Java-вызова (`int?`) и `nil`; такая сигнатура соответствует результату. Planned: тот же консервативный результат, без обещания, что другие исключения невозможны. Замена возвращаемого типа на `int?` должна быть отдельным отрицательным тестом проверки возвращаемого значения. `e` доступен только в теле этого `catch`, с классом `NumberFormatException`.

### 4. Пограничный случай: нормальное и аварийное завершение finally

```clojure
(try 42
     (finally "cleanup completed"))

(try 42
     (finally (throw (Exception. "cleanup failed"))))

(do (throw (Exception. "stop"))
    42)
```

Current: все три формы получают тип последнего значимого значения `42`, поскольку результат `finally` игнорируется, а `infer-body` теряет ранний `never`. Planned: первая форма сохраняет `42`, две остальные дают `never`. При исключении из `finally` прежний результат не возвращается; исключение из `finally` не перехватывается соседним `catch` того же `try`. Недостижимую форму можно проверять для локальных ошибок, но она не должна менять тип результата или факты живого пути.

### 5. Assert и ранний выход — разные основания для сужения

```clojure
(defn with-assert
  {:t/sig '[(s/nilable string?) :-> string?]}
  [x]
  (assert (string? x))
  x)

(defn with-guard
  {:t/sig '[(s/nilable string?) :-> string?]}
  [x]
  (if (string? x)
    nil
    (throw (Exception. "expected string")))
  x)
```

Current: ни одна первая форма не передаёт сужение в последующую `x`; проверка возврата видит nullable-параметр. Planned: `with-guard` допускается после реализации передачи фактов по нормальным выходам. Для `with-assert` политика по умолчанию не разрешает сужение, зависящее от assertions. В будущем отдельный режим сужения допустим только при гарантированном включении assertions **при компиляции проверяемой формы**, а не при случайном значении `*assert*` в процессе checker. Сам `assert` при успешной проверке возвращает `nil`, а не тип проверенного значения.

## Planned: алгоритм проверки

Ниже — проект консервативного анализа. Это **не доказанный sound алгоритм для всего Clojure**: нужны уточнение семантики макросов, модель эффектов и проверка правил композиции. До этого нельзя объявлять закрытый набор исключений или удалять `catch` по предположению, что вызов «не бросает».

### 1. Вход и представление

Вход: AST из `parse`, позиции форм, окружение типов и imports, локальные bindings, факты narrowing, конфигурация assertions. Существующие типы сохраняются: `{:t :never}`, `{:t :union :types [...]}`, Java-классы и `unknown`.

Для композиции требуется внутренний результат проверки, отдельно от пользовательского типа: нормальный тип `normal`, факты нормального выхода `facts`, сведения о проверенности `coverage` и вид ненормального перехода. `normal = never` означает отсутствие нормального завершения, **не** «точно выбрасывает исключение»: текущий `recur` тоже даёт `never`. Не смешивать исключение, повтор цикла и возможную дивергенцию. На первом этапе не строить точные множества исключений; считать обработчики потенциально достижимыми.

Факты относятся к стабильным локальным значениям, а не к произвольному выражению. Нельзя переносить факт о результате `deref` или чтении изменяемого объекта через вызов/повторное чтение без отдельной модели эффектов.

### 2. Последовательность и ветвление

1. Начать последовательность с нормального типа `nil` и входных фактов.
2. Проверять формы слева направо. Передавать следующей форме только факты нормального выхода предыдущей.
3. Если нормального выхода нет, последующие формы не восстанавливают его. Возможный диагностический обход мёртвого кода выполняется отдельно, без участия в выводе результата.
4. Для условной формы проверить условие и получить два контекста через правила `narrow`. Если само условие не завершается нормально, ветви не создают нормальный выход.
5. Объединить типы нормальных выходов. Факты после слияния — только утверждения, верные на каждом нормальном пути. Если один путь заканчивается `throw`, его факты не участвуют; это позволяет `with-guard`.

Это изменение требуется не только `do`: вычисление аргументов, `let`-инициализаторов и условий тоже должно сохранять отсутствие нормального продолжения. Локальная правка одного `infer-body` недостаточна.

### 3. Throw

1. Проверить форму и ровно один операнд; ошибку формы привязать к `throw`.
2. Проверить операнд с учётом порядка вычисления. Если он сам не имеет нормального выхода, не создавать фиктивное последующее исключение от `throw`.
3. Для нормального значения проверить совместимость с `java.lang.Throwable`. Заведомо несовместимое значение — `proposed TSP420-01`; неизвестное — явно непроверенный контракт. Отдельно определить политику `nil`: JVM бросает NPE при `throw null`, а значит это всё равно не нормальный выход, хотя полезен lint о вероятной ошибке.
4. Результат нормального выхода — `never`. Сохранить диагностики вычисления операнда независимо от результата.

### 4. Try и catch

1. Разобрать грамматику: тело, упорядоченные `catch`, необязательный последний `finally`. Неверный порядок, класс не-Throwable и неверное связывание не должны молча превращаться в обычные формы.
2. Проверить тело по правилу последовательности.
3. Каждый `catch` проверять в отдельном контексте: внешние стабильные факты плюс локальное исключение заданного класса. Не переносить в него факты нормального выхода тела: исключение могло возникнуть раньше.
4. Проверить разрешение класса и наследование от `Throwable`; для неизвестного класса отметить непроверенность. Проверить покрытие более позднего класса более ранним как отдельную структурную диагностику, не как доказательство отсутствия исключений из тела.
5. Консервативно объединить нормальные результаты тела и обработчиков. Исключения, возникшие в теле `catch`, не направлять в последующие `catch` этого же `try`.
6. На первом этапе допускается завышенный union из всех обработчиков. Убирать обработчик по достижимости можно лишь после исследования исключительных переходов и неизвестных вызовов.

### 5. Finally

Проверить `finally` в контексте, безопасном для всех входящих путей, включая исключительные; не брать только факты успешного тела. При нормальном завершении `finally` его значение отбросить, сохранив прежний нормальный результат. Если `finally` гарантированно не имеет нормального выхода, весь `try` не имеет нормального результата. При смешанных путях сохранить прежний результат только для нормальных выходов `finally`; аварийные выходы не добавляют возвращаемого значения. Перехват исключений из `finally` возможен лишь снаружи.

Без точной модели эффектов не выводить новые внешние факты из `finally`. Нужно отдельно исследовать дивергенцию, вложенные `try` и допустимость `recur` через границу `try`; `never` недостаточен для этой задачи.

### 6. Assert и результат проверки

Распознавать именно стандартный `clojure.core/assert`, не одноимённую пользовательскую функцию. Проверить условие, а сообщение — в контексте провала, когда оно вычисляется. По умолчанию после формы сохранить входные факты: политика должна покрывать и компиляцию без assertions. Для подтверждённого режима assertions-on использовать факты истинного условия на нормальном выходе; ложный путь завершает форму исключением. Для assertions-off тело макроса не исполняется: возможный lint его исходника не равен проверке исполняемого потока.

Выход checker: тип нормального результата, факты продолжения, покрытие и диагностики с позицией, фактическим/ожидаемым типом и объяснением пути. Для синтаксиса управления предлагается `proposed TSP420-02`; для непроверенного контракта исключения — `proposed TSP420-03`. Эти коды ещё **не зарегистрированы**. Несовместимость результирующего типа с сигнатурой должна идти через существующую проверку возврата, а не через новый код F420. Новая политика assertions должна быть видимой в выводе/конфигурации, иначе результат проверки невоспроизводим.

## Интеграция и ограничения

- Точки изменений: `check.clj` — `infer-body`, `infer-list`, `special` для `throw`, `if`, `try`, новое правило `assert`; связывание фактов через `bind`/`narrow`. Это будущие изменения, не сделанные этой карточкой.
- `types.clj/union` уже подходит для объединения нормальных значений, но не заменяет модель переходов. Внешние сигнатуры могут оставаться без эффектов.
- Проверки классов используют существующее разрешение imports и Java-наследование; диагностики используют `report!` и позиции AST.
- Неизвестные вызовы могут бросать исключения. Статический тип результата — не обещание успешного выполнения, отсутствия исключений или окончания программы.
- Полная точность catch-порядка, исключений из макросов/Java, invalidation фактов и связи с `recur` требует отдельных исследований. Нельзя заявлять soundness на основе пяти примеров.
- Стандартный макрос без правила сейчас может быть пропущен без предупреждения. Нужно отдельное подтверждение покрытия для assertions, а не только отсутствие ошибок.

|---|---|---|

| `(throw "x")` | Только `never` | `proposed TSP420-01` на операнде |
| Ноль/два аргумента throw | Нет отдельной проверки формы | `proposed TSP420-02` на форме |
| Throw с unknown и с nil | Нет проверки контракта | Unknown виден в покрытии; для nil зафиксировать политику, normal = never |
| Пример 3 с nullable-сигнатурой | Union int/nil | Положительный тест |

| Локальный e в catch / обращение снаружи | Локальный bind в catch | Тип класса внутри, отсутствие утечки наружу |
| Catch String / неразрешённый класс | Нет проверки Throwable; возможен unknown | Ошибка класса / явная непроверенность |
| Catch Exception перед NumberFormatException | Все обработчики объединяются | Структурная диагностика затенённого обработчика |
| Обычный finally из примера 4 | Тип тела | Тип тела, значение finally не входит в union |
| Бросающий finally из примера 4 | Ошибочно тип тела | `never`, даже если тело/catch возвращает значение |
| Условно бросающий finally | Результат finally игнорируется | Нормальный тип сохраняется лишь на нормальных путях |
| Throw перед последней формой do/let | Теряется ранний never | `never`; мёртвый код не меняет вывод |
| Throw в условии или аргументе вызова | Нет общего flow-результата | Последующие вычисления не создают нормальный выход |
| Оба пути if бросают | Union never/never → never | `never` |
| with-guard из примера 5 | Нет переноса фактов | Следующая x имеет string |
| Assert default/on/off | Нет специального правила | Default не сужает; on сужает; off не использует предикат |
| Ошибка в сообщении assert | Содержимое пропускается | Проверяется на пути провала в режиме on |
| Вложенный try; throw внутри catch/finally | Нет модели исключительных переходов | Не ловить соседним catch; разрешить внешний catch |
| Recur и бесконечный путь | Общий never | Не интерпретировать never как конкретное исключение |

Существующий `test/features/src/f/core.clj`, функция `j4`, проверяет простой `try/catch` с Java-методом и локальным `e`. В `test/typespec/demo_test.clj` этот fixture проверяется по diagnostics/маркерам, но это не отдельная проверка типа каждого выхода. Среди просмотренных тестов нет прямых проверок `throw`, `assert` и `finally`; это пробел, а не свидетельство полноты. Новые тесты должны проверять и типы, и позиции диагностик, и непроверенное покрытие. Golden-обновления не заменяют независимые ожидаемые результаты.
