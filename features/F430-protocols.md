# F430 · Протоколы и reify

## Зачем

Протокол задаёт общий интерфейс для разных представлений данных: например, файлового и сетевого хранилища или нескольких форматов вывода. Ошибка в результате одного метода обнаруживается далеко от реализации — в клиентском коде. Нужна проверка каждого видимого тела относительно одного контракта, включая анонимные реализации `reify`, без предположения, что все реализации во всей программе известны.

Контракт метода и факт доступности диспетчеризации — разные вещи. Объявление результата `string?` не доказывает, что произвольное значение поддерживает протокол. Наличие метода с тем же именем тоже не означает реализацию протокола.

## Current: что действительно есть

В `env/collect-file` собираются `s/def`, `s/fdef`, `defn`, `defn-`, `defmacro`; таблицы протоколов и реализаций нет. Самостоятельный `s/fdef` попадает в `:vars` через `env/build`, даже без `defn`: это позволяет проверять обычный вызов по объявленной сигнатуре, но не связывает её с телом метода.

В `check/infer-list` стандартный макрос без специального правила получает `t/unknown`, его тело не обходится. Специальных правил для `defprotocol`, `reify`, `extend-type`, `extend-protocol` сейчас нет. Отсутствие ошибки внутри них **не означает успешную проверку**; обещанного предупреждения о каждом таком пропуске тоже пока нет. В `test/examples/src/ex/more.clj` есть `reify java.util.Comparator`, возвращающий строку из `compare`, но это не тест поддержки протоколов и не свидетельство проверки его тела.

`docs/reference.md`, §6, описывает цель: `:t/sig` у методов и проверка `extend-*` в других namespace. Это проектное обещание, а не реализованный механизм. Способ размещения и чтения такой сигнатуры ещё нужно согласовать; ниже используется обычный `s/fdef`, без выдуманной грамматики аннотаций методов.

## Примеры: current и planned

Все блоки иллюстративные, не golden-тесты. Примеры независимы. `planned` означает целевую проверку после реализации этой карточки, а не сегодняшнюю диагностику.

### 1. Корректный контракт и анонимная реализация

```clojure
(ns sample.good
  (:require [clojure.spec.alpha :as s]))

(defprotocol Renderable
  (render [this prefix]))
(s/fdef render :args (s/cat :this any? :prefix string?) :ret string?)

(defn make-renderer []
  (reify Renderable
    (render [_ prefix] (str prefix "document"))))
```

**Current:** `s/fdef` читается; тело `reify` не проверяется. **Planned:** параметр `prefix` получает `string?`, результат тела совместим со `string?`; выражение `reify` несёт факт непосредственной реализации `sample.good/Renderable`. `any?` у receiver здесь лишь обход отсутствия публичного типа протокола в текущей грамматике: он не доказывает допустимость вызова на любом объекте.

### 2. Ошибка результата, скрытая сегодня

```clojure
(ns sample.bad
  (:require [clojure.spec.alpha :as s]))

(defprotocol Renderable
  (render [this prefix]))
(s/fdef render :args (s/cat :this any? :prefix string?) :ret string?)

(defn make-renderer []
  (reify Renderable
    (render [_ prefix] 42)))
```

**Current:** ошибки несовместимости `42` с результатом протокола нет: тело пропущено. **Planned:** ошибка на `42`, ожидается `string?`, фактически литерал `42`; дополнительно ссылка на контракт `sample.bad/render` и арность 2. Проверку результата следует строить на существующем механизме `check-return!`, а не сравнивать текст аннотаций.

### 3. Несколько арностей: receiver считается аргументом

```clojure
(ns sample.arity
  (:require [clojure.spec.alpha :as s]))

(defprotocol Renderable
  (render [this] [this prefix]))
(s/fdef render
  :args (s/cat :this any? :prefix (s/? string?))
  :ret string?)

(defn make-renderer []
  (reify Renderable
    (render [_] "document")
    (render [_ prefix] (str prefix "document"))))
```

**Planned:** две отдельные реализации покрывают арности 1 и 2, обе возвращают строку. Удаление второго тела должно дать сообщение о непроверенной/неполной реализации арности 2; добавление `(render [_ prefix suffix] "x")` — ошибку неподдерживаемой арности. Не нужно обещать, что сама JVM обязательно отвергнет каждую неполную реализацию при создании объекта: политика checker может быть строже runtime. **Current:** контракт `s/fdef` можно разобрать, покрытия тел он не проверяет.

### 4. Расширение в другом namespace и открытый мир

```clojure
(ns sample.api
  (:require [clojure.spec.alpha :as s]))
(defprotocol Renderable (render [this]))
(s/fdef render :args (s/cat :this any?) :ret string?)

(ns sample.extensions
  (:require [sample.api :as api]))
(extend-type java.lang.String
  api/Renderable
  (render [this] this))
```

Это два исходных файла. **Planned:** при анализе обоих файлов разрешить alias `api`, найти контракт, проверить тело с `this : java.lang.String`. Если файл расширения отсутствует, нельзя заключать, что строка никогда не поддерживает протокол. Даже наличие файла в наборе анализа не доказывает, что его namespace уже загружен в конкретной точке исполнения. **Current:** связь `extend-type` с контрактом не строится.

### 5. Metadata-dispatch — не доказательство от satisfies?

```clojure
(ns sample.metadata
  (:require [clojure.spec.alpha :as s]))
(defprotocol Renderable
  :extend-via-metadata true
  (render [this]))
(s/fdef render :args (s/cat :this any?) :ret string?)

(def value
  (with-meta {} {`render (fn [_] "from metadata")}))

(render value)
(satisfies? Renderable value)
```

**Planned:** без отдельной модели metadata-dispatch результат проверки реализации — «не проверено», а не «контракт доказан». `satisfies?` не является универсальным тестом наличия metadata-реализации; нельзя приравнивать его к возможности вызова или выводить из отрицательной ветки отсутствие такого метода. **Current:** `s/fdef` может дать вызову `render` объявленный результат, но реализация из metadata не проверяется. Семантику этого пограничного случая перед поддержкой нужно закрепить runtime-тестом на выбранной версии Clojure; поддержка здесь не заявляется.

## Planned: алгоритм проверки ограниченного статического подмножества

Это план интеграции, **не доказанный sound алгоритм для всей динамики Clojure**. Первый этап — `defprotocol`, прямой `reify` и видимые `extend-type`/`extend-protocol` с разрешимыми именами. Вычисляемый `extend`, metadata-dispatch, загрузка namespace и изменяемый набор расширений требуют отдельного исследования.

1. **Вход.** AST исходников с позициями, namespace/aliases/imports из parser, окружение `s/fdef` и типов, явно выбранный набор анализируемых файлов. Не исполнять макросы и код проекта ради получения runtime-таблицы протокола.
2. **Сбор до проверки тел.** Распознать `defprotocol` отдельным правилом; построить проектную таблицу по полному имени протокола. Для каждого метода хранить полное имя var, допустимые фиксированные арности (включая receiver), позиции объявления, типы параметров/результата и происхождение контракта. Сначала собрать все файлы, затем проверять расширения, чтобы порядок файлов не влиял на результат.
3. **Согласование.** Сопоставить объявленные формы метода с сигнатурами `s/fdef`; в будущем добавить согласованный методный `:t/sig`. Несовпадение арностей или двух явных контрактов — диагностика, не молчаливый выбор. Без контракта известна только форма интерфейса, типы остаются `unknown`; факт проверки формы не выдавать за проверку типов. Не дублировать общие правила приоритета источников сигнатур.
4. **Разбор реализации.** Для каждого блока разрешить протокол, метод и арность, сохранить положение тела. У `reify` учитывать отдельные формы для разных арностей; у `extend-*` — их собственную структуру методов. Не принимать одноимённую функцию другого протокола за нужный метод. Проверить лишние методы, дубликаты, неверные арности; отдельно отметить отсутствующие методы/арности. Проверка полноты — политика статического покрытия, не глобальная теорема о runtime satisfaction.
5. **Контекст тела.** Переиспользовать лексическое окружение и связывание параметров checker. В `reify` сохранить захваченные locals, а receiver снабдить отдельным фактом непосредственной реализации. В расширении класса receiver получает известный класс; расширение `nil` требует отдельного случая, не фиктивного класса. Остальные параметры получают типы контракта. Не позволять реализации самостоятельно сузить входы: она обязана принимать все входы выбранной сигнатуры.
6. **Проверка.** Вызвать обычный вывод типов тела и проверку результата на совместимость с контрактом для каждой арности. `unknown` в теле не превращать в доказанный контракт: учитывать степень проверенности отдельно от номинального факта реализации. Перед повторным использованием `infer-fn`/`check-defn` выделить общую проверку тела с ожидаемыми параметрами: текущие функции не являются готовым адаптером протокольного метода.
7. **Тип значения и вызовы.** Предлагаемое внутреннее представление: номинальный идентификатор протокола плюс факты реализации/степень доверия; это **не существующий новый `t/` синтаксис**. Для прямого `reify` сохранять факт принадлежности, не выводить его структурно из имён методов. Вызов метода проверять существующим `call-fn` по контракту, но допустимость receiver проверять отдельно. Если она не доказана, не объявлять весь вызов безопасным. Видимое внешнее расширение хранить как условный факт, зависящий от загрузки, а не безусловную принадлежность всех значений класса.
8. **Выход.** Типы выражений, проверенные тела, непроверенные участки и диагностики. У ошибки указывать исходную позицию, протокол/метод/арность, expected/actual и источник контракта. Использовать существующие диагностики результата/аргументов там, где их смысл подходит. Новые категории ниже — только предложения.

### Диагностики, которых пока нет

- **proposed TSP430-01:** метод/арность реализации не соответствует объявлению протокола; позиция заголовка метода.
- **proposed TSP430-02:** отсутствует проверенная реализация метода/арности; позиция блока реализации, перечень пробелов. Severity и отличие неполного runtime-объекта от статической ошибки требуют решения.
- **proposed TSP430-03:** протокольная реализация или допустимость receiver не проверены; позиция конструкции/вызова и конкретная причина: неизвестный контракт, metadata, вычисляемое расширение или неизвестная загрузка.

## Интеграция и ограничения

- `src/typespec/env.clj`: отдельные записи протоколов/реализаций, не маскировать методы под обычные `defn`; использовать существующие разрешение имён и парсинг `s/fdef`.
- `src/typespec/check.clj`: специальные правила до общего fallback стандартных макросов; проверка тел через общие механизмы, позиции — оригинального AST. `check-files` уже строит окружение до обхода форм.
- `src/typespec/types.clj`: необходимы правила совместимости номинальных протокольных фактов, отображения и их сохранения в union. Текущая грамматика reference не задаёт тип протокола; нельзя без решения трактовать любой символ как такой тип.
- Не переносить автоматически правила Java-интерфейсов на протоколы: интерфейс JVM и внешнее расширение класса — разные пути диспетчеризации. Смешанные `reify` с Java-интерфейсами требуют согласования проверок, не подмены одной другой.
- Открытые вопросы: наследование расширений и fallback `Object`, `nil`, переопределение расширений, динамическая загрузка, коллизии методов нескольких протоколов, рекурсивные вызовы через receiver, экспорт контрактов библиотек. Их нельзя покрыть одним сравнением арностей.
- Сужение по `satisfies?` не входит в первый этап: нужны отдельная модель времени жизни фактов, проверки metadata-семантики и тесты мутации таблиц расширения. Проект должен явно выбрать границу доверия к загруженным библиотекам и изменениям runtime.

## Конкретная матрица тестов

Ниже будущие тесты, не утверждение о существующем покрытии. Фикстуры должны проверять не только количество ошибок, но и позицию, метод, арность и причину.

| Случай | Ожидаемый planned результат |
| --- | --- |
| Пример 1: `str` в `reify` | Тело проверено, строковый результат, факт прямой реализации |
| Пример 2: `42` вместо строки | Ошибка результата на `42`, ссылка на контракт |
| Пример 3: обе арности | Обе проверены; receiver включён в подсчёт |
| Пример 3 без второй арности | Неполное покрытие, proposed TSP430-02 |
| Пример 3 с третьим параметром | Неверная арность, proposed TSP430-01 |
| Дублированный метод одной арности | Ошибка на повторном заголовке |
| Метод без сигнатуры | Проверена структура, типовая часть явно непроверена |
| `s/fdef` объявляет лишнюю арность | Конфликт с `defprotocol`, не расширение интерфейса |
| Пример 4, файлы в обратном порядке | То же разрешение имён и результат проверки тела |
| Пример 4, контракт отсутствует | Непроверенный блок, без выдуманного контракта |
| `extend-protocol` с двумя классами, одно неверное тело | Ошибка только соответствующего тела; два receiver-типа |
| Захваченный local в `reify` имеет неверный тип результата | Ошибка результата, local не теряет тип |
| Вызов `render` с числом вместо `prefix` | Обычная ошибка аргумента по `s/fdef` |
| Наличие `extend-type` без доказательства загрузки | Нет безусловного факта поддержки в точке вызова |
| Пример 5 и вычисляемый `extend` | Явно непроверенная динамическая реализация |
| `satisfies?` с metadata и без неё | Runtime-характеризация; нет необоснованного сужения |
| `nil`, `Object`, смешанный Java/protocol `reify` | До отдельной поддержки — видимая граница проверки |

Перед `implemented` нужны parser/env unit-тесты, тесты тел и вызовов, межфайловые фикстуры и отдельные runtime-характеризации динамических случаев. Нынешний runner `test/typespec/demo_test.clj` выполняет карточки только с маркированными `clojure example`/`text output`; обычные блоки этой карточки намеренно не включены в этот механизм.
