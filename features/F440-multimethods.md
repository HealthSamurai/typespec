# F440 · Multimethod dispatch

## Зачем

Multimethod позволяет расширять обработку событий, команд, форматов и других данных без изменения центральной функции. В отличие от обычной функции, его реализации могут находиться в разных namespaces и добавляться позднее. Проверка должна связать общий контракт аргументов и результата с каждым методом: после dispatch по `:kind` обработчик получает соответствующий вариант данных, а не произвольную map.

Нужно различать три утверждения: тело отдельного метода корректно; известные методы согласованы с контрактом; любой допустимый вызов найдёт единственный метод. Последнее нельзя вывести просто из списка просмотренных файлов.

## Что работает сейчас

`implementation: not-implemented` сохранён: механизма типизации dispatch пока нет.

- В `src/typespec/check.clj` форма `defmulti` входит в список пропускаемых форм: возвращается `t/unknown`, dispatch-функция не проверяется этим обработчиком.
- Обработчик `special 'defmethod` пропускает имя multimethod и dispatch-value, находит вектор параметров, связывает **фиксированные** параметры через `env/pattern-type` и проходит тело через `infer-body`. Это позволяет находить некоторые обычные ошибки внутри тела, но не даёт сужения по dispatch, проверки результата по общему контракту или проверки полноты. Rest-параметр этот обработчик специально не связывает.
- `env/build` собирает `s/fdef`, включая декларации без `defn`, поэтому общий контракт может быть доступен для проверки вызовов. Это не означает проверки реализаций `defmethod`: таблицы multimethod и методов в окружении нет.
- В `test/` нет упоминаний `defmulti`/`defmethod`; текущий `demo_test.clj` запускает golden-проекты и специально помеченные примеры карточек. Примеры ниже — обычные fences, не исполняемые golden-тесты.

Reference описывает **целевое** поведение: типизированный dispatch, сужение по keyword и закрытый dispatch через `{:t/closed true}`. Наличие этих правил в reference не означает их реализации.

## Примеры и ожидаемое поведение

### 1. Корректный обработчик размеченного объединения — planned

```clojure
(ns demo.events
  (:require [clojure.spec.alpha :as s]))

(s/def :created/kind #{:created})
(s/def :deleted/kind #{:deleted})
(s/def ::id string?)
(s/def ::created (s/keys :req-un [:created/kind ::id]))
(s/def ::deleted (s/keys :req-un [:deleted/kind ::id]))
(s/def ::event (s/or :created ::created :deleted ::deleted))

(s/fdef handle :args (s/cat :event ::event) :ret string?)
(defmulti handle :kind)
(defmethod handle :created [event] (:id event))
(defmethod handle :deleted [event] (str "deleted:" (:id event)))
(handle {:kind :created :id "job-7"})
```

Planned: в первом методе `event` имеет тип `::created`, во втором — `::deleted`; оба результата — `string?`. Общий контракт вызова не зависит от того, какие расширения загружены. Метки `:created`/`:deleted` у `s/or` не являются dispatch: связь даёт именно поле `:kind`. Current: `s/fdef` доступен окружению, но тип аргумента метода из него не переносится; успешное прохождение отдельных выражений не доказывает весь пример.

### 2. Ошибка результата метода — planned

Следующий фрагмент — альтернативное определение метода из примера 1, а не дополнительное определение в том же проекте.

```clojure
(defmethod handle :created [event]
  (count (:id event)))
```

Planned: вход сужается до `::created`, тело возвращает `int?`, а контракт `handle` требует `string?`. Диагностика `TSP2322` на результирующем выражении должна ссылаться на `s/fdef` и dispatch `:created`. Код `TSP2322` уже используется для несовместимого результата обычных функций; его применение к multimethod ещё не реализовано. Current: возможная ошибка чтения ключа у непроверенного параметра не заменяет эту проверку; целевого сравнения результата нет.

### 3. Default — не отдельный вариант с тегом `:default`

Здесь используются декларации `::event` из примера 1, но другой multimethod.

```clojure
(s/fdef summarize :args (s/cat :event ::event) :ret string?)
(defmulti summarize :kind :default :fallback)
(defmethod summarize :created [event] (:id event))
(defmethod summarize :fallback [event]
  (str "unhandled:" (:id event)))
(summarize {:kind :deleted :id "job-8"})
```

В Clojure вызов выбирает fallback. Planned: при открытом наборе методов безопасная начальная проверка fallback использует **весь** `::event`, а не выдуманный вариант `{:kind :fallback}`. Даже если в текущем снимке fallback получает только `::deleted`, удаление метода `:created` изменит это множество. Для стабильного закрытого снимка допустимо точнее вычислять остаток. Current: опция `:default` и связь fallback с контрактом не анализируются.

### 4. Закрытый dispatch: пропущенный вариант

```clojure
(s/fdef closed-handle :args (s/cat :event ::event) :ret string?)
(defmulti closed-handle {:t/closed true} :kind)
(defmethod closed-handle :created [event] (:id event))
;; Нет метода :deleted и нет default.
(closed-handle {:kind :deleted :id "job-9"})
```

В Clojure при отсутствии других регистраций вызов не найдёт метод. `:t/closed` — метаданные проекта, не runtime-запрет расширять multimethod. Planned: если проверяющему дан подтверждённый закрытый набор регистраций, сообщить о непокрытом `:deleted` (`proposed TSP440-01`). Если есть только метка, но граница сборки не доказана, сообщить, что закрытость не подтверждена (`proposed TSP440-03`), а не выдавать сертификат полноты. Current: метка не проверяется; missing-method статически не ищется. Формат манифеста закрытой границы пока не определён.

### 5. Произвольный dispatch, иерархия и неоднозначность

```clojure
(def h (-> (make-hierarchy)
           (derive ::square ::shape)
           (derive ::square ::drawable)))
(defmulti render (fn [x] (:kind x)) :hierarchy #'h)
(defmethod render ::shape [_] "shape")
(defmethod render ::drawable [_] "drawable")
(render {:kind ::square})
;; При таком снимке иерархии оба метода подходят, победителя нет.
;; (prefer-method render ::shape ::drawable) меняет выбор.
```

Это отдельный namespace-сценарий, не продолжение контракта `handle`. Снимок имеет два несравнимых подходящих метода. Planned для первой версии: произвольная функция dispatch и mutable hierarchy помечаются как неподдержанная часть анализа (`proposed TSP440-04`), без фиктивного сужения или доказательства уникальности. Будущий анализ зафиксированного снимка мог бы дать `proposed TSP440-02` о неоднозначности. Current не моделирует ни иерархию, ни preference. Даже тип результата dispatch `keyword?` сам по себе не позволяет восстановить тип `x`: для этого нужна доказанная связь результата с входом.

## Пошаговый алгоритм: ограниченное ядро, а не решение общего случая

Первый этап целесообразно ограничить одним аргументом, dispatch через literal keyword, конечным объединением структурных map с обязательным полем-тегом и конечными literal-типами этого поля. Неизвестная/изменяемая иерархия не считается пустой автоматически: даже keyword-dispatch в Clojure может использовать `isa?`. Режим точного равенства требует отдельного подтверждения отсутствия влияющих иерархических связей. Ниже — проект алгоритма для этого ограниченного режима; general dispatch и доказательство закрытости требуют исследований.

1. **Вход.** AST всех файлов выбранной границы, разрешение aliases/namespaces, общий контракт `s/fdef` (и другие поддерживаемые источники сигнатуры), декларации типов ключей, `defmulti`, `defmethod`, настройки default/hierarchy и сведения о закрытости. Не исполнять проектный код, чтобы получить таблицу методов. Не путать соглашение об источниках сигнатуры с доказательством runtime-состояния.
2. **Сбор до проверки тел.** Добавить в окружение отдельную запись по fully-qualified символу multimethod: контракт `{:t :fn :arities ...}`, описание dispatch, default-value, методы с AST/позициями/dispatch-value, режим открытости и происхождение допущений. Регистрации из других namespaces присоединяются по разрешённому символу; порядок файлов не задаёт runtime-порядок загрузки. Повторные определения одного dispatch нельзя молча сворачивать в «последний файл победил»: если порядок не доказан, результат анализа неполный.
3. **Проверка контракта dispatch.** Убедиться, что общий контракт и поддерживаемая арность известны. Dispatch принимает тот же аргумент, что multimethod; для keyword проверить возможность чтения поля во всех входных вариантах. В первом ядре отсутствие обязательного поля, широкий `keyword?`, неизвестный тип, произвольное вычисление dispatch или неизвестная hierarchy выводят проверку покрытия/сужения за поддерживаемую границу. Это не обязательно ошибка программы.
4. **Представление фактов.** Использовать существующие `:ref`, `:union`, `:lit`, структурные map и `t/never`; ссылка на spec раскрывается через окружение. Дополнительно хранить факт «dispatch-path аргумента равен literal d» с причиной и позицией метода. Для входного union оставить варианты, чьё обязательное поле допускает d, и пересечь тип поля с `{d}`. Несовместимые варианты удалить; пустой результат — `never`. Не создавать обязательный ключ из необязательного без доказательства. Это конечная фильтрация, не общий inverse-image произвольной функции.
5. **Проверка каждого тела.** Связать параметры/деструктуризацию с полученным типом через инфраструктуру `bind-pattern`; проверить арность против контракта; передать контекст в `infer-body`. Сравнить результат с общим return-type через ту же логику, что `check-return!` для `defn`. Для открытого default использовать полный входной тип. Пустая область допустимых входов метода не доказывает безопасность его тела и не является ошибкой по умолчанию: расширение может быть не предназначено для данного контракта; отметить, что проверка тела на допустимых входах вакуозна.
6. **Выбор и полнота — отдельно.** Только для подтверждённого стабильного закрытого набора и конечного домена перечислить значения dispatch. Для каждого найти точный метод; если его нет — default; если нет обоих — записать missing-method. В этом ядре один literal не имеет двух разных выбранных методов: повторные регистрации уже остановили доказательство на шаге 2. При наличии hierarchy/preferences этот упрощённый выбор неприменим. В открытом режиме не выдавать exhaustiveness даже при покрытии всех текущих значений; допускается лишь условное утверждение о просмотренном снимке.
7. **Результат и диагностики.** Вернуть общий тип вызова из контракта, результаты проверки тел и отдельный статус `checked` / `partial` / `unsupported` для dispatch, покрытия и закрытости (предлагаемый внутренний формат). Не выводить глобальный return-type как union только просмотренных методов открытого multimethod. Диагностики содержат позицию, имя multimethod, dispatch-value, ожидаемый/полученный тип либо отсутствующее доказательство и ссылки на контракт/конфликтующий метод. Не заменять неизвестность на `any?` и не маркировать непроверенные тела как проверенные.

### Диагностики

- Существующий `TSP2322`: несовместимый результат; интеграция с `defmethod` planned.
- `proposed TSP440-01`: допустимое значение dispatch не покрыто в подтверждённом закрытом режиме.
- `proposed TSP440-02`: неоднозначный выбор в доказанном снимке hierarchy/preferences; не часть первого ядра.
- `proposed TSP440-03`: закрытая граница заявлена, но не подтверждена.
- `proposed TSP440-04`: dispatch/регистрация/иерархия за поддерживаемой границей; анализ неполон, не утверждение о runtime-ошибке.

Новые коды здесь только предложения, не уже существующие диагностики. Точные severity и формат coverage ещё нужно согласовать.

## Интеграция с текущим checker

`env/collect-file` и `env/build` должны собирать регистрации до проверки тел, сохраняя существующее согласование сигнатур. `special 'defmulti` должен перестать безусловно пропускать форму; `special 'defmethod` — получать контракт и факты из новой таблицы, а не только hints/шаблон параметра. Повторно использовать `infer-body`, `bind-pattern`, сравнение результата и существующие операции над union/map; это не означает, что текущее сужение автоматически поддерживает обратный образ dispatch.

Для вызовов достаточно общего function contract; более точный результат конкретного метода — отдельная возможность, требующая стабильного выбора и зависимого контракта. Проверка межфайловых регистраций выполняется после сбора окружения, не как побочный эффект последовательного обхода тел. Нужен отдельный отчёт о доверии к externs/границе, иначе наличие `s/fdef` скрывает непроверенные реализации.

## Ограничения и нерешённые вопросы

- **Закрытость:** какие namespaces, зависимости, AOT-сборка и загрузочные пути входят в манифест? Как исключить поздние `defmethod`, `remove-method`, `remove-all-methods`, переопределение Var, `eval` и REPL-изменения? Одна метка `:t/closed` недостаточна. Пока протокола нет, доказательство полноты условное.
- **Иерархии:** `derive`, `underive`, `prefer-method`, пользовательская hierarchy и глобальная hierarchy меняют выбор без изменения сигнатуры. Полный анализ требует модели `isa?`, отношения предпочтения, default и обновлений; её корректность здесь не доказана.
- **Другие dispatch:** классы, vector dispatch, несколько аргументов, variadic и функции с эффектами не покрыты конечной фильтрацией map. Для пользовательской функции нужен доказанный refinement-контракт; выходного типа недостаточно. Нельзя произвольно исполнять её при анализе.
- **Доступность метода не равна чистоте:** даже доказанный выбор не гарантирует отсутствие исключений в теле или termination. Указанные return-типы описывают нормальный возврат.
- **Открытые расширения:** проверка всех известных методов относительно общего контракта полезна без закрытости, но не обещает корректность будущих непроверенных методов.

## Конкретная матрица тестов

Все строки — план новых тестов, не заявление о текущем прохождении. Сначала нужны baseline-тесты существующего пропуска `defmulti` и обхода тела `defmethod`, затем отдельные тесты ядра. Не переводить карточку в implemented только из-за удачных примеров.

| Сценарий | Ожидаемая проверка |
|---|---|
| Пример 1, два варианта с обязательным literal-тегом | Типы параметров сужены; оба результата совместимы; открытая полнота не заявляется |
| Пример 2 | `TSP2322` на результате, ссылка на контракт и метод |
| Пример 3, custom default | Default получает весь вход в открытом режиме; не факт `:kind = :fallback` |
| Пример 4, подтверждённая граница | `proposed TSP440-01` с конкретным `:deleted` |
| Та же метка без манифеста | `proposed TSP440-03`, нет сертификата полноты |
| Закрытый снимок, все literal покрыты либо есть default | Полнота только при зафиксированных допущениях |
| `:kind` optional, отсутствует или имеет широкий тип | Неполный анализ ядра; не выдумывать обязательный ключ и конечный домен |
| Метод с dispatch вне входного union | Пустая область допустимых входов; не выдавать ложную проверку тела |
| Метод в другом ns с alias, обратный порядок файлов | Тот же контракт и результат; независимость от порядка обхода |
| Две регистрации одного literal без известного порядка загрузки | Неполнота, не произвольный выбор последнего файла |
| Несовпадение арности, variadic/rest | Арность проверяется либо случай явно unsupported; rest не теряется молча |
| Произвольная dispatch-функция возвращает keyword | Нет автоматического сужения входа; `proposed TSP440-04` |
| Пример 5; затем добавление preference | В первом ядре unsupported; будущая модель отличает неоднозначность от выбранного метода |
| Добавление/удаление метода или изменение hierarchy после анализа | Инвалидация гарантии закрытого снимка, не повторное использование старого доказательства |
| `s/fdef` есть, реализация внешняя/непросмотренная | Вызов проверяется по контракту; доверие к реализации отражается отдельно |
| Ошибка в теле, не связанная с dispatch | Сохранён текущий обычный обход тела; неподдержанный dispatch не скрывает найденную ошибку |
