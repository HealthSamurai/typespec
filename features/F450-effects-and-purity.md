# F450 · Эффекты и проверяемая чистота

## Зачем

Отличать вычисление значения от чтения состояния, изменения состояния и I/O. Явная pure-аннотация — проверяемое требование, не разрешение доверять произвольному коду. Возможное дальнейшее применение — ограниченное вычисление констант при проверке. Это не обязательная часть первого выпуска.

## Примеры целевого поведения

Синтаксис metadata предлагаемый; сейчас не поддерживается.

```clojure
(defn square
  {:t/pure true}
  [x]
  (* x x))
;; Pure при известном числовом контракте и проверенном контракте *.
```

```clojure
(defn current-count
  {:t/pure true}
  [state]
  @state)
;; Нарушение: результат зависит от изменяемого состояния.
;; Отсутствие записи недостаточно для pure.
```

```clojure
(defn announce
  {:t/pure true}
  [message]
  (println message))
;; Нарушение: I/O. Аналогично swap!/reset! дают эффект записи.
```

```clojure
(defn delayed-output [xs]
  (map (fn [x] (println x) x) xs))
;; Эффект отложен до реализации seq.
;; Нельзя объявлять результат безопасным для compile-time по телу фабрики.
```

```clojure
(defn divide [a b] (/ a b))
;; Без I/O и мутаций, но может бросить исключение.
;; Чистота не означает тотальность, завершение или малую стоимость.
```

## Предлагаемая модель

Отдельно от типа результата хранить summary эффектов: чтение состояния, запись, I/O, недетерминированность, неизвестный вызов; отдельно — возможное исключение. Контракты callbacks и lazy-результатов должны нести отложенные эффекты. Pure требует отсутствия наблюдаемых эффектов и зависимости от изменяемого внешнего состояния; политика исключений задаётся явно, не скрывается в одном boolean.

## Алгоритм первого приближения

1. Собрать effect summaries проверенных core-примитивов и внешних аннотаций. Происхождение доверенного контракта сохранять.
2. Анализировать выражения вместе с типами; объединять эффекты достижимых веток. Неизвестный вызов даёт unknown-effect, не pure.
3. Переносить эффекты аргументов и вызываемой функции. Для callback учитывать, вызывается ли он немедленно, сохраняется или возвращается внутри lazy-значения. До поддержки этой модели не доказывать чистоту таких случаев.
4. Считать чтение atom, динамических vars, часов, случайности и изменяемых Java-объектов зависимостью от состояния. Локальный immutable snapshot — отдельное значение, а не обещание стабильности следующего чтения.
5. Для рекурсивных функций решать summaries по компонентам графа до устойчивого состояния; ограничение анализа означает «не доказано».
6. Сравнивать summary с заявленным требованием pure, показывать цепочку до источника эффекта. Не выдавать доверенный extern за проверенное тело.

Это эскиз консервативного анализа, не доказательство чистоты всего Clojure. Aliasing, Java, callbacks, динамическая диспетчеризация и lazy evaluation требуют отдельной проработки.

### Представление отложенных эффектов и HOF

Внутренняя нотация (не публичный синтаксис): `infer(expr) -> {type, nowEffects, provenance}`, `Fn[args, callEffects, result]`, `Delay[e,T]`, `LazySeq[e,T]`. Вызов объединяет эффекты вычисления функции, аргументов и инстанцированный `callEffects`. Проверка тела `fn`/`delay` сохраняет его эффекты в типе результата, не добавляя их к эффектам исполнения тела фабрики. Для `map` переносить в latent summary **и callback, и ленивый источник**; `first`/`dorun` потребляют этот summary.

```clojure
(defn prepare [] (delay (println "later") 42))
(let [d (prepare)]
  (force d)
  (force d)) ; may-I/O сохраняется даже после первого force, без typestate
(defn twice [f x] (f x) (f x))
(twice println 1) ; I/O
(twice inc 1)     ; независимая инстанциация эффекта, не заражена println
```

Повторный `force` того же успешно реализованного delay возвращает кешированное значение и не повторяет тело. Сохранение may-effect во втором вызове — сознательная потеря точности без отслеживания состояния и aliases, а не описание повторного runtime-эффекта.

Первый solver: конечные множества may-effects и монотонное объединение по SCC; исчерпание бюджета даёт unknown-effect. Для generic HOF свежий effect-параметр создаётся на каждом вызове; это effect-часть взаимодействия с [F230](F230-generics-and-hof.md), не замена её type-параметров. Контракт с [F720](F720-module-interfaces.md): интерфейс хранит summary и зависимости от внешних контрактов/вызываемых summaries; изменение зависимости требует пересчёта затронутой SCC, а не повторного использования прежнего pure-результата. Открытые rows — поздний вариант: нормализовать labels/tail, сопоставить labels, расширить открытые хвосты недостающими labels через свежие переменные, выполнить occurs-check. Нельзя решить `e = <io | e>` бесконечным расширением или просто переиспользовать record-row solver. Это не заявление principal types для сочетания union/subtyping Typespec.

Обязательны внешние декларации core и библиотек: арности `(map f)` и `(map f xs)`, `partial`, `future` имеют разные способы исполнения. `future` запускает работу, а не ждёт `deref`. До отдельных контрактов — unknown-effect; value-level `unknown` остаётся безопасным top, не разрешением произвольных операций. May-summary не обещает exactly-once (chunked seq, повторный `swap!`). Pure не доказывает compile-time termination.

Дополнительные planned-тесты: эффект ленивого источника не теряется при чистом callback; два `force` сохраняют may-effect; независимые вызовы HOF не делят `e`; неподдержанная арность не считается pure; исчерпание бюджета SCC не даёт pure.

Основание: [отчёт Koka](../docs/research-koka.md), Findings 2–4. В этом переносе прочитан отчёт, первоисточники заново не аудированы. В отчёте выборочно разобраны §2.3–2.7 [статьи 2014](https://arxiv.org/pdf/1406.2061) и `unifyEffect` в [Unify.hs](https://github.com/koka-lang/koka/blob/b66091b2a5a7ea20c5ed9498ad1e1f03caee9589/src/Type/Unify.hs); [delayed.kk](https://github.com/koka-lang/koka/blob/b66091b2a5a7ea20c5ed9498ad1e1f03caee9589/lib/std/core/delayed.kk) прочитан целиком, включая unsafe-границу. Доказательства и inference engine целиком не проверялись; модель Clojure здесь — проект адаптации.

## Compile-time: отдельное разрешение, не следствие pure

Обычный check по-прежнему не запускает пользовательский код. Даже доказанно чистая функция может не завершиться, расходовать много памяти или бросить исключение. Будущий evaluator должен быть отдельным opt-in механизмом: закрытые константные входы, разрешённое подмножество операций, фиксированная среда, лимиты шагов/памяти/размера результата, без require/eval, сети и файловых операций. Доверенной pure-аннотации недостаточно для разрешения исполнения. При превышении лимита — отказ от вычисления, не успешное доказательство и не изменение поведения программы.

## Матрица тестов

| Случай | Ожидание |
|---|---|
| Арифметика над известными числами | Pure, при корректном контракте примитива |
| deref atom, время, случайность | Не pure |
| println, reset!, запись Java-поля | Эффект с причиной и позицией |
| Вызов неизвестного var | Чистота не доказана |
| Ленивый map с println | Сохранён отложенный эффект |
| Доверенный pure extern | Явная граница доверия, не проверенное тело |
| Чистая бесконечная рекурсия | Не разрешает неограниченное compile-time исполнение |
| Деление на ноль при вычислении константы | Управляемый отказ evaluator, без падения checker |
