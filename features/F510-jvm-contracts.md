# F510 · Чтение контрактов JVM

## Зачем

Clojure-программы используют JDK и Java-библиотеки напрямую. Повторять их методы в ручных externs дорого, а контракт не той версии библиотеки даёт ложную уверенность. F510 отвечает за получение доступного JVM-контракта и его происхождение: какой класс найден, откуда он взят, какие сведения действительно доступны. Это основание для проверки interop, а не отдельная реализация всех правил Java.

`status: designed`, `implementation: partial` сохранены: reflection-reader уже есть, самостоятельного bytecode-reader и согласования classpath ещё нет. Требования §4.3 reference — целевой дизайн, не перечень реализованного.

## Текущее поведение и граница карточки

- `types/load-class` вызывает `Class/forName(name, false, contextClassLoader)`; примитивы обрабатываются отдельно. Класс загружается без запроса его инициализации. Это **не** чтение `.class` без загрузки и не гарантия отсутствия действий пользовательского classloader.
- `java/methods-named` читает публичные, в том числе унаследованные, методы через `getMethods`, фильтрует имя и static/instance. Контракт: `{:params [имена-классов] :ret имя-класса :declaring имя-класса :varargs boolean}`. Используются erased-типы `getParameterTypes/getReturnType`, не generic signatures и не аннотации.
- Результат сортируется по числу параметров и предпочтению возврата не-`Object`; методы с одинаковыми параметрами схлопываются. Это эвристика, не доказанное разрешение bridge/covariant методов.
- `java/field-info` читает объявленный JVM-тип и модификатор `final` публичного поля через `Reflector/getField`, учитывая static и instance. `java/field-class` возвращает имя типа. Чтение метаданных обходится без значения поля и инициализации класса.
- `java/constructors` читает типы параметров и признак varargs публичных конструкторов через `getConstructors`. Обе формы вызова передают эти сигнатуры в проверку [F520](F520-java-overloads.md).
- `check/java-call` потребляет эти записи; `types/class-type` переводит Java-типы во внутренние карты. Например, `String` → `{:t :prim :name :string}`, `LocalDate` → `{:t :class :name "java.time.LocalDate"}`, `Object` → `:any`, `void` → `:nil`.
- Когда форма коллекции хранит JVM-класс, `check` проверяет методы этого класса. Например, результат `file-seq` сохраняет `LazySeq`, а вызов метода на возможном `nil` из `iterator-seq` получает `TSP2531`.
- Для векторного литерала чекер различает класс значения и тип,
  известный компилятору. `.length` разрешается на `IPersistentVector`,
  а `.size` зависит от того, свернул ли компилятор литерал в константу.
- Результаты Java обычно получают platform-пометку. Отдельный ручной список `nullable-returns` даёт nilable-результаты для известных методов. Это не чтение nullability из байткода.

`make-array` выводит класс и ранг результата из известного класса
компонента. Например, `(make-array Integer/TYPE 2 3)` имеет тип `int[][]`,
а `(make-array String/1 2)` — `String[][]`. Для `TYPE` распознаются
поля обёрток примитивов. Литеральный `Class/forName` разрешается через
загрузку класса без инициализации. Чекер проверяет типы размеров, известные
отрицательные размеры после преобразования в `int`, переполнение и
предел суммарного ранга в 255. Для вычисляемого `Class` без известного
компонента результат остаётся `t/unknown`.

`to-array` возвращает исходный ссылочный массив с тем же JVM-классом
и известной длиной. Примитивные массивы, строки, мапы и `Iterable`
преобразуются в `Object[]`. Для `nil` результат имеет длину `0`.
Обычный `check` проверяет вход по этим случаям JVM и сохраняет тип
компонента для последующего `aset`.

Одноаргументный `into-array` использует JVM-класс первого элемента.
Пустой вход и первый элемент `nil` дают `Object[]`. Например,
`(into-array [42 43])` имеет тип `Long[]`, а `4.5` во второй
позиции даёт `TSP2345`. При неизвестном классе первого элемента
результат имеет ковариантный тип `Object[]` с известной длиной,
если длина входа доступна.

Явный примитивный компонент в `into-array` выводит класс и известную
длину JVM-массива. Clojure 1.12.4 применяет проверяемые преобразования к
`byte`, `short`, `int`, `char` и `float`. Для `long`, `double` и
`boolean` действуют правила распаковки и расширения JVM. Например,
`(into-array Integer/TYPE [1.5])` даёт `int[]` с элементом `1`,
а `(into-array Long/TYPE [1.5])` даёт `TSP2345` на элементе.

Для явного ссылочного компонента `into-array` проверяет совместимость
с JVM-классом элемента и принимает `nil`. Например, `Integer[]` принимает
`(int 42)` и элементы из `int[]`, а литерал `42` даёт `TSP2345`,
поскольку имеет класс `Long`. Когда числовой Spec или хинт допускает
несколько классов обёрток, чекер сообщает, что совместимость не доказана.

В двухаргументном вызове явный компонент должен быть `java.lang.Class`.
В обеих арностях `into-array` принимает `nil`, JVM-массивы, `Seqable`,
`Iterable`, `CharSequence` и `Map`. Чекер отмечает известные нарушения
этих требований, например строку вместо класса и `Iterator` вместо
источника. Для вычисляемого `Class` без известного компонента тип
результата остаётся `t/unknown`.

`to-array-2d` принимает внешнюю `java.util.Collection` и применяет
правила `to-array` к каждой строке. Строка `nil` преобразуется в
пустой `Object[]`. Результат имеет JVM-класс `Object[][]` и сохраняет
известное число строк. Тип вложенного массива остаётся ковариантным,
поскольку строку можно заменить через `aset`.

F510 задаёт транспорт, происхождение и полноту контрактов. Хинты (F111), выбор перегрузки, generic-подстановка, nullability и проверка реализаций интерфейсов должны использовать общий контракт, но их алгоритмы здесь не дублируются.

## Примеры

Обычные `clojure`-блоки ниже — иллюстрации, не подключённые golden-тесты. «Сейчас» означает вывод из реализации; имеющиеся тестовые подтверждения перечислены отдельно.

### 1. Корректный публичный static-метод — сейчас

```clojure
(ns sample.clock)

(defn today []
  (java.time.LocalDate/now))
;; Сейчас: найден публичный static now без параметров.
;; Результат вызова — platform java.time.LocalDate, не unknown.
;; Проверка читает сигнатуру, а не вызывает now и не узнаёт дату.
```

Планируемый bytecode-reader должен дать тот же контракт, дополненный происхождением класса и версией среды.

### 2. Контракт позволяет отвергнуть аргумент — сейчас

```clojure
(ns sample.date)

(java.time.LocalDate/of 2024 1 "2")
;; Сейчас: TSP2345 на "2": аргумент не подходит ни одному
;; кандидату с соответствующей позицией параметра.
(java.time.LocalDate/of 2024 1 2)
;; Сейчас: типы принимаются; результат — platform LocalDate.
;; Допустимость календарной даты этим не доказана.
```

Reader поставляет сигнатуры обеих трёхаргументных перегрузок; диагностику строит checker. Он не выполняет метод и не проверяет его предусловия вроде допустимого дня месяца. Ошибочный вариант уже представлен в `test/features`.

### 3. Отсутствующий метод в найденном классе — сейчас

```clojure
(ns sample.text)

(defn size [^String s]
  (.lenght s))
;; Сейчас: TSP2339, String has no method lenght, подсказка length.
;; Контракт класса найден: это ошибка имени, не отсутствие classpath.
```

Такую ошибку важно отличать от невозможности прочитать сам класс. В текущем reader эти ситуации ещё не оформлены единым типизированным результатом.

### 4. Чтение параметра Java varargs

```clojure
(ns sample.format)

(String/format "%s" (into-array String ["hello"]))
;; String[] совместим с JVM-параметром Object[].
(String/format "%s" "hello")
;; TSP2345 на строковом аргументе.
```

Reader передаёт descriptor с массивом и признак `:varargs`. Чекер проверяет этот параметр по правилам [F520](F520-java-overloads.md).

### 5. Недоступная библиотека — planned

```clojure
(ns sample.vendor
  (:import [com.example.vendor Client]))

(defn version []
  (Client/version))
;; Условие: библиотека отсутствует в classpath проверяемого проекта.
;; Planned: ошибка получения контракта с именем класса,
;; местом использования и описанием проверенного classpath;
;; результат использования — unknown/непроверено, не успешная проверка.
```

Сейчас `load-class` перехватывает любой `Throwable` и возвращает nil; причина недоступна. Кроме того, dispatch зависит от разрешения имени класса, поэтому нельзя обещать единую диагностику всего приведённого фрагмента. Планируемый `proposed TSP510-01` относится к ошибке получения контракта, а не к отсутствию метода в успешно прочитанном классе.

## Алгоритм получения и согласования контрактов

Это проект интерфейса reader, **не sound-алгоритм всей Java interop**. Точные правила Clojure для перегрузок и преобразований нужно исследовать отдельно.

1. **Вход.** Получить AST-узел и позицию использования, полное имя класса после разрешения imports, запрос члена (имя, static/instance), упорядоченный classpath проекта, целевой JDK и при наличии extern-уточнение. Типы аргументов нужны downstream-checker, не для выбора версии класса. Сейчас реально используется context classloader процесса; отдельного снимка проектного classpath нет.
2. **Зафиксировать среду.** Planned: определить порядок директорий/JAR, target JDK, применимую multi-release запись и fingerprint источников. Не выбирать класс по «наиболее удобной» сигнатуре. Для нескольких определений зафиксировать выбранное и затенённые; политика warning/error остаётся открытой. Ключ кеша должен включать среду. Сейчас `load-class` мемоизирован только по имени, что непригодно для смены classloader/classpath в одном процессе.
3. **Получить данные без запуска приложения.** Сейчас — загрузка без инициализации и reflection. Planned — чтение classfile bytes, constant pool, descriptors и необходимых атрибутов без `require`/`eval` исходников, запуска методов, чтения значений static-полей или инициализации классов. Ошибки отсутствия, несовместимой версии и повреждения classfile должны различаться. Ошибки reflection при `getMethods` сейчас отдельно не нормализованы.
4. **Построить сырой контракт.** Planned: binary name, superclass/interfaces, объявления членов с владельцем, descriptor, access flags, varargs, bridge/synthetic flags; отдельно необязательные generic signatures и annotations. При разрешении наследования учитывать доступность членов и неполноту зависимостей. Не удалять различные объявления до обработки bridge/covariant случаев. При неизвестном атрибуте сохранить erased descriptor и признак потери точности, а не выдумывать тип.
5. **Согласовать источники.** JVM descriptor задаёт физическую форму члена; generic signature уточняет её только после проверки согласованности erasure. Аннотации и externs добавляют семантические уточнения с указанием источника. Они не могут молча создать несуществующий метод или поменять его arity. Конфликт нужно сохранить и диагностировать; приоритет конфликтующих nullability-источников ещё требует решения. Хинт Clojure — утверждение у места вызова, не замена декларации JVM.
6. **Нормализовать для checker.** Сохранить сырой descriptor рядом с текущими `:params/:ret/:declaring/:varargs`. Получить внутренние `:class/:prim/:nil/:any` через отдельный адаптер, не теряя в сыром контракте различия `int`/`long`, array descriptor и `Object`. Provenance и полнота — отдельные факты, не тип `any` для всех отказов. Planned-результат reader: контракт с источником и ограничениями либо структурированная ошибка с причиной.
7. **Передать проверку потребителю.** `java-call` проверяет наличие метода, arity, совместимость параметров и вычисляет результат; `method-call` дополнительно проверяет receiver. Сейчас при нескольких разных результатах возвращается unknown, а числовая совместимость упрощена. Эти решения нельзя выдавать за точное воспроизведение компилятора Clojure. Успех reader не снимает обязанность checker отметить непроверенный вызов.
8. **Сформировать диагностику.** Для доступного класса сохранить существующие `TSP2339` (метод), `TSP2554` (arity), `TSP2345` (аргумент), привязанные к AST. Planned для reader: `proposed TSP510-01` — класс/его зависимость недоступны; `proposed TSP510-02` — байткод не читается или несовместим; `proposed TSP510-03` — конфликт источников контракта. Сообщение содержит класс, источник, причину, место запроса и что осталось непроверенным. Это новые предложения, в коде их нет.

## Интеграция и ограничения

Точка замены — `types/load-class`/`java/methods-named`, но переход не сводится к замене одного вызова: подтипизация в `types` также использует загруженные `Class` и `isAssignableFrom`. Для режима «только байткод» потребуется согласованный граф наследования и единое разрешение классов; иначе reader и checker смогут видеть разные версии класса.

Не закрыты: JPMS/export visibility, multi-release JAR и target JDK, дубликаты на classpath, неполные транзитивные зависимости, безопасная инвалидизация кеша, bridge/covariant методы, поведение повреждённого generic Signature. Сложные случаи требуют fixtures и сравнения с фактическим компилятором Clojure, а не заявления о soundness. Отключение инициализации не делает произвольный classloader безопасным.

Сейчас не читаются generic signatures, nullability annotations и значения полей; `Object` превращается в `any`, многие примитивные различия стираются. Обещания reference о generics, arrays, SAM, varargs и интерфейсах нельзя считать выполненными лишь потому, что класс найден. Checked exceptions по reference не отслеживаются.

## Конкретная матрица тестов

| Случай | Ожидаемая проверка | Состояние |
|---|---|---|
| `LocalDate/now()` | Static, 0 параметров, return LocalDate; без исполнения метода | Новый reader + integration тест |
| `LocalDate/of 2024 1 "2"` | TSP2345 на строковом аргументе | Есть в `test/features/src/f/core.clj` и `expected.txt` |
| `LocalDate/of 2024 1 2` | Принимается; platform LocalDate | Новый парный положительный тест |
| `.lenght` на `^String` | TSP2339 + подсказка length | Есть в `test/features` |
| `System/getenv` → `.length` | TSP2531; источник — ручной nullable-список, не аннотации | Есть в `test/features` |
| Public inherited method / private method | Первый доступен с правильным declaring, второй не появляется | Новый reader fixture |
| Public static field | Объявленный JVM-тип передаётся в проверку без инициализации класса | Есть в `java-fields-test`, включая static-массив и совпадающее имя метода |
| Public instance field | `.-field` использует объявленный JVM-тип поля. `.field` читает поле при отсутствии метода без аргументов | Есть в `java-fields-test`, включая nil, Spec и совпадающие имена |
| Одно имя static/instance | Фильтрация не смешивает контракты | Новый reader fixture |
| `String/format` | JVM-параметр `Object[]` участвует в проверке аргументов | Есть в `java-varargs-test`, включая массив из Spec другого namespace |
| Класс отсутствует / отсутствует зависимость его метода | Разные причины reader-ошибки; AST position + unknown downstream | Planned fixture и диагностики |
| Static initializer пишет marker/бросает исключение | Получение контракта не создаёт marker и не запускает initializer | Новый изолированный Java fixture |
| Две версии класса в разных JAR; смена classpath | Контракт выбран по порядку, provenance виден, кеш не устарел | Planned integration тест |
| Multi-release JAR / неподдерживаемая версия classfile | Выбран правильный target-вариант / явная ошибка | Planned bytecode тест |
| Bridge/covariant methods | Не потерять правильную декларацию; стабильный результат при разном порядке reflection | Planned differential fixture |
| Generic Signature отсутствует/повреждён; extern против descriptor | Erased-контракт с потерей точности либо конфликт; не молчаливый успех | Planned reader тест |

Текущие golden-проверки собирает `test/typespec/demo_test.clj`. Наличие fixture не означает, что эта редакция карточки запускала тесты. Готовность F510 требует отдельных reader-тестов происхождения/полноты, отрицательных fixtures и интеграции диагностик; полный охват зависимых Java-фич не входит в эту карточку.
