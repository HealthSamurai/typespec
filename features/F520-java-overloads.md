# F520 · Java-вызовы и перегрузки

## Зачем

В Clojure Java interop — обычная часть программы: строки, файлы, даты, коллекции и библиотеки JVM. Проверка должна отличать неправильный вызов от корректного, но рефлексивного, и объяснять, почему подходит конкретная перегрузка. Особенно важно не менять смысл программы автоматической вставкой type hint: устранение reflection само по себе не доказывает сохранение выбранного метода.

Область карточки — применимость и выбор методов и конструкторов, преобразования аргументов и безопасность hint fix. Полная модель Java generics, аннотаций nullability, массивов и реализации интерфейсов сюда не переносится: здесь используются результаты соответствующих механизмов.

## Что есть сейчас, а что спроектировано

`implementation: partial` сохранён: `check/java-call` уже проверяет некоторые вызовы, но это **не полный overload resolver**. Reference §4 задаёт цель, а не перечень реализованных гарантий.

| Возможность | Current: по исходникам | Planned |
|---|---|---|
| Instance/static methods | `.method` и `Class/method`; public methods через reflection | Согласованный с поддерживаемой версией Clojure выбор конкретного descriptor |
| Конструкторы `Class.` / `new` | Аргументы обходятся; возвращается тип разрешённого класса, сигнатура конструктора не проверяется | Отбор public constructors и проверка вызова |
| Арность и аргументы | Фильтр по числу аргументов; приближённая совместимость | Точные правила преобразования и выбора |
| Boxing/numeric conversions | Несколько JVM-типов схлопнуты; любые два числовых типа считаются совместимыми | Различать JVM primitive/reference и допустимые преобразования |
| Varargs | Обычный `check` учитывает последний JVM-параметр массива и соседние перегрузки с фиксированной арностью | Уточнить выбор descriptor для перегрузок с несколькими применимыми кандидатами |
| Неоднозначность | Нет выбора наиболее специфичного кандидата и отдельной диагностики | Явный результат ambiguous/unverified |
| Hint fix | `TSP7023` может сразу предложить `risk: safe` | Проверять сохранение выбора метода; иначе только review или без fix |

## Примеры и ожидаемое поведение

Это иллюстрации, не исполняемые golden-тесты. `Current` ниже — результат чтения алгоритма прототипа, не отчёт о запуске этих фрагментов. Примеры независимы, в обычном режиме без `strict-nil`.

### 1. Корректные instance/static вызовы

```clojure
(.substring "hello" 1 4)
(Integer/parseInt "42")
```

**Current:** `substring` проходит фильтр арности 2 и числовую проверку, результат `(t/platform String)`; `parseInt` с одним String даёт primitive `int`. Ошибки interop не ожидаются. **Planned:** сохранить результат, но дополнительно зафиксировать выбранные JVM descriptors и преобразование Clojure integer в параметр `int`. Совпадение возвращаемых типов само по себе не является доказательством единственности метода.

### 2. Неверный тип и неверная арность

```clojure
(.substring "hello" :start)
(.substring "hello" 0 1 2)
```

**Current:** первый вызов получает `TSP2345` на `:start` (нужен `int`); второй — `TSP2554` на вызове (допустимы 1 или 2 аргумента). В первом случае checker всё ещё может вывести возвращаемый тип по отвергнутому кандидату; наличие типа результата не означает успешной проверки. **Planned:** сохранять состояние invalid отдельно от восстановительного типа результата, чтобы последующая обработка не считала вызов доказанно корректным.

### 3. Конструктор: видимый пробел реализации

```clojure
(StringBuilder. "hello")
(StringBuilder. :not-a-string)
(new StringBuilder :not-a-string)
```

**Current:** все три формы получают тип `StringBuilder`; ошибки выбора конструктора во второй и третьей нет. Это не разрешение передавать keyword в Java constructor, а отсутствие проверки. **Planned:** первая форма принимается, следующие две отклоняются: ни `int`, ни `String`, ни `CharSequence` не принимают keyword. Обе формы синтаксиса должны использовать один resolver.

### 4. Varargs с явным JVM-массивом

```clojure
(String/format "%s" (object-array ["hello"]))
(String/format "%s" ["hello"])
(String/format "%s" "hello")
```

Clojure 1.12.4 передаёт varargs в одном JVM-параметре массива. Первый вызов даёт `String`, остальные получают `TSP2345` на аргументе. Вызов `(String/format "hello")` получает `TSP2554`, поскольку JVM-сигнатура требует аргумент массива. Обычные перегрузки того же имени тоже проверяются. Например, `(java.util.List/of "a" "b")` подходит перегрузке с двумя параметрами.

### 5. Сужение типа не доказывает безопасность hint fix

```clojure
(defn append-text [builder x]
  (when (and (instance? StringBuilder builder)
             (string? x))
    (.append builder x)))
```

**Current:** checker умеет использовать сужение, но `compiler-knows?` — отдельная эвристика: локальная переменная не становится compiler-hinted от проверки `instance?`. При известном классе receiver `TSP7023` предлагает `^StringBuilder` как `safe`, не сравнивая выбор overload до и после изменения. `append` имеет несколько применимых reference-параметров, а checker не выбирает наиболее специфичный. **Planned:** предупреждение о reflection допустимо независимо от ошибки типов; safe fix допустим лишь после доказательства сохранения dispatch, включая остающийся без hint аргумент `x`. Без доказательства — review/без fix. Пример не утверждает, что именно этот hint меняет результат; он показывает отсутствующую проверку.

## Текущий алгоритм и точки интеграции

1. **Вход:** AST вызова с позициями, `ctx` с imports, locals, фактами сужения и hinted bindings. `infer-list` направляет `.method` в `method-call`, `Class/method` — в `java-call`. Конструкторы сейчас идут отдельными ветками и обходят resolver.
2. **Receiver:** `method-call` выводит тип, применяет `eff`; `class-of` убирает nil-член и требует один оставшийся тип. `:class` даёт имя класса, `:prim`/`:lit` переводятся в JVM-класс. Несколько несовпадающих классов не разбираются по веткам. Unknown/any receiver даёт `TSP7020`, если compiler-knows? ложен, и результат unknown; возможный nil известного receiver даёт `TSP2531`.
3. **Кандидаты:** `java/methods-named` загружает класс без инициализации, читает `getMethods`, фильтрует имя и staticness. Запись содержит `:params`, `:ret`, `:declaring`, `:varargs`. Сортировка по арности и Object-result, затем дедупликация только по params — это не разрешение перегрузок.
4. **Ранние выходы:** отсутствующий класс → unknown; отсутствующий метод → `TSP2339` (кроме нуль-арного обращения к известному public field, которое тоже даёт unknown). Отсутствие нужной арности → `TSP2554`. JVM-параметр varargs-массива занимает одну позицию.
5. **Аргументы:** выводятся через `infer`. `java-arg-ok?` принимает unknown/any; для reference-параметров снимает nil; использует `sub?`, затем допускает любую numeric/numeric пару и даже `:class` для `char`. `types/class-type` объединяет int/long/short/byte и wrappers в `:int`, float/double — в `:double`. Точной JVM-информации уже не хватает.
6. **Ошибка применимости:** если нет подходящего кандидата, ищется первая позиция, которую отвергают **все** кандидаты нужной арности. Только тогда выдаётся `TSP2345`. Если каждый аргумент подходит какому-то overload, но ни одному целиком, ошибка теряется. Сообщение берёт ожидаемый параметр первого кандидата, а не объясняет весь набор причин.
7. **Выход:** одинаковые типы возврата всех оставшихся кандидатов дают этот тип, разные — unknown. Если никто не подошёл, используются даже отвергнутые кандидаты нужной арности. `java-ret` применяет platform-политику и небольшой список nullable returns. Выбранный descriptor и степень доказанности не сохраняются.
8. **Reflection/fix:** предупреждение `TSP7023` строится в `method-call` до `java-call`; сейчас нет связи между решением о `safe` и результатом overload resolution. Тест JSON fix закрепляет именно текущий формат, не семантическую безопасность.

## Целевой алгоритм: проект, не доказанная sound-процедура

Ниже — план реализации и проверки. Точные правила Clojure compiler/runtime dispatch ещё нужно исследовать; нельзя заменить их Java/JLS resolver и объявить задачу решённой.

1. **Нормализовать вход.** Представить instance/static/constructor call одним запросом: receiver, имя/класс, AST аргументов, выведенные типы и факты, явные hints/param-tags, версия Clojure/JDK и classpath. Отдельно хранить тип, известный checker, и сведения, реально доступные компилятору.
2. **Сохранить JVM-форму.** Для кандидатов хранить descriptor, declaring class, primitive/reference/array параметры, static/varargs/bridge/synthetic признаки. Для аргумента — Clojure value type, nilability, известную JVM-форму, источник факта и unknown. Нельзя восстанавливать byte против long из уже схлопнутого `:int`; потребуется расширение представления/отдельные факты.
3. **Собрать доступных кандидатов.** Public methods либо constructors. Наследование, bridge и covariant returns нормализовать по проверенным правилам, не дедуплицировать вслепую по params. Недоступный classpath отмечать как unverified, не «нет метода».
4. **Проверить применимость целиком.** Для каждого кандидата проверить арность и каждый аргумент; сохранить причины отказа, а не искать лишь одну общую плохую позицию. Таблица преобразований должна отличать primitive widening, boxing/unboxing, reference assignability, nil и массивы. Варargs-путь включать только для подтверждённого поведения данной версии Clojure. Unknown — недостаток доказательства, а не успешное преобразование.
5. **Разделить статический и рефлексивный выбор.** Применить подтверждённые правила предпочтения/специфичности; для runtime-dispatch проверить все допустимые runtime-классы либо признать результат unverified. Для union нельзя позволять разным аргументам независимо «найти свой» overload: нужно учитывать допустимые сочетания и имеющиеся корреляции. Ограничить перебор; при превышении лимита честно отказаться от доказательства.
6. **Вернуть структурированное решение.** `resolved` с descriptor и преобразованиями; `invalid` с причинами; `ambiguous` с конкурирующими кандидатами; `unverified` с недостающими фактами. Тип результата и platform/nullability вычислять отдельно. Если runtime-ветви выбирают разные методы, допустим типовой результат по всем ветвям, но не фиктивный единственный descriptor.
7. **Диагностики.** Сохранить существующие `TSP2339`, `TSP2554`, `TSP2345`, `TSP2531` там, где их причины доказаны. Для пустого множества применимых кандидатов показывать несколько ближайших сигнатур и причины, даже когда нет общей плохой позиции. Неоднозначность упомянута в reference как `TSP7022`, но в текущем Java-checker не реализована: здесь новый код не вводится. Unverified должно быть наблюдаемым состоянием отчёта, не молчаливым успехом.
8. **Безопасный fix.** Повторить анализ до/после предлагаемого hint, включая способы компиляции и runtime dispatch. `safe` только если выбор и преобразования сохраняются для всех допустимых значений. Иначе review/без fix. Не применить hint автоматически в `check`. Перед включением safe-пути нужны differential-тесты против реального Clojure compiler и runtime.

## Ограничения и вопросы

- Нужно зафиксировать поддерживаемые версии Clojure/JDK: правила compiler, reflection и Clojure 1.12 method values/param-tags нельзя считать одинаковыми. Последние здесь не объявляются реализованными.
- Прототип использует erased reflection signatures, не `getGenericParameterTypes`; generic return не обещается выводить из аргументов.
- Нынешнее numeric/numeric и class→char правило слишком широкое для доказательства применимости. Ни диапазон числа, ни narrowing conversion не проверяются точно.
- Статическое поле имеет лишь fallback unknown; `has-field?` не проверяет staticness. Полная проверка полей остаётся отдельной задачей.
- Nullable receiver, null reference argument и unboxing nil — разные случаи. Существующая platform-политика не заменяет анализ преобразований.
- Для открытой иерархии runtime-классов доказательство dispatch может быть недоступно. Неопределённый ответ лучше ложного safe fix.
- Ограничение вывода кандидатов: показывать только соответствующую арность и ближайшие причины отказа, с общим числом остальных; точный лимит и порядок требуют UX-тестов.

Ниже — конкретные необходимые проверки, не заявление об уже существующем покрытии. Для нестандартных overload использовать маленький Java fixture; запускать отдельно от полного suite.

| Случай | Current / что зафиксировать | Целевой критерий |
|---|---|---|
| Пример 1: substring и parseInt | Возврат String/platform и primitive int | Проверить точный descriptor и преобразования |
| Пример 2: keyword / лишний аргумент | `TSP2345` / `TSP2554`, правильные ranges | Нет успешного resolved после ошибки |
| Несуществующий `.subtring` | `TSP2339`, предложение имени | Не смешать с ошибкой загрузки класса |
| Пример 3: обе формы конструктора | Пока нет ошибки аргумента | Положительный String, отрицательный keyword, общая логика |
| Пример 4: Object[], vector, отдельная строка | Проверено на JVM и через `java-varargs-test` | JVM-массив принимается, остальные аргументы получают `TSP2345` |
| `List/of`: fixed overload рядом с varargs | Проверено на JVM и через `java-varargs-test` | Вызов с двумя строками получает тип `java.util.List` |
| Fixture: `m(String,int)` и `m(int,String)`, вызов `m("a","b")` | Сейчас нет общей плохой позиции и можно пропустить ошибку | Отказ: ни один кандидат не принимает всю пару |
| Fixture: `m(String)` / `m(Integer)`, аргумент nil | Нет полноценного ambiguity result | Сверка диагностики с compiler/runtime; не произвольный первый кандидат |
| Числа: byte/int/long/double, boxed и nil | Приближённая совместимость | Матрица разрешённых преобразований и запрещённого unboxing |
| Unknown аргумент, одинаковые return types | Сейчас возможен конкретный return без выбора | Unverified dispatch не маскируется одинаковым return |
| Пример 5: narrowed receiver и hint | Сейчас `TSP7023`, safe без resolver | Review до доказательства; сравнить descriptor/поведение до и после |
| Унаследованный method + bridge/covariant return | Дедупликация по params | Не потерять значимый кандидат, не создать ложную неоднозначность |
| Отсутствующий класс / nil receiver | unknown / `TSP2531` при известной nilability | Разные причины, правильная позиция, без ложного safe fix |

Существующие `test/features/src/f/core.clj` (`n7`) и `test/typespec/demo_test.clj` проверяют сужение/предупреждение и JSON hint fix. Они не доказывают полноту overload resolution. Готовность карточки требует targeted тестов всей матрицы и подтверждённого соответствия resolver правилам Clojure, а не только исчезновения warnings.
