# F610 · Макросы и границы проверяемого кода

## Зачем это нужно Clojure

Макрос получает формы, а не вычисленные аргументы: он может вводить имена, менять порядок вычислений, не вычислять часть тела или добавлять ветку с `nil`. Проверка его как обычной функции либо даёт ложные ошибки на символах связывания, либо пропускает реальные ошибки. Для DSL, ресурсных обёрток и обычных `->`/`for` нужна проверка смысла формы без загрузки приложения.

Цель — различать «проверено встроенным правилом», «проверено при доверии описанию» и «пропущено». Отсутствие ошибок внутри пропущенного тела не означает его корректность. Карточка описывает выбор и границы макроконтрактов; правила самих типов и ветвлений остаются в профильных карточках.

## Что есть сейчас, а что только спроектировано

Источником текущего поведения служит код, а не полный список обещаний в `docs/reference.md`.

| Механизм | Current | Planned |
|---|---|---|
| Чтение исходника | `rewrite-clj`, маленький AST с позициями; проект не загружается | Сохранить этот безопасный путь по умолчанию |
| Встроенные правила | `special` в checker: например `let`, `when`, `->`, `for`, `doseq`, `try`, `with-open` | Проверять полноту каждого правила отдельно; наличие метода ещё не означает полную поддержку |
| Неполные правила | `cond->`/`cond->>` проверяют начальное выражение и условия, но не шаги; результат `t/unknown` | Явно показывать непроверенные части, затем реализовывать семантику шагов |
| Макрос проекта | `env/collect-file` собирает имена `defmacro`; вызов такого макроса без правила даёт warning `TSP7031`, тело вызова не проверяется, результат `t/unknown` | Описания с происхождением и границей доверия |
| Другие пропуски | Известный stdlib-макрос без правила возвращает `t/unknown` **без** `TSP7031`; тело `defmacro` не проверяется | Не скрывать эти пропуски в отчёте покрытия |
| `:lint-as`, SCI hooks, `:t/macro` в externs | Не реализованы как механизм макроконтрактов | Импорт конфигурации clj-kondo, разбор и применение контрактов |
| `:macros {:expand true}` | Worker expansion не реализован | Только явное включение, отдельный ограниченный процесс; исполнение макроса считается доверием |

Неизвестное внешнее имя не обязательно распознаётся как макрос: набор `:macros` строится из прочитанных файлов. Нельзя обещать `TSP7031` для любого внешнего макроса. Также `:trust` сейчас считает только `:cast`, `:any`, `:ignore`, а не макроконтракты.

## Примеры и ожидаемое поведение

Все блоки ниже — иллюстрации, не исполняемые golden-тесты. `Current` описывает ветви исходного checker; `Planned` — требования к будущему механизму, а не доступный API.

### 1. Корректное тело под встроенным правилом — Current

```clojure
(ns sample.thread-ok
  (:require [clojure.string :as str]))

(defn normalize [xs]
  (for [x [" a " " b "]]
    (-> x str/trim str/upper-case)))
;; Current: for связывает x с типом элемента коллекции;
;; -> передаёт тип результата очередному вызову.
;; Результат тела for — string?, всей формы — последовательность строк.
;; Ошибок типов в этой форме не ожидается. xs здесь не используется.
```

### 2. Ошибка в проверяемом теле — Current

```clojure
(ns sample.thread-bad
  (:require [clojure.string :as str]))

(defn invalid []
  (-> 42 str/upper-case))
;; Current: upper-case получает число вместо строки, ожидается TSP2345.
;; Диагностика относится к исходной форме, не к macroexpand-дереву.
```

`thread` строит синтетический узел `__threaded` с позицией предыдущего выражения и отображаемым исходным текстом. Точную колонку следует фиксировать отдельным тестом, а не обещать универсальную карту исходников для всех макросов.

### 3. Ошибочный код, который сейчас сознательно пропускается — Current

```clojure
(ns sample.unknown
  (:require [clojure.string :as str]))

(defmacro unless [test & body]
  `(if ~test nil (do ~@body)))

(defn use-unless [x]
  (unless x (str/upper-case 42)))
;; Current: TSP7031 [warning] на unless, результат — t/unknown.
;; Ошибка upper-case НЕ найдена: формы внутри вызова не обходятся.
;; Определение defmacro тоже не проверяется как функция преобразования AST.
```

Это соответствует уже существующему примеру `f7` в `test/features/src/f/core.clj` и записи в `test/features/expected.txt`. Предупреждение — сообщение о дыре проверки, не замена ошибки в теле.

### 4. Пограничный случай: известное имя ещё не означает проверенное тело — Current / Planned

```clojure
(ns sample.partial
  (:require [clojure.string :as str]))

(defn partial-rule []
  (cond-> 42
    true str/upper-case))
;; Current: проверяются 42 и true, но НЕ str/upper-case.
;; Вся форма имеет t/unknown; TSP2345 из этого шага не ожидается.
;; Planned: либо проверенный переход типа через шаг с TSP2345,
;; либо явный учёт пропущенного шага; не отметка «всё проверено».
```

### 5. Почему похожая форма — ещё не контракт — Planned

```clojure
(ns sample.contract)

(defmacro safely [& body]
  `(try ~@body (catch Exception _# nil)))

(defn parse-or-nil [s]
  (safely (Long/parseLong s)))

;; Предполагаемая конфигурация, НЕ поддержанная текущим checker:
{:lint-as {sample.contract/safely clojure.core/do}}
;; Такое описание неверно: do теряет альтернативный результат nil.
;; Planned: корректное доверенное преобразование должно сохранить try/catch;
;; при числовом типе тела результат содержит этот тип И nil.
;; Current: вызов safely даёт TSP7031 и t/unknown, конфигурация не применяется.
```

Даже совпадение результатов раскрытия на десяти примерах не доказывает корректность описания для всех входных форм. Автоматическое доказательство эквивалентности `:lint-as` реальному макросу не обещается.

## Алгоритм: существующий путь

1. **Вход.** `parse` читает файлы без загрузки проекта. Узлы содержат `:op`, `:children`/`:val`, `:pos`; файл — namespace, aliases и refers. `env/build` собирает декларации и множество квалифицированных имён `:macros`.
2. **Контекст.** `check-files` добавляет `:ns-defs`, создаёт `ctx` с `:env`, `:file`, `:opts`, `:locals`. Типы — структуры из `types.clj`, например `{:t :unknown}` и `{:t :coll :kind :seq :of T}`. Ветвевые факты и локальные связывания передаются существующими правилами, а не извлекаются из тела `defmacro`.
3. **Выбор.** `infer-list` сначала учитывает локально связанное имя. Затем `env/head` нормализует голову формы; `own?` препятствует применению встроенного правила к собственному одноимённому определению. Если есть подходящий метод `special`, вызывается он. Это текущая эвристика, не доказательство полной корректности разрешения имён.
4. **Проверка известной формы.** Правило определяет, какие подформы являются выражениями и где появляются связывания. `let` применяет `bind-pairs`; `for` — `bind-seq-pairs`; `->` последовательно строит синтетические вызовы и передаёт их в `infer`; `try` объединяет тип тела и обработчиков. Обычные вызовы внутри проверяются через существующие `call-fn` и отношения типов.
5. **Пропуск.** Stdlib-макрос без правила сразу получает `t/unknown`. Для прочитанного макроса проекта без правила выдаётся warning `TSP7031` на голове, возвращается `t/unknown`, аргументы не обходятся. Неопознанное имя идёт по обычному разрешению вызова; нельзя механически объявлять его макросом.
6. **Выход.** `infer` записывает тип узла через `record!`; `check-files` возвращает диагностики, записи типов, окружение, сигнатуры и текущие счётчики доверия. Существующие подавления и уровни диагностик применяются в общем завершающем проходе. Отдельной записи «контракт макроса применён/тело пропущено» пока нет.

## Алгоритм согласования будущих источников контрактов

Ниже — проект интеграции, **не sound алгоритм доказательства макросов**. Soundness требует отдельно определить семантику поддержанного подмножества и условия корректности каждого доверенного преобразования.

1. **Собрать входы, не исполняя их.** Исходный AST и позиции, разрешённое квалифицированное имя, лексический контекст; встроенный реестр правил; явные настройки проекта; импортированные `:lint-as`/hooks; externs; разрешение worker expansion. У каждого описания хранить источник, версию/хеш и поддержанную грамматику форм.
2. **Разрешить имя до выбора контракта.** Локальная функция не должна стать макросом из-за совпадения короткого имени. Учитывать aliases, refers, исключения core и затенение. При неоднозначности не применять контракт по догадке.
3. **Согласовать описания.** Предлагаемая политика: встроенное правило нельзя молча заменить импортом; явная настройка выбирает один внешний источник, но конфликт с встроенным требует отдельного явного решения. Несколько несовместимых импортов без выбора — диагностика и непроверенный результат. Циклы `lint-as` и отсутствующая целевая форма — отказ, не бесконечная переадресация. Политику приоритетов ещё нужно утвердить.
4. **Проверить применимость.** Контракт должен описывать не только итоговый тип, но и выражения/данные, связывания и их области, ветки, повторные/отложенные вычисления. Для function-like extern-контракта допустима только явно заявленная модель аргументов-выражений; нельзя передавать в `call-fn` произвольное тело DSL как обычные аргументы. Неподдержанная форма даёт `unknown` с причиной.
5. **Получить проверяемую форму.** Встроенный обработчик работает напрямую; `lint-as` применяет правило целевой формы как доверенную модель; hook преобразует AST в ограниченной среде SCI. Нужны гигиена свежих имён, карта исходных позиций и сохранение структуры ветвлений. Проверить формат результата и лимиты, затем передать его в `infer` с корректным локальным контекстом. Ошибка преобразования не разрешает fallback к `any`.
6. **Опциональное раскрытие.** Только при явном разрешении запускать макрос в worker с лимитами времени/памяти/глубины и контролем файлового доступа и сети. Отдельный процесс сам по себе не sandbox. Таймаут, авария, цикл раскрытия или неверный AST дают диагностируемый непроверенный результат, не успешную проверку. Проверка раскрытия относится к этой форме и этой среде, не доказывает контракт макроса вообще.
7. **Результат и происхождение.** Сохранить тип, диагностики и отдельные факты о способе проверки: встроенное правило / доверенный контракт / доверенное исполнение / пропуск. Не сужать значение на основании пропущенного тела. Диагностику раскрытия привязывать к исходному вызову и, где возможно, точной подформе; показывать источник контракта. Счётчики покрытия и доверия подключать к общему отчёту, не смешивая с `cast`.

Для будущих ошибок предлагаются только новые обозначения: **proposed TSP610-01** — конфликт/цикл контрактов; **proposed TSP610-02** — форма вне грамматики контракта; **proposed TSP610-03** — сбой/лимит hook или worker. Это не существующие коды. Для обнаруженного неописанного макроса уже есть `TSP7031`; обычная ошибка аргумента после преобразования остаётся обычной ошибкой типов, например `TSP2345`.

### Два независимых результата DSL-модели

Разделить внешний контракт на `definitions` (созданные vars, арности, типы) и `body-rule` (связывания, обход, control flow и режим исполнения). Сначала собрать инертные definitions для разрешения имён; затем проверять тела по body-rule. Наличие definitions не повышает coverage тела. В provenance хранить эти два основания отдельно; внешние декларации обязательны и для core, и для библиотечных DSL, но сами по себе не заменяют правила макросов.

```clojure
(defendpoint get-user [id]
  (inc "oops"))
;; Extern get-user : string -> map позволяет проверять вызовы get-user,
;; но без body-rule ошибка внутри остаётся пропуском, не checked body.
(delay (println "later"))
;; Поддержанное правило проверяет тело сейчас, но хранит I/O как latent.
```

Режим исполнения подформы — отдельная часть body-rule: немедленно / отложено в результате / запущено асинхронно / не вычисляется. `delay` переносит summary в `Delay[e,T]` (F450); `future` нельзя моделировать тем же правилом, будто работа начинается при deref. Отсутствие режима или неподдержанная арность не даёт pure: сохранять unknown-effect и причину непроверенности, независимо от известного типа созданного Var. Value-level `unknown` — безопасный top, не Sorbet `T.untyped` и не Pyright Unknown.

Planned-тесты: extern созданного Var не скрывает unchecked DSL-body; добавление body-rule выявляет `(inc "oops")` на исходной позиции; изменение definitions не отмечает тело проверенным; `delay` сохраняет latent I/O, `future` не получает его правило; сбор declarations не выполняет `require`, reflection или макрос приложения. Это не обещает проверку истинности самих definitions.

Основание: [Sorbet, Finding 5](../docs/research-sorbet.md) и [Koka, Finding 4](../docs/research-koka.md). Здесь прочитаны отчёты; первоисточники заново не аудированы. В Sorbet-отчёте прочитаны релевантные разделы [RBI](https://sorbet.org/docs/rbi) и [Unsupported](https://sorbet.org/docs/unsupported), но не весь inference; в Koka-отчёте целиком прочитан [delayed.kk](https://github.com/koka-lang/koka/blob/b66091b2a5a7ea20c5ed9498ad1e1f03caee9589/lib/std/core/delayed.kk), включая unsafe-границу. Ни RBI, ни тип Koka не доказывают семантику произвольного Clojure-макроса.


## Ограничения и необходимые исследования

- `:lint-as` утверждает семантическое сходство, а не доказывает его. Нужен явный учёт доверия, особенно для исключений, `nil`, новых имён, повторных вычислений и ленивых тел.
- Контракт, зависящий от `&env`, `&form`, metadata или внешнего состояния, нельзя свести к фиксированной сигнатуре без дополнительных условий. Требуется определить поддерживаемое подмножество; остальные случаи оставлять непроверенными.
- Гигиена, source map, инвалидация кеша при изменении hook/конфигурации/зависимостей и воспроизводимость worker требуют отдельного дизайна. Импорт clj-kondo не гарантирует, что его lint-преобразование сохраняет типовую семантику.
- Встроенные обработчики тоже требуют аудита: `with-open` сейчас выводит тип тела и связываний, но это не доказательство корректного закрытия ресурса; `cond->` пропускает шаги; перечень core.async в reference не является свидетельством реализации.
- Сверка раскрытий и тесты на контрпримерах полезны, но недостаточны для soundness. Не обещаем проверять реализацию произвольного `defmacro` или доказывать соответствие контракта произвольному Clojure-коду.

## Конкретная матрица тестов

`Current` ниже — регрессионная цель по прочитанному коду; наличие теста явно отмечено отдельно. Новые тесты этой правкой не добавляются.

| Сценарий | Ожидаемая проверка | Слой / состояние |
|---|---|---|
| `for` + `->` над строками, пример 1 | Тип seq строк, без ошибки аргумента | `check-files` / Current, добавить точный тест |
| `-> 42 str/upper-case`, пример 2 | `TSP2345`, исходная позиция | `thread` + diagnostics / Current, добавить точный тест |
| `unless` с неверным телом, пример 3 | Один `TSP7031`, нет ошибки скрытого вызова | Existing `f7` + `expected.txt` |
| `cond->` с неверным шагом, пример 4 | `unknown`, ошибка шага сейчас отсутствует | Current regression; Planned — проверка или видимый пропуск |
| Локальная функция с именем `when` | Обычный вызов, не макроправило | Разрешение имён / Current, добавить |
| Макрос другого прочитанного ns через alias | `TSP7031` по разрешённому имени | `env` + `infer-list` / Current, добавить |
| Stdlib-макрос без метода, например `lazy-seq` | `unknown`, тело не обходится, `TSP7031` нет | Current regression; Planned — учёт пропуска |
| `safely` описан как `do`, пример 5 | Контрпример показывает потерю `nil`; не принимать тестовую сверку за доказательство | Planned, исследование доверия |
| Два импортированных разных контракта; цикл A → B → A | Отказ выбора, proposed TSP610-01 | Planned resolver |
| Hook: новый binding, затенение, gensym | Нет захвата имени, верная область видимости, ошибка ведёт к исходной подформе | Planned AST/source map |
| Hook возвращает неверный AST или зависает | Ограниченный отказ, proposed TSP610-03, не `any` | Planned runner |
| Expansion выключен; макрос имеет побочный эффект | Код не исполняется, эффект отсутствует | Current архитектурный инвариант; тест изолированного fixture |
| Expansion включён: исключение/цикл/доступ к сети | Ограниченный отказ, факт доверенного запуска, без тихого успеха | Planned sandbox integration |
| Изменён контракт при неизменном исходнике | Старый результат не используется | Planned cache/provenance |

Критерий готовности: тесты различают проверенные и пропущенные узлы, фиксируют источник контракта и позиции диагностик; у каждого поддержанного правила есть корректная форма, намеренная ошибка и пограничная форма. `implementation: partial` сохраняется: встроенный путь и `TSP7031` существуют, общий механизм контрактов ещё нет.
