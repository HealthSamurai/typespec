# F710 · Контракты библиотек и экспорт интерфейсов

## Обновление реализации — топ-10

Работают явно заданные локальные EDN-наборы и provenance; core override требует :externs-core :override. Registry, проверка версий пакетов, jar exports и emit ещё не реализованы.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Мотивация и граница ответственности

Clojure-приложение использует функции библиотек, исходники которых нельзя или не нужно менять. Без описания аргументов и результата проверка теряет информацию на каждом таком вызове. Отдельные файлы аннотаций **для существующих библиотек и `clojure.core` — обязательная возможность Typespec**, а не рекомендация переписывать зависимости или добавлять им runtime-инструментацию.

[F130](F130-namespace-sidecars.md) отвечает за type-only EDN: запись типов, соответствие namespace/var, согласование с inline-сигнатурами, spec и hints. F710 отвечает за **наборы** этих аннотаций: поиск, загрузку, версии, происхождение, упаковку, распространение и явные overrides. Здесь описан алгоритм согласования источников, а не новый алгоритм подтипизации или формат сигнатур.

Контракт позволяет проверить использование библиотеки, но не доказывает правильность её реализации. Если собственная реализация входит в проверяемые исходники, внешняя аннотация задаёт обязательство для её тела, а не отключает его проверку.

## Что есть сейчас, что проектируется

**Current, проверено по исходникам:**

- `src/typespec/core_types.clj`: `externs` — quoted map с сигнатурами `clojure.core` и `clojure.string`; `table` строится через `types/parse-sig`. Это встроенный каталог в коде проверяющего, не загрузка внешних файлов аннотаций.
- `env/build` собирает `s/def`, `s/fdef`, `:t/sig` и hints из переданных исходников. `:vars` хранит тип и источник; `:specs` — именованные типы. Несогласие `:t/sig` и `s/fdef` уже даёт `TSP2790`.
- `check/check-files` строит окружение и обходит формы. Разрешение вызова использует `var-type` и `core/table`; часть core-операций имеет специальную логику checker, а не только табличную сигнатуру.
- `main/run-check` читает конфигурацию и `.clj`/`.cljc` из source paths. Чтение ключа `:externs` в конфигурации само по себе ничего не загружает. Нет загрузчика наборов, проверки версий, импорта `typespec.exports/` и команд `emit`/`extern`.

**Planned:** всё описанное ниже о внешних наборах, их приоритете, overrides и публикации. Поэтому `implementation: not-implemented` сохранён: существующий core-каталог — основание интеграции, но не реализация F710.

## Примеры и ожидаемое поведение

Все блоки — обычный Clojure-синтаксис для чтения человеком, не исполняемые golden-тесты. EDN-фрагменты читаются как данные, не через `load-file` и не через `eval`. Внешние наборы ниже вымышлены; их версии не обещают совместимость реальных библиотек.

### 1. Корректный вызов по локальному набору — planned

```clojure
;; typespec/externs/acme.codec@2.4.0.edn (данные)
{acme.codec/encode [string? :-> string?]}

;; src/app/codec.clj (обычный исходник, библиотека не изменяется)
(ns app.codec (:require [acme.codec :as codec]))
(defn greeting {:t/sig '[:-> string?]} []
  (codec/encode "hello"))
```

При реально разрешённой зависимости `acme/codec` версии `2.4.0` набор должен дать тип вызову и позволить проверить результат `greeting`. Связь имени файла, Maven coordinate и namespace обязана быть явной в метаданных набора: namespace не является coordinate. Точный формат метаданных ещё проектируется; имя файла взято из §5 reference. Сейчас этот EDN не читается, поэтому пример не является подтверждением поддержки внешних контрактов.

### 2. Ошибка аргумента и граница доверия — planned

```clojure
;; Тот же набор acme.codec@2.4.0.edn
{acme.codec/encode [string? :-> string?]}

(ns app.bad-codec (:require [acme.codec :as codec]))
(defn broken {:t/sig '[:-> string?]} []
  (codec/encode 42))
```

После загрузки контракта ожидается ошибка аргумента на `42`: обычная проверка вызова уже использует `TSP2345` для несовместимых типов. Диагностика должна дополнительно указать файл/версию выбранного контракта. Если библиотека на деле принимает число, это повод исправить контракт, а не считать библиотеку доказанно ошибочной. В текущем checker отсутствие внешней сигнатуры не даёт обещанной проверки этого вызова.

### 3. Отдельный набор для Clojure core — planned; встроенная сигнатура уже есть

```clojure
;; typespec/externs/org.clojure.clojure@1.12.0.edn (данные)
{clojure.core/subs ([string? int? :-> string?]
                   [string? int? int? :-> string?])}

(ns app.text)
(defn tail {:t/sig '[string? :-> string?]} [s]
  (subs s 1))
(defn wrong-tail {:t/sig '[:-> string?]} []
  (subs 42 1))
```

Предлагаемый внешний набор привязан к версии **целевого Clojure**, а не случайно к JVM, на которой запущен Typespec. `tail` корректен по типам; `wrong-tail` должен получить ошибку аргумента. Та же сигнатура `subs` уже есть во встроенном `core/externs`, поэтому эти вызовы проверяются без EDN; это не тест внешнего загрузчика. Контракт не гарантирует допустимость индекса и отсутствие исключения при короткой строке. Generic-сигнатуры core не обещаются этим примером: их внешний формат и применение требуют отдельной поддержки движка.

### 4. Конфликт источников и несовпадение версии — planned, пограничный случай

```clojure
;; Локальный typespec/externs/acme.codec@2.4.0.edn
{acme.codec/decode [string? :-> string?]}

;; Контракт внутри jar 2.5.0, под typespec.exports/
{acme.codec/decode [string? :-> (s/nilable string?)]}

;; Исходник потребителя
(ns app.decode (:require [acme.codec :as codec]
                        [clojure.string :as str]))
(defn normalize {:t/sig '[string? :-> string?]} [s]
  (str/upper-case (codec/decode s)))
```

Пусть разрешена версия `2.5.0`. По reference несовпадение версии локального набора даёт warning. **Предлагаемое уточнение:** warning не разрешает молча использовать старый, более сильный контракт. Старый набор остаётся неактивным без явного подтверждения совместимости; выбирается совместимый jar-контракт. Тогда использование потенциального `nil` должно дать обычную nil-диагностику (`TSP2531`). При совпадающих версиях различие локального и jar-контрактов тоже должно быть видно: override требует указания заменяемого источника и причины. Синтаксис override ещё не утверждён; несуществующий ключ конфигурации здесь не изображён как готовое API.

### 5. Экспорт своей библиотеки не заменяет проверку тела — planned

```clojure
;; Локальная аннотация собственного публичного API
{app.codec/encode [string? :-> string?]}

;; Проверяемая собственная реализация
(ns app.codec)
(defn encode [s] 42)

;; Предлагаемое содержимое экспорта после исправления реализации:
;; jar!/typespec.exports/<package>/...edn
{app.codec/encode [string? :-> string?]}
```

Импорт локальной аннотации обязан сохранить `:parts`/`:pfile` собственной функции и проверить её тело. Возврат `42` нарушает обещание `string?`: ожидается обычная ошибка возврата `TSP2322`. До исправления `emit` не должен публиковать такой API как проверенный. После исправления экспорт включает публичные сигнатуры и необходимые определения типов, а не тела функций. Точное имя ресурса внутри `typespec.exports/` и manifest пока не определены. Сегодня ни импорт этой аннотации, ни `emit` не реализованы.

## Алгоритм поиска и согласования источников — planned

Это алгоритм выбора доверенных деклараций. Он **не является доказательством soundness** типов библиотеки или произвольных generic-контрактов.

1. **Зафиксировать входы.** Получить root и конфигурацию проекта, parsed source files, реально разрешённые dependency coordinates/версии/classpath, целевые версии Clojure и платформу. `deps.edn` недостаточен: aliases, overrides и транзитивные зависимости меняют фактический граф. Для git/local deps нужны SHA или иной устойчивый идентификатор; нельзя притворяться, что это Maven version.
2. **Собрать кандидатов без исполнения.** Локальные наборы из `:externs`; ресурсы `typespec.exports/` зависимостей; доступные `s/fdef` из исходников библиотек; заранее полученные наборы общего репозитория; встроенный core-каталог как fallback для core. Не делать `require` произвольной библиотеки для поиска деклараций. Не скачивать изменяемый latest во время обычного check: получение и фиксация общего набора — отдельная операция.
3. **Проверить контейнер и версию.** Безопасно прочитать данные с ограничениями размера/глубины, без пользовательских reader handlers. Проверить schema version, владельца namespace, coordinate, целевую версию, платформу, целостность ресурса и дублирующиеся записи. Сопоставлять с разрешённым графом, для core — с целевым `org.clojure/clojure`. Несовпадение сохранить в диагностике и не активировать автоматически. Совпадение версии — условие применимости, не доказательство корректности.
4. **Нормализовать декларации по F130.** Получить записи вида «fully qualified var → тип + происхождение» и именованные типы. Происхождение содержит путь/позицию, coordinate, версию, hash и вид источника. Для типов использовать текущие `{:t :fn :arities [...]}`, `:params`, `:ret`, `:rest`, ссылки на `:specs`; отдельно хранить метаданные выбора, не зашивать их в отношение подтипизации. Неизвестный конструктор/незамкнутая ссылка делает декларацию непригодной, а не незаметно успешной через `t/unknown`.
5. **Сгруппировать по var и согласовать.** Базовый порядок из reference: local externs → jar exports → source `s/fdef` → shared repository → unknown. Встроенный core-каталог — дополнительный fallback для core до unknown. Равные нормализованные декларации можно объединить, сохранив все источники. Различные декларации не склеивать в перегрузку и не разрешать порядком обхода файлов. Различия одного уровня — конфликт; затенение нижнего уровня другим типом — только явный override с причиной и точным источником назначения. До разрешения конфликта результат проверки не считается успешным.
6. **Не подменять контракт собственного тела.** Для vars из проверяемых source paths согласовать внешний тип с inline/spec/hints по F130. Сохранить информацию об определении и передать согласованный тип проверке реализации. Даже разрешённый override чужого набора не разрешает игнорировать ошибку собственного тела. Совместимость с hints и декларациями не сводится к текущему `sub?`: функциям требуется отдельное согласование сигнатур, включая арности.
7. **Встроить результат перед inference.** В `main/run-check` добавить отдельный этап сбора наборов; согласованное окружение передавать в `check/check-files` до обхода форм. `env/build` расширить декларациями, не заменяя сведения об исходниках. Централизовать обращение к core-каталогу и внешним vars, чтобы отдельный путь `core/table` не обходил приоритеты. Аудировать специальные core-правила: если внешняя аннотация противоречит их предположениям, отказать в override, пока нет правила согласования, а не молча применить оба.
8. **Проверить использование и объяснить выбор.** Арность/аргументы/результат проверяет существующий checker; ошибки загрузки и конфликтов идут отдельными diagnostics с путями обоих источников. `sig`/JSON должны показывать выбранный источник, версию, причину override и недоверенные границы. При отсутствии контракта сохранять unknown и видимость непроверенного участка; отсутствие ошибки не считать доказательством безопасности.
9. **Экспортировать воспроизводимый интерфейс.** Только после успешной проверки собственного кода собрать публичные сигнатуры и транзитивное замыкание ссылок на типы. Отказать при неразрешённых ссылках/конфликтах; не обозначать unknown как проверенный точный тип. Сериализовать данные вместе с manifest версии формата, dependency identities и provenance; проверить round-trip отдельным consumer-проектом без исходников производителя. Дизайн `typespec extern` и `--verify` из reference — отдельная будущая операция: сгенерированный черновик требует ревью, запуск тестов/instrument даёт лишь sample-based validation.

### Диагностики

Новых реализованных кодов F710 нет. Для проектирования предлагаются только:

- **proposed TSP710-01** — несовместимая/неопределённая версия набора или schema version; показать ожидаемую и найденную версии.
- **proposed TSP710-02** — конфликт наборов либо отсутствующий явный override; показать var и оба источника.
- **proposed TSP710-03** — повреждённый/неполный набор: неверный владелец, ссылка, декларация или неподдержанный тип; показать путь и проблемную запись.
- **proposed TSP710-04** — экспорт не может считаться проверенным: ошибка тела, незамкнутые типы или непроверенные публичные сигнатуры.

`TSP2345`, `TSP2554`, `TSP2531`, `TSP2322` уже применяются checker к обычным вызовам/возвратам; их использование после импорта — будущая интеграция, не готовые golden-результаты примеров.

### Экспорт predicate summaries — planned, после F250/F251

Сигнатура `value -> boolean` не описывает сужение. Если пакет экспортирует summary предиката, хранить отдельный payload: truthy-факт, falsy-факт (каждый может отсутствовать), пути к параметрам, основание доверия и hash проверенного тела/зависимостей. Например, после `(if (vendor/nonempty-string? x) (clojure.string/upper-case x) nil)` trusted положительный summary разрешает строковую операцию; отсутствие отрицательного summary не разрешает считать `x` не-строкой в else. Не получать отрицательную сторону отрицанием положительной.

Тесты: round-trip сохраняет односторонность; замена тела/extern инвалидирует summary; ручной extern не становится body-checked при импорте. Обычная проверка вызовов без runtime enforcement остаётся условной относительно этих допущений. До поддержки summaries неизвестный payload отвергать, не заявлять сужение по одной boolean-сигнатуре. Это расширение существующего формата, не готовый перенос логики Racket.

Основания: [отчёт Typed Racket, §6 и приоритеты](../docs/research-typed-racket.md), первичные [режимы исполнения](https://docs.racket-lang.org/ts-reference/behavior-of-types.html) и [propositions](https://docs.racket-lang.org/ts-guide/occurrence-typing.html). Здесь прочитан отчёт; upstream повторно не читался, доказательство soundness и эксперимент не выполнены.

## Ограничения и открытые решения

- §5 reference задаёт приоритет и warning версии, но не manifest, явные overrides и политику неактивных несовместимых наборов. Эти уточнения — предложения этой карточки, требующие согласования, а не реализованный формат.
- Namespace не доказывает происхождение var. Нужны правила для split namespaces, нескольких jar с одним var, shaded библиотек и git/local deps. Автоматическое исполнение библиотеки для разрешения неоднозначности недопустимо.
- Текущий `types/sub?` допускает unknown и не является полноценной проверкой совместимости функциональных контрактов. Для сравнения generic-сигнатур, variance, overloads, recursive types и alpha-equivalence нужны исследования и тесты; простой `=` годится лишь как консервативный критерий совпадения ограниченного нормализованного формата.
- Core-спецправила, макросы и effects нельзя безопасно переопределить одной сигнатурой. Первая версия должна явно ограничить overrides таким подмножеством, для которого проверена согласованность с checker; generic core-контракты остаются planned.
- Проверяемый экспорт подтверждает только поддержанное checker подмножество и заявленный trust budget. Непроверенное тело зависимости, `any?`, unknown, opaque specs и runtime-исключения не исчезают от упаковки в jar.
- Для кеша важны hashes исходников/наборов, разрешённый graph, версия checker и целевой Clojure. Без invalidation смена override может оставить старый тип.
- Публикация в общий репозиторий, аутентичность пакетов, отзыв ошибочных контрактов и сетевой протокол ещё не определены. Обычная проверка должна работать воспроизводимо и offline.

## Конкретная матрица тестов

Все loader/export-тесты ниже — **planned**, не утверждение о текущем покрытии. Текущий `test/typespec/demo_test.clj` проверяет snapshots, `sig`, hints, trust counters и карточки с особыми executable fences; обычные блоки этой карточки им не исполняются.

| Сценарий / вход | Ожидаемый результат |
|---|---|
| Пример 1, только локальный набор подходящей версии | Тип вызова `string?`, provenance указывает локальный файл; исходники зависимости не изменены |
| Пример 2, число вместо строки | Ошибка аргумента на `42`, ссылка на выбранный контракт |
| Тот же var, неверная арность | Обычная диагностика арности, не ошибка загрузки |
| Пример 3, внешний core-набор и совпавшая версия Clojure | Загрузка без изменения `clojure.core`; корректный вызов принят, ошибочный отклонён |
| Тот же core-набор, другая целевая версия | Warning несовпадения; набор не активирован без явного решения |
| Пример 4, устаревший локальный набор и совместимый jar | Выбран jar; nil-ошибка у потребителя; старый набор виден как неактивный |
| Разные local/jar типы одной версии, override отсутствует | Конфликт, нет ложного успешного check |
| Явный override с причиной и совпавшим hash источника | Выбран указанный контракт; provenance и trust фиксируют замену |
| Override с устаревшим hash / несовместимым core-спецправилом | Отказ, не молчаливое применение |
| Два набора одного уровня: одинаковые / разные декларации | Дедупликация с provenance / конфликт независимо от порядка файлов |
| Jar отсутствует, есть source `s/fdef`, затем только shared snapshot | Выбор соответственно третьего и четвёртого уровня без исполнения библиотеки |
| Ни одного контракта | Видимый unknown; нет сообщения «API проверен» |
| EDN с неизвестным tag, повреждённым типом, циклом ссылок | Без исполнения; ограниченная по ресурсам диагностика, не stack overflow |
| Пример 5, неверное собственное тело | Ошибка возврата; export как проверенного API запрещён |
| Inline/spec и внешний тип расходятся | Согласование по F130; тело не пропущено и декларации не затёрты |
| Export → jar → consumer без source producer | Тот же публичный тип, замкнутые ссылки и версии; private vars не экспортированы |
| Изменение версии зависимости/набора/override после первого check | Кеш инвалидирован, новый выбор и диагностики |
| Запуск check без сети, набор уже зафиксирован | Тот же результат, без загрузок и runtime-инструментации |
