# F711 · Внешние декларации для библиотек и core

## Обновление: rank-1 solver

Реализован первый ограниченный срез: явный `t/all`, свежая инстанциация на вызов, проверка generic-тела с rigid-параметрами, простые primitive bounds, generic extern и контекст параметров inline `fn`. Сигнатуры сравниваются с учётом переименования binders. Нерешённые ограничения дают TSP210-01, а не доказательство. Одна фиксированная арность; без higher-rank, row inference, автоматического let-generalization и общего вывода из ожидаемого результата. Подробности и исполняемые тесты: [solver-usage](../docs/solver-usage.md). Общий запуск: 60 тестов / 309 assertions плюс golden/CLI. Прежние утверждения ниже об отсутствии solver описывают историческое состояние.


## Обновление реализации — топ-10

Внешние декларации core/библиотек и собственных функций загружаются по :externs. Проверяются конфликты, неизвестные type refs и собственные тела. Это доверенные контракты, не доказательство библиотечного кода.

`clojure.string/upper-case`, `lower-case` и `capitalize` вызывают `.toString` на аргументе. Их встроенный контракт принимает любое ненулевое значение и возвращает строку.
`clojure.string/blank?` возвращает `true` для `nil` и `false`. Для остальных значений она проверяет `CharSequence`.

Каталог `clojure.core` описывает все четыре арности `range`. При целых начале и шаге тип элементов остаётся `int?`, даже если верхняя граница дробная. Для общего числового начала или шага результат имеет элементы `number?`. Обычный `check` проверяет типы аргументов и отвергает лишний аргумент.

`clojure.core/boolean` принимает одно значение, включая `nil`, и возвращает `boolean?`. Этот тип виден в проверке `s/fdef` и обычных вызовов.

Контракты `clojure.string/starts-with?`, `ends-with?` и `includes?` принимают
любой первый аргумент, кроме `nil`. Clojure вызывает на нём `.toString`.
Второй аргумент имеет тип `string?` для первых двух функций и
`java.lang.CharSequence` для `includes?`.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Мотивация и приоритет

Обязательная возможность первого рабочего выпуска. Описывать типы существующих vars без изменения исходников библиотеки, включая clojure.core.

## Пример целевого поведения

```edn
;; typespec/externs/clojure/string.edn — предлагаемый путь
{clojure.string/upper-case [string? :-> string?]
 clojure.string/includes? [string? string? :-> boolean?]}

;; typespec/externs/clojure/core.edn
{clojure.core/count [string? :-> int?]}
;; Последняя запись иллюстрирует синтаксис, НЕ полный контракт count.
;; Нельзя заменять ей встроенный контракт молча.
```

Иллюстрация, не исполняемый тест и не утверждение о текущей реализации.

## Алгоритм и границы

1. Найти наборы через явную конфигурацию и разрешённые зависимости; без загрузки namespaces и исполнения форм.
2. Безопасно прочитать EDN, проверить schema version, fully qualified var names, типы и арности.
3. Сверить версию библиотеки/целевого Clojure. Для каждой записи сохранить источник и trust status.
4. Согласовать кандидатов с inline/spec/hints и встроенным core-каталогом. Дубли и несовместимости диагностировать; override только явный.
5. Передать контракт обычному checker вызовов. Generic-контракт использовать только после реализации generics; неизвестный оператор не выдавать за поддержку.
6. При наличии собственного проверяемого тела сохранить его проверку. Аннотация чужой библиотеки — доверенный контракт, не доказательство тела.
7. В sig/JSON показать происхождение контракта; изменение декларации инвалидирует зависимые интерфейсы.

## Критерии готовности и тесты

Корректный вызов upper-case принимается, числовой аргумент отклоняется. Отсутствующая декларация видна как непроверенная граница. Конфликт версий и случайное переопределение core не проходят молча. Аннотация собственного var не скрывает ошибку результата. Повторный запуск не исполняет библиотечный код.

## Проверка деклараций не через загрузку библиотеки — planned

По аналогии с каталогом typeshed нужен статический conformance-набор для обязательных внешних деклараций core и библиотек: отдельно проверять структуру/арности и fixtures использования. Например, `(clojure.string/upper-case 42)` должен дать ошибку аргумента со ссылкой на extern; после удаления записи — неизвестную границу, а не прежнее доказательство проверки. Если остаётся встроенный fallback, сначала явно исключить его из этого тестового окружения.

Не включать аналог mypy `stubtest` в обычный `check`: runtime import/introspection выполняет код и всё равно не доказывает тип результата. План теста безопасности: fixture namespace с побочным эффектом при загрузке; чтение его деклараций не должно выполнить эффект. Интеграционное исполнение допускается только отдельным явно запускаемым тестом, не условием статической проверки. Проверка арностей также не доказывает истинность extern.

Основания: [отчёт Python, §1](../docs/research-python.md), [mypy stubtest](https://github.com/python/mypy/blob/master/docs/source/stubtest.rst), [typeshed](https://github.com/python/typeshed/blob/main/README.md). Здесь прочитаны профильные разделы отчёта; первичные ссылки перенесены из него, upstream повторно не аудирован, инструменты и fixtures не запускались.
