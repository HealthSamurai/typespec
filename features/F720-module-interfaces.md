# F720 · Интерфейсы ns и инкрементальная проверка

Разрешение вложенных Var и проверка их инициализации реализованы в
[F721](F721-var-initialization.md).

[F722](F722-project-contract-index.md) добавляет команду `contracts`
для полного прогона и привязки использований к публичным контрактам.
Инвалидация кэша остаётся в проекте ниже.

## Мотивация и границы

В большом Clojure-проекте изменение реализации одной функции не должно заставлять checker повторно обходить всех её потребителей. Но неизменный текст `s/fdef` ещё не означает неизменный контракт: тип может ссылаться на изменившийся `s/def`, зависеть от classpath или настроек проверки. Нужна граница ns, которая учитывает именно зависимости проверки, а не только список `:require`.

Цель — тот же результат, что у чистой полной проверки, с меньшим объёмом работы. Карточка задаёт сбор интерфейса и пересчёт зависимостей; правила согласования самих деклараций остаются у F115/F112, форматы externs — у F710, требования strict — у F730. Здесь нельзя обещать корректность произвольного межмодульного вывода типов только на основании хеширования сигнатур.

## Что есть сейчас

- `main/run-check` заново находит и разбирает все выбранные `.clj`/`.cljc`, затем вызывает `check/check-files`. Это не инкрементальный путь.
- `env/build` собирает общее окружение из текста; `check-files` проверяет формы всех файлов и возвращает `:diagnostics`, `:types`, `:trust`, `:env`, `:sigs`.
- `check/var-type` вычисляет недекларированный результат функции и запоминает его в `*rets*` **внутри одного запуска**. При рекурсии сначала кладёт объявленную часть типа, а не решает уравнения SCC до неподвижной точки.
- CLI `sig` выводит человекочитаемые сигнатуры и источник (`s/fdef`, `t/sig`, hints/body), но сам запускает полную проверку. `sig-lines` выбирает записи `:vars` по ns, без фильтра публичности; это не сериализованный публичный интерфейс и не ключ кэша.
- В strict `check-defn` выдаёт `TSP7010` для публичной функции без достаточной сигнатуры. Само это правило не создаёт модульный checker.
- Персистентного кэша интерфейсов, графа инвалидации, планировщика SCC, параллельной проверки и watch сейчас нет. `implementation: partial` относится к `sig` и проверке границ strict, а не к ускорению повторных запусков.

## Скорость обычного `check`

CLI `check` собирает диагностики и trust-счётчики. Индекс типов выражений
и полный каталог сигнатур строятся при запросе, например для `type-at`
и `sig`. При поиске верхнеуровневого `import` parser сначала смотрит
на голову списка. Идентификаторы диагностики используют тот же SHA-256
и записывают первые 16 байт в hex напрямую.

На Mac arm64 с OpenJDK 27 сравнили исполняемые JAR до и после правки.
Корпус состоит из 588 сгенерированных файлов и 39 396 строк с вызовами
между namespace, Spec, Java interop и трансдьюсерами. Запуск
`java -Xmx1536m -jar typespec.jar check --root <project> --json` начинался
в новой JVM. В контрольной серии версии чередовались, по три запуска каждой.
Медиана сократилась с 5,23 до 4,39 с. JSON с 4704 диагностиками совпал
байт в байт. Замер описывает этот корпус.

Пустой запуск CLI занял 0,62 с. В тёплой JVM после правки полный проход
без сериализации JSON занял 1,24 с по медиане четырёх повторов. Разбор
занял 0,41 с, построение окружения 0,12 с, остальная проверка 0,70 с.
Для частых запусков первой проверяемой гипотезой остаётся живой JVM-процесс.
Для задержки ниже времени полного тёплого прохода нужен пересчёт
изменившихся файлов и зависимых контрактов по правилам ниже.

## Примеры поведения

Ниже обычные иллюстрации, не исполняемые golden-тесты. `current` — поведение существующих механизмов по исходникам; `planned` — требования к будущему инкрементальному пути. Фрагменты с разными `ns` мысленно размещаются в разных файлах.

### 1. Корректный контракт и изменение только тела

```clojure
(ns demo.price (:require [clojure.spec.alpha :as s]))
(s/fdef total :args (s/cat :x number?) :ret number?)
(defn total [x] (+ x 1))
;; Вторая версия тела: (+ x 2), s/fdef тот же.

(ns demo.client (:require [demo.price :as price]))
(defn result {:t/sig '[number? :-> number?]} [x]
  (price/total x))
;; current: вызов и оба варианта тела соответствуют контрактам;
;;          каждый запуск проверяет оба файла.
;; planned: повторно проверить price, сохранить тот же interface hash;
;;          client можно не перепроверять при неизменных прочих входах.
```

Оптимизация разрешена только после проверки нового тела: неизменный экспорт не означает отсутствие ошибки внутри ns.

### 2. Ошибка тела при неизменном интерфейсе

```clojure
(ns demo.price (:require [clojure.spec.alpha :as s]))
(s/fdef total :args (s/cat :x number?) :ret number?)
(defn total [x] "not a number")
;; current: TSP2322 на несовместимом возвращаемом значении.
;; planned: тот же TSP2322 после тёплого запуска, даже если hash
;;          объявленного интерфейса совпал с предыдущим.
;; Нельзя возвращать прежний успешный результат проверки всего проекта.
```

Потребитель может продолжать проверяться против объявленного контракта, но сборка проекта остаётся ошибочной. Кэш результатов тела и кэш интерфейса — разные сущности.

### 3. Изменение интерфейса ломает потребителя

```clojure
(ns demo.price (:require [clojure.spec.alpha :as s]))
;; Было: :args (s/cat :x number?), тело (+ x 1).
(s/fdef total :args (s/cat :x string?) :ret number?)
(defn total [x] (count x))

(ns demo.client (:require [demo.price :as price]))
(defn result {:t/sig '[:-> number?]} [] (price/total 10))
;; current: TSP2345 — число передано вместо строки.
;; planned: изменение интерфейса price инвалидирует client;
;;          тёплый запуск обязан обнаружить тот же TSP2345.
```

Нельзя останавливать инвалидацию только потому, что возвращаемый тип функции остался прежним: значимы аргументы, арности и остальные части контракта.

### 4. Пограничный случай: текст сигнатуры не менялся, spec менялся

```clojure
(ns demo.ids (:require [clojure.spec.alpha :as s]))
(s/def ::id string?) ; раньше было int?

(ns demo.api (:require [clojure.spec.alpha :as s]
                      [demo.ids :as ids]))
(s/fdef echo :args (s/cat :x ::ids/id) :ret ::ids/id)
(defn echo [x] x)

(ns demo.client (:require [demo.api :as api]))
(defn result {:t/sig '[:-> string?]} [] (api/echo "a"))
;; current: в этой версии аргумент и результат согласованы через :demo.ids/id.
;; planned: изменение demo.ids должно дойти до интерфейса demo.api
;;          и его потребителей, хотя строка s/fdef echo не менялась.
```

В типе хранится ссылка на именованный spec; хеш одного символа `:demo.ids/id` недостаточен. Нужен отпечаток его определения и транзитивных зависимостей.

### 5. Пограничный случай: результат выведен из тела

```clojure
(ns demo.value)
(defn value [] 1)
;; Вторая версия: (defn value [] "one")

(ns demo.client (:require [demo.value :as value]))
(defn result {:t/sig '[:-> number?]} [] (value/value))
;; current, без strict: var-type выводит результат из тела;
;;                     вторая версия приводит к TSP2322 в result.
;; current, strict: value без объявления результата получает TSP7010.
;; planned: замена тела value меняет наблюдаемый тип у client;
;;          правило «тело не инвалидирует потребителей» здесь неприменимо.
```

Для первого выпуска допустимо не кешировать такие границы и пересчитывать их консервативно. Это безопаснее обещания общего решения взаимной рекурсии без исследования.

## Предлагаемый алгоритм проверки и пересчёта

Это проект алгоритма для **явно объявленных границ**, не доказанный sound-алгоритм общего вывода Clojure. Базовый критерий — эквивалентность полному запуску текущего checker, включая его ограничения.

1. **Зафиксировать входы одного запуска.** Снимок исходных файлов, пути и reader-режим, конфигурация, версия checker и схемы кэша, classpath/JDK и встроенные сигнатуры. В будущем добавить sidecars, externs, provider outputs и macro-конфигурацию, когда появятся соответствующие загрузчики. Изменение входа без известной модели зависимостей означает полный пересчёт. Нельзя смешивать файлы до и после изменения во время watch.
2. **Разобрать изменённые файлы и обновить каталог деклараций.** Использовать текущие `parse` и `env/build`, а не загружать пользовательские ns. Сначала допустимо пересобирать всё окружение: это отделит оптимизацию проверки тел от более сложной инкрементальной сборки env. Удалённые файлы и vars удалять из каталога, а не оставлять в кэше.
3. **Собрать интерфейс и зависимости.** Представление: квалифицированное имя var → канонический тип функции с арностями, параметрами, rest/kwargs, результатом и признаком declared/inferred; отдельно именованные типы/specs и прочие факты, доступные снаружи. Текущие типы — EDN-подобные карты с `:t`, в частности `:fn`/`:arities` и `:ref`. Позиции, AST и текст для печати не включать в семантический hash. Происхождение и позиции хранить отдельно для объяснений. Отсутствие var в известном ns — тоже наблюдаемый факт, важный для `TSP2305`.
4. **Согласовать источники до хеширования.** Переиспользовать текущие правила env и диагностики конфликтов, не выбирать произвольную «победившую» строку `sig`. Ссылки на specs учитывать вместе с определениями. Нужна отдельная спецификация канонизации: порядок независимых деклараций не должен менять hash, но `unknown`, `any`, platform/nullability и арности нельзя сливать. Пока канонизации нет, сравнение более грубых снимков безопаснее пропуска значимых отличий.
5. **Построить граф наблюдаемых зависимостей.** Ребро A → B означает, что проверка A читает тип/факт из B. `:require` — начальная консервативная оценка, не полный граф: нужны квалифицированные обращения, ссылки на specs, вызовы вывода `var-type`, обращения к Java и будущие macro hooks. Полноту графа ещё надо обосновать; при неполном учёте зависимостей отключать пропуск проверок. Приватные helpers могут менять выведенный публичный результат.
6. **Выбрать работу.** Изменённое тело всегда проверяется. При изменении отпечатка интерфейса обходить обратные рёбра и перепроверять потребителей; после каждого пересчёта сравнивать их интерфейсы и продолжать распространение только при изменении наблюдаемых фактов. При изменении глобальной конфигурации консервативно перепроверять весь проект, включая оформление диагностик и trust.
7. **Обработать циклы.** Свернуть граф в SCC, зависимости компонентов обрабатывать раньше потребителей. В компоненте с полными явными сигнатурами сначала собрать все декларации, затем проверять тела против них; ошибки тел не скрывать. SCC с выведенными рекурсивными результатами пока проверять полным существующим путём, без обещания независимого кеширования. Итерация «до совпадения хеша» без доказательства монотонности, конечности и выбора widening не является решением вывода типов.
8. **Выполнить проверку и сохранить результат.** Начальная реализация может переиспользовать `check-files` для целой выбранной группы, но ей понадобится полный env зависимостей: передача только изменённых файлов сейчас теряет декларации остальных. Извлечь явный API проверки тел с неизменяемым env; отделить `*rets*`, диагностики, `:types`, ignores и trust каждого задания. Только после этого рассматривать параллельный запуск.
9. **Собрать ответ.** Объединить свежие и допустимые кешированные результаты: диагностики в стабильном порядке, актуальные диапазоны для `type-at`, trust без двойного счёта, сигнатуры и статус проекта. Хранить отдельно ключ результата тела (содержимое + все входы) и hash интерфейса. Записывать кэш атомарно; повреждённый/несовместимый кэш считать промахом и пересчитать. Метрики hit/miss — служебная информация, не утверждение об отсутствии ошибок.

### Уточнение инвалидации: доверие и завершённость тоже наблюдаемы

Для будущего загрузчика F711 внешние декларации **core и библиотек обязательны как входы кеша**, не необязательное дополнение ради скорости. Manifest фиксирует координаты/версию библиотеки, версию и hash пакета деклараций, схему; удаление записи — изменение границы, даже если после fallback напечатанный тип остался прежним. Семантический hash типа отделить от отпечатка качества границы: `declared/inferred`, `verified/trusted`, причины неизвестности F210 и завершённость проверки. Их изменение инвалидирует зависимые диагностики/trust, хотя текст сигнатуры может совпадать.

Например, `(vendor/upper-case 42)` при внешнем контракте `[string? :-> string?]` и отсутствии любого встроенного/другого fallback даёт ошибку аргумента; удаление единственного контракта не должно возвращать кешированный «проверенный» вызов или скрывать `missing-extern`. Результат `inconclusive(reason)` по общему бюджету F295 нельзя сохранять/читать как proved. Его допустимо хранить лишь как явно неполный результат с соответствующими входами и бюджетом; изменение бюджета требует пересчёта такого результата.

При дальнейшем переходе от namespace к var-level графу хранить `наблюдаемый факт → зависимые цели`, а не только импорт файла: например, сигнатура `lib/f` → проверка `client/g`. Сначала использовать консервативный namespace-граф выше; старые лишние рёбра дают лишний пересчёт, потерянные рёбра — пропущенную проверку. **Planned-тесты:** удаление/замена extern при неизменном source; trusted → verified при прежнем типе обновляет отчёт; малый бюджет → inconclusive, больший → новая проверка; каждый результат сравнить с холодным запуском.

Основание: [Python, §1/5](../docs/research-python.md), [Luau, §4.4](../docs/research-luau.md); первоисточники — [mypy deps.py](https://github.com/python/mypy/blob/7ba681974e1eae6350c0bc0842a0de832a4e5ec5/mypy/server/deps.py), [mypy update.py](https://github.com/python/mypy/blob/7ba681974e1eae6350c0bc0842a0de832a4e5ec5/mypy/server/update.py), [typeshed](https://github.com/python/typeshed). Здесь прочитаны отчёты; в Python-отчёте изучены выбранные участки механизма triggers/updates, не весь daemon. Не приписывать тот же алгоритм Pyright: отчёт подтверждает у него dirty-file propagation, не эквивалент mypy. Запуск incremental checker и benchmark здесь не проводились.

### Диагностики и объяснимость

Существующие `TSP7010`, `TSP2790`, `TSP2322`, `TSP2345`, `TSP2305` остаются результатами обычной проверки, а не получают отдельные «кешированные» варианты. В трассировке пересчёта полезно показывать причину: «изменился :demo.ids/id → demo.api/echo → demo.client». Новые TSP-коды этой карточкой не вводятся. Ошибка чтения кэша должна приводить к пересчёту, не к ложному зелёному результату.

## Ограничения и открытые вопросы

- Пока не определён полный формат экспортируемых фактов: одних публичных `defn` недостаточно для macros, protocols, multimethods и классов. Каждый такой механизм должен задать свою границу зависимости до включения в оптимизацию.
- Нужно определить политику обращения к private vars и вывода через private helpers; текущий `sig` нельзя использовать как нормативный список публичных экспортов.
- Для рекурсивных именованных типов нельзя бесконечно разворачивать ссылки ради hash. Нужен канонический граф определений и устойчивое сравнение циклов; это отдельная работа, а не готовый механизм прототипа.
- Требуется доказать/проверить независимость результатов от порядка файлов и обращений к `var-type`. Текущий рекурсивный memoization не доказывает её. До этого SCC и пропуск проверок ограничиваются явно объявленными границами.
- Изменение уровня диагностики, suppression или позиции в файле может не менять тип, но меняет пользовательский результат. Поэтому равенства interface hash недостаточно для повторного использования диагностик самого файла.
- Watch, конкурентные записи и отмена устаревшего запуска — отдельная задача. Нельзя публиковать результаты старого снимка как текущие.

## Конкретная матрица тестов

Будущие incremental-тесты должны сравнивать **полный результат тёплого запуска с чистым запуском после той же правки**, а также отдельно проверять список реально перепроверенных ns. Само совпадение вывода не доказывает ускорение.

| Сценарий | Проверка результата | Проверка пересчёта |
|---|---|---|
| Первый запуск примера 1 | Нет ошибок в обеих функциях | Холодный запуск проверяет оба ns |
| Замена `(+ x 1)` на `(+ x 2)` | Результат равен чистому запуску | Тело price проверено, client пропущен |
| Замена тела на строку, пример 2 | Свежий `TSP2322`, проект не успешен | Нельзя использовать прежний результат price |
| Смена аргумента, пример 3 | `TSP2345` в client | price и client пересчитаны |
| Изменение только spec, пример 4 | Новые типы аргумента/результата совпадают с cold | Инвалидация проходит через ссылку на spec |
| Выведенный результат, пример 5 | Вторая версия даёт `TSP2322`; strict даёт `TSP7010` | Консервативный пересчёт, не пропуск по тексту объявления |
| Удаление/переименование экспортируемого var | Нет старой сигнатуры; при известном ns `TSP2305` | Все зависимые вызовы проверены |
| Добавление ранее отсутствовавшего var | Старая ошибка отсутствия исчезает | Инвалидация отрицательной зависимости |
| Изменение private helper под выведенным экспортом | Новый тип виден потребителям | Зависимость через helper не потеряна |
| Цикл с явными сигнатурами | Равенство cold/warm, включая ошибочное тело | SCC проверена как единая группа |
| Цикл с выводом результатов | Нет зависания; ограничения не скрыты | Оптимизация отключена до отдельного решения |
| Перестановка деклараций/комментарий | Типы прежние, диапазоны актуальны | Не возникает лишней инвалидации потребителей |
| Смена strict, strict-nil, levels, classpath | Результат равен новому cold | Глобальная инвалидация в первом выпуске |
| Пустой/повреждённый/старый кэш | Обычный результат полной проверки | Промах, безопасная перезапись |
| Ошибка и `t/ignore`, повторный запуск | Trust и предупреждения не удваиваются | Результаты агрегируются один раз |

Сегодня `test/typespec/demo_test.clj` проверяет вывод `sig` из fdef, hints и тела, strict-диагностики, trust и `type-at`; это не тесты инкрементальности. Примеры выше не включены в автоматический runner карточек. При реализации нужны отдельные multi-file fixtures и операции последовательного изменения файлов, а не только golden-снимок конечного вывода.

## Основание и критерий готовности

Прочитаны локальные первоисточники: [reference.md](../docs/reference.md), [PLAN.md](../PLAN.md), [main.clj](../src/typespec/main.clj), [env.clj](../src/typespec/env.clj), [check.clj](../src/typespec/check.clj), [demo_test.clj](../test/typespec/demo_test.clj). Архитектурная схема PLAN — план, не свидетельство наличия кэша в текущем коде.

Минимально готовый этап: последовательная проверка явно объявленных границ, консервативная инвалидация неподдержанных зависимостей, корректная обработка удаления файлов, совпадение cold/warm по матрице и измеримый пропуск неизменных потребителей. Общий вывод в циклах, параллелизм и watch не входят в это обещание.
