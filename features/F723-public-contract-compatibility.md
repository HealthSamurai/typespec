# F723 · Совместимость публичных контрактов между ревизиями

```sh
clojure -M:check contracts-diff ../typespec-base src --root . --json
```

Оба каталога проверяются по исходникам. Базовую ревизию можно передать
из отдельного Git worktree. Аргументы `[paths]` выбирают одинаковые пути
в обоих каталогах. По умолчанию каждый проект использует свои настройки.

Ревизия проходит проверку, если сохраняет допустимые вызовы и гарантии
результата публичных функций. Например, заменить `int?` на `number?`
в аргументе безопасно. Заменить `s/*` на `s/+` значит запретить прежний
вызов с нулём повторяющихся аргументов.

Для `:ret ::account`, где `::account` ссылается на `::id`, замена
`string?` на `int?` видна по цепочке
`catalog.api/account → :catalog.schema/account → :catalog.schema/id`.
Отчёт содержит объявления, оба типа и известные места вызовов.
Изменение набора тегов именованного `s/or` сопровождается списком
затронутых Vars и прямых вызовов `s/conform` с буквальным именем spec.

| Код | Результат |
|---|---|
| 0 | Доказанных нарушений совместимости нет. Неполная проверка указывается как `inconclusive` |
| 1 | Есть `breaking`, например удалённая арность, потерянное обязательное поле или изменённый тег |
| 2 | Ревизию нельзя прочитать или в её исходниках есть конфликтующие объявления |

Обычные диагностики чекера доступны в `diagnostics.before`
и `diagnostics.after`. Для проверки ошибок исходников в CI используется
`typespec check`.

Первая версия сравнивает публичные позиционные `s/fdef`, `:t/sig`
и сигнатуры из type hints, а также именованные `s/or` из исходников.
Для непрозрачных предикатов, рекурсии, неподдержанных сигнатур и
перегрузок, для которых покрытие нельзя доказать, результат
`inconclusive`. В местах использования перечисляются ссылки,
доступные статическому анализу исходников.
