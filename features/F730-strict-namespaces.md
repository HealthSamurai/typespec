# F730 · Строгий режим по namespace

## Что и зачем

В Clojure удобно постепенно добавлять контракты к уже работающему коду. Но глобальный `--strict` делает миграцию большого проекта неудобной: готовый модуль хочется проверять строго, не требуя немедленно размечать все соседние namespace. Нужна явно видимая граница: какие исходники проверены, какие интерфейсы только приняты на доверие, где проверка неполна.

F730 задаёт **область действия политики**, а не новую систему типов. `:local` требует строгой проверки своего namespace; `:transitive` распространяет обязательства на статические зависимости. Это не доказательство безопасности всей работающей программы: REPL, `eval`, динамический resolve, Java и макросы требуют отдельных моделей.

## Что есть сейчас, а что запланировано

**Current, по исходникам:**

- `main/run-check` объединяет `typespec.edn` с переданными опциями, причём переданные опции имеют приоритет, и передаёт одну карту `opts` всем файлам. CLI поддерживает `--strict`, но не режимы namespace и не `--no-strict`.
- `check/check-defn` выдаёт `TSP7010` публичной функции, если источник её типа — `:hints` и хотя бы у одной арности неизвестен тип результата или фиксированного параметра. Это не полноценная проверка отсутствия `unknown`: явно написанная сигнатура проходит именно этот фильтр даже с `any?`/`t/unknown`, а rest-параметр им не обследуется.
- Строгость также участвует в `TSP2304` для неизвестного qualified key **в уже известном namespace ключей** (`:key-nss`). Формулировка reference «key without a type» шире текущего условия.
- `:strict-nil` — независимая опция. Включение `:strict` не делает platform types nullable автоматически.
- `parse/parse-ns-form` извлекает namespace, aliases, refers и imports, но не политику `:typespec/strict` и не полный граф зависимостей. `check-files` проверяет все переданные файлы с одинаковыми опциями.
- `test/typespec/demo_test.clj` проверяет 11 диагностик `TSP7010` при глобальном strict на demo. Это регрессия текущего режима, не тест F730.

**Planned:** локальная политика, транзитивное замыкание, отчёт о выполнении обязательств и явных границах доверия. YAML `implementation: not-implemented` сохранён: существующий глобальный флаг не реализует эту фичу. Reference — проектная спецификация; её обещание «no implicit unknown» пока нельзя приписывать прототипу.

## Примеры

Фрагменты — обычные исходники для статического чтения Typespec, не команды исполнения. `:typespec/strict` ниже — предлагаемый синтаксис; текущий checker его не применяет. Ожидания current выведены из кода, а не из нового запуска тестов.

### 1. Корректный локальный интерфейс

```clojure
(ns app.labels
  {:typespec/strict :local})

(defn label
  {:t/sig '[string? :-> string?]}
  [text]
  text)

(label "ready")
```

**Current:** явная сигнатура используется; `TSP7010` не возникает даже с глобальным `--strict`. Метаданные namespace ничего не включают. **Planned:** локальный режим проверяет публичную сигнатуру и тело без необходимости включать strict всему проекту. Отсутствие ошибок здесь не говорит о других namespace.

### 2. Публичная функция без контракта

```clojure
(ns app.labels
  {:typespec/strict :local})

(defn label [text] text)
(defn- identity-helper [x] x)
```

**Current:** без глобального strict нет `TSP7010`; с ним `label` получает `TSP7010`, private helper исключён из этого требования. **Planned:** достаточно `:local`; ошибка у имени `label`, с предложением добавить `s/fdef`, `:t/sig` либо полные hints. Private helper проверяется внутри области, но явная экспортная сигнатура ему не обязательна. Неизвестные внутренние значения регулируются отдельной политикой, а не запретом всех private-функций без аннотаций.

### 3. Пограничный случай: явно небезопасная сигнатура

```clojure
(ns app.forward
  {:typespec/strict :local})

(defn forward
  {:t/sig '[any? :-> any?]}
  [x]
  x)
```

**Current:** `TSP7010` отсутствует: источник типа `:sig`. Это не означает, что вызовы безопасны. Счётчик `:trust :any` сейчас увеличивается для директивы `t/any`, а не для каждого `any?` в сигнатуре. **Planned:** наличие сигнатуры и допустимость `any?` — две разные проверки; такой экспорт должен оставаться видимой границей доверия, а не получать отметку «полностью проверен». Будет ли нарушение политики ошибкой или разрешённым исключением, надо определить совместно с F210/F840; синтаксис разрешения здесь не изобретается.

### 4. Вызов типизированного var из нестрогой зависимости

```clojure
;; app/legacy.clj — отдельный файл
(ns app.legacy)
(defn normalize
  {:t/sig '[string? :-> string?]}
  [s] s)
(defn unrelated [x] x)

;; app/api.clj — отдельный файл
(ns app.api
  {:typespec/strict :transitive}
  (:require [app.legacy :as legacy]))
(defn normalize
  {:t/sig '[string? :-> string?]}
  [s] (legacy/normalize s))
```

**Current:** если оба файла входят в paths, контракт вызова известен. Без глобального strict метаданные не заставят проверять `unrelated` на наличие сигнатуры; с глобальным strict она получит `TSP7010`. **Planned:** для `:local` достаточно доступного контракта вызываемого var, но источник остаётся помеченным нестрогим. Для `:transitive` предлагается проверять весь достижимый исходный namespace, в том числе `unrelated`: ошибка в зависимости мешает подтверждению корня. Зависимость не обязана сама писать `:local`; обязательство приходит от корня. Это проектное решение нужно утвердить до реализации, а не скрывать в обходе графа.

### 5. Alias для ключей — не вызов чужого кода

```clojure
(ns app.keys
  {:typespec/strict :transitive}
  (:require [app.domain :as-alias domain]))

(defn key-name
  {:t/sig '[:-> keyword?]}
  [] ::domain/id)
```

**Current:** parser умеет `:as-alias` и разрешение keyword; транзитивного режима нет. **Planned:** такое ребро используется для разрешения имени/контракта, но само по себе не доказывает и не требует загрузки тела `app.domain`. Нельзя строить граф исполнения простым обходом `:aliases`: он смешивает `:as` и `:as-alias`. Если для проверки значения нужен spec ключа, его доступность проверяется отдельно; символическое имя keyword не доказывает тип его возможного значения.

## Предлагаемый алгоритм: согласование политики и результатов checker

Это алгоритм оркестрации существующих проверок. Он не заменяет алгоритмы подтипов, вывода, narrowing, проверки макросов или доверенных контрактов и не претендует на доказанную soundness.

1. **Вход.** Получить AST файлов с позициями, root/paths, проектные и явно переданные CLI-опции; декларации namespace; окружение типов из `env/build`. Не загружать Clojure-код. Отдельно учитывать, какие исходники доступны, а какие зависимости представлены только контрактом. Отсутствующий файл не считать успешно проверенным.
2. **Нормализация политики.** Проверить значения `:typespec/strict`, собрать одну политику на namespace. Предлагаемый начальный набор — отсутствие настройки, `:local`, `:transitive`, без локального `:off`. Проектный/CLI strict задаёт нижнюю границу `:local` для выбранных исходников; локальный `:transitive` её усиливает. Отсутствие локальной настройки наследует базу. Сначала объединить проектные и явные CLI-опции как сейчас, затем усилить область локальной настройкой: не путать приоритет опций с запретом усиления. Конфликт деклараций одного namespace — ошибка, а не «последний файл победил». Новые CLI-режимы и возможность ослабить политику требуют отдельного решения.
3. **Представление фактов.** Ввести таблицу namespace → `{declared-mode, effective-obligations, origin, source-files, outcome}`. Для каждого обязательства хранить корень и путь зависимости. Типы остаются текущими картами (`:t :fn`, `:arities`, `:params`, `:ret`, `:rest` и др.), у var уже есть `:source`, `:complete?`, `:private?`, позиция. Эти поля — сведения о декларации, не сертификат: `:complete?` сейчас не гарантирует отсутствия вложенного `unknown`. Добавить отдельные факты о непроверенном теле, доверенном контракте и явном opt-out; их определение согласовать с профильными карточками.
4. **Граф.** Из AST собрать рёбра с типом и позицией: обычный require, alias-only, статически разрешённое обращение к var, внешний контракт, неизвестная динамическая зависимость. Одной карты aliases недостаточно: она теряет require без alias и вид ребра. Для первой версии выбрать консервативную политику: обычные require включают весь namespace, `:as-alias` — только разрешение имён. Fully-qualified статические обращения тоже учитывать. Для `requiring-resolve`/`eval` фиксировать неполноту, не притворяться, что граф замкнут.
5. **Распространение обязательств.** У `:local` проверить только свой исходный namespace; соседний контракт не повышает статус реализации соседа. У `:transitive` пройти выбранные статические рёбра до замыкания. Вычислить SCC, объединить обязательства внутри компоненты и обработать DAG компонент от зависимостей к корням. Алгоритм завершается на конечном наборе входных namespace, потому что обязательства только добавляются. SCC означает группировку проверки, а не поддержку циклической загрузки Clojure. Она также не решает рекурсивный вывод типов: декларации собираются до проверки тел; недостаточные контракты нельзя «довывести» обещанием fixed point без отдельного исследования.
6. **Проверка тел и интерфейсов.** Передавать в контекст каждого файла effective opts вместо единой карты. Переиспользовать `check-defn`, проверки вызовов и ключей; `:strict-nil` не менять неявно. Требование публичной сигнатуры должно охватывать все поддержанные арности и rest, но правила полноты/unknown/any брать из F115/F210, а не придумывать второй набор здесь. Контракт extern считать доверенным интерфейсом, не успешной проверкой чужого тела (F710/F720). Отсутствие реализации, неподдержанный macro и динамическую границу хранить как отдельные исходы.
7. **Агрегация.** Для namespace вернуть результат тела, выполнение экспортных обязательств, список доверенных/неполных границ и состояние зависимостей. Для транзитивного корня успех означает выполнение всех выбранных обязательств; отсутствие диагностик после suppression не является достаточным условием. Предлагаемые исходы отчёта: `checked`, `checked-with-trust`, `incomplete`, `failed`; это новый формат, не текущий API. Сохранять исходные результаты до применения `:levels`/`t/ignore`, иначе выключение ошибки ошибочно создаст сертификат строгости.
8. **Диагностики.** Существующие ошибки типов и `TSP7010` сохраняют свои коды и позиции. Новые коды только проектные: **proposed TSP730-01** — неверная/конфликтующая политика (позиция декларации); **proposed TSP730-02** — транзитивное обязательство не выполнено (позиция require/обращения, корень и путь к причине); **proposed TSP730-03** — замыкание невозможно подтвердить из-за недоступного исходника/динамической границы. Не копировать все ошибки зависимости на каждое ребро: оставить первичную ошибку и одну сводку с путём. Текстовый и JSON-вывод строить из общей структуры, с теми же кодами и ranges.

## Интеграция и границы ответственности

- `parse.clj`: сохранить декларации политики и виды зависимостей вместе с позициями; parser остаётся статическим.
- `main.clj`: сохранить различие «опция не задана»/«задана», определить набор исходников для транзитивного обхода. Сейчас paths просто перечисляют проверяемые файлы; автоматического поиска исходников зависимостей нет.
- `env.clj`: переиспользовать общий сбор деклараций; не считать `:complete?` готовым сертификатом F730.
- `check.clj`: локализовать opts в `check-files`, собирать исходы до фильтрации диагностик. Существующий порядок прохода по файлам не объявлять топологической или SCC-проверкой.
- F710/F720 определяют доступность и доверие интерфейсам, F210 — операции с unknown/any, F840 — бюджет доверия. F730 только применяет согласованные правила к области и агрегирует результат. Новых правил типов эта карточка не вводит.

## Ограничения и нерешённые вопросы

- Нужен явный выбор: транзитивность по всему статическому require или по реально используемым var. Здесь предложен первый, консервативный вариант; он может требовать контракт для неиспользуемой функции (пример 4).
- Не определены допустимые исключения для `any?`, Java, externs, hooks и suppressions. Нельзя обещать «strict = sound», пока эти границы не описаны и не проверяются отдельно.
- Макросы могут создавать зависимости и публичные var. Без корректной модели расширения граф и список экспортов неполны; группировка SCC это не исправляет.
- `def` с функциональным значением, `defmulti`, generated vars и динамическая переустановка var требуют согласования понятия «публичная функция». Текущий `check-defn` не универсальный аудит всех экспортов.
- Несколько файлов одного namespace, `.cljc` и reader conditionals требуют платформенно определённого набора деклараций. Конфликт нельзя разрешать случайным порядком файлов.
- Поведение при зависимости вне paths: нужны явный resolver/manifest и воспроизводимый classpath; до этого статус `incomplete`, а не молчаливый успех.
- Ошибки, превращённые в warning/off, и `t/ignore` должны менять представление диагностики, но не стирать факт невыполненного обязательства. Формат такого отчёта ещё предстоит согласовать.

## Конкретная матрица тестов

Все новые строки — план тестов; существующий тест глобального strict не подтверждает их реализацию. Для каждого отрицательного случая проверять код, namespace, исходную позицию, режим и путь причины; для положительного — отсутствие именно соответствующей ошибки, а не просто exit code.

| Сценарий | Ожидание |
|---|---|
| Пример 1, без глобального strict | Planned: локальный интерфейс проверен, соседние ns не усилены |
| Пример 2, metadata-only | Current: нет TSP7010; planned: TSP7010 только у public label |
| Пример 2, глобальный strict | Current и planned: TSP7010 у label, не у defn- |
| Полные hints без t/sig; отдельно пропущенный return hint | Первый удовлетворяет требованию сигнатуры; второй проверяет нехватку контракта |
| Несколько арностей и неизвестный rest | Отдельный контроль каждого экспортного входа; не полагаться на текущий shallow-фильтр |
| Пример 3, явный any?; отдельно t/unknown внутри коллекции | Не смешивать наличие декларации с полнотой; граница доверия/неполнота видна по согласованной политике |
| Пример 4: local против transitive | Local не требует сигнатуру unrelated; transitive не подтверждает корень при её отсутствии |
| Пример 5: as-alias против обычного require | Alias-only не включает проверку тела; require включает |
| Require без alias и fully-qualified вызов | Оба не теряются при построении графа |
| A → B → C, ошибка только в C | Первичная ошибка в C, сводка корню с путём A/B/C |
| Цикл A ↔ B в статических входных данных | Завершение обхода и единые обязательства SCC; не проверка работоспособности загрузки цикла |
| Зависимость вне paths / extern-only / dynamic resolve | Различимые исходы unavailable, trusted, incomplete; ни один не маскируется под проверенное тело |
| Нет настройки / проектный strict / local / transitive | Проверка наследования и усиления; явные CLI-опции сохраняют приоритет над проектными |
| Неизвестное значение strict; конфликт двух деклараций ns | proposed TSP730-01 с позицией, без last-write-wins |
| Опечатка qualified key в известном key-ns и совсем новый key-ns | Сохранить текущий TSP2304 там, где он применим; не обещать тотальный запрет всех undeclared keys |
| strict отдельно от strict-nil | Область строгости не меняет nullability platform types |
| Ошибка зависимости скрыта через levels/off или t/ignore | Представление меняется, подтверждённая строгость не появляется |
| Одинаковый запуск text/JSON, иной порядок файлов | Совпадают коды/ranges и итог областей; детерминированные пути причин |

Критерий готовности: эти сценарии покрыты узкими регрессиями, metadata-only реально меняет проверку, отчёт отличает проверенное тело от доверенного интерфейса, а ограничения отражены в CLI/JSON. До этого примеры planned не являются рабочим демо.
