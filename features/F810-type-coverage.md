# F810 · Покрытие типами

## Что и зачем

В Clojure типизированные функции соседствуют с динамическими map, библиотеками без сигнатур и макросами. Отсутствие ошибок может означать как успешную проверку, так и то, что checker не дошёл до тела или получил `t/unknown`. F810 должна показывать эту разницу и помогать выбирать следующий участок для типизации.

Покрытие — **полнота выполненной проверки в рамках поддерживаемых правил**, а не доказательство безопасности программы. Тип результата, успешность проверки и зависимость от доверенных предположений — разные свойства. Например, `str` возвращает `string?`, даже когда его аргумент неизвестен; ошибочное сложение может получить числовой тип восстановления после диагностики.

Считаем исходные выражения, не строки и не количество вызовов `infer`. Оболочки деклараций, имена привязок, объявления типов и комментарии не входят в знаменатель; исполняемые инициализаторы и тела функций входят. Правила подсчёта должны иметь версию. Бюджеты доверия и сравнение PR относятся к F840; здесь определяются исходные факты, на которых такие политики могут работать.

## Что есть сейчас, а что проектируется

**Current, подтверждено чтением исходников:**

- `check/record!` добавляет в `:types` записи `{:file :pos :type :ns}`; узлы с `:synthetic` пропускаются. Нет идентификатора исходного выражения, причины unknown или результата проверки обязательств.
- `check-defn` записывает также типы параметров; сама форма `defn` возвращает unknown. Поэтому даже подсчёт всех записей `:types` не является подсчётом выражений.
- `quietly` и вывод возвращаемых типов в `var-type` отключают запись типов. Число проходов и число записей не определяют знаменатель.
- `infer-list` пропускает тело известного пользовательского макроса без правила, выдавая `TSP7031`. Ветка стандартного макроса без правила тоже возвращает unknown, но без этой диагностики.
- `infer` применяет `t/cast` и `t/any` после вывода исходного типа; `:trust` считает `:cast`, `:any`, `:ignore`. Эти счётчики не содержат происхождения результата и не являются метрикой покрытия.
- `main` реализует `check`, `sig`, `type-at`. JSON команды `check` содержит diagnostics и trust, не coverage. Упоминание `typespec coverage --trust` в reference — дизайн, не действующая команда.

**Planned:** отдельный реестр исходных выражений, факты посещения/пропуска/проверки, рекурсивная классификация типов, происхождение доверия и одинаковый отчёт CLI/JSON. `implementation: not-implemented` остаётся корректным.

## Примеры

Все пять блоков — обычные иллюстрации, не автоматические snapshot-тесты карточки. Они дополнительно проверены целевым smoke test: содержимое каждого блока прочитано из этой карточки и передано в `parse/parse-string`, затем `check/check-files` с опциями `{}`. Запуск выполнен через `clojure -M -e` с `JAVA_HOME=/opt/homebrew/opt/openjdk@25` и `PATH="$JAVA_HOME/bin:$PATH"`; первоначальная ошибка поиска Java относилась к окружению запуска, а не к отсутствию установленной JVM. Полный suite не запускался. Проверенные результаты:

| Пример | Диагностики current | Существенный результат |
|---|---|---|
| 1 | Нет | Сложение и вызов `twice` имеют `int?` |
| 2 | `TSP2322`, `TSP2345` | Сложение получает `number?` после ошибки аргумента; этот результат также не соответствует объявленному `int?` |
| 3 | Нет | `[x]`: `(s/coll-of t/unknown :kind vector?)`; `str`: `string?`, lookup остаётся unknown |
| 4 | Нет | Вектор: `(s/coll-of any? :kind vector?)`; trust: cast=1, any=1, ignore=0 |
| 5 | `TSP7031` | Вызов макроса unknown; вложенное сложение отсутствует в записях типов |

Это проверка существующего inference, не несуществующей команды coverage. Численные проценты ниже намеренно не обещаются.

### 1. Корректный код с явным контрактом

```clojure
(ns coverage.good)

(defn twice
  {:t/sig '[int? :-> int?]}
  [n]
  (+ n n))

(twice 3)
```

**Current:** сигнатура задаёт тип параметра и результата; `+` проверяется по встроенной таблице сигнатур. Отдельного отчёта покрытия нет.

**Planned:** оба чтения `n`, сложение, литерал `3` и вызов `twice` имеют определённые типы и выполненные проверки. Имя функции, вектор параметров и данные `:t/sig` не увеличивают знаменатель. Зависимость от встроенной модели `+` обозначается отдельно от пользовательского cast. Наличие такого доверенного основания не должно объявлять всё приложение непроверенным: состав базовой модели явно указан в отчёте.

### 2. Тип результата не отменяет найденную ошибку

```clojure
(ns coverage.bad)

(defn broken
  {:t/sig '[int? :-> int?]}
  [n]
  (+ n "x"))
```

**Current:** `call-fn`/проверка аргументов обнаруживают несовместимый аргумент. Выведенный после ошибки тип нельзя принимать за сертификат успешной проверки.

**Planned:** выражение сложения отмечено `failed`, с привязкой к исходной диагностике; литерал `"x"` сам по себе имеет известный тип. В отчёте отдельно видны обработанные выражения и успешно проверенные. Исправление строки на число убирает ошибку, но не меняет знаменатель. Специальная coverage-ошибка поверх уже найденной ошибки типов не нужна.

### 3. Вложенный unknown и известный внешний результат

```clojure
(ns coverage.partial)

(defn wrap [x]
  [x])

(defn label [row]
  (str (:name row)))
```

**Current:** `wrap` получает коллекцию с неизвестным элементом, а не полностью известную коллекцию. У `str` в `core_types.clj` результат `string?`; это ничего не доказывает о типе `row`. В текущем `types/sub?` unknown допускается в отношениях совместимости; обещание reference «narrow first» нельзя автоматически приписывать прототипу.

**Planned:** у чтения `x` есть дыра в корне типа, у `[x]` — в пути типа `:of`. `row` и чтение `:name` остаются видимыми дырами даже при известном типе результата `str`. Для `str` различаются «тип результата известен» и «весь подграф вычисления проверен»: неизвестность аргумента не делает результат unknown, но не исчезает из покрытия. Нужность narrowing-диагностики определяется F210/F240, а не F810.

### 4. Any и cast не превращаются в доказанные типы

```clojure
(ns coverage.trusted)

(defn escape [x]
  [#_(t/any) x
   #_(t/cast string?) x])
```

**Current:** parser присоединяет директивы к следующим формам; checker возвращает для первого чтения `any?`, для второго — указанный тип. Счётчики trust отражают применение директив. После объединения элементов вектор может потерять детализацию: `types/union` поглощает другие варианты при наличии any.

**Planned:** оба места сохраняют собственные диапазоны и причины — `explicit-any` и `cast`; cast не повышает «успешно проверено без обхода проверки». Тип вектора и его provenance хранятся независимо, чтобы нормализация union не стирала источники доверия. Any в параметре встроенной функции, принимающей любые значения, не приравнивается к пользовательскому `t/any`.

### 5. Пропущенное тело макроса не должно исчезать

```clojure
(ns coverage.macros)

(defmacro hidden [& body]
  (cons 'do body))

(hidden
  (+ 1 "x"))
```

**Current:** вызов известного пользовательского макроса без правила получает `TSP7031` и unknown; тело вызова не проверяется. Ошибка сложения внутри не обязана быть обнаружена.

**Planned:** отчёт показывает диапазон вызова как `skipped-macro` и сохраняет диапазон его содержимого как непросмотренную область. Для неизвестного макроса нельзя честно утверждать, что `(+ 1 "x")` — исполняемое выражение: макрос мог его удалить или трактовать как данные. Поэтому такой участок не исчезает, но и не получает выдуманный точный счётчик выражений. Пока нет контракта макроса, отчёт имеет `complete: false`, число непросмотренных областей и не выдаёт процент по всему файлу как точный. После появления правила, подтверждающего семантику `do`, сложение становится отдельным выражением и проверяется.

## Алгоритм учёта и проверки — проект

Это алгоритм сбора измерений, не новый алгоритм вывода типов. Он требует доработки parser/checker; одного прохода по `:types` недостаточно. Там, где семантика исходника неизвестна, результат явно неполный.

1. **Зафиксировать вход.** Версия метрики, набор файлов и их содержимое/хеши, выбранная ветка reader conditional, настройки checker (`strict`, `strict-nil`), окружение типов и поддержанные правила макросов. Сравнимы только отчёты с совместимыми настройками; файл, который не удалось разобрать, отмечается как пропущенный, а не как файл с нулём дыр.
2. **Построить реестр исходных мест до inference.** Из позиционного дерева получить `source-id` (файл + диапазон + роль + путь узла) и роль: выражение, binding, декларативные данные, quoted data, непросмотренная область. Реестр не зависит от того, посетит ли узел `infer`. В известных специальных формах применять таблицу ролей: у `let` учитывать инициализаторы и тело, у `defn` — тело, у `def` — инициализатор. Голова обычного вызова относится к проверке вызова, а не добавляет отдельную единицу только потому, что написана символом. Вложенные вызовы и вычисляемые значения коллекций считаются отдельно. `quote` — одно выражение, его содержимое не обходится как код.
3. **Не выдумывать роли неизвестного синтаксиса.** Для неизвестного макроса сохранить сам вызов и непросмотренные диапазоны аргументов. Без контракта не классифицировать все списки внутри как код. Для неподдержанного reader-синтаксиса сохранить диапазон ещё на уровне исходного дерева: текущий parser часть узлов отбрасывает. Таким образом неизвестные области остаются в отчёте, а точность знаменателя явно ограничена. Макросы проекта ради метрики не исполнять.
4. **Собирать факты checker по source-id.** Для каждого места фиксировать посещение, правило проверки, исходный и итоговый тип, обязательства проверки и их исходы (`passed`, `failed`, `not-checked`), причину пропуска, ссылки на диагностики и происхождение доверия. Типы остаются существующими map с тегом `:t`; coverage-факты хранятся рядом, не кодируются фиктивными типами. Обязательства связывать с выражением в момент проверки, а не только по пересечению диапазонов диагностики. Записывать факты до фильтрации `t/ignore`/severity: скрытая ошибка не становится успешной проверкой.
5. **Привязать преобразования к исходнику.** Синтетические узлы получают ссылки на исходные места; один source-id даёт одну единицу знаменателя. Повторный вывод типа и анализ нескольких ветвей объединяют факты по идентификатору и контексту: для успешного исхода нужны все обязательства, для ошибки достаточно одного failed. Пропущенный путь нельзя заменить последним успешным посещением. Флаг `:synthetic` сам по себе не обеспечивает эту связь; нынешних диапазонов недостаточно для всех преобразований.
6. **Рекурсивно найти неполноту типа.** Посетить элементы коллекций, поля `:req`/`:opt` map и хвосты, элементы tuple, варианты union/merge, параметры/результаты/остаточные аргументы функций; `:ref` разрешать через окружение. Для каждого пути сохранить unknown, any и platform-признак. Голые `map?`, `vector?`, `fn?` не выдавать за знание содержимого: отметить `unspecified-structure`, когда детализация отсутствует. Для неизвестного конструктора или неразрешимой ссылки вернуть `unclassified`, не «полный тип». Использовать множество посещённых ссылок; цикл сам по себе не unknown, но до определения правил рекурсивных типов его полнота не считается доказанной. `never` у элемента пустой коллекции не является дырой; неизвестные типы остальных элементов нельзя скрывать за ним.
7. **Хранить несколько независимых измерений.** `visit` отвечает, дошёл ли checker; `type-quality` — есть ли вложенная неполнота; `obligations` — выполнены ли проверки; `trust` — на какие допущения они опираются. Пример 2 может иметь известный тип и failed; пример 3 — известный тип внешнего вызова и дыры в дочерних выражениях. Provenance переносится отдельно от `union`/widen, иначе any/unknown стирает причины. Перенос доверия через межфункциональные вызовы требует отдельной модели зависимостей; пока её нет, обозначать отчёт как локальный, не заявлять полноту транзитивного анализа.
8. **Агрегировать без двойного счёта.** `N` — число уникальных исходных выражений с установленной ролью. Публиковать отдельно количество посещённых, failed, неполных типов, пользовательских обходов проверки и непросмотренных областей. Эти измерения пересекаются и не складываются в 100%. Строгий числитель `P` включает только посещённые места с полным типом, успешно выполненными обязательствами и без непроверенных допущений за пределами явно указанной базовой модели. `P/N` — доля среди классифицированных выражений, а не всего исходника, если остались неизвестные области. При `N=0` процент отсутствует, не равен 100%. Для CI обязательно отдавать абсолютное число дыр и `complete`, чтобы добавление литералов не маскировало пропуски.
9. **Отдать один отчёт двум интерфейсам.** Проектируемая команда `coverage` и JSON используют один агрегатор. Запись места содержит source-id, файл, полуоткрытый диапазон, роли/причины, пути неполноты типа и связанные диагностики. Отчёт содержит версию метрики, настройки, границы базовой модели, счётчики и completeness. CLI группирует эти же записи по причинам, не пересчитывает процент самостоятельно. Новые TSP-коды для самого учёта не требуются; ошибка порога CI — отдельная политика, не ошибка типов.

## Интеграция с текущим checker

- **`parse.clj`:** сохранить связь с исходным деревом до потери неподдержанных reader forms; отделить директивы `#_(t/...)` от исполняемых выражений. Нынешний выбор `:clj`/`:default` задокументировать как границу покрытия, не обещать одновременно CLJS.
- **`check.clj`:** дополнить точки `infer`, `record!`, `infer-list`, проверки аргументов и возвращаемых значений событиями покрытия. Явно регистрировать обе ветки пропуска макросов. Не менять смысл существующих ошибок ради улучшения процента.
- **`types.clj` и `env.clj`:** обходить фактические конструкторы и ссылки на specs; не пытаться извлекать вложенные дыры из строк `t/show`. Происхождение объявлений хранить отдельно от нормализованного типа. Extern-происхождение добавляется вместе с F710, а не объявляется доступным уже сейчас.
- **`main.clj`:** добавить новый режим только после появления единого результата coverage; не использовать `:types` как готовый публичный coverage JSON. `type-at` продолжает показывать тип, но сам по себе не отвечает на вопрос, доказан ли он.
- **Тесты:** существующий `demo_test.clj` проверяет diagnostics/snapshot и маркеры ERR/WARN; блоки `clojure example` имеют специальный смысл. Эта карточка не добавляет такой блок, пока coverage API не реализован. Нужны отдельные assertions по coverage-фактам и позициям, а не только снимок текста.

## Ограничения и нерешённые вопросы

- **Точный знаменатель для неизвестного макроса невозможен без семантики макроса.** Нужны контракты F610 либо честное `complete: false`. Простое рекурсивное перечисление всех list-узлов — не sound способ считать выражения Clojure.
- **Выведенный тип не является журналом доказательства.** Нынешний checker допускает unknown при совместимости и использует приближённые модели core/JVM. Метрика не исправляет эти ограничения и не может называться доказанным отсутствием runtime-ошибок.
- Нужно согласовать базу доверия: встроенные правила, библиотечные сигнатуры, Java platform-типы и пользовательские casts различаются. Полностью типизированный вызов доверенного extern не равнозначен проверке реализации extern.
- Межпроцедурный перенос доверия, рекурсия, слияние path-sensitive фактов и стабильная привязка macro expansion требуют исследований и тестов. Описанная структура отчёта — не готовое доказательство корректности этих механизмов.
- Неактивные ветви `.cljc`, неразобранные файлы, code generation и код, конструируемый через `eval`, должны иметь явную область исключения. Нельзя молча считать их покрытыми.
- Изменённый код требует сопоставления выражений между версиями, а не сравнения строковых диапазонов. Формат baseline, переименования и политика отказа при несовместимой версии метрики остаются задачами интеграции с F840.

## Конкретная матрица тестов

Все coverage-проверки ниже — **planned**. Наличие диагностического теста не означает наличие покрытия.

| Сценарий | Что проверять |
|---|---|
| Пример 1 | Тело и вызов посещены; нет вложенных unknown; сигнатура и bindings не в `N`; базовая модель указана |
| Пример 2 → исправление `"x"` на `1` | До исправления failed и ссылка на диагностику; после — passed; `N` неизменен |
| Пример 3: `[x]` | Unknown у чтения и в `:of` вектора; вектор не полностью типизирован |
| Пример 3: `str` | Результат string не стирает дыры `row`/lookup; неизвестность аргумента не подменяет тип результата |
| Пример 4 | Два исходных места, две разные причины; нормализация union сохраняет provenance |
| Пример 5 | `TSP7031` остаётся; непросмотренное содержимое не исчезает; `complete=false`; точного общего процента нет |
| Стандартный макрос без правила | Пропуск учитывается и без `TSP7031`; fixture выбирается по текущей таблице special/core |
| `[]` и `(quote (+ 1 "x"))` | Пустой элемент never не дыра; quoted список не проверяется как сложение |
| `let`, комментарии, `s/fdef`, метаданные | Добавление комментария/декларации не увеличивает `N`; init и тело остаются выражениями |
| Вложенные map/tuple/union/function/ref | Обход каждого поддержанного конструктора находит неполноту на правильном пути |
| Голые `map?`/`fn?`, неизвестный конструктор | Нет ложного статуса «структура полностью известна»; unclassified виден |
| Циклическая или отсутствующая spec-ссылка | Нет зависания; непроверенная полнота ссылки не превращается в успех |
| `->`, повторный inference, несколько ветвей | Один source-id считается один раз; пропуск/failed не затёрт последним посещением |
| `t/ignore` и severity off поверх ошибки | Диагностика может скрыться, факт failed остаётся; успешное покрытие не растёт |
| `^String` и `strict-nil` | Platform-факт отличим от nil-проверки; настройки входят в идентичность отчёта |
| Reader conditional / неподдержанный reader | Выбранная платформа записана; непроанализированная область видна |
| Пустой файл, ошибка парсинга | Для пустого файла `N=0`, процент отсутствует; ошибка разбора даёт incomplete, не успех |
| CLI против JSON | Одинаковые множества source-id, причины, диапазоны и агрегаты; порядок детерминирован |
| Изменение baseline | Увеличение абсолютного числа дыр не маскируется добавленными константами; несовместимые версии явно отклоняются политикой |

Критерий готовности: реализованы сбор фактов и отчёт; матрица проверяет отсутствие как пропущенных дыр, так и ложных дыр; опубликовано реально выполненное демо с версией метрики. До этого разовый подсчёт `:types` нельзя публиковать как доказанное покрытие.
