# F820 · Линты подозрительной обработки nil

## Что и зачем

В Clojure `nil` — обычное значение: отсутствие результата, отсутствующий ключ, конец последовательности. `(str nil)` возвращает пустую строку, а `if` объединяет `nil` и `false` в одну ветку. Это корректные операции, но иногда они незаметно стирают важное различие: «значение отсутствует» против «значение задано и пустое», «неизвестно» против «нет».

F820 — предупреждение для ревью, **не ошибка совместимости типов и не доказательство ошибки программы**. Оно не запрещает nil-punning и не предлагает автоматически подставить `""`, `false` или исключение. Намерение автора нельзя восстановить из одного типа.

## Current: что действительно есть

`implementation: not-implemented` остаётся верным: специализированных линтов F820 нет.

- В `src/typespec/core_types.clj` у `clojure.core/str` сигнатура `[& any? :-> string?]`: nil допустим, результат — строка.
- `types.clj` представляет nil как `{:t :nil}`, объединение как `:union`, неизвестность как `:unknown`; `members` раскрывает ссылки, `nilable?` ищет явную nil-альтернативу, `remove-nil` удаляет её.
- `check.clj`: `problems` выдаёт существующий `TSP2531`, когда nilable-значение передают туда, где nil недопустим. Это не случай `str`.
- `narrow` учитывает `some?`, `nil?` и ветвления над локальными переменными, но не реализует полноценное разделение `false` и `nil`: в истинной ветке локального теста сейчас удаляется nil, а не все ложные значения.
- Есть `report!`, уровни `:levels` и общий конвейер диагностик в `check-files`. В `main.clj` есть текстовый и JSON-вывод. Инфраструктура предупреждений не означает наличие этих правил.

`docs/reference.md` описывает дизайн, включая возможности сверх прототипа; здесь реализация сверена с исходниками. Примеры ниже — обычные иллюстрации, не golden-тесты и не запись запуска checker.

## Примеры: current и planned

### 1. Корректно: отсутствие обрабатывается явно

```clojure
(ns lint.good (:require [clojure.spec.alpha :as s]))
(s/fdef label :args (s/cat :x (s/nilable string?)) :ret string?)
(defn label [x]
  (if (some? x)
    (str x)
    "<нет значения>"))
;; label nil => "<нет значения>"; label "" => "".
;; Current: some? сужает x в истинной ветке; F820 отсутствует.
;; Planned: нет предупреждения — в точке str тип x уже без nil.
```

### 2. Подозрительно: строка скрывает отсутствие

```clojure
(ns lint.loss (:require [clojure.spec.alpha :as s]))
(s/fdef label :args (s/cat :x (s/nilable string?)) :ret string?)
(defn label [x] (str x))
;; label nil и label "" оба возвращают "".
;; Current: str допускает nil; это не TSP2531, F820 нет.
;; Planned: warning proposed TSP820-01 на аргументе x.
;; Если различие важно по контракту приложения, это ошибка смысла,
;; но не типов. Если такое преобразование намеренно, код допустим.
```

### 3. Погранично: неизвестность и platform — не доказательство

```clojure
(ns lint.boundary)
(defn unknown-label [x] (str x))
(defn hinted-label [^String x] (str x))
(defn always-empty [] (str nil))
;; Current: специализированных предупреждений нет во всех трёх случаях.
;; Planned MVP: unknown-label — молчать (тип параметра неизвестен).
;; hinted-label — молчать: platform не равен доказанному nilable.
;; always-empty — warning proposed TSP820-01: аргумент точно nil.
;; Для MVP platform исключается и при --strict-nil: это политика линта,
;; а не отмена strict-nil ошибок в обычной проверке типов.
```

### 4. Отдельное исследуемое правило: boolean или отсутствие

```clojure
(ns lint.flag (:require [clojure.spec.alpha :as s]))
(s/fdef flag-text :args (s/cat :x (s/nilable boolean?)) :ret string?)
(defn flag-text [x] (if x "да" "нет"))
(s/fdef explicit-flag :args (s/cat :x (s/nilable boolean?)) :ret string?)
(defn explicit-flag [x]
  (if (nil? x) "неизвестно" (if x "да" "нет")))
;; Current: ни одно определение не получает F820.
;; Planned, не MVP: первый if — кандидат proposed TSP820-02.
;; Второе определение — без этого предупреждения после nil?-ветвления.
;; false и nil ложны, но 0, "" и [] в Clojure истинны.
```

### 5. Избыточна только nil-защита, а не любая проверка truthiness

```clojure
(ns lint.guard)
(defn known-text [x]
  {:pre [(string? x)]}
  (if (some? x) x "fallback"))
(defn flag [x]
  {:pre [(boolean? x)]}
  (if x "да" "нет"))
;; Current: pre-предикаты дают типы, но F820 отсутствует.
;; Planned, не MVP: some? в known-text — proposed TSP820-03.
;; flag — без предупреждения: non-nil boolean всё ещё может быть false.
;; Удалять pre или ветку автоматически нельзя: это меняет контракт кода.
```

## Planned: границы первой реализации

MVP проверяет только **прямой одноаргументный вызов именно `clojure.core/str`** с явным nil в типе аргумента, включая литерал nil. Ноль и несколько аргументов, `apply`, вызов через значение функции и произвольные макросы не входят. Локальная функция по имени `str` не должна считаться core-функцией.

Уровни `off` / `warning` / `error` используют существующую `:levels`; для введённого правила целевой уровень — `warning`, без автофикса. До включения по умолчанию нужна оценка шума на реальном Clojure-коде. Boolean- и redundant-guard-правила ниже — отдельный этап, не обещание готового анализа.

## Пошаговый алгоритм MVP

1. **Вход.** Разобранный узел вызова с позициями; разрешённая идентичность вызываемой функции; `ctx` с `:locals`, `:env`, `:opts`; уже вычисленный тип аргумента в данной ветке. Нужен именно тип в точке вызова, а не исходная сигнатура параметра.
2. **Отбор узла.** Проверить прямой вызов core/str и ровно один аргумент. Сначала учитывать локальные bindings и определения текущего namespace, затем core. Проверка только текста `str` или результата `env/head` недостаточна: нужно не спутать shadowing с core. Если разрешение неоднозначно — пропустить линт.
3. **Представление фактов.** Переиспользовать типы checker; раскрыть ссылки через `t/members` с имеющейся защитой от циклов. Для линта различать `explicit-nil`, `known-non-nil`, `uncertain`, `unreachable`. Это предлагаемые категории анализа, не новые формы языка типов. `:never` не даёт предупреждения. `:unknown`, `:any`, неразрешённая ссылка и platform делают доказательство неопределённым; в MVP такое значение пропускается, даже если рядом сохранилась nil-альтернатива.
4. **Не потерять происхождение.** Проверять platform-флаг до `eff`, который при strict-nil добавляет nil. Если после раскрытия/сужения происхождение потеряно, классифицировать как uncertain, а не угадывать. Полноценного графа происхождения сейчас нет: для MVP допустимо ограничить правило типами, чью неплатформенную природу можно установить; расширение требует дополнительных фактов.
5. **Решение.** Для полностью известных, неплатформенных альтернатив проверить наличие `:nil`. Есть nil — создать одну lint-диагностику; нет — ничего не добавлять. Наличие nil означает возможность по статическому типу, а не доказательство достижимости конкретного выполнения. Не применять обратный вывод «`nilable?` вернул false, значит значение точно non-nil»: unknown тоже не содержит явного nil.
6. **Результат.** Тип результата вызова остаётся `string?`; локальные факты и проверка совместимости не меняются. Диагностика `proposed TSP820-01`, severity warning, диапазон аргумента, текст примерно: «str преобразует возможный nil в пустую строку; проверьте, нужно ли различать отсутствие и пустую строку». Привести исходный тип через `t/show`, не заявлять, что намерение автора известно. `:fixes` не добавлять.
7. **Общий вывод.** Передать событие через `report!` с `:severity :warning`; сохранить подавление `:quiet` для внутренних проб inference. В `check-files` сохранить deduplication, применение `:levels`, идентификаторы и сортировку. JSON и текст должны описывать одну и ту же диагностику. Режим error влияет на exit code через уже существующий подсчёт ошибок в CLI.

Это консервативная эвристика подозрительного преобразования, **не sound-доказательство функциональной ошибки**. Soundness всей системы типов здесь не заявляется.

## Интеграция и следующие правила

Точка интеграции — обычный путь вызова в `check.clj` (`infer-list` / `call-fn`) после разрешения функции и получения типов аргументов. Аргумент нельзя повторно обходить ради линта: повторный `infer` может повторить диагностики и учёт доверенных операций. Нужен небольшой рефакторинг передачи уже полученных типов, а не второй независимый checker поверх исходного текста. Постпроход только по `:types` недостаточен: он не хранит всю информацию о разрешении вызова и происхождении nil.

**Boolean (`proposed TSP820-02`, не MVP):** взять тип теста до разделения веток; убедиться, что все известные альтернативы — boolean/nil, что возможны и false, и nil; выдать предупреждение об объединении состояний, не type error. Nilable string и unknown не подходят. Для literal unions нужно отдельно проверить представление boolean-литералов; нельзя выводить возможность false просто из отсутствия nil. Перед реализацией нужны исследования шума, точности boolean narrowing и области правила (`if` сначала, `when`/`cond`/макросы позже).

**Избыточная защита (`proposed TSP820-03`, не MVP):** сначала только `some?`/`nil?` над стабильной локальной переменной в условии. Все альтернативы должны быть известны, достижимы, неплатформенны и non-nil; тогда nil-ветка невозможна относительно принятого контракта. Не распространять автоматически на `if x`: false допустим. Не переносить факт между двумя deref или вызовами. Для расширения на `or`, повторные вычисления, mutable state и пользовательские guards требуется отдельный анализ стабильности и эффектов; перечисление синтаксических шаблонов его не заменяет.

## Матрица тестов (planned, не существующее покрытие)

| Случай | Ожидаемый результат F820 |
|---|---|
| `str` от явного `(s/nilable string?)` | один warning proposed TSP820-01 |
| `(str nil)` | один warning proposed TSP820-01 |
| `str` от string, числа, false | нет |
| `str` в положительной ветке `some?` и отрицательной `nil?` | нет после сужения |
| nilable spec через одну/несколько ссылок | warning; тип читаемо отображён |
| циклическая/неразрешённая ссылка, unknown, any | нет; обход завершается |
| platform из hint или Java, strict-nil off/on | нет в MVP; обычные type errors сохраняются |
| недостижимая ветка с типом never | нет |
| `str` с 0/2 аргументами, `apply str`, локальный alias | нет в MVP |
| локальный параметр `str`, `let`-binding, свой namespace var `str` | нет false positive |
| полностью квалифицированный core/str без shadowing | то же правило, что для обычного core-вызова |
| тот же вызов в тихом inference и итоговом обходе | одна, не две диагностики |
| уровни off / warning / error | 0 / warning / error; exit code соответствует severity |
| существующий механизм `t/ignore` | подавление без нового механизма; учёт unused не ломается |
| CLI и JSON | одинаковые code/file/позиции/severity, стабильный id JSON, нет fixes |
| nil передан в `subs`, а не в `str` | обычный TSP2531; не подменять линтом |
| nilable boolean в `if` | кандидат TSP820-02 только после реализации второго этапа |
| boolean без nil; nil явно отделён; `if 0`, `if ""`, `if []` | нет TSP820-02 |
| `some?` над известной строкой / platform / unknown | TSP820-03 только для первой, после второго этапа |
| `if` над boolean; два deref mutable значения | не считать избыточной защитой |

Тесты нужны на уровне классификатора фактов, разрешения вызовов, branch narrowing и end-to-end вывода. Текущий `test/typespec/demo_test.clj` сравнивает golden-диагностики и маркеры ERR/WARN; он также запускает карточки лишь с особыми example/output fences. Эта карточка намеренно не выдаёт planned-сценарии за такие тесты. В `test/features/src/f/core.clj` уже есть сценарии nil/narrowing, но они не проверяют F820.

## Ограничения и критерий готовности

- Линт не знает, намеренно ли вызывающий код превращает отсутствие в пустую строку. Нужна ручная оценка false positives на форматировании, логировании и выводе текста.
- Доверенные сигнатуры, hints и preconditions могут быть неверны или не проверяться при выполнении. Предупреждение основано на модели checker, а не на runtime-доказательстве.
- При platform/unknown консервативное молчание создаёт false negatives. Не включать их в «доказанно безопасные» случаи отчёта покрытия.
- Полнота проверки макросов, indirect calls, происхождение nil и полноценная truthiness-модель остаются вне MVP. Смежный narrowing должен улучшаться независимо, без копирования его алгоритма в линтер.
- Готовность MVP: реализованы только заявленные границы, матрица первого этапа проходит, CLI/JSON согласованы, оценён шум, приведён действительно проверенный пример вывода. Boolean и redundant-guard этапы имеют собственные критерии и не блокируют честный выпуск одного str-lint.
