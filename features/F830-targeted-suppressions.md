# F830 · Подавление конкретной диагностики

## Зачем это нужно в Clojure

В динамическом Clojure часть вызовов проходит через макросы, плагины и старые API, для которых checker ещё не знает точного контракта. Иногда нужно временно принять одну известную диагностику, не отключая проверку тела `let`, `do` или функции целиком. Широкий `ignore` скрывает и новые ошибки: исправление типов аргумента может незаметно сопровождаться неправильной арностью другого вызова.

Цель F830 — локальное исключение **по коду диагностики**, с причиной и видимым учётом доверия. Это не доказательство корректности кода, не `cast` и не превращение результата выражения в `any?`. Директива `#_` не выполняется Clojure и не требует runtime-библиотеки.

## Что есть сейчас, а что проектируется

`implementation: not-implemented` относится к адресному подавлению и остаётся верным.

- **Current:** `parse/convert-seq` прикрепляет распознанный `#_(t/ignore ...)` к следующей форме среди соседних узлов, пропуская пробелы и комментарии. `check/infer` берёт только первую директиву `t/ignore` на узле, увеличивает `:trust :ignore` и запоминает файл, диапазон формы и позицию директивы.
- **Current:** `check/check-files` сначала получает диагностики, затем удаляет все попавшие в диапазон, независимо от кода и severity. Неиспользованная директива даёт `TSP2578`. Выбирается первое совпавшее подавление; для перекрывающихся диапазонов это не спецификация приоритета.
- **Важное расхождение с reference:** §6 требует строку-причину, но `infer` не проверяет ни наличие, ни содержимое аргументов `t/ignore`. Поэтому запись с кодом сегодня тоже будет широким подавлением, а не адресным. Формулировка «работает подавление с причиной» не означает, что причина валидируется.
- **Planned:** обязательные код и непустая причина, фильтрация по коду, запреты из конфигурации, детерминированное разрешение перекрытий, отдельный учёт директив и скрытых диагностик. Имена новых настроек и полей результата пока не утверждены.

## Примеры и ожидаемое поведение

Все примеры — обычный Clojure-исходник для проверки, не тестовые fixtures. Current ниже подтверждён точечным запуском эквивалентных форм через `parse-string`/`check-files`; planned остаётся проектом. Сигнатура `inc` есть в `core_types.clj`; несовместимый аргумент даёт `TSP2345`, неправильная арность — `TSP2554`.

### 1. Корректное локальное исключение (planned)

```clojure
(ns sample.targeted)

#_(t/ignore TSP2345 "ISSUE-123: временно принимаем известную ошибку")
(inc "old-value")

(inc 1)
```

Planned: скрывается `TSP2345` первого вызова, второй корректен, unused нет. Current: внешне тот же результат, но только потому, что широкое подавление тоже скрывает эту ошибку. Само выражение `(inc "old-value")` не становится безопасным для выполнения.

### 2. Ошибка другого класса должна остаться (planned)

```clojure
(ns sample.other-error)

#_(t/ignore TSP2345 "ISSUE-124: исправляем тип отдельно от арности")
(do
  (inc "old-value")
  (inc))
```

Planned: `TSP2345` скрыт, `TSP2554` у `(inc)` остаётся. Current: обе диагностики скрываются. Это основной регрессионный пример: принятие нового синтаксиса старым checker не подтверждает поддержку F830.

### 3. Пограничный случай: только следующая форма

```clojure
(ns sample.scope)

(do
  #_(t/ignore TSP2345 "ISSUE-125: исключение только для первого вызова")
  ;; Комментарий не является целевой формой.
  (inc "first")
  (inc "second"))
```

Planned и current: первая ошибка скрыта, `TSP2345` второго вызова виден. Директива относится к одному вызову, а не ко всему окружающему `do`. Если поставить её перед `do`, областью будет весь `do`, включая вложенные формы.

### 4. Ошибочная директива не должна отключать проверку

```clojure
(ns sample.invalid)

#_(t/ignore TSP2345 "   ")
(inc "bad")
```

Planned: после trim причина пуста; выдать ошибку директивы (proposed `TSP830-01`) и оставить `TSP2345`. Невалидная директива не получает ещё и unused. Current: причина не проверяется, ошибка вызова скрыта. То же расхождение есть у `(t/ignore)` без аргументов. Старая форма с одной строкой должна мигрировать явным изменением: автоматически угадывать нужный код нельзя.

### 5. Устаревшее исключение после исправления

```clojure
(ns sample.unused)

#_(t/ignore TSP2345 "ISSUE-126: строка уже заменена числом")
(inc 1)
```

Planned и current: `TSP2578` уровня warning на директиве, поскольку подавлять нечего. В planned даже наличие другого кода в целевой форме не делает исключение использованным: без совпадения именно `TSP2345` оно остаётся unused.

## Пошаговый алгоритм (предлагаемый контракт)

Это алгоритм отбора диагностик, не новый алгоритм вывода типов. Он не доказывает soundness программы с подавлениями. Правила перекрытий ниже — предложение для реализации и тестов, а не уже существующая гарантия.

1. **Вход.** Исходные файлы с AST и позициями, обычные опции checker, набор известных кодов и политика запрещённых кодов. Набор кодов нужен явно: сейчас центральный реестр для этой проверки не показан. Все сравнения кодов должны использовать одну каноническую строку, например `"TSP2345"`.
2. **Сбор директив.** На этапе разбора/отдельного обхода собрать все `t/ignore`, а не только первую из `find-d`. Запись содержит уникальный ID по файлу и позиции, `code`, `reason`, позицию самой директивы и диапазон следующей формы. Не привязывать сбор исключительно к `infer`: не всякий синтаксический узел обязательно проверяется как выражение. Нужна отдельная диагностика для директивы без следующей формы; сейчас оставшийся `pending` теряется.
3. **Валидация.** Принимать ровно один символ-код и одну строку-причину; после trim строка не пуста. Неизвестный код, неверное число аргументов, старая форма без кода и отсутствие цели — proposed `TSP830-01`. Код, запрещённый политикой, — proposed `TSP830-02`. Ошибочная директива не участвует в подавлении. На первом этапе списки кодов не принимаются; несколько директив допустимы, с правилами шага 6.
4. **Обычная проверка типов.** Выполнить `env/build`, `infer*`, проверки аргументов/арности и запись типов без изменения семантики. Типы остаются текущими структурами checker (`:t`, параметры, возвращаемые типы); окружение локальных типов и факты сужения не модифицируются. Запретить раннее прекращение анализа целевой формы: иначе новые ошибки не будут найдены. Получить полный список диагностик до применения `:levels` и `:off`.
5. **Сопоставление.** Для каждой исходной диагностики искать только валидные директивы с тем же файлом и кодом. Предлагаемая область — полуоткрытый диапазон `[start, end)` целевой формы, содержащий начальную позицию диагностики. В текущем `inside?` верхняя граница включена; это требует явного изменения и теста на соседние формы. При неизвестной позиции не подавлять. Вложенные выражения внутри диапазона включаются; диагностика, поставленная на внешнюю форму вне диапазона, не включается даже при наличии ошибки в дочернем узле.
6. **Перекрытия и повторы.** Предлагается назначать каждой диагностике ровно одного владельца: ближайшую вложенную целевую форму, при одинаковой цели — первую директиву в исходном порядке. Одна директива подавляет все совпавшие диагностики своего кода, не только первую. Дублирующая директива без собственных совпадений получает unused. Для некорректно пересекающихся диапазонов не угадывать владельца: нужна валидация source mapping до включения таких источников в механизм.
7. **Результат и аудит.** Разделить список на видимые и подавленные; у подавленной хранить исходную диагностику, ID директивы и причину. Для каждой валидной директивы без назначенных совпадений создать существующий `TSP2578`. Ошибки директив и unused добавлять после фильтра и не подавлять другими `ignore`. Запрет их глобального отключения через `:levels` — отдельное решение политики, не часть уже работающего механизма.
8. **Severity и вывод.** После сопоставления применять `:levels`, удаление `:off`, ID и стабильную сортировку к видимым диагностикам, как сейчас. Поэтому факт использования подавления не зависит от настройки severity. `:off` не считать локальным подавлением. CLI и JSON должны брать одну итоговую коллекцию, а не повторять фильтр независимо. Сохранять позиции и severity исходных диагностик в аудите.
9. **Доверие.** Отдельно считать встреченные директивы (включая невалидные), валидные использованные директивы и реально подавленные диагностические события. Не менять молча смысл существующего `:trust :ignore`; расширение формата/совместимость утвердить до реализации. Это проект счётчиков, не реализованный CI trust budget.

## Интеграция с текущим checker

- `src/typespec/parse.clj`: `convert-seq` уже сохраняет директивы на AST; надо сохранить и ошибки привязки, а не терять хвост `pending`.
- `src/typespec/check.clj`: заменить регистрацию через единственный `find-d` и финальный `hit` на валидированные записи и отбор по коду. Не менять `infer*`, `assignable!` или тип результата из-за `ignore`.
- Сейчас `distinct @*diags*` устраняет одинаковые записи целиком. Не использовать `diag-id` как ключ подавляемого события: его hash учитывает код, basename файла и сообщение, но **не позицию**, поэтому одинаковые ошибки в разных местах могут иметь одинаковый ID. Для аудита нужен ключ с полным файлом и диапазоном; изменение публичного ID — отдельная задача совместимости.
- `src/typespec/main.clj`: `format-diag` и `diag->json` уже используют общие диагностики. Если аудит станет частью JSON, это отдельное расширение сериализации, а не утверждение о текущем выводе.
- `docs/reference.md` §6 описывает широкую запись с причиной; при реализации понадобится согласовать миграцию reference и API. Эта карточка не меняет существующий reference.

## Матрица тестов для реализации

| Случай | Конкретная проверка planned |
|---|---|
| Один неверный аргумент, нужный код | Пример 1: нет видимых ошибок; 1 использованная директива, 1 подавленное событие |
| Разные коды в одной форме | Пример 2: виден только `TSP2554`; аудит содержит только `TSP2345` |
| Соседние формы и комментарий | Пример 3: второй `TSP2345` остаётся; комментарий не меняет привязку |
| Пустая/пробельная причина, причина не строка | Пример 4 и варианты: proposed `TSP830-01` + исходная ошибка; 0 подавлений |
| Нет кода, лишний аргумент, неизвестный код | Ошибка директивы, исходные диагностики сохранены; автоматической миграции нет |
| Исправленная форма | Пример 5: ровно один `TSP2578` на диапазоне директивы |
| В форме только другой код | Директива для `TSP2345` перед `(inc)`: `TSP2554` + `TSP2578` |
| Запрещённый код | Политика запрещает `TSP2345`: proposed `TSP830-02` + исходный `TSP2345`, без unused |
| Два одинаковых кода в разных местах | Перед `(do (inc "a") (inc "b"))`: 2 события аудита, 1 использованная директива; ID не склеивают позиции |
| Две директивы разных кодов | Перед примером 2: обе использованы, 2 события; AST не теряет вторую директиву |
| Дубли одной директивы | Первая получает событие, вторая — `TSP2578`; счётчик событий не удвоен |
| Вложенные подавления одного кода | При единственной внутренней ошибке внутреннее использовано, внешнее unused |
| Границы диапазона | Начало включено, конец исключён; соседняя форма, другой файл и неизвестная позиция не подавляются |
| Директива в конце файла/списка | Нет следующей формы: proposed `TSP830-01`, не тихая потеря |
| Непосещаемый inference узел | Обход директив всё равно валидирует запись; отсутствие диагностики означает unused |
| `:levels` меняет severity или ставит `:off` | Совпадения и аудит те же; видимый вывод меняется только после фильтра |
| Неизменность типов | `:types`/сигнатуры совпадают с запуском без `ignore`; нет превращения в `any?` |
| CLI / JSON | Одинаковые код, severity, файл и старт; JSON сохраняет конец диапазона; сортировка стабильна |

## Ограничения и нерешённые вопросы

- Подавление по коду и диапазону не различает две разные причины одного кода внутри большого `do`. Это сознательная граница F830; для большей точности размещать директиву перед меньшей формой. Механизм «ровно одна ошибка» здесь не обещан.
- Нужны отдельные исследования происхождения диагностик после macro expansion и корректного source mapping. Само попадание координаты в диапазон не доказывает, что ошибка причинно принадлежит выражению. На первом этапе контракт ограничен исходными AST с надёжными позициями.
- Требуется решить политику для reader conditionals, discarded data и областей, которые checker не анализирует: универсальный сбор директив не должен превращать произвольные данные в инструкции. Текущий parser поддерживает лишь часть reader forms.
- Нужно согласовать реестр известных/неподавляемых кодов, формат конфигурации запретов, аудит в JSON и версионирование широкого синтаксиса. До этого нельзя безопасно рекомендовать новую запись для production CI: старый checker примет её слишком широко.
- Предложенные правила приоритета и неподавляемости ошибок директив требуют тестов, а не заявления о soundness. Более строгая политика может запретить перекрывающиеся директивы полностью.

## Проверенные локальные источники и границы проверки

Прочитаны `docs/reference.md` (§6, §7 и таблица кодов), `src/typespec/parse.clj` (`convert-seq`, `parse-string`), `src/typespec/check.clj` (`infer`, `inside?`, `diag-id`, `check-files`, проверки аргументов/арности), `src/typespec/core_types.clj` (сигнатура `inc`), `src/typespec/main.clj` (общий результат и сериализация), `test/typespec/demo_test.clj` (проверка trust counters). Последняя проверяет существующие счётчики демо, но не является тестом адресного подавления.

Первый запуск без `JAVA_HOME` не удался (`Unable to locate a Java Runtime`). Повторный точечный запуск `clojure -M -e` с `JAVA_HOME=/opt/homebrew/opt/openjdk@25` и `PATH="$JAVA_HOME/bin:$PATH"` успешно проверил эквивалентные формы всех пяти примеров через `parse-string`/`check-files`: №1 — `[]`, №2 — `[]` (оба кода скрыты), №3 — `["TSP2345"]`, №4 — `[]` (пробельная причина принята), №5 — `["TSP2578"]`. Во всех пяти случаях trust равен `{:cast 0 :any 0 :ignore 1}`. Контрольный вариант №2 без директивы дал `["TSP2345" "TSP2554"]` и `:ignore 0`. Это подтверждает current, но не реализует planned. Полный suite и `--update` не запускались. Поле `origin: Flow` сохраняет происхождение идеи; внешняя документация в рамках этой доработки не проверялась.
