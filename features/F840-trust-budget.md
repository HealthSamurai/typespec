# F840 · Бюджет доверия и baseline в CI

## Зачем это Clojure-проекту

Проверку типов обычно внедряют постепенно: вокруг динамических API, Java-вызовов и старого кода остаются непроверенные границы. Зелёный CI полезен только если исправление ошибок не сводится к добавлению `any`, приведений и подавлений. Бюджет делает такие изменения видимыми человеку; он не определяет намерения автора и не доказывает корректность программы.

Здесь два независимых механизма: **baseline диагностик** разрешает конкретные ранее известные ошибки, а **бюджет доверия** ограничивает непроверенные допущения. Удаление одной ошибки не должно автоматически оплачивать новое подавление в другом месте. F810 отвечает за охват проверки, F830 — за семантику конкретного `ignore`; эта карточка отвечает за сравнение результатов между ревизиями и решение CI.

## Что уже работает, а что спроектировано

**Current, по исходникам:**

- `parse/convert-seq` сохраняет `#_(t/cast ...)`, `#_(t/any ...)`, `#_(t/ignore ...)` в `:directives` следующего узла AST. В runtime Clojure это reader-discard, не проверка значения.
- `check/infer` сначала проверяет исходное выражение, затем подменяет его тип через `cast` или `any`. Счётчики `:cast`, `:any`, `:ignore` увеличиваются при обработке директив. Если у узла есть одновременно `cast` и `any`, ветка `cast` имеет приоритет; это не независимый подсчёт всех текстовых вхождений.
- `check-files` возвращает `:trust {:cast n :any n :ignore n}`, типы выражений, сигнатуры и диагностики. Внутренние тихие проходы `quietly` и вывода результата функции имеют отдельные атомы счётчиков. Поэтому текущие числа — результат обхода checker, не гарантированный реестр уникальных мест доверия.
- Подавления фильтруются по файлу и диапазону выражения. Неиспользованное подавление даёт существующий warning `TSP2578`, но всё равно увеличивает `:ignore`. После этого применяются `:levels`, включая `:off`.
- `main` печатает `:trust` в JSON и текстовом отчёте. Exit code зависит только от оставшихся диагностик уровня `:error`, а не от роста доверия.

**Planned:** чтение и сравнение baseline, проверка роста доверия и ослаблений контрактов, отдельный учёт trusted guards, platform, hooks и externs. Наличие `:baseline` в дизайне конфигурации не означает работающий механизм: `main/run-check` передаёт конфигурацию checker, но сравнения снимков в текущем коде нет. Обязательная причина для `any`/`ignore` описана в reference; показанный обработчик `infer` её не валидирует. `implementation: partial` оставлено именно из-за существующих трёх счётчиков, не из-за готового CI-gate.

## Примеры и ожидаемое поведение

Ниже обычные иллюстрации, не исполняемые golden-тесты. Current сверен с исходниками и точечным запуском `parse-string` → `check-files` через `clojure -M -e` с `JAVA_HOME=/opt/homebrew/opt/openjdk@25`. Проверены восемь вариантов: чистое выражение, ошибка аргумента, any, использованный и неиспользованный ignore, cast и обе сигнатуры из примера 5. Получены ожидаемые счётчики и коды: `TSP2345` для ошибочного аргумента (также под cast), `TSP2578` для unused-ignore; остальные варианты без диагностик. Полный suite не запускался. Planned — требования к будущему gate, не доступные сегодня команды.

### 1. Корректное изменение без дополнительного доверия

```clojure
(ns sample.counter)

;; До изменения: (inc 1)
(inc 2)
;; Current: директив нет, trust = {:cast 0 :any 0 :ignore 0}.
;; Planned: при том же scope/config и отсутствии новых диагностик
;; baseline с нулевыми бюджетами пропускает изменение.
```

Литеральное изменение не требует согласования нового допущения. Само отсутствие директив ещё не доказывает полноту охвата: проверенные пути и настройки должны совпадать со снимком.

### 2. Ошибочное «исправление» через any

```clojure
(ns sample.counter)

;; До: (inc "bad") — строка не подходит числовому аргументу.
(inc #_(t/any "temporary legacy boundary") "bad")
;; Current: тип аргумента заменяется на any; :any увеличивается на 1.
;; Это не преобразование строки в число в runtime.
;; Planned: baseline с :any 0 отклоняет +1,
;; даже если диагностика несовместимого аргумента исчезла.
```

Считать нужно явные допущения, а не только ошибки после подавления. `any?` внутри сигнатуры — отдельный путь ослабления: он не становится автоматически директивой `t/any` и не обязан увеличивать текущий счётчик.

### 3. Граница: подавление перестало быть нужным

```clojure
(ns sample.counter)

#_(t/ignore "LEGACY-17: replace string input")
(inc "bad")
;; Current: диагностика внутри диапазона подавляется; :ignore = 1.

;; После исправления этого же места:
#_(t/ignore "LEGACY-17: replace string input")
(inc 1)
;; Current: :ignore = 1, warning TSP2578 (unused t/ignore).
;; Planned: не считать это погашением долга; удалить саму директиву.
```

Два фрагмента показывают альтернативные ревизии; если вставить оба одновременно, директив будет две. Warning сам по себе не ломает текущий CLI; будущая политика может отдельно запрещать новые unused-ignore, но обязана явно указать это в снимке.

### 4. Cast не скрывает ошибку внутри проверяемого выражения

```clojure
(ns sample.counter)

#_(t/cast int?)
(inc "bad")
;; Current: сначала infer* проверяет вызов inc, затем меняется его тип.
;; Ошибка аргумента остаётся, :cast увеличивается на 1.
;; Planned: отдельно показать новую ошибку и новое допущение;
;; cast не даёт права записать выражение как «доказанное».
```

Не следует трактовать счётчик как число успешных исправлений: директива может сосуществовать с ошибкой. Запрет роста бюджета и baseline ошибок проверяются независимо.

### 5. Ослабление сигнатуры без роста счётчиков

```clojure
(ns sample.config)

;; Исходный контракт:
(defn label {:t/sig [string? :-> string?]} [x] x)

;; Предлагаемая замена определения в следующей ревизии:
;; (defn label {:t/sig [any? :-> any?]} [x] x)
;; Current: в обеих версиях нет t/any/t/cast/t/ignore; их счётчики нулевые.
;; Planned: сравнение объявленных контрактов требует review замены на any?.
```

Это пример политики сохранения гарантий, а не утверждение, что расширение любого входного типа математически неправильно. У функции входы контравариантны, результаты ковариантны; полезное расширение API нельзя надёжно отличить от обхода проверки одним общим числом.

## Алгоритм: согласование двух снимков проверки (planned)

Это алгоритм CI-политики, не новый sound алгоритм вывода типов. Проверку выражений выполняет существующий checker. Для первой версии надёжнее ограниченный структурный diff контрактов и явный review неизвестных изменений, чем обещание распознавать все семантические ослабления.

1. **Зафиксировать входы.** Получить снимок из доверенной базовой ревизии, текущие исходники, одинаковые пути и платформу, конфигурацию, версию checker и схему baseline. Снимок из текущего PR нельзя молча считать разрешением собственного роста. Обновление baseline — отдельное явно проверяемое действие, не побочный эффект `check`.
2. **Проверить сопоставимость.** Сравнить scope, список файлов, версии, strict/strict-nil, уровни диагностик и доступные источники типов. Сужение путей, отключение diagnostic или смена платформы должны давать отдельное изменение политики, а не уменьшение долга. При несовместимом формате или отсутствующем обязательном baseline — fail с объяснением, не «пустой успешный снимок».
3. **Собрать факты текущего прохода.** Использовать AST и результат `check-files`: диагностики, `:sigs`, `:types`, `:env`, текущие счётчики. Для полноценного бюджета добавить реестр уникальных trust-событий: категория, относительный путь, определение-владелец, структурный путь выражения, диапазон для показа, причина, источник (`directive`, `guard`, `platform`, `hook`, `extern`). Нельзя восстановить такой реестр из трёх чисел. Внутренние повторные проходы не должны порождать новые события.
4. **Сохранить происхождение типов.** В checker типы представлены EDN-map с тегом `:t`, например `{:t :any}`, `{:t :unknown}`, union и ref; `:platform` является дополнительным признаком. Не подменять `unknown` категорией `any`. В снимке контрактов хранить нормализованный объявленный тип, fully-qualified имя, арности и происхождение, отдельно от выведенного типа тела. Учёт guards/hooks/externs пока требует отдельной инструментализации и схемы события; отсутствие такого учёта явно показывать как неполный охват.
5. **Сопоставить диагностики.** Нужны устойчивые ключи: относительный путь, владелец, код, структурное место и нормализованная причина, плюс количество одинаковых событий. Отступы и сдвиг строки не должны создавать новый долг. Неоднозначное сопоставление не разрешает новое событие автоматически. Сравнить мультимножества: сохранённые, устранённые, новые. Текущий `diag-id` — hash от code/basename/message — недостаточен: разные каталоги и одинаковые ошибки могут совпасть. Не доверять только этому ID.
6. **Сопоставить доверие.** Сравнить события по категориям и местам, затем вывести агрегаты. Минимальный gate на имеющихся данных способен лишь запретить положительную дельту каждой из трёх категорий; он должен честно называться ограниченным. Целевой gate дополнительно показывает новые и исчезнувшие места, чтобы удалённый cast не автоматически разрешал новый cast в другой функции. Для hooks/externs учитывать изменение содержимого/версии источника, а не число использований; для platform заранее определить единицу учёта. Между категориями нет взаимозачёта.
7. **Сравнить контракты.** На поддержанном фрагменте выделить точечные изменения: добавление nil, потерю обязательного ключа, закрытая → открытая map, появление any в сигнатуре. Разрешать refs только в зафиксированном окружении и с защитой от циклов. Сравнивать также определения, на которые ссылается неизменившаяся сигнатура. Направление изменения и позицию аргумент/результат показать человеку. Не использовать `sub?` с permissive any как универсальный детектор ослабления. Для рекурсивных refs, перегрузок, полиморфизма и неоднозначной эквивалентности результат — «нужен review», не «безопасно».
8. **Принять решение и объяснить его.** Старые разрешённые ошибки остаются видимыми, новые блокируют gate; рост доверия и неподтверждённые изменения политики блокируют независимо. Показать before/after по категориям, конкретные места, изменения контрактов, устранённый долг и непокрытые категории. Предлагаемые, ещё не существующие коды: **proposed TSP840-01** — новая baseline-диагностика; **proposed TSP840-02** — новое доверие сверх политики; **proposed TSP840-03** — изменение контракта требует review; **proposed TSP840-04** — несопоставимый снимок/настройки. Не скрывать исходные TSP-диагностики за одним общим сообщением.

### Интеграция с текущим checker

Сравнение снимков располагается после обычной проверки и до выбора exit code в `main`, а не внутри каждого правила подтипизации. Сбор событий и необработанных диагностик нужно добавить в `check-files`: сейчас наружу выдаются уже подавленные и отфильтрованные по `:levels` диагностики. Нельзя потерю этих данных выдавать за отсутствие ошибок. Для baseline следует явно выбрать отдельные представления сырых диагностик, эффективных диагностик и подавленных событий; подавленный долг учитывается через trust, а не молча исчезает.

Совместимость JSON требует версии схемы для новых полей; текущие `:trust` можно сохранить как агрегаты. Существующий `main` пока не имеет baseline-команды, режима обновления снимка или gate-диагностик. Не придумывать пользователю действующие флаги. Первую реализацию можно ограничить тремя категориями и базовыми контрактами, но вывод должен перечислять непокрытые категории.

### Доверие к фактам сужения и к удалению подавлений — planned

В snapshot контракта учитывать не только вход/выход, но и экспортируемые truthy/falsy summaries предиката, их происхождение и fingerprint доказательства (тело, checker/config, externs). Замена checked summary на ручной extern при прежнем `boolean?`-результате — изменение основания доверия, даже если число cast/any не выросло. Например, `(if (vendor/text? x) (clojure.string/upper-case x) nil)` может зависеть от внешнего положительного факта. В отчёте показывать это допущение, не обещать runtime-защиту; Optional Typed Racket тоже не обеспечивает такую защиту. Отсутствующий falsy-факт нельзя восполнить автоматически. Метка `pure` не доказывает compile-time termination и не разрешает исполнять предикат для проверки summary.

Согласование с F830: `unused` доказан лишь когда соответствующее правило действительно исполнялось для места в сопоставимом snapshot checker/config/externs. Отключённое правило, пропущенный макрос или incomplete проход дают «не установлено», а не повод удалить suppression или уменьшить долг. Агент не удаляет подавления автоматически.

План тестов: одинаковая boolean-сигнатура при смене checked→trusted даёт review-событие; изменение extern инвалидирует fingerprint; при отключении diagnostic прежний ignore не становится доказанно unused; возврат правила восстанавливает проверку. Это критерии CI, не новые правила подтипизации и не реализованный gate.

Основания: [Typed Racket, §6](../docs/research-typed-racket.md), [Python, §3](../docs/research-python.md), первичные [Optional semantics](https://docs.racket-lang.org/ts-reference/behavior-of-types.html), [mypy gradual adoption](https://github.com/python/mypy/blob/master/docs/source/existing_code.rst). Прочитаны профильные разделы отчётов, upstream повторно не проверялся; тесты и доказательство soundness не выполнялись.

## Ограничения и открытые вопросы

- Число директив не измеряет риск: один ignore вокруг большой формы может скрывать больше, чем несколько локальных. Нужно показывать диапазон и реально подавленные диагностики; весовой «риск-балл» пока не обоснован.
- Нужна определённая единица platform-события: объявление Java-границы или каждое употребление. Ни одно из этих правил сейчас не реализовано счётчиком `:trust`.
- Нужна политика переносов/переименований файлов и определений. Надёжность matching важнее красивого процента уменьшения долга; неоднозначность должна быть видима.
- Рефакторинг эквивалентных типов и корректное расширение входного API могут выглядеть как ослабление. Исследование нормализации, variance и рекурсивных типов обязательно до обещания семантической полноты; структурный detector имеет false positives и ограниченную полноту.
- Применение reader conditionals сейчас ориентировано на `:clj`; снимок не доказывает свойства непроверенной `:cljs` ветки. Макросы и внешний код также требуют честного учёта охвата, не нулевого бюджета по умолчанию.
- Причина в комментарии объясняет долг, но не разрешает его автоматически. Кто утверждает baseline и отдельные исключения, определяется CI-процессом проекта.

## Конкретная матрица тестов

Строки planned — будущие тесты, не утверждение о наличии покрытия. Сейчас `demo_test.clj` содержит aggregate assertion `{:cast 1 :any 0 :ignore 2}`; это не тест baseline и не доказательство уникальности событий.

| Сценарий | Ожидаемая проверка |
|---|---|
| Чистый `(inc 2)` | Current: три нуля, нет ошибок этого выражения; planned: равный baseline проходит |
| `inc` со строкой, затем any на аргументе | Current: +1 any; planned: новая уступка блокирует даже после исчезновения ошибки |
| Cast на ошибочном вызове | Current: +1 cast и исходная ошибка аргумента остаётся |
| Использованный → неиспользованный ignore | Current: ignore не уменьшается, появляется TSP2578; planned: долг не погашен |
| any? в объявленной сигнатуре | Current: счётчик директив не растёт; planned: отдельный diff контракта |
| Одно место удалено, другое добавлено при равном итоге | Planned: новые места видны; равенство агрегатов не даёт автоматического разрешения |
| Сдвиг строк и изменение пробелов | Planned: не создавать новую диагностику или trust-событие |
| Одинаковый basename в разных каталогах, два одинаковых сообщения | Planned: сохранять разные пути и кратность, не схлопывать по текущему ID |
| Повторный тихий вывод типа функции | Planned: одно source-событие, стабильные агрегаты при порядке вызовов |
| Добавление nil / удаление req / открытие map | Planned: отдельный before/after, позиция в контракте и требование review |
| Изменение referenced spec при неизменной сигнатуре | Planned: сравнивать разрешённые зависимости, не только текст ref |
| Исключён файл, `:levels :off`, strict-nil отключён | Planned: изменение scope/policy, не успешное уменьшение долга |
| Повреждён baseline или другая версия схемы | Planned: явный fail, без автоматического перезаписывания |
| Изменились extern/hook, появилась platform-граница | Planned: отдельные категории; до поддержки явно неполный охват |
| Устранена старая ошибка без новых уступок | Planned: gate проходит и показывает погашенный долг |
