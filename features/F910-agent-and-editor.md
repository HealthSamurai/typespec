# F910 · Диагностика, редактор и цикл агента

## Обновление реализации — топ-10

ID теперь SHA-256, усечённый до 128 бит, с путём и диапазоном; это практическая устойчивость к коллизиям, не математическая уникальность. JSON неполных проверок содержит reasons. Полноценный LSP/cache не реализован.

Проверено набором `clojure -M:test`: 34 регрессионных теста / 239 assertions и существующие golden/CLI-тесты. Подробности: [implementation-top10](../docs/implementation-top10.md). Ниже сохранён проект полного механизма; прежние пометки current, противоречащие этому обновлению, описывают состояние до данного изменения. Иллюстрации карточки не стали автоматически исполняемыми тестами.


## Мотивация и граница карточки

В Clojure один контракт может быть виден в spec, метаданных, Java hints и теле функции. Редактору и агенту нужны согласованные ответы: что известно в этой точке, откуда взялся nil, какую декларацию исправлять и не скрыла ли правка ошибку. Отсутствие ошибок само по себе не означает, что весь код проверен.

Это обзорная карточка протокола взаимодействия, а не новый алгоритм подтипизации. Проверка деклараций принадлежит F110–F150, narrowing — F240, nil — F320, Java — F510–F530, бюджет доверия — F840. Здесь определены сбор результатов, согласование источников, представление диагностики и безопасная последовательность действий человека или агента.

## Что уже работает, а что только спроектировано

**Current**, по `src/typespec/main.clj` и `check.clj`:

- CLI `check`, `sig`, `type-at`; `check --json` печатает объект с `version: 1`, `diagnostics`, `trust`.
- Диагностика содержит `id`, `code`, `severity`, `file`, `range.start/end`, `message`, иногда `fixes`. `version` находится в оболочке, не в каждой диагностике.
- `check` завершает процесс с кодом 1 при наличии ошибок и 0 иначе; одни предупреждения не дают код 1.
- `sig` печатает сигнатуры и краткий источник (`t/sig`, `s/fdef`, hints или тело). Это не полный журнал происхождения типа.
- `type-at` ищет записанное выражение по позиции и печатает тип; при отсутствии попадания — `no expression here`.
- Есть текстовые `Did you mean …?`, объяснения некоторых источников nil и edit-предложение добавить Java hint для `TSP7023`. Предложение не применяется автоматически.

**Planned**: LSP, работа с несохранёнными/неполными буферами, `order`, `annotate`, команда применения `fix`, полный граф причин и связанные места. `file_sha`, структурированные `expected`/`actual`, `cause_of`, `related` и `range.base` из §8 reference сейчас не выдаются. CLI `coverage` также не реализован. Поэтому образец JSON в reference — целевой дизайн, не текущая схема API.

## Примеры и ожидаемое поведение

Ниже обычные иллюстративные блоки, не golden-тесты. Целевой in-memory smoke test через `parse-string` → `check-files` подтвердил current-сценарии примеров 1–4: единственный TSP2345 для строкового аргумента, сигнатуру twice, TSP2531 с optional-причиной до guard и отсутствие этой ошибки после guard, TSP7023 с insertion edit до hint и отсутствие предупреждения после hint. После guard остаётся отдельный TSP7023: устранение nil не устраняет reflection. Hover в этом smoke test отдельно не проверялся. Пример 5 и planned-поведение не объявляются проверенными исполнением.

Для запуска использованы `JAVA_HOME=/opt/homebrew/opt/openjdk@25` и `PATH="$JAVA_HOME/bin:$PATH"`: JDK установлен, но первоначально не был доступен через окружение запуска. Полный suite и `--update` не запускались.

### 1. Корректная сигнатура и запрос типа — current

```clojure
(ns example)

(defn twice
  {:t/sig '[number? :-> number?]}
  [x]
  (+ x x))

(twice 3)
;; check: для этого вызова не ожидается ошибка аргумента.
;; sig example: twice имеет [number? :-> number?], источник t/sig.
;; type-at на выражении (twice 3): number?.
;; Позиция вне записанного выражения: "no expression here".
```

`type-at` берёт наиболее маленький из подходящих сохранённых диапазонов, а не повторно выводит тип по строке текста. Разные позиции внутри одного вызова могут относиться к разным узлам.

### 2. Ошибочный аргумент: исправить причину, не скрыть её — current/planned

```clojure
(ns example)

(defn twice {:t/sig '[number? :-> number?]} [x] (+ x x))
(twice "3")
;; Current: TSP2345, строка не подходит к number?.
;; Current: JSON сообщает место и текст, но не отдельные expected/actual.

(twice 3)
;; Возможная ручная правка, только если требовалось именно число 3.
;; Planned: агент предлагает её человеку, а не выводит намерение из типа.
;; Ослабить аргумент до any? или добавить cast — не safe fix.
```

Типовая ошибка не доказывает, что правильна замена литерала: возможно, нужно изменить источник данных или контракт. Диагностика должна отделять факт несовместимости от предложенного изменения смысла.

### 3. Пограничный случай optional key и происхождение nil — current

```clojure
(ns example (:require [clojure.spec.alpha :as s]))
(s/def ::label string?)
(s/def ::item (s/keys :opt [::label]))

(defn label-size
  {:t/sig '[::item :-> number?]}
  [item]
  (let [label (::label item)]
    (.length label)))
;; Current: TSP2531 при разыменовании потенциально nil.
;; why-of умеет объяснить, что ::label optional в ::item.
;; Возможное дополнительное предупреждение о reflection — отдельная проблема.

(defn label-size-or-zero
  {:t/sig '[::item :-> number?]}
  [item]
  (let [label (::label item)]
    (if (some? label) (.length label) 0)))
;; Current: в then-ветке nil устранён проверкой some?.
;; Возврат 0 — выбранная автором семантика, не автоматический safe fix.
```

Сегодня `:why` переносит текст причины через некоторые локальные привязки; это не полный граф зависимости значений. Нельзя обещать, что любой nil будет объяснён до его первичного источника.

### 4. Предложение hint и устаревший диапазон — current/planned

```clojure
(ns example)

(defn file-name
  {:t/sig '[java.io.File :-> String]}
  [f]
  (.getName f))
;; Current: TSP7023 warning, если checker знает класс,
;; но компилятор не имеет hint. fixes предлагает ^java.io.File.

(defn file-name-hinted
  {:t/sig '[java.io.File :-> String]}
  [f]
  (.getName ^java.io.File f))
;; Иллюстрация результата ручного применения: hint у target.
;; Planned: если текст изменился после check, старый edit отвергается;
;; заново check, затем новый preview. Сейчас file_sha в JSON отсутствует.
```

Текущий генератор помечает этот edit `risk: "safe"`. Это локальная оценка checker, не гарантия сохранения поведения любого Java-кода: hints способны влиять на выбор перегрузки и требуют отдельного обоснования. Добавление `^…` не заменяет проверку nil.

### 5. Несогласованные источники и граница автоматической аннотации — planned

```clojure
(ns example (:require [clojure.spec.alpha :as s]))
(s/fdef read-label :args (s/cat :x string?) :ret string?)

(defn read-label
  {:t/sig '[string? :-> number?]}
  [x]
  42)
;; Planned для цикла annotate: показать конфликт контрактов и происхождение,
;; не выбрать молча тип из тела и не переписать spec.
;; Нужна проверка правил конфликта в карточке деклараций;
;; этот пример не обещает конкретную текущую диагностику checker.

;; Наблюдение теста: (read-label "x") => 42.
;; Это свидетельство об одном пути, а не доказательство контракта для всех x.
;; Агент может подготовить черновик, но не считать его verified.
```

## Алгоритм: собрать, согласовать, проверить, предложить

### 1. Зафиксировать вход

Current: `main/run-check` объединяет `typespec.edn` с переданными opts (opts побеждают), выбирает paths, по умолчанию `src`, сортирует `.clj`/`.cljc` файлы и вызывает `parse/parse-file`. Парсер строит AST с позициями, не загружая и не исполняя исходники. Отдельные команды заново запускают проверку проекта; общего сохранённого snapshot между ними нет.

Planned: адаптер редактора сохраняет ревизию каждого буфера, конфигурацию, classpath и версии подключённых источников. Все ответы одного прохода относятся к этому snapshot. До проектирования восстановления после синтаксической ошибки нельзя обещать диагностику для незаконченной формы.

### 2. Представить типы и происхождение

Current: `env/build` создаёт окружение спецификаций и vars; checker использует внутренние карты типов с тегом `:t`, `:locals`, `:why`, диапазоны AST и записи `:types`. `t/show` переводит типы в печатный язык. `:sigs`, `:env` и `:trust` входят во внутренний результат `check-files`, но не все они экспортируются в CLI JSON.

Planned: хранить рядом с кандидатным контрактом ссылку на декларацию и вид основания: явный контракт, внешняя схема с версией, вывод checker, наблюдение теста, предположение из текста. Не смешивать «тип доказан при этих допущениях» и «тип предложен агентом».

### 3. Согласовать источники, не изобретая второй checker

1. Сгруппировать кандидаты по полностью квалифицированному var/ключу и snapshot.
2. Передать явные декларации существующим правилам построения окружения и проверки контрактов. Правила совместимости задают карточки деклараций, не приоритет модели агента.
3. При конфликте сохранить обе ссылки и остановить автоматическую аннотацию затронутого контракта. Не исправлять конфликт объединением с `any?` и не выбирать тип по числу совпавших тестов.
4. При отсутствии явного контракта предложить черновик из доступного вывода/внешних данных. Трассы и docstrings — материал для рассмотрения, не доказательство полноты.
5. Выбор обязательности ключа, nullability или изменения поведения требует проверки человеком; повторная проверка тела обязательна после принятия декларации.

Это целевой протокол согласования, не реализованный общий resolver всех источников. Providers, sidecars и сложные отношения деклараций должны иметь собственные доказанные правила до включения в автоматический цикл.

### 4. Выполнить текущую проверку

`check-files` обходит формы через `infer`. Проверки аргументов, returns, ключей, nil и interop используют существующие функции checker. `report!` добавляет код, severity (по умолчанию error), файл, позицию и текст; `record!` сохраняет типы выражений. `why-of` даёт ограниченное текстовое происхождение nil. Адаптер редактора не повторяет эти правила самостоятельно.

После обхода checker удаляет дубли, применяет диапазоны `t/ignore`, добавляет `TSP2578` для неиспользованного ignore, применяет `:levels`, убирает `:off`, вычисляет id и сортирует по файлу, строке, колонке, коду. Trust сейчас — счётчики cast/any/ignore, не реализованный запрет ослабления типов в PR.

### 5. Выдать согласованный ответ

Current: `run-check` делает пути диагностик и `:types` относительными root; `diag->json` переводит поля в формат CLI. `type-at` использует полуоткрытый диапазон `[start,end)` и выбирает попадание по размеру диапазона. `sig-lines` форматирует сигнатуры из того же результата, если вызывающий код переиспользует его.

Planned: LSP-адаптер переводит координаты парсера в требуемые LSP позиции, явно проверяя Unicode, CRLF и конец диапазона. CLI JSON нельзя передавать в LSP без преобразования. `expected`/`actual` должны сериализоваться через общий принтер; `related` и причинные связи должны ссылаться на факты checker, а не генерироваться из догадок по тексту сообщения. Новые TSP-коды для этого протокола пока не нужны.

### 6. Замкнуть цикл правки — planned

1. Сохранить исходные diagnostics и trust; выбрать одну причину, показать diff.
2. Проверить совпадение ревизии файла; при несовпадении отказаться от применения старых edits.
3. Проверить допустимость диапазонов и отсутствие пересечений, применять edits от конца файла. Межфайловые изменения требуют атомарного плана либо явного отката только собственных правок.
4. Не применять автоматически изменения поведения, ослабление контракта, any/cast/ignore. Не считать `risk` доказательством безопасности.
5. Повторить checker и целевые runtime-тесты. Проверить исчезновение исходной проблемы, новые ошибки и изменения trust; не измерять успех только уменьшением числа diagnostics.
6. Отдать результат на review, остановиться при отсутствии прогресса или лимите итераций. Не зацикливать annotate/check.

`order` должен учитывать циклы зависимостей namespaces, например группировать strongly connected components перед bottom-up порядком. Граф, политика invalidation и правила повторного анализа пока не реализованы; это задача исследования, а не обещание sound инкрементального алгоритма.

### 7. Инкрементальный ответ без устаревшего успеха — planned

В связке с F720 хранить два разных hash: входного snapshot (source, checker/config, extern/spec manifests, JVM/Clojure/classpath) и нормализованного экспортного интерфейса. Изменённое тело всегда перепроверять локально; зависимых потребителей инвалидировать при изменении интерфейса, включая экспортируемые guard summaries. Отдельно по F720 хранить boundary-quality fingerprint (trusted/verified, причины incomplete) и budget fingerprint: изменение качества при прежней сигнатуре обновляет dependent trust/diagnostics; смена бюджета не позволяет переиспользовать прежнюю оценку полноты. Например, `a/f` сохраняет `[string? :-> string?]`, но теперь возвращает `42`: ошибка обязана появиться в `a`, даже если клиентский интерфейс не изменился. Для inferred return смена типа меняет interface hash. Не переиспользовать старые позиции и предложения edit после смены source hash.

Первый этап — namespace summaries, не fine-grained daemon. Граф включает spec keys, macro contracts и classpath, не только require; циклы обрабатываются как SCC. Исчерпание бюджета итераций означает incomplete, а не возврат старого успешного ответа. Тестировать равенство cold/incremental diagnostics после правки тела, сигнатуры, extern, spec key, macro contract и config; отдельно удаление определения. Скорость не обещается до измерений.

Основания: [Python, §5](../docs/research-python.md), первичные mypy [deps.py](https://github.com/python/mypy/blob/master/mypy/server/deps.py), [astdiff.py](https://github.com/python/mypy/blob/master/mypy/server/astdiff.py), [update.py](https://github.com/python/mypy/blob/master/mypy/server/update.py). Здесь прочитан раздел отчёта с разбором trigger/target; исходники upstream повторно не аудированы. Namespace cache — наш упрощённый дизайн, а не утверждение, что Pyright реализует алгоритм mypy. Тесты пока только предложены.

## Ограничения и открытые вопросы

- Текущий id — 32-битный hash `[code basename(file) message]`. Он не включает диапазон: одинаковые сообщения в одном файле и файлы с одинаковым basename могут иметь одинаковый id. Изменение message меняет id. Это не надёжный ключ для baseline, причинного графа или автоматической правки.
- Нужен выбор идентичности диагностики между ревизиями: диапазон ломается при вставке строк, текст сообщения — при уточнении типа. Нельзя обещать одновременно уникальность и стабильность без отдельной схемы и тестов коллизий.
- В текущем JSON нет snapshot/checksum; получатель не может доказать актуальность edit только по ответу CLI.
- `safe` для Java hints нуждается в проверке перегрузок и компиляторного поведения; отсутствие ошибок типов не доказывает эквивалентность программ.
- Нет полного provenance/DAG каскадных ошибок. Требуются исследования сохранения причин через aliases, ветвления, макросы и вывод возвращаемого типа.
- Неполные буферы, cancellation, устаревшие ответы, переименование файлов, нормализация путей и кодировки позиций требуют отдельного LSP-протокола и тестов.
- Аннотация не должна молча регистрировать новые `s/def`: это может менять runtime validation. Запись в type-only хранилище тоже требует реализации и проверки его правил, а не только генерации текста.

| Незакрытая форма и старый ответ | Честное сообщение о неполном анализе; старый результат не публикуется | Planned LSP recovery/versioning |
| Цикл namespaces, повтор без изменений | Конечный план order; ограниченное число итераций | Planned агентский цикл |
| any/cast/ignore или ослабление типа как «fix» | Не классифицировать как safe; явный review | Planned policy, не текущий CI budget |

Готовность первого CLI-этапа: воспроизводимая схема ответа, описанные координаты/ограничения id, проверки check/sig/type-at и отсутствие автоматической записи. Готовность редакторского этапа отдельно требует snapshot-aware протокола и матрицы выше; текущий `partial` не обещает LSP или автоматического исправления.
